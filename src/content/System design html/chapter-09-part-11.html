📖 The Story — Netflix During World Cup Final
Traffic Jumps 7x

FIFA World Cup Final begins. Millions of users open Netflix immediately after the match. Traffic jumps from 2M to 15M requests/minute. Nothing changed in the code. Only traffic changed. Question: Can your architecture survive sudden demand? Performance engineering is preparing before the traffic arrives.

Performance answers: How efficiently does the system perform work? Two major metrics: Latency (time per request) and Throughput (requests per second). Optimizing one doesn't always optimize the other. Like a supermarket: latency is time for one customer, throughput is customers served per hour.

🎯 Latency vs Throughput
Latency: Time required to complete one request. Example: Checkout takes 150ms. Lower latency = faster responses.

Throughput: How much work can be completed per unit time. Example: 10,000 requests/sec.

These are different. A system can have low latency but low throughput (fast but handles few requests), or high throughput but high latency (slow but handles many requests).

✅ Stateless Services
Stateless Services: Store no client session in memory. Any instance can process any request. Example: Request → Service → Database → Response. No local state. This enables horizontal scaling - any of 100 instances can handle any request. Stateful services (storing session in memory) require sticky sessions and reduce scalability.
📊 Caching Architecture

How Caching Works

Client ↓ Service ↓ Cache (Redis) ↓ Cache Hit? → Return (1ms) ↓ Cache Miss? → Database (50ms) ↓ Update Cache ↓ Return Cache Hit Ratio = Hits / (Hits + Misses) Target: 95%+
🔄 Load Balancing
Load Balancer: Distributes traffic across multiple service instances. Algorithms: Round Robin (rotate), Least Connections (send to least busy), Weighted (powerful servers get more), Consistent Hashing (same user to same server). Prevents any single instance from becoming overloaded.

🏭 Production Example
Real World

Amazon Black Friday Scaling

Amazon uses: Redis cache for product catalog (95%+ hit ratio), stateless services behind load balancers, Kubernetes HPA for autoscaling (5 pods morning → 50 pods evening peak), Kafka for async order processing, connection pooling for databases, compression for API responses, pagination for large lists. Everything scales independently. Checkout path stays fast. Analytics runs in background.

🎯 Interview Callout
Q
"How do you handle 20x traffic spike?"
"Cache everything cacheable (Redis, CDN). Make services stateless for horizontal scaling. Use load balancers to distribute traffic. Autoscale based on CPU/request rate. Offload background work to message queues. Compress responses. Paginate large datasets. Monitor cache hit ratios, queue lengths, and database connections. Load test before the event. Use canary deployments for last-minute changes."
🧠 Memory Trick
Cache → Stateless → Load Balance → Autoscale → Async → Compress → Paginate. Layer optimizations like an onion.
