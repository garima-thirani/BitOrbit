📖 The Story — Amazon Checkout Problem
One Click, Ten Services

Customer clicks "Buy Now". Amazon must validate customer, verify payment, reserve inventory, calculate shipping, generate invoice, notify warehouse, send email, update analytics, update recommendations, detect fraud. Should Order Service directly call all ten services? Absolutely not. Every new service increases dependencies. Eventually one service depends on dozens of others. This architecture becomes fragile.

Inside a monolith, calling Payment Service is just a function call: `paymentService.processPayment()`. Simple. Fast. Milliseconds. In Microservices, it becomes: network → serialization → authentication → load balancer → retries → timeouts → response. Suddenly takes 20-200ms. Communication becomes the biggest engineering challenge.

🎯 Synchronous vs Asynchronous
Golden Rule: Use synchronous communication only when the caller MUST wait for the answer. Everything else should be asynchronous if business requirements allow. Payment authorization → synchronous (user waits). Sending confirmation email → asynchronous (user doesn't wait). Updating analytics → asynchronous (nobody waits).

🔄 Request-Reply vs Fire-and-Forget

Request-Reply (Synchronous)

Order Service ↓ Payment Service ↓ Wait for response ↓ Continue Use when: User needs immediate answer

Fire-and-Forget (Async)

Order Service ↓ Kafka ↓ Return immediately Analytics processes later Use when: User doesn't need to wait
✅ API Composition & BFF
API Composition: Instead of frontend calling 4 services (Orders, Payments, Shipping, Reviews), an Aggregator service calls them all and returns one response. Reduces client-side complexity.
Backend For Frontend (BFF): Different clients need different APIs. Mobile needs small payloads. Desktop needs rich dashboards. TV needs streaming metadata. BFF provides client-specific optimized endpoints instead of one-size-fits-all API.
🏭 Production Example
Real World

Amazon Checkout Communication

Synchronous: Payment authorization (user waits for approval), Inventory validation (must confirm stock exists).

Asynchronous: OrderCreated event → Kafka → Shipping, Email, Analytics, Recommendations, Fraud Detection, Warehouse. Each processes independently. User doesn't wait for these.

This separation keeps checkout fast (synchronous path is short) while enabling scalable background processing (asynchronous).

🎯 Interview Callout
Q
"When should you choose REST over Kafka?"
"Use REST when the caller requires an immediate response, such as payment authorization or user authentication. Use Kafka when downstream processing can occur asynchronously, such as analytics, notifications, recommendations, or audit logging. The key question is: does the user need to wait for this?"
🧠 Memory Trick
User Waits → Synchronous (REST/gRPC). User Doesn't Wait → Asynchronous (Kafka). Keep the critical path short.
