Ticketmaster Case Study
Designing a Ticket Booking System

Ticket booking systems face extreme traffic spikes during flash sales, require real-time inventory management, and must prevent overselling. This case study applies caching strategies to solve these challenges.

📖 Problem Statement
Design Challenge

Design a ticket booking system like Ticketmaster or BookMyShow.

Design a ticket booking system where users can: Browse events, Search for concerts/movies/shows, Select seats, Book tickets, Make payments, View booking history. The system must handle millions of users during high-demand events like IPL matches or concert ticket releases.

📋 Requirements

✅ Functional

Event listing, Seat selection, Booking, Payment processing, Cancellation, Waitlist, Notifications, Booking history

📊 Non-Functional

High availability during flash sales, Low latency booking, Prevent overselling, Fair queueing, Handle 1M+ concurrent users, Secure payments

⚠️ Key Challenges
💥 Flash Sale Traffic
Millions of users hit the site simultaneously when tickets go on sale
🎫 Inventory Management
Must prevent overselling — only 1000 seats, cannot sell 1001
⚡ Real-time Updates
Seat availability must be accurate across all users
🐢 Database Pressure
Cannot let millions of requests hit the database directly
🏛 High-Level Architecture
Ticket Booking Architecture: Users → API → Redis (Inventory) → Queue → Database
⚡ Caching Strategy

Redis is the hero of this architecture:

🎫 Seat Inventory
Store available seats in Redis for fast reads/writes
🔒 Booking Locks
Use Redis locks to prevent double-booking
⏱ TTL
Unpaid bookings expire after 5 minutes
📊 Event Metadata
Cache event details, prices, venue info
🔄 Booking Flow with Caching
User Selects Seats ↓ Check Redis (Seats Available?) ├── No → Show "Sold Out" └── Yes │ Reserve in Redis (TTL = 5 min) │ Queue Booking Request │ Process Payment │ Confirm in Database │ Success!
🛠 Preventing Overselling

Critical: Cannot sell more seats than available.

1️⃣ Redis Atomic Operations
Use DECR to atomically decrement seat count
2️⃣ Distributed Locks
Lock seat selection during booking
3️⃣ TTL for Unpaid
Release seats if payment not completed in 5 min
4️⃣ Database as Source of Truth
Final confirmation writes to database
⚡ Handling Flash Sales

When 1 million users try to book simultaneously:

🚦 Rate Limiting
Limit requests per user/IP
📋 Waiting Room
Queue users before they reach booking system
⚡ Redis First
All seat checks go to Redis, not database
🔄 Async Processing
Queue booking requests, process sequentially
📊 Cache Invalidation

When a booking is confirmed or cancelled:

Booking Confirmed ↓ Decrement Redis Seat Count ↓ Update Database Booking Cancelled ↓ Increment Redis Seat Count ↓ Update Database
🎯 Interview Walkthrough

A strong interview answer:

1️⃣ Identify challenges
Flash sales, overselling, database pressure
2️⃣ Use Redis for inventory
Fast reads/writes, atomic operations
3️⃣ Implement TTL
Release unpaid seats automatically
4️⃣ Queue bookings
Prevent database overload
5️⃣ Rate limiting
Protect against abuse
6️⃣ Database for persistence
Source of truth for confirmed bookings
🧠 Memory Trick
Flash Sales → Redis + Queue. Inventory → Atomic Operations. Overselling → Never.
