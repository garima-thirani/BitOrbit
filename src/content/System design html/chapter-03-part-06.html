📖 The Story — Finding a Name in a Phone Book
Why Indexes Exist

Without an index, you'd read every page.

Imagine a phone book with 10 million names. Without an index, you'd start from page one and read until you found "John Smith." Now imagine the names are sorted alphabetically. You immediately jump near "J" and quickly narrow your search. That alphabetical organization is exactly what a database index provides.

🎯 Why Indexes Exist

When a table is small, scanning every row is acceptable. As data grows into millions of rows, full table scans become expensive. Indexes reduce the amount of data the database must inspect.

❌ Without Index

Query → Read Every Row → Slow

✅ With Index

Query → Index → Matching Rows → Fast

📐 What is an Index?
Database Index: An auxiliary data structure that stores searchable information about one or more columns, allowing the database to locate matching rows efficiently. Think of it as a map pointing to where the real data lives.
🌳 B-Tree Index

Most relational databases use B-Trees because they remain balanced as data grows. Instead of searching linearly through 1,000,000 rows, the tree repeatedly eliminates large portions of the search space.

B-Tree Structure: 50 / \ 25 75 / \ / \ 10 30 60 90 Searching becomes O(log n) rather than O(n).

B-Trees efficiently support: equality lookups (WHERE age = 25), range queries (WHERE age > 30), sorting (ORDER BY age), and prefix searches.

🔑 Hash Index

A hash index computes a hash from the key and jumps directly to the bucket.

✅ Excellent For

WHERE id = 42 — equality lookups are instant

❌ Poor For

WHERE id > 42 or ORDER BY id — cannot preserve ordering

🔗 Composite Index

Sometimes queries filter on multiple columns. A composite index on (customer_id, status) allows both conditions to be evaluated efficiently.

Leftmost Prefix Rule: Given index (customer_id, status, created_at), efficient queries include: customer_id alone, customer_id + status, customer_id + status + created_at. Searching only by status usually cannot fully use this index.
📋 Clustered vs Non-Clustered Index

📦 Clustered Index

The table's rows are physically stored in index order. Fast range scans, good locality. A table generally has only one clustered index.

📋 Non-Clustered Index

Stores keys separately from table data. Index → Pointer → Actual Row. A table can have many non-clustered indexes.

🎯 Interview Callout
Q
"Why not create an index on every column?"
"Indexes improve reads but increase storage and write costs. Each additional index must be maintained whenever data changes."
🧠 Memory Trick
Indexes speed up reads. Indexes slow down writes. Everything is a trade-off.

Indexes speed up SELECT queries but slow down INSERT/UPDATE/DELETE because the index structure must be updated.
