📖 The Story — The Invisible Failure
Uber's Missing Receipts

Everything looks healthy, but customers don't get receipts.

Everything appears healthy at Uber. Kafka brokers running. CPU low. Memory normal. Network latency fine. Yet customers complain: "My ride completed 20 minutes ago, but I still haven't received my receipt." You inspect: Payment Service ✔, Kafka ✔, Notification Service ✔, Email Service ✔. Everything looks healthy. Eventually you discover: one malformed event entered the notification pipeline. Every consumer kept retrying it. The queue became blocked. Thousands of valid receipts waited behind one bad event. One poisoned message caused a production incident.

☠️ Poison Message

One event triggers thousands more
🌐 Broker Failure
Kafka cluster becomes unavailable
☠️ Poison Messages & DLQ
Poison Message: An event that consistently fails processing. Instead of retrying forever, move it to a Dead Letter Queue after max retries.
Poison Message Flow: Consumer → Retry → Retry → Retry → DLQ ↓ Operations team investigates DLQ prevents queue blocking!
📊 Consumer Lag
Consumer Lag: Difference between latest produced offset and latest consumed offset. Indicates how far consumers are behind.
Producer Offset: 100,000 Consumer Offset: 95,000 Lag: 5,000 events High lag = consumers can't keep up!
🔄 Retry Strategy
❌ Bad: Immediate retry Fail → Retry → Fail → Retry → Storm ✅ Good: Exponential backoff + jitter Fail → Wait 1s → Retry → Wait 2s → Retry → Wait 4s → Retry → Wait 8s → DLQ Add random jitter to prevent retry storms!
🔍 Distributed Tracing
Correlation ID: Unique ID linking all events from the same business request. Enables end-to-end tracing across services.
Order Created (correlationId: abc-123) ↓ Payment Completed (correlationId: abc-123) ↓ Inventory Reserved (correlationId: abc-123) ↓ Shipment Created (correlationId: abc-123) All events traceable!

🎯 Interview Callout
Q
"Kafka is healthy but customers report delayed order confirmations. How do you investigate?"
"First examine consumer lag, retry counts, and DLQ growth. Use distributed tracing to follow a delayed order through all services. Check for poison messages, schema validation failures, slow downstream dependencies, and backpressure. Scale consumers or replay failed events after resolving the root cause."
🧠 Memory Trick
Event → Retry → DLQ → Replay → Tracing → Monitoring → Recovery. Production EDA requires observability infrastructure, not just Kafka.
