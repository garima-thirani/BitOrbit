📖 The Story — The Multi-Layer Security System
Why Multiple Cache Layers

Security guards at multiple checkpoints.

Imagine a high-security building. There's a guard at the main entrance, another at the lobby, another at the floor, and another at the office door. Each guard filters requests before they reach the inner layers. If the first guard handles most visitors, the inner guards rarely need to act. Multi-tier caching works the same way — each layer absorbs requests, reducing load on deeper layers.

🎯 Why Multi-Tier Caching?

A single cache layer has limitations. Multi-tier caching: Reduces latency at multiple levels, Distributes load across layers, Provides redundancy, Optimizes for different access patterns, Enables geographic distribution.

Key Insight: Each cache layer serves a different purpose. Together, they create a comprehensive caching strategy.
📐 The Four Cache Tiers

L1: Browser Cache

Closest to the user. Stores static assets locally.

User's Device ├── Images ├── CSS ├── JavaScript └── HTML TTL: Hours to days Hit Rate: High for repeat visits

L2: CDN Edge Cache

Geographically distributed. Serves content from nearby locations.

CDN Edge Servers (Worldwide) ├── Static assets ├── Images ├── Videos └── API responses (sometimes) TTL: Minutes to days Hit Rate: Very high for popular content

L3: Application Cache (Redis/Memcached)

In-memory cache close to application servers.

Redis Cluster ├── Database query results ├── Session data ├── Computed values └── API responses TTL: Seconds to hours Hit Rate: High for hot data

L4: Database Cache

Built into the database itself.

Database Buffer Pool ├── Frequently accessed rows ├── Index pages └── Query results TTL: Managed by database Hit Rate: Varies
🔄 Request Flow Through Tiers
Request flows through cache layers until it finds data or reaches the database.
🌍 Geo Replication

Replicate cache data across geographic regions for global applications:

🗺 Active-Active
Multiple regions serve writes. Complex conflict resolution.
📖 Active-Passive
Primary region handles writes. Replicas serve reads.
⏱ Replication Lag
Data takes time to propagate. Accept eventual consistency.
🔀 Routing
Route users to nearest region for lowest latency.
📊 Cache Hierarchy Strategy

Different data belongs in different tiers:

L1 (Browser)
Static assets, images, CSS, JS — long TTL
L2 (CDN)
Static content, API responses, public data — medium TTL
L3 (Redis)
Database results, sessions, computed values — short TTL
L4 (Database)
Source of truth, frequently accessed rows
⚖ Consistency Across Tiers

Challenge: Keeping all cache layers synchronized.

Data Changes in Database ↓ Invalidate L3 (Redis) ↓ Invalidate L2 (CDN) ↓ Browser cache expires naturally (L1) Result: All layers eventually consistent.
🏭 Production Example
Real World

Global E-commerce Platform

A global e-commerce site uses multi-tier caching: L1: Browser caches product images for 24 hours. L2: CDN caches product pages for 1 hour across 200 edge locations. L3: Redis caches product details, prices, inventory for 5 minutes in each region. L4: PostgreSQL stores source of truth. Result: 95% of requests served from cache. Database handles only 5% of traffic.

🎯 Interview Callout
Q
"How would you design caching for a global application?"
"I would use multi-tier caching: browser cache for static assets, CDN for geographic distribution, Redis for application-level caching, and database cache for query results. Each layer reduces load on the next."
🧠 Memory Trick
L1 Browser → L2 CDN → L3 Redis → L4 Database. Each layer catches what the previous one misses.
