📖 The Story — The Vanishing Payment Service
IP Addresses Change Constantly

Amazon has 100 Payment Service instances. Today, 10.0.2.15 processes payments. Tomorrow, Kubernetes restarts it. Now it becomes 10.0.8.91. Every service that knew the old IP fails. Hardcoding addresses doesn't work. In cloud systems, servers are temporary. Services move constantly. We need Service Discovery.

Old enterprise systems had static IPs that never changed. Configuration lasted years. Cloud environments look different: containers are created and destroyed continuously. Infrastructure changes constantly. Service Discovery answers two questions: Where is Service X? How do I reach it? Instead of hardcoding addresses, services discover each other dynamically.

🎯 What is Service Discovery?
Service Discovery: A mechanism that allows services to locate each other dynamically without hardcoded IP addresses. Services register themselves with a Service Registry. When a service needs to call another service, it asks the registry for the current address. This works even when containers restart and IPs change.

🔄 API Gateway Pattern
API Gateway: A single entry point for all clients. Instead of clients calling 50 services directly, they call the Gateway, which routes to appropriate services. Gateway handles: Authentication, Authorization, Rate Limiting, SSL Termination, Logging, Monitoring, Request Aggregation. Think of it as a hotel front desk - you don't enter rooms directly, you check in at the front desk first.

🔄 Service Mesh
Service Mesh: As microservices grow, every service implements Retry, Timeout, Circuit Breaker, mTLS, Tracing, Logging. Huge duplication. Service Mesh moves networking concerns outside applications into sidecar proxies. Applications focus only on business logic. Istio and Linkerd are popular Service Meshes.
🏭 Production Example
Real World

Amazon's Networking Stack

Amazon uses API Gateway as single entry point for all clients. Internal services use Kubernetes DNS for service discovery (payment.default.svc.cluster.local). Services register automatically with health checks. For advanced traffic management, mTLS, and observability, they use Service Mesh (Istio). Every service gets a sidecar proxy (Envoy) that handles networking concerns.

🎯 Interview Callout
Q
"Why do we need API Gateway in microservices?"
"API Gateway provides a single entry point, handles authentication/authorization once instead of in every service, enables rate limiting and request aggregation, simplifies client code, and provides a place for cross-cutting concerns. Without it, every client must know about every service and handle security, retries, and timeouts independently."
🧠 Memory Trick
Services Need Addresses → Service Registry Finds Them → API Gateway Routes Clients → Service Mesh Handles Networking. Four layers of modern microservice networking.
