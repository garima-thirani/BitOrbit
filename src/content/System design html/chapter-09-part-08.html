📖 The Story — The 500 Error Mystery
Everything Looks Healthy

Amazon Checkout returns 500 errors. Users cannot place orders. Monitoring dashboard shows Order Service is healthy. CPU normal. Memory normal. Network normal. Everything looks fine. Yet customers cannot buy anything. Without observability, engineers spend hours searching logs. With observability, they identify the failing service within minutes.

Monitoring answers "What happened?" Observability answers "Why did it happen?" Imagine one user request travels through Gateway → Orders → Payments → Inventory → Shipping. Where did it fail? Without tracing, nobody knows. This is why modern systems need all three pillars: Logs, Metrics, and Traces working together.

🎯 The Three Pillars
Observability Three Pillars: Logs record discrete events (what happened). Metrics measure system health over time (how healthy). Traces show how a request flows across services (why it happened). Together they provide complete visibility. None replaces the others. Use all three.

📊 Structured Logging

❌ Bad Log

Payment Done!! Missing: timestamp, service, order ID, trace ID, severity Nearly useless for debugging

✅ Good Log (JSON)

{ "timestamp":"2026-08-01T10:15:33Z", "service":"payment", "level":"ERROR", "traceId":"abc123", "message":"Payment failed", "orderId":"ORD902", "error":"Insufficient funds" } Searchable, indexable, machine-readable
🔄 Distributed Tracing
Distributed Tracing: Follows one request across multiple services. Each request gets a Trace ID. Every service propagates the same ID. Example: Customer checkout → Trace ID "xyz789" → Gateway (30ms) → Orders (60ms) → Payments (400ms!) → Inventory (25ms). Trace shows Payment is slow. Without traces, you'd never know.
✅ Key Metrics to Monitor

Four Golden Signals (Google SRE)

L - Latency: Time per request T - Traffic: Requests per second E - Errors: Error rate S - Saturation: Resource usage Remember: LTES

RED Method (For APIs)

R - Rate: Requests per second E - Errors: Failed requests D - Duration: Response time Perfect for microservices

🏭 Production Example
Real World

Amazon Observability Stack

Every request gets Trace ID and Correlation ID. Structured JSON logs flow to Elasticsearch. Metrics go to Prometheus. Traces stored in Jaeger. Grafana dashboards show real-time health. AlertManager triggers PagerDuty for critical issues. Engineers debug checkout failures by searching Trace ID across all services. Root cause identified in minutes, not hours.

🎯 Interview Callout
Q
"How do you debug a slow request across 10 microservices?"
"Use distributed tracing with Trace IDs propagated through all services. Each service logs the Trace ID. Search Jaeger for the Trace ID to see the complete request path. Identify which service is slow. Check logs for that service using the same Trace ID. Metrics confirm if it's a pattern or one-off. This is why Trace IDs are non-negotiable in microservices."
🧠 Memory Trick
Logs tell "What". Metrics tell "Where". Traces tell "Why". Together they tell the complete story. Every request needs a Trace ID.
