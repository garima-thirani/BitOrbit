📖 The Story — The Shared Database Disaster
Distributed Monolith

Company migrates monolith into 6 microservices but they all share one database. They proudly announce Orders, Payments, Inventory, Shipping, Catalog, and Notification services. Everyone celebrates. Then someone notices: the services were independent, but the data wasn't. Nothing had actually changed. They had built a distributed monolith.

Splitting code is relatively easy. Splitting data is extremely difficult. Every business capability needs data. Order Service needs Customer, Inventory, Payment, and Shipping data. Question: Should it directly query everyone else's database? Absolutely not. That creates hidden coupling. If Payments renames a column, Orders breaks. This is why Database per Service is fundamental to microservices.

🎯 Why Data is the Hardest Problem
Golden Rule: "If another service can directly query your database, it owns part of your service." Data ownership is what enables independent deployment, schema evolution, and team autonomy. Without it, services remain tightly coupled no matter how independent the code looks.

📊 Shared Database Anti-Pattern

❌ NEVER Do This

Orders Service ↓ Payments Service ↓ Inventory Service ↓ Shipping Service ↓ ONE SHARED DATABASE Problems: - Tight coupling - Schema conflicts - Deployment coordination - Security issues - Hidden dependencies
✅ Polyglot Persistence
Polyglot Persistence: Using different database technologies for different workloads. One database cannot optimize every use case. Orders need ACID transactions (PostgreSQL). Search needs full-text search (Elasticsearch). Cache needs speed (Redis). Analytics needs time-series (ClickHouse). Each database is chosen for its specific strength.

🔄 Handling Cross-Service Queries

Solution 1: API Composition

Customer Dashboard ↓ Aggregator Service ↓ Orders API + Payments API + Shipping API ↓ Combine into one response Pros: No data sharing Cons: Multiple network calls

Solution 2: CQRS Projections

Orders Event + Payments Event + Shipping Event ↓ Projection Service ↓ Customer Dashboard DB (pre-computed) ↓ One fast query Pros: Fast reads Cons: Eventual consistency
✅ Eventual Consistency
Eventual Consistency: In microservices, data is eventually consistent, not immediately consistent. Customer places order → Dashboard may not show it immediately → Seconds later, projection updates → Everything consistent. This is acceptable because services communicate asynchronously. Waiting for every service would destroy performance.
🏭 Production Example
Real World

Amazon's Data Architecture

Orders Service uses PostgreSQL for ACID transactions. Search Service uses Elasticsearch for product search. Sessions use Redis for speed. Analytics uses ClickHouse for OLAP. Recommendations use DynamoDB for scale. Each service owns its database. No cross-service SQL joins. Customer Dashboard uses CQRS projection built from events. Data duplication is acceptable when it reduces coupling.

🎯 Interview Callout
Q
"Why can't microservices share a database?"
"Sharing a database creates tight coupling. Schema changes require coordinated deployments, hidden dependencies emerge, and services lose independence. Database per Service ensures each team can evolve its schema, scale independently, and deploy without coordinating with other teams. Communication happens through APIs or events, never through direct database access."
🧠 Memory Trick
Service Owns Data → API/Events for Communication → No Cross-Service Joins → Polyglot Persistence → Eventual Consistency. Data ownership enables independence.
