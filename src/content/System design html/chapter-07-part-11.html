📖 The Story — The Banking Disaster
Why Delivery Guarantees Matter

Transferring ₹1,00,000 twice.

You transfer ₹1,00,000 to a friend. Your internet disconnects before confirmation. You click transfer again. What happened? Case 1: First request never reached - second succeeds. Fine. Case 2: First succeeded, second also succeeds - now ₹2,00,000 transferred. Disaster. Case 3: Second detected as duplicate - only one transfer. Perfect. This uncertainty is why delivery guarantees exist in distributed systems.

🎯 The Two Generals Problem

Two generals on opposite hills communicate via messengers. General A sends "Attack at dawn". How does he know it arrived? General B sends "Received". How does B know A got it? A acknowledges B's acknowledgement. Now B doesn't know if that arrived. This never ends. Absolute certainty is impossible in distributed systems. Instead, we build practical guarantees.

Key Insight: Distributed systems cannot guarantee perfection. We trade off between message loss and duplicates.
📐 Three Delivery Guarantees

1. At-Most-Once Delivery

Message delivered zero or one time. Never duplicated. Possible loss.

Producer → Broker → Consumer ↓ Network Failure ↓ Message LOST No retry. No duplicate.
✅ Use Case
Metrics, monitoring, non-critical data

2. At-Least-Once Delivery (Most Common)

Every message will eventually arrive. Duplicates are possible.

Producer → Broker → Consumer ↓ ACK Lost ↓ Broker Retries ↓ DUPLICATE POSSIBLE
✅ Use Case
Most production systems (RabbitMQ, Kafka default)

3. Exactly-Once Delivery

Every message processed exactly once. No duplicates. No loss. Very difficult to achieve.

Requires: - Idempotent Producer - Transactional Broker - Idempotent Consumer - Transactional Database One weak link breaks everything.
⚠️ Reality
True end-to-end exactly-once is extremely expensive
🔑 What is Idempotency?
Idempotency: Performing the same operation multiple times produces the same final result. Critical for handling duplicate messages safely.
Idempotent: Set User Status = "Active" Run once → Active Run 100 times → Still Active ✓ Safe to retry Non-Idempotent: Balance += 100 Run once → ₹100 Run twice → ₹200 ✗ Dangerous
🎫 Idempotency Key

Modern payment systems use idempotency keys to prevent duplicate processing.

POST /payments Idempotency-Key: a8d91c21-xyz Server stores: Key: a8d91c21-xyz → Result: Success Duplicate request with same key? → Return previous result → Don't execute again
💡 Example
Stripe uses idempotency keys for all payment requests
🔄 Retry Mechanisms

Never retry immediately. Use exponential backoff with jitter.

Retry Strategy: Try → Fail Wait 1 sec → Retry → Fail Wait 2 sec → Retry → Fail Wait 4 sec → Retry → Fail Wait 8 sec → Retry → Fail Wait 16 sec → Dead Letter Queue Add random jitter to prevent retry storms
💀 Dead Letter Queue (DLQ)
DLQ: Messages that fail permanently after max retries are moved to a Dead Letter Queue for manual investigation.
Main Queue → Retry → Retry → Retry → DLQ ↓ Operations team investigates

🏭 Production Examples
Real World

Amazon, Uber, Stripe

Amazon: Uses at-least-once delivery with idempotent consumers. Order ID prevents duplicate shipments.

Uber: Ride events use at-least-once. Ride ID ensures invoice generated only once.

Stripe: Payment processing uses idempotency keys. Network retry doesn't cause duplicate charges.

🎯 Interview Callout
Q
"How do you prevent duplicate payment processing?"
"I use idempotency keys - a unique key per payment request. The server stores processed keys. Before processing, it checks if the key exists. If yes, returns previous result. If no, processes and stores the key. This makes retries safe."
🧠 Memory Trick
At-Most-Once = Fast but may lose. At-Least-Once = Reliable but may duplicate. Exactly-Once = Perfect but expensive. Idempotency makes duplicates safe.
