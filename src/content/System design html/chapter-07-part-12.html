📖 The Story — WhatsApp's Scale
2 Billion Users, 100 Billion Messages Daily

From 100 users to 2 billion.

Day 1: 100 users. Simple server sends messages. Day 3 years: 2 billion users. Every second: millions of messages, typing events, read receipts, presence updates, image uploads. Every design decision matters. How do you deliver messages in 30-80ms globally? How do you handle offline users? How do you scale to billions of WebSocket connections?

📋 Requirements

✅ Functional

Send/receive messages, Real-time delivery, Read receipts (✓✓), Typing indicators, Online status (presence), Group chats, Media sharing (images/videos), Push notifications, Offline message sync, Multi-device support

📊 Non-Functional

Low latency (<100ms delivery), High availability, Horizontal scalability, Message durability, Offline support, Global distribution, End-to-end encryption

🏛 High-Level Architecture
Mobile → Load Balancer → WebSocket → Messaging Service → Kafka/DB/Redis
🔌 Why WebSockets?

HTTP is request-response. Chat needs server to push messages instantly. WebSockets maintain persistent bidirectional connection.

HTTP: Client → Request → Response → Close WebSocket: Client ⇅ Persistent Connection ⇅ Server Server can push messages anytime
✅ Benefit
Instant message delivery, no polling overhead
💬 Message Flow
Alice sends "Hello Bob" ↓ WebSocket → Messaging Service ↓ Kafka (for durability) ↓ Database (store message) ↓ Bob online? → Push via WebSocket ↓ Bob offline? → Store + Push notification ↓ Bob reconnects → Sync missing messages
📊 Message Status

WhatsApp shows three statuses, each is an event:

✓ Sent
Message stored on server
✓✓ Delivered
Delivered to recipient's device
✓✓ Blue Read
Recipient opened the message
🟢 Presence Service

Track who's online/offline. Redis is perfect because presence changes constantly and doesn't need permanent storage.

User connects → Redis: {userId: online, lastSeen: timestamp} User disconnects → Redis: {userId: offline, lastSeen: timestamp} Friends query → Redis returns online status
📱 Offline Sync

When Bob reconnects after being offline:

Bob reconnects ↓ Client sends: lastMessageId = msg_950 ↓ Server queries: messages > msg_950 ↓ Returns: msg_951, msg_952, msg_953... ↓ Bob receives all missed messages
👥 Group Chat

Alice sends message to group of 100:

Alice → "Hi Everyone" ↓ Fan-out to 100 members ↓ Kafka partitions by groupId ↓ Each member receives message Challenge: 10M member groups need hierarchical fan-out
🔢 Message Ordering

Per-conversation sequence numbers ensure ordering:

Conversation: {userId1, userId2} Sequence: 101, 102, 103... If messages arrive out of order: Client reorders using sequence numbers
🔔 Push Notifications

For offline users:

Message for offline Bob ↓ Store in database ↓ Notification Service → APNS (iOS) / FCM (Android) ↓ Bob's phone shows: "New message from Alice" ↓ Bob opens app → Full sync
🖼️ Media Messages

Never send media through Kafka. Use object storage:

Alice sends image ↓ Upload to S3 ↓ Get URL: https://s3.amazonaws.com/abc123.jpg ↓ Send message with URL (not image) ↓ Bob downloads image from S3
🎯 Interview Callout
Q
"How would you design WhatsApp for 2 billion users?"
"Use WebSockets for real-time delivery, Kafka for event streaming, Redis for presence, durable storage for message history, object storage for media, push notifications for offline users. Partition by conversation ID for ordering. Use message IDs for deduplication. Scale each component independently."
🧠 Memory Trick
Connect → Send → Store → Deliver → ACK → Read → Sync. WebSocket for real-time, Kafka for events, Redis for presence.
🧪 Test Your Knowledge
1. Why are WebSockets preferred over HTTP polling for chat?
A) WebSockets are simpler
B) Persistent bidirectional connection enables instant server push without polling overhead
C) HTTP doesn't support JSON
D) WebSockets use less memory
WebSockets maintain persistent connections, allowing servers to push messages instantly without repeated client polling.
2. Why shouldn't images be stored in Kafka?
A) Kafka doesn't support binary data
B) Images are too small
C) Kafka is optimized for event streaming, not large binary objects. Use S3 instead.
D) Images can't be replicated
Kafka is designed for streaming events, not storing large files. Object storage like S3 is better suited for media.
