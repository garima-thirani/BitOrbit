📖 The Story — The Order Processing Problem
Why Advanced Patterns Exist

Order succeeds, inventory fails, now what?

Customer places order. Payment succeeds. Inventory fails. Should payment remain? Should shipping continue? Should loyalty points be awarded? Should confirmation emails be revoked? You can't "rollback" an email or SMS. Distributed systems need sophisticated patterns to handle these scenarios without distributed transactions.

🎯 The Distributed Transaction Problem

In a monolith: BEGIN → Update Order → Update Inventory → Update Payment → COMMIT. Easy. In microservices: Each service has its own database. No global transaction possible. Two-Phase Commit (2PC) is slow, blocking, and doesn't scale. Modern systems use eventual consistency with patterns like Saga.

Key Insight: Distributed transactions don't scale. Embrace eventual consistency with compensating transactions.
🔄 Saga Pattern
Saga: A sequence of local transactions where each service commits independently. If something fails, previously completed work is compensated (undone) using business logic.
Normal Flow: Order Created → Payment Completed → Inventory Reserved → Shipping Started Failure & Compensation: Shipping Failed → Release Inventory → Refund Payment → Cancel Order Compensating transactions undo business actions
📋 Choreography vs Orchestration

Choreography

Order Created ↓ Payment Service (reacts) ↓ Payment Completed ↓ Inventory Service (reacts) ↓ Inventory Reserved ↓ Shipping Service (reacts) No central coordinator
✅ Pros
Highly scalable, no bottleneck
❌ Cons
Hard to debug, complex flow

Orchestration

Saga Orchestrator ↓ Calls Payment Service ↓ Calls Inventory Service ↓ Calls Shipping Service ↓ Monitors each step ↓ Handles failures Central coordinator
✅ Pros
Easier to monitor, simpler logic
❌ Cons
Orchestrator is bottleneck
📦 Transactional Outbox Pattern
Transactional Outbox: Store events in an outbox table within the same database transaction as business data. A background publisher reliably sends events to Kafka/RabbitMQ.
Problem: Database Commit ✔ → Kafka Publish ❌ Inconsistent! Solution: BEGIN ↓ Save Order ↓ Save Event to Outbox Table ↓ COMMIT (both succeed or fail together) ↓ Outbox Publisher reads and sends to Kafka
💡 Key Insight
Never publish Kafka events directly after database commit. Use Outbox pattern.
📥 Inbox Pattern
Inbox Pattern: Consumer stores processed event IDs before processing. If duplicate event arrives, it's ignored.
Kafka Event → Check Inbox Table ↓ Already processed? ↓ YES → Ignore ↓ NO → Process → Store ID
🔄 Change Data Capture (CDC)
CDC: Automatically capture database changes (INSERT, UPDATE, DELETE) and stream them to Kafka. Applications don't publish events - the database does.
Database (MySQL Binlog) ↓ CDC Tool (Debezium) ↓ Kafka ↓ Consumers (Analytics, Search, ML) Applications remain unchanged
✅ Benefit
No application code changes needed
📚 Event Sourcing
Event Sourcing: Store every state change as an event. Current state is computed by replaying events. Complete audit trail built-in.
Traditional: Store current state Balance: ₹5000 Event Sourcing: Store all events Account Created Deposit ₹500 Withdraw ₹100 Deposit ₹4600 Current balance = sum of all events
✅ Benefits
Complete audit trail, replay history, time travel, debugging
🏭 Production Example - Amazon
Real World

Complete Order Processing Flow

1. Order Service creates order + saves to Outbox table (same transaction)
2. Outbox Publisher sends OrderCreated event to Kafka
3. Kafka consumers: Inventory reserves stock, Shipping prepares shipment, Analytics tracks metrics, Recommendations update
4. If Shipping fails: Saga orchestrator executes compensation (refund payment, release inventory, cancel order)
5. All events persisted for replay and audit

🎯 Interview Callout
Q
"How do you ensure no order event is lost in a distributed system?"
"I use Transactional Outbox pattern: store the event in the same database transaction as the order. A background publisher reliably sends events to Kafka. This ensures that if the database commit succeeds, the event will eventually be published. Combined with Saga for distributed transactions and Inbox pattern for idempotent consumers, we achieve reliable event delivery."
🧠 Memory Trick
Saga = Compensating transactions. Outbox = Reliable publishing. CDC = Database streaming. Event Sourcing = Store everything.
