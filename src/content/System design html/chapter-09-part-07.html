📖 The Story — Black Friday at Amazon
Payment Service Slows Down

Black Friday. Millions of users shopping. Payment Service normally takes 50ms. Suddenly it takes 8 seconds. Every Order Service thread waits. Soon all threads blocked. Inventory waits. Shipping waits. Checkout stops. Customers cannot place orders. The problem wasn't Payment. The problem was everyone waited forever.

Distributed systems fail constantly: network issues, machine crashes, container restarts, slow databases, full disks, memory leaks, CPU spikes, DNS failures, cloud outages. Good systems expect failure. They don't ask "Will it fail?" but "When it fails, what happens?" This is resilience—designing systems that survive failures gracefully.

🎯 The Golden Rule
Golden Rule: Never assume another service will always respond. Always design for: slow responses, no responses, partial responses, wrong responses. Before calling any external service, answer: "What happens if this call fails?" If you don't have an answer, the design isn't complete.

📊 Retry with Exponential Backoff

❌ Bad: Immediate Retry

Fail → Retry → Fail → Retry → Storm All clients retry at same time Overwhelms already struggling service

✅ Good: Exponential Backoff + Jitter

Fail → Wait 1s → Retry → Wait 2s → Retry → Wait 4s → Retry → Wait 8s → DLQ Add random jitter to prevent synchronized retries!
🔄 Circuit Breaker Pattern
Circuit Breaker: Like a home electrical circuit breaker. When failures exceed threshold, circuit "opens" and stops sending traffic. After waiting, allows few test requests. If successful, "closes" circuit. Prevents cascading failures. Three states: Closed (normal), Open (failing), Half-Open (testing recovery).
✅ Bulkhead Pattern
Bulkhead: Ships have watertight compartments. If one floods, others stay dry. Similarly, separate thread pools/resources for different services. Payment failure doesn't block Inventory. Example: Thread Pool A for Payments, Thread Pool B for Inventory. Payment issues don't consume Inventory threads.
🔄 Timeout & Fallback

Timeout

Never wait forever Payment: 5s timeout Internal API: 500ms timeout Cache: 50ms timeout After timeout → Fallback

Fallback

Recommendation Service fails? → Return popular products Checkout still works! Graceful degradation keeps core functionality alive
🏭 Production Example
Real World

Netflix Resilience Engineering

Netflix built Chaos Monkey to randomly kill production instances. If systems survive random failures, they're resilient. Every service uses: Retry with exponential backoff + jitter, Circuit Breaker (Hystrix), Timeouts (fail fast), Bulkhead (separate thread pools), Fallback (default content), Health Checks, and Monitoring. This is why Netflix streaming rarely fails despite millions of concurrent users.

🎯 Interview Callout
Q
"Why are retries alone dangerous?"
"Retries increase traffic during failures. Without exponential backoff, jitter, and limits, they can overwhelm already struggling services and create retry storms. Retries should always be combined with timeouts and circuit breakers. Retry = hope. Backoff = strategy. Circuit Breaker = protection."
🧠 Memory Trick
Fail → Retry (with backoff) → Timeout → Circuit Breaker → Fallback → Bulkhead → Chaos Test. Layer defenses like an onion.
