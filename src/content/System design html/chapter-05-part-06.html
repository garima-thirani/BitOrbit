📖 The Story — The Broken ATM
When Caching Goes Wrong

Caching the wrong data can be dangerous.

Imagine an ATM that caches account balances for 5 minutes to reduce database queries. A customer withdraws ₹10,000. The balance updates in the database. But the ATM still shows the old balance from cache. The customer checks their balance on another ATM — it shows the correct updated balance. Now the customer is confused. Worse, if the customer tries to withdraw more money, the ATM might allow an overdraft because it's showing stale data. This is why not everything should be cached.

🎯 Why Caching Isn't Always the Answer

Caching introduces:

🔄 Consistency Complexity
Keeping cache synchronized with database is hard
💾 Memory Cost
RAM is expensive. Caching everything is wasteful
🐛 Debugging Difficulty
Stale data creates hard-to-reproduce bugs
🔒 Security Risks
Caching sensitive data can create vulnerabilities
Key Insight: Caching is a trade-off. Sometimes the costs outweigh the benefits.
❌ When NOT to Cache

1. Frequently Changing Data

If data changes every second, caching provides minimal benefit.

❌ Real-time stock prices ❌ Live sports scores ❌ Active session tokens ❌ One-time passwords (OTPs)

Why: The cache expires almost immediately. You're adding complexity without meaningful performance gains.

2. Highly Sensitive Data

Caching sensitive data increases attack surface.

❌ Credit card numbers ❌ Passwords (even hashed) ❌ Personal health records ❌ Authentication tokens

Why: Caches are often less secure than databases. A compromised cache exposes sensitive data.

3. Rarely Accessed Data

Caching data that's accessed once a month wastes memory.

❌ Yearly financial reports ❌ Archived logs ❌ Historical data rarely queried

Why: The cache hit rate would be near zero. You're paying for memory without benefits.

4. Data Requiring Strong Consistency

Banking and financial systems often cannot tolerate stale data.

❌ Account balances during transfers ❌ Inventory counts during checkout ❌ Seat reservations

Why: Stale data can cause financial errors, overselling, or double bookings.

5. Data That's Cheap to Compute

If computing the data is already fast, caching adds unnecessary complexity.

❌ Simple database lookups with good indexes ❌ Fast mathematical calculations ❌ Small, frequently updated configs

Why: The database query is already fast enough. Caching adds complexity without meaningful gains.

⚠️ Warning Signs You're Caching Too Much
📉 Low Hit Rate
Below 50%? You're caching the wrong things
🐛 Stale Data Bugs
Users reporting outdated information
💸 High Memory Costs
Cache costs exceed performance benefits
🔄 Constant Invalidation
Cache entries expire before being reused
🎯 Decision Framework

Before caching, ask:

1️⃣ Is the data read frequently?
If no, don't cache
2️⃣ Is the data expensive to compute?
If no, don't cache
3️⃣ Can stale data cause problems?
If yes, don't cache or use short TTL
4️⃣ Is the data sensitive?
If yes, be very careful with caching
5️⃣ Will the cache hit rate be high?
If no, don't cache
🏭 Production Example
Real World

Payment Processing System

A payment system does NOT cache: Account balances (stale data = financial errors), Transaction status (must be accurate), Authentication tokens (security risk). It DOES cache: Product catalog (read-heavy, changes infrequently), User preferences (personalization, low risk), Country codes (static reference data).

🎯 Interview Callout
Q
"Would you cache user passwords?"
"Absolutely not. Passwords should never be cached. Even hashed passwords in cache create security risks. Authentication should always verify against the secure database."
🧠 Memory Trick
Don't cache: Sensitive, volatile, rare, or cheap-to-compute data.
