Keeping Cache Fresh

Caching is easy. Keeping cached data synchronized with the source of truth is hard. Invalidation determines when cached data should be removed or updated after the underlying data changes.

📖 The Story — The Outdated Menu
Why Invalidation Matters

A cached menu that shows old prices creates problems.

Imagine a restaurant updates its menu prices. The website caches the menu for 24 hours. Customers see old prices for an entire day. Some order at the old price. The restaurant loses money. This is a cache invalidation problem. The cache served fast responses, but the data was wrong. Great engineers design invalidation strategies that balance freshness with performance.

🎯 The Cache Invalidation Problem

Phil Karlton famously said: "There are only two hard things in Computer Science: cache invalidation and naming things."

The challenge: The database is the source of truth. The cache is a copy. When the database changes, the cache must eventually reflect that change. But how? When? Who decides?

📐 What is Cache Invalidation?
Cache Invalidation: The process of removing or updating stale cache entries when the underlying data changes. Goal: Keep cache fresh without sacrificing performance.
🔄 Common Invalidation Strategies

1. TTL-Based Invalidation

Set a time-to-live. The entry automatically expires after the TTL.

Cache Entry: Product #123 TTL: 1 hour Result: Automatically removed after 1 hour. Next request fetches fresh data.
✅ Advantages
Simple, automatic, no application logic needed
❌ Disadvantages
Data may be stale until TTL expires

2. Event-Based Invalidation

Invalidate cache when data changes. The application explicitly removes or updates the cache entry.

User updates profile ↓ Database updated ↓ Application deletes cache entry ↓ Next request fetches fresh data
✅ Advantages
Fresh data, immediate consistency
❌ Disadvantages
Requires application logic, more complex

3. Write-Through Invalidation

Every write updates both cache and database simultaneously.

Application → Update Cache → Update Database Cache always has latest data.
✅ Advantages
Strong consistency, cache always fresh
❌ Disadvantages
Higher write latency, more complex

4. Write-Behind (Write-Back) Invalidation

Writes go to cache first. Cache asynchronously updates database.

Application → Update Cache → Async → Database Cache is immediately fresh. Database catches up later.
✅ Advantages
Fast writes, smooth traffic spikes
❌ Disadvantages
Risk of data loss if cache fails

🎯 Choosing the Right Strategy
Use TTL
Data changes infrequently, eventual consistency acceptable
Use Event-Based
Data changes frequently, freshness critical
Use Write-Through
Strong consistency required, write volume manageable
Use Write-Behind
Extreme write throughput, can tolerate eventual consistency
🏭 Production Example
Real World

Social Media Post

When a user edits a post: 1) Event-based invalidation removes the old cached post. 2) Next request fetches the updated version. 3) The new version is cached with a TTL. This combines immediate invalidation with periodic refresh.

🎯 Interview Callout
Q
"How do you keep cache consistent with the database?"
"I use event-based invalidation for critical data and TTL for less critical data. The choice depends on how fresh the data must be and how often it changes."
🧠 Memory Trick
TTL = Time-Based. Event = Change-Based. Write-Through = Immediate. Write-Behind = Async.

A) TTL-Based
B) Write-Behind
C) Event-Based or Write-Through — immediately update cache on changes

Event-based and write-through invalidation update the cache immediately when data changes, providing strong consistency.
2. What is the main trade-off of TTL-based invalidation?
A) It is too complex
B) Data may be stale until the TTL expires
C) It requires application logic
D) It is too expensive
TTL-based invalidation is simple but data can remain stale until the TTL expires. This is acceptable for data that doesn't change frequently.
