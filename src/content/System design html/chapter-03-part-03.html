📖 The Story — The Global Inventory Problem
Why BASE Exists

Should Tokyo wait for London before accepting an order?

Imagine an e-commerce company with warehouses in New York, London, and Tokyo. A customer in London buys the last gaming console. At the exact same time, another customer in Tokyo also buys it. Should the Tokyo customer wait until London confirms the purchase? If every warehouse waits for every other warehouse before accepting orders, the website becomes slow or unavailable whenever networks have problems. Instead, many distributed systems accept temporary inconsistency and synchronize later. This philosophy is the foundation of BASE.

🎯 Why BASE Exists

Relational databases excel at strong consistency, but internet-scale systems introduced new challenges:

👥 Millions of Concurrent Users
Traditional ACID transactions become bottlenecks under massive concurrency
🌍 Multiple Regions
Global deployment requires data replication across continents
🔌 Network Partitions
Networks fail. Systems must remain available despite disconnections
📈 Massive Write Traffic
Billions of writes per day require horizontal scaling
Key Insight: Companies like Amazon needed systems that remained available even when communication between regions became unreliable. The answer was to relax some guarantees provided by ACID.
📐 What is BASE?
BASE stands for: Basically Available, Soft state, Eventually consistent. Unlike ACID, BASE is not a strict transaction model. It is a design philosophy for distributed systems that prioritizes availability and scalability over immediate consistency.
🟢 Basically Available

Intuition: The system should continue serving requests even during failures.

Example: A social media application may continue loading posts even if the "Like Count" service is temporarily unavailable. The application is degraded — but still usable. Availability is prioritized.

🔄 Soft State

Traditional databases assume committed data remains immediately stable. Distributed systems often do not. Data may temporarily differ between replicas while synchronization occurs.

Region A: Likes = 100 Region B: Likes = 98 For a short period, both values may exist simultaneously. This temporary inconsistency is acceptable.
⏱ Eventual Consistency

Intuition: Given enough time — and no new updates — all replicas eventually converge to the same value.

Time T0: Replica A = 100, Replica B = 98 ↓ Replication Time T1: Replica A = 100, Replica B = 100 The system is temporarily inconsistent but eventually becomes consistent.
🌍 Real-World Examples

✅ Social Media Likes

If a post displays 1,000 likes in New York and 998 likes in Singapore, most users will never notice. Eventual consistency is perfectly acceptable.

❌ Banking

Would eventual consistency be acceptable for your account balance? Absolutely not. Financial systems usually require stronger guarantees.

📋 Where BASE Is a Poor Choice
❌ Financial Transactions
Money must never disappear or double-count
❌ Inventory with Strict Guarantees
Overselling is unacceptable
❌ Medical Records
Patient safety depends on data accuracy
❌ Airline Seat Booking
Without safeguards, double-booking occurs
🏭 Production Example — Amazon Shopping Cart
Real World

Amazon Favors Availability for Shopping Carts

Amazon has historically favored availability for some shopping cart operations. If a cart update briefly appears on one device before another, the user experience remains acceptable. The cart eventually converges. Losing the ability to add items entirely would be a worse experience.

🎯 Interview Callout
Q
"Should every distributed system use eventual consistency?"

🚨 Common Mistakes
❌ Assuming BASE Means "Inconsistent Forever"
Eventual consistency means convergence, not permanent inconsistency
❌ Thinking NoSQL Never Provides Strong Consistency
Many NoSQL databases offer configurable consistency levels
❌ Using Eventual Consistency for Financial Transactions
Money requires strong guarantees
