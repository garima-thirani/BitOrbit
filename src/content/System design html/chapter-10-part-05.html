📖 The Story — Amazon's Growing Orders Database
When One Database Isn't Enough

Amazon starts with one database. Initially 100 orders/day. Everything works. Years later: 50 million orders/day. The database suffers from high CPU, slow queries, large indexes, storage limits. Buying a larger server no longer helps.

Amazon's solution is Sharding. By splitting data across multiple databases, each server handles only a subset of the data. This distributes the workload and enables horizontal scaling. Sharding is inevitable at internet scale.

🎯 What is Sharding?
Sharding: Horizontal partitioning across multiple machines. Each database (shard) contains only a subset of the data. A shard router determines which shard stores or retrieves each record. Enables both storage and workload scaling.

✅ Choosing a Shard Key
Good Shard Key: High cardinality, even distribution, frequently queried, stable. Bad Shard Key: Low cardinality (Country), sequential (timestamp), mutable. Example: Using "Country" as shard key means 80% US traffic hits one shard - hotspot!
🔄 Hotspots & Rebalancing
Hotspot: One shard receives much more traffic than others. Example: Celebrity account with millions of followers on one shard. Rebalancing: Moving data between shards to distribute load. Requires online migration, minimal downtime, and careful planning.
🏭 Production Examples
Real World

Instagram & Uber

Instagram: Users sharded by User ID using hash-based sharding. Media stored separately. Follower graph uses different storage. Different services use different shard keys.

Uber: Trips sharded by Trip ID, Drivers by Driver ID, Payments by Region. Each service chooses shard keys based on query patterns.

🎯 Interview Callout
Q
"How do you choose a shard key?"
"A good shard key has high cardinality, distributes data evenly, remains stable, and aligns with common query patterns. Avoid low-cardinality keys like country or status. Prefer user IDs, UUIDs, or composite keys. The shard key is the most important long-term design decision."
🧠 Memory Trick
Hash = even distribution. Range = ordered queries. Directory = flexible. Choose shard key carefully - changing it later is very expensive.
