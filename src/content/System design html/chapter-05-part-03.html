Cache Eviction Policies
LRU, LFU, FIFO — When to Remove Data

Caches have limited memory. When the cache is full, something must leave. Eviction policies decide which data stays and which goes — and this decision directly affects hit rates and performance.

📖 The Story — The Full Bookshelf
Why Eviction Is Necessary

You must remove old books to make room for new ones.

Imagine a bookshelf that holds exactly 50 books. When you buy a new book, you must decide which existing book to remove. Do you remove the book you read most recently? The book you've read most often? The book you bought first? The book that hasn't been touched in years? Each strategy produces a different result. Cache eviction policies work the same way.

🎯 Why Eviction Matters

A cache with infinite memory would never need eviction. But real caches have limits. Poor eviction choices lead to: Low cache hit rates, Wasted memory on rarely-used data, Frequent misses for popular data, Poor application performance.

Key Insight: The right eviction policy can dramatically improve hit rates without increasing cache size.
📐 What is Cache Eviction?
Cache Eviction: The process of removing data from a full cache to make room for new entries. The eviction policy determines which entries are removed.
🔄 Common Eviction Policies

1. LRU — Least Recently Used

Remove the item that hasn't been accessed for the longest time.

Access Order: A → B → C → D → E Cache Full? Remove A (oldest access).
✅ Best For
General purpose, temporal locality
❌ Weakness
Doesn't consider frequency

2. LFU — Least Frequently Used

Remove the item accessed least often.

Access Counts: A(100), B(50), C(10), D(5), E(1) Cache Full? Remove E (fewest accesses).
✅ Best For
Stable access patterns, popularity-based
❌ Weakness
Old popular items may block new trends

3. FIFO — First In First Out

Remove the oldest entry regardless of usage.

Insert Order: A → B → C → D → E Cache Full? Remove A (inserted first).
✅ Best For
Simple, predictable, streaming data
❌ Weakness
Ignores access patterns entirely

4. TTL — Time To Live

Remove entries after a fixed time period.

Entry inserted at 10:00 AM with TTL = 1 hour Automatically removed at 11:00 AM.
✅ Best For
Data with known freshness requirements
❌ Weakness
May remove still-popular data

🎯 Choosing the Right Policy
Use LRU
Most general-purpose workloads. Recent data is likely to be accessed again soon.
Use LFU
When some items are consistently popular regardless of recency.
Use FIFO
When simplicity matters more than optimization.
Use TTL
When data freshness is critical (sessions, OTPs).
🏭 Production Example
Real World

Redis Default: LRU

Redis uses an LRU-like eviction policy by default. When memory is full, it evicts the least recently used keys. This works well for most workloads because recently accessed data is likely to be accessed again. For session data, TTL is often combined with LRU.
