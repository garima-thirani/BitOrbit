📖 The Story — Organizing a Warehouse
Why Schema Design Matters

A well-organized schema reduces work for every query.

Imagine two warehouses. The first labels every shelf, groups similar products together, and keeps an inventory map. The second throws everything into random boxes. Finding a product in the first warehouse takes seconds. Finding it in the second takes hours. The warehouse layout is like a database schema. A well-organized schema reduces work for every query.

📐 What is a Database Schema?
Schema: Defines tables, columns, data types, relationships, constraints, and indexes. It is the structural blueprint of a database.
🔑 Primary Keys & Foreign Keys

🔑 Primary Key

Uniquely identifies every row. Properties: Unique, Not NULL, Stable, Frequently indexed. Examples: UUID, Auto Increment, Snowflake IDs.

🔗 Foreign Key

Connects tables. Ensures referential integrity, prevents orphan records, and establishes clear relationships between entities.

📐 Normalization

Intuition: Avoid storing the same information repeatedly.

❌ Bad Design

Orders table stores Customer Name, Address, Phone — repeated thousands of times.

✅ Normalized Design

Customers table (id, name, address) + Orders table (customer_id, amount). Store customer info once.

Benefits: Less duplication, smaller storage, easier updates, better consistency. Trade-off: Queries often require JOINs.

📦 Denormalization

Sometimes duplication is intentional. Example: Store Customer Name inside an order record for historical accuracy — if the customer changes their name later, past invoices remain unchanged. Denormalization also improves read performance by reducing joins.

⚡ Query Optimization

Fast systems are built with efficient queries.

❌ Avoid SELECT *
Returns unnecessary columns. More network traffic, memory, and disk reads.
✅ Filter Early
Use WHERE clauses to reduce rows before processing.
📊 Use EXPLAIN
Inspect query execution plans to find bottlenecks.
🔗 Fix N+1 Queries
One query + N child queries = N+1 problem. Use JOINs or batch loading.
🎯 Interview Callout
Q
"When would you denormalize a database?"
"When reducing joins significantly improves read performance and the application can tolerate some controlled data duplication."
🧠 Memory Trick
Normalize for correctness. Denormalize for performance.
🧪 Test Your Knowledge
1. When would you choose denormalization over normalization?
A) When storage is expensive
B) When read performance is critical and JOINs are too slow
C) When data integrity is most important
D) When writes are frequent
Denormalization trades storage for read speed by reducing the need for JOINs.
2. What causes the N+1 query problem?
A) Using too many indexes
B) One parent query followed by one query for every child record
C) A slow network connection
D) Too many JOINs in a single query
N+1 occurs when you fetch N parent records and then execute one additional query per child. Solution: Use JOINs or batch loading.
