📖 The Story — Amazon Checkout Transaction
One Transaction, Four Databases

Customer places order. Amazon must: Create Order, Charge Credit Card, Reserve Inventory, Create Shipment. Inside monolith: one transaction spanning all operations. Simple. Now imagine each operation belongs to a different microservice with its own database. Question: How can one transaction span four databases? It can't. Not efficiently.

Order succeeds, Payment succeeds, Inventory fails. Should Payment be refunded? Should Order be cancelled? Who decides? Traditional ACID transactions were designed for single databases. In microservices, each service performs local transactions. There is no global transaction. This is why we need the Saga pattern.

🎯 Why ACID Breaks in Microservices
ACID Properties: Atomicity (all or nothing), Consistency (valid state), Isolation (concurrent safety), Durability (survives crashes). These work perfectly inside one database. But microservices have multiple databases: Orders DB, Payments DB, Inventory DB, Shipping DB. A single SQL transaction cannot span all databases efficiently.

🔄 Choreography vs Orchestration

Choreography (Event-Driven)

OrderCreated ↓ Payment Service ↓ PaymentCompleted ↓ Inventory Service ↓ InventoryReserved ↓ Shipping Service No central coordinator Each service reacts to events

Orchestration (Centralized)

Saga Orchestrator ↓ Tell Orders: Create ↓ Tell Payments: Charge ↓ Tell Inventory: Reserve ↓ Tell Shipping: Create Central coordinator Explicit workflow
✅ Compensating Transactions
Compensating Transaction: A business operation that undoes the effect of a previous operation. Unlike database rollbacks (which undo data changes), compensating transactions reverse real-world business effects. Example: If Payment succeeded but Inventory failed, the compensation is "Refund Payment" and "Cancel Order". These are business operations, not database operations.
🏭 Production Example
Real World

Amazon Checkout Saga

Amazon uses Saga for checkout: Order Service creates order → Payment Service charges card → Inventory Service reserves stock → Shipping Service creates shipment. Each service performs local transaction and publishes event. If Inventory fails after Payment succeeds, compensating actions execute: Refund Payment, Cancel Order, Notify Customer. Idempotency ensures retries are safe. Timeouts prevent infinite waits. DLQ handles repeated failures.

🎯 Interview Callout
Q
"Why can't we use 2PC for microservices?"
"Two-Phase Commit is a blocking protocol with a single coordinator. It creates availability issues, has poor scalability, high latency, and the coordinator is a single point of failure. Modern internet companies prefer Sagas because they provide better availability, scalability, and resilience. BASE (Basically Available, Soft state, Eventual consistency) is preferred over strict ACID in distributed systems."
🧠 Memory Trick
Local Transaction → Publish Event → Next Service → If Failure → Compensate Previous Steps. Saga breaks one big transaction into many small ones with undo actions.
