📖 The Story — The Digital Newspaper
Events Are Like Newspapers

Millions read, nobody knows who.

A newspaper prints today's news. Millions read it. The newspaper doesn't know who reads it, when they read it, or why. It simply publishes facts. Readers decide what interests them. Events work exactly the same way. A producer publishes facts. Consumers independently decide whether to react. An event is not just a message—it's an immutable business fact describing something that already happened.

🎯 What is an Event?
Event: An immutable business fact describing something that has already happened inside the system. Events use past tense because they represent completed actions.
Events (Past Tense): - OrderCreated - PaymentCompleted - InventoryReserved - RideCompleted - UserRegistered NOT events (Commands): - CreateOrder - ProcessPayment - ReserveInventory
📦 Event Anatomy

A production event contains more than business data. It includes metadata for infrastructure understanding.

Complete Event Structure: ┌─────────────────────────────────────┐ │ Metadata │ │ - eventId: "evt_123" │ │ - eventType: "OrderCreated" │ │ - timestamp: "2026-07-01T10:15:00Z" │ │ - version: 1 │ │ - source: "OrderService" │ │ - correlationId: "req_56789" │ ├─────────────────────────────────────┤ │ Business Payload │ │ - orderId: 123 │ │ - customerId: 456 │ │ - total: 899.99 │ └─────────────────────────────────────┘
🏷️ Event Metadata

Event ID

Globally unique identifier. Used for duplicate detection, tracing, debugging, idempotency.

Timestamp

Always use UTC. Helps with ordering, debugging, auditing, analytics.

Event Type

Examples: OrderCreated, PaymentCompleted. Consumers use this to determine processing.

Source

Which service published it. Useful when many services publish similar events.

Version

Schema version. Prevents breaking older consumers when events evolve.

Correlation ID

Links all events from the same business request. Enables distributed tracing.

Causation ID

Identifies the immediate parent event that triggered this event.

👤 Producers & Consumers

Producers

Responsibilities: ✔ Create events ✔ Validate payload ✔ Publish reliably ✔ Never know consumers Examples: - Order Service - Payment Service - User Service

Consumers

Responsibilities: ✔ Validate schema ✔ Process event ✔ Handle duplicates ✔ Retry failures ✔ Record metrics Examples: - Analytics - Recommendations - Notifications
🔑 Key Principles
Immutable
Events never change. Publish new events instead.
One Producer
Exactly one authoritative source per event type.
Many Consumers
Multiple services can react to same event.
Event Contract
Schema must evolve carefully with versioning.
🏭 Production Example
Real World

Amazon OrderCreated Event

Order Service publishes OrderCreated with full metadata. Twenty services consume it: Inventory reserves stock, Shipping prepares shipment, Analytics tracks metrics, Recommendations update, Fraud detects anomalies, ML trains models. Order Service knows nothing about them. This is loose coupling at scale.

🎯 Interview Callout
Q
"What makes an event different from a message?"
"A message is a transport mechanism. An event represents an immutable business fact describing something that already happened. Events carry business meaning and are used for communication in Event-Driven Architecture, while messages are simply containers for transmitting data."
🧠 Memory Trick
Business Action → Event → Metadata + Payload → Broker → Consumers. Events are facts, never instructions.
