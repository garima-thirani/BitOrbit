📖 The Story — Amazon's Product Page
One Page, Ten Services

Product page loads in milliseconds despite ten data sources.

Opening an Amazon product page shows: product name, price, images, reviews, rating, stock, similar products, delivery estimate, seller info, frequently bought together. Data comes from at least ten different services. Question: Should every page request call all ten services? Absolutely not. The page would take seconds. Instead, Amazon builds a Read Model optimized for queries. This is CQRS.

🎯 What is CQRS?
CQRS: Command Query Responsibility Segregation. Separates reads and writes into different models. Write model optimizes for correctness. Read model optimizes for speed.

🏭 Production Example
Real World

Amazon Customer Dashboard

Write side: Order Service writes to PostgreSQL. Events flow through Kafka. Projection services build specialized read models: Customer Dashboard (Redis), Search Index (Elasticsearch), Analytics (ClickHouse), Warehouse Queue (PostgreSQL). Each read model is optimized for its specific query pattern. Customer dashboard loads in milliseconds by querying precomputed Redis cache instead of joining ten tables.

🎯 Interview Callout
Q
"Why does CQRS separate reads and writes?"
"Read and write workloads have different characteristics. Writes prioritize consistency and business rules, while reads prioritize speed and aggregation. CQRS allows each to be optimized independently, improving scalability and flexibility. For example, writes use PostgreSQL for transactions, while reads use Redis for millisecond responses."
🧠 Memory Trick
Command → Write Model → Event → Projection → Read Model → Query. Separate what changes from what's read.
