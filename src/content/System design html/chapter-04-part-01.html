📖 The Story — The Growing Library
Why Sharding Exists

From one giant room to multiple library branches.

Imagine a city library with one giant room containing every book. At first, it works perfectly. Years later, the library contains 100 million books. People wait hours while librarians search shelves. Buying bigger shelves helps only for a while. Eventually the city builds multiple library branches, each storing a subset of books. Instead of one enormous library, the workload is divided. Database sharding follows the same idea.

🎯 Why Sharding Exists

A single database eventually reaches limits:

🖥 CPU
Processing power becomes saturated under high query volume
💾 Memory
RAM limits the size of working data and index caches
💿 Disk Capacity
Storage fills up as data grows exponentially
⚡ Disk I/O
Read/write throughput hits hardware limits
🌐 Network
Bandwidth and connection limits are reached
Key Insight: Even the largest server has physical limits. At internet scale, we distribute data across many database servers.
📐 What is Sharding?
Sharding is the process of splitting one logical database into multiple smaller databases called shards. Each shard stores only a portion of the total data. Unlike replication where every server has the same data, every shard owns different data. Applications still see one logical database.
The shard router decides which shard stores or retrieves a row based on the shard key.
🔀 Horizontal vs Vertical Partitioning

📊 Horizontal Partitioning (Sharding)

Split rows across shards. Each shard has the same schema but different rows.

Users Table 1-1,000,000 → Shard A 1,000,001-2,000,000 → Shard B

📋 Vertical Partitioning

Split columns or services. Different parts of a record in different databases.

User Service: id, name, email Profile Service: avatar, bio, prefs
🗝 Choosing a Shard Key

The shard key determines where data lives. A bad shard key creates hotspots.

✅ Good Shard Keys
User ID, Customer ID, Tenant ID — evenly distributed, naturally partitioned
❌ Poor Shard Keys
Country (uneven sizes), Boolean values, Status fields — causes hotspots
📋 Common Sharding Strategies

1️⃣ Range-Based Sharding

1 - 1,000,000 → Shard A 1,000,001 - 2,000,000 → Shard B

✅ Advantages

Simple implementation. Efficient range queries.

❌ Disadvantages

New data often accumulates in the last shard, creating hotspots.

2️⃣ Hash-Based Sharding

hash(user_id) % N = shard_number Example: hash(42) % 4 = 2 → Store on Shard 2

✅ Advantages

Better data distribution across shards.

❌ Disadvantages

Range queries become difficult. Adding shards requires rehashing.

3️⃣ Geographic Sharding

Europe → EU Database India → APAC Database USA → US Database

✅ Advantages

Compliance with data residency laws. Lower latency for local users.

❌ Disadvantages

Uneven data distribution. Cross-region queries are slow.

🔥 Hotspots
The Hot Shard Problem

Uneven traffic distribution causes bottlenecks.

Imagine every celebrity account is stored on one shard. Millions of requests target that shard while others remain idle. This is called a hot shard. Solutions include: better shard keys, consistent hashing (covered in Part 2), caching frequently accessed data, and replication for read-heavy hotspots.

🔄 Cross-Shard Queries

Suppose you ask: SELECT COUNT(*) FROM Users; — the answer exists across every shard. The coordinator must: 1) Query all shards. 2) Aggregate results. 3) Return one answer. Cross-shard joins and transactions become expensive.

🔄 Re-Sharding

Eventually shards fill up. You may need to split a shard into two. Moving data between shards is operationally expensive and should be planned carefully.

Shard A (Full) ↓ Split Shard A1 + Shard A2
⚖ Advantages & Disadvantages

✅ Advantages

• Near-unlimited horizontal growth
• Smaller indexes
• Better write throughput
• Reduced lock contention
• Independent scaling

❌ Disadvantages

• Operational complexity
• Cross-shard transactions
• Rebalancing data is hard
• Harder backups
• Harder analytics queries

🎯 Interview Callout
Q
"When would you shard a database?"
"Only after optimizing queries, adding indexes, caching, and using read replicas. Sharding increases operational complexity and should be introduced when a single database can no longer meet scalability requirements."

🚨 Common Mistakes
❌ Sharding Too Early
Optimize queries, add indexes, and use replicas before sharding.
❌ Choosing a Poor Shard Key
Bad keys create hotspots and uneven distribution.
❌ Ignoring Hotspot Formation
Monitor shard utilization. Hotspots defeat the purpose of sharding.
❌ Forgetting Cross-Shard Operations
Cross-shard joins and transactions are expensive and complex.
🧪 Test Your Knowledge
1. What is the difference between sharding and replication?
A) They are the same thing
B) Replication copies data; sharding splits data across servers
C) Sharding is faster than replication
D) Replication is only for NoSQL databases
Replication keeps the same data on multiple servers for redundancy. Sharding divides different data across servers for horizontal scaling.
2. Which sharding strategy is best for evenly distributing data but makes range queries difficult?
A) Range-Based Sharding
B) Hash-Based Sharding — hash(key) % N ensures even distribution
C) Geographic Sharding
D) Vertical Partitioning
Hash-based sharding spreads data uniformly across shards but loses the natural ordering needed for efficient range queries.
3. What creates a "hot shard"?
A) A shard with too much RAM
B) A poor shard key that concentrates popular data on one shard
C) A shard that is too fast
D) A shard in a cold data center
Hot shards occur when a bad shard key causes all popular data to land on the same shard, overwhelming it while others sit idle.
