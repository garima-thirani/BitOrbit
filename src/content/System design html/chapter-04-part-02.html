Consistent Hashing
Minimizing Data Movement When Nodes Change

Traditional hashing works well until the number of servers changes. Consistent hashing was invented to minimize data movement when nodes are added or removed.

📖 The Story — Lockers in a Train Station
Why Modulo Hashing Fails

Adding one locker forces everyone to move.

Imagine 1,000 passengers storing luggage in 10 lockers. Each passenger uses: Locker = Ticket Number % 10. Now the station adds one more locker. The rule becomes Ticket Number % 11. Almost every passenger must move luggage to a different locker. This creates chaos. Traditional hashing behaves exactly like this.

❌ The Problem with Modulo Hashing

Suppose we distribute users across 4 servers:

Server = hash(user_id) % 4

Adding a fifth server changes the formula to hash(user_id) % 5. Result:

📦 Most Keys Move
Nearly all data must be redistributed when N changes
💥 Cache Misses Spike
All cache entries become invalid, causing a thundering herd
🚚 Massive Data Migration
Terabytes of data may need to move across the network
For large systems, this is unacceptable. Consistent hashing solves this.
🎯 What is Consistent Hashing?
Consistent Hashing places both servers and keys on the same logical hash ring. Instead of recalculating every key when servers change, only keys near the affected server move. This dramatically reduces rebalancing.
🔄 The Hash Ring
Servers A, B, C are placed on the hash ring. Key X is assigned to the next server clockwise — Server A.
📋 How It Works

Imagine hash values arranged in a circle from 0 to 2³²-1:

Hash Ring (0 to 2³²-1) Servers placed on ring: hash(server_ip) → position Keys placed on ring: hash(key) → position Each key → next server clockwise Example: Server A at 100°, Server B at 200°, Server C at 300° Key X at 150° → next clockwise server = B
➕ Adding a New Server

Before

A ---- B ---- C

After adding D

A ---- B ---- D ---- C

Only keys between B and C move to D. No global reshuffling is required.

➖ Removing a Server

If Server C fails:

Before: A ---- B ---- C ---- D After: A ---- B ---- D

Only C's keys move to D. This enables graceful recovery from failures.

🔷 Virtual Nodes (vNodes)

Real servers rarely have identical capacity. Instead of placing one point per server on the ring, each physical server owns multiple virtual nodes.

Server A → A1, A2, A3 (3 virtual nodes on ring) Server B → B1, B2, B3 Server C → C1, C2, C3
📊 Better Load Distribution
Virtual nodes spread data more evenly across physical servers
⚖ Easier Balancing
Different servers can have different numbers of vNodes based on capacity
🔄 Smoother Scaling
Adding/removing servers causes minimal disruption
Modern systems almost always use virtual nodes.
🏭 Production Use Cases
⚡ Distributed Caches
Redis Cluster and Memcached use consistent hashing to distribute keys across nodes
🗄 Distributed Databases
Cassandra, DynamoDB use consistent hashing to partition data across nodes
🌐 CDNs
Edge servers use consistent hashing to route content while minimizing cache invalidation
⚖ Advantages & Disadvantages

✅ Advantages

• Minimal data movement when nodes change
• Easy horizontal scaling
• Better fault tolerance
• Improved cache hit ratios
• Reduced operational cost during expansion

❌ Disadvantages

• More complex than modulo hashing
• Requires metadata about the ring
• Poor implementation can still create hotspots

Q
"Why is consistent hashing preferred over hash(key) % N?"

🚨 Common Mistakes
❌ Forgetting Clockwise Lookup
The rule is always "next server clockwise" from the key's position
❌ Ignoring Virtual Nodes
Without vNodes, load distribution can be highly uneven
❌ Assuming Perfect Balance
Consistent hashing improves distribution but doesn't guarantee perfect balance

A) All keys are redistributed across all servers

C) All keys must be rehashed

In consistent hashing, only keys belonging to the removed server are reassigned. All other keys remain untouched.

Virtual nodes allow each physical server to appear at multiple positions on the ring, creating a more even distribution of keys.
