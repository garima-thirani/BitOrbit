📋 Quick Revision Notes

Database Sharding

Splits rows across multiple databases. Each shard stores different data. Benefits: Near-unlimited horizontal growth, smaller indexes, better write throughput. Challenges: Cross-shard queries, rebalancing, operational complexity. Replication copies data. Sharding splits data.

Consistent Hashing

Places servers and keys on a hash ring. Only nearby keys move when nodes change. Virtual nodes improve load distribution. Used by Redis Cluster, Cassandra, CDNs. Modulo hashing = move almost everything. Consistent hashing = move only what's necessary.

Primary-Replica Pattern

Primary accepts writes. Replicas serve reads. Replication copies changes. Challenge: Replication lag. Solution: Read your own writes, sticky reads, accept eventual consistency for non-critical data. Primary Writes. Replicas Read.

Multi-Leader Replication

Multiple databases accept writes. Reduces global write latency. Challenge: Write conflicts. Solutions: Last Write Wins, application-level resolution, version vectors, CRDTs. Multiple Writers = Multiple Conflicts.

Connection Pooling

Reuses database connections to avoid TCP handshake, authentication, and session initialization overhead. Pool sizing matters: too small = waiting, too large = overwhelmed database. Connections are expensive. Queries are cheap. Reuse connections.

💡 Flashcards
Q: Difference between sharding and replication?
A: Sharding distributes different data. Replication copies the same data.
Sharding splits data for horizontal scaling. Replication copies data for redundancy and read scaling.
Q: Why is consistent hashing better than modulo hashing?
A: Only a small subset of keys move when nodes change
Modulo hashing requires nearly all keys to move when N changes. Consistent hashing only moves keys near the affected node.
Q: Can read replicas increase write capacity?
A: No. Replicas only distribute read traffic. All writes go to primary.
Read replicas scale reads horizontally. Write capacity remains limited by the primary unless multi-leader replication is used.

🚨 Common Mistakes
❌ Sharding Too Early
Optimize queries, add indexes, use replicas first
❌ Poor Shard Key
Creates hotspots and uneven distribution
❌ Ignoring Replication Lag
Critical reads must go to primary
❌ Multi-Leader Without Conflict Strategy
Always explain how conflicts are resolved
❌ Unlimited Connections
Connection pooling is essential for performance
🧪 Final Quiz
1. Your e-commerce site has 95% reads, 5% writes. Primary handles 500 writes + 15,000 reads. How do you scale?
A) Shard the database immediately
B) Add read replicas to distribute the 15,000 reads
C) Switch to multi-leader replication
D) Buy a bigger server
Read replicas are the simplest solution for read-heavy workloads. The primary handles writes, replicas handle reads.
2. When would you choose multi-leader replication?
A) For banking systems requiring strong consistency
B) For global applications where low write latency is critical
C) When you don't want to handle conflicts
D) For simple single-region deployments
Multi-leader replication reduces write latency for globally distributed users but requires conflict resolution strategies.
