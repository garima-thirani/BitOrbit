📖 The Story — The Double Payment Problem
When Two Services Process the Same Payment

Two Payment Services receive the same payment request. Both read the order. Both see UNPAID. Both charge the customer. Result: $100 charged twice. The problem is not the payment code. The problem is coordination.

Without coordination, multiple machines can interfere with each other. Distributed Coordination ensures that only one node performs critical operations at a time. This prevents duplicate work, race conditions, and data corruption.

🎯 What is Distributed Coordination?
Distributed Coordination: Mechanisms that synchronize work across multiple machines. Ensures exclusive access to shared resources, elects leaders, manages configuration, and prevents conflicting operations.

🔄 Lease-Based Locks
Lease: A lock with automatic expiration. If the lock holder crashes, the lock automatically expires after a timeout. Others can then acquire it. Prevents permanent deadlocks from abandoned locks. Example: 30-second lease, renewed by heartbeats.
✅ Optimistic vs Pessimistic Locking
Optimistic: Assume conflicts are rare. Read data, modify, check version, update. Retry if conflict. High throughput, low contention. Pessimistic: Assume conflicts are common. Acquire lock before modifying. Lower concurrency, prevents conflicts.
🏭 Production Examples
Real World

Kubernetes & HBase

Kubernetes: Uses etcd for cluster state, leader election, and configuration. Every pod, deployment, and service depends on etcd coordination.

HBase: Uses ZooKeeper for master election, region assignment, and failure detection. Ensures only one active master at a time.

🎯 Interview Callout
Q
"Why can't we use a database for distributed locking?"
"You can, but databases aren't optimized for coordination. ZooKeeper and etcd provide specialized primitives: ephemeral nodes (auto-delete on disconnect), sequential nodes (ordering), watches (notifications), and fast consensus. These features make them better suited for coordination than general-purpose databases."
