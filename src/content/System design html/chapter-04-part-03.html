Primary-Replica & Read-Write Separation
Scaling Reads

Most production systems receive far more reads than writes. Read/Write Separation distributes this workload so the primary database handles writes while replicas serve reads.

📖 The Story — The Famous Restaurant
Why Read/Write Separation Exists

The chef should focus on cooking, not answering questions.

Imagine a famous restaurant. There is only one head chef who prepares every dish. Customers don't just place orders — they also constantly ask: "Can I see the menu?", "What are today's specials?", "How many desserts do you have?" Soon, the chef spends more time answering questions than cooking. The owner hires several assistants. The assistants answer customer questions while the chef focuses only on cooking. The restaurant becomes much more efficient. This is exactly how read/write separation works.

🎯 Why Read/Write Separation?

In many applications, 90-99% of operations are reads, only 1-10% are writes. Examples: Social media feeds, E-commerce product browsing, News websites, Blogs, Video platforms. Sending every request to one database wastes resources.

📐 What is the Primary-Replica Pattern?
Primary (Leader): Accepts all write operations.
Replicas (Followers): Continuously copy data from the primary. Serve read-only queries.

Applications send: Writes → Primary · Reads → Replicas
🏛 Basic Architecture
Primary handles writes. Replicas handle reads. Replication copies changes from primary to replicas.
📋 Write Flow
Client → Primary Database → Write Successful → Replication → Replicas Updated

Only the primary accepts writes. This ensures consistency and avoids conflicts.

📋 Read Flow
Client → Application → Replica Database → Result Returned

The primary remains free to process writes while replicas handle read traffic.

📈 Why This Improves Scalability

Without replicas: Primary handles 15,500 req/s (500 writes + 15,000 reads). With three replicas: Primary handles 500 writes, each replica handles 5,000 reads. Load is distributed efficiently.

⏱ Replication Lag
The Lag Problem

Replication is rarely instantaneous.

Example: Primary shows Balance = ₹500 after a deposit. User reads from Replica — Balance = ₹600 (old value). The replica has not yet processed the latest update. This delay is called replication lag.

🔄 Handling Replication Lag
📖 Read Your Own Writes
After updating data, temporarily read from the primary
🔑 Critical Reads
Important operations (payments, profile updates) read from primary
⏱ Eventual Consistency
Accept temporary stale data for non-critical info (view counts, ratings)
🏭 Production Example

An online shopping platform: Product browsing goes to replicas. Checkout always goes to the primary. This ensures product pages load fast while payment processing has the latest data.

🎯 Interview Callout
Q
"A user updates their profile but immediately sees the old value. Why?"
"The application probably read from a replica before replication completed. This is a classic replication lag issue."
