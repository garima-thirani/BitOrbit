📖 The Story — The Broken Checkout
One Field Breaks Half the Company

customerId → userId breaks everything.

Today's OrderCreated event: {"orderId": 101, "customerId": 501, "amount": 999}. Life is good. Twenty services consume it. Six months later, marketing introduces coupons. Developer changes event to include discountCode. Still fine. Three months later, another developer renames customerId to userId. Now Shipping crashes. Analytics crashes. Fraud crashes. ML crashes. Recommendations crashes. One tiny schema change broke half the company. This is why schema evolution is one of the most important topics in Event-Driven Architecture.

🎯 Why Schemas Change
Schema Evolution: Business never stays the same. Events must evolve safely. Version 1 has orderId and customerId. Version 2 adds coupon. Version 3 adds tax. Version 4 adds currency. Every business evolution requires schema changes.

📊 Compatibility Types

Backward Compatibility

New consumers can read old events. Add optional fields with defaults.

Forward Compatibility

Old consumers can read new events. Ignore unknown fields.

Full Compatibility

Both directions work. Safest but hardest to maintain.

✅ Safe vs Dangerous Changes

✅ Safe Changes

✔ Add optional field ✔ Add field with default ✔ Add enum values ✔ Add metadata ✔ Deprecate (don't remove)

❌ Dangerous Changes

❌ Rename fields ❌ Remove fields ❌ Change field types ❌ Change semantics ❌ Make optional field required
📦 Schema Registry
Schema Registry: Central repository for versioned schemas. Producers and consumers validate against it, preventing incompatible changes and enabling controlled evolution.
Producer → Schema Registry → Validate → Kafka → Consumer → Schema Registry → Validate

🏭 Production Example
Real World

Netflix Schema Evolution

Netflix's PlaybackStarted event evolved from V1 (profileId, movieId) to V5 (device, country, quality, subtitles, audio). Each version added optional fields. Old consumers ignored unknown fields. New consumers used defaults for missing fields. Schema Registry prevented breaking changes. Gradual migration over months ensured zero downtime.

🎯 Interview Callout
Q
"How would you add a new field to an event consumed by 200 services?"
"Add the field as optional with a default value. Register the new schema version. Update consumers to accept both old and new schemas. Deploy consumers first, then deploy producers. Monitor schema validation errors before deprecating older versions."
🧠 Memory Trick
Schema → Registry → Version → Compatibility → Migration. Never break contracts. Always add, never rename or remove.
