Multi-Leader Replication & Conflict Resolution
Multiple Writable Databases

A single primary database eventually becomes a bottleneck for globally distributed write-heavy applications. Multi-leader replication allows multiple databases to accept writes simultaneously — but introduces the challenge of conflicting updates.

📖 The Story — Two Bank Branches
Why Multi-Leader Exists

Both branches should process deposits independently.

Imagine a bank with one branch in London and another in Singapore. If only the London branch can update account balances, every transaction from Singapore must travel across the world. Customers experience unnecessary latency. Instead, suppose both branches can process deposits independently. Performance improves dramatically. But what happens if both branches update the same account at the same time? Both changes are valid. Which one should win? This is the central problem of multi-leader replication.

🎯 Why Multi-Leader Replication?

Single-primary systems are simple but have limitations:

🌍 Higher Write Latency
Distant users must write to a remote primary
🚧 Primary Bottleneck
All writes flow through one database
💥 Regional Outages Impact Writes
If primary region fails, writes stop
Key Insight: Multi-leader replication distributes write traffic across multiple writable databases, reducing global write latency.
📐 Single-Leader vs Multi-Leader

Single-Leader

Only one database accepts writes. All others are read-only replicas. Simple but creates a write bottleneck.

Multi-Leader

Multiple databases accept writes. Each leader asynchronously replicates changes to others. Lower latency, more complex.

🔄 Replication Flow

Example: Customer in Europe updates profile.

Europe Client → Leader A → Replication → Leader B Customers in Asia update Leader B directly. Latency is reduced for both regions.
⚠ The Conflict Problem
When Both Leaders Update the Same Data

Both changes are valid. Which one should win?

Suppose two users edit the same document. Leader A: Name = Alice. Leader B: Name = Alicia. Both updates occur before replication completes. Now each leader contains different values. This is a conflict.

🛠 Conflict Resolution Strategies
1️⃣ Last Write Wins (LWW)
The newest timestamp wins. Simple, fast. Earlier updates may be lost.
2️⃣ Application-Level Resolution
The application decides. Example: Git merge. Humans resolve conflicts manually.
3️⃣ Version Vectors
Each update carries version metadata. Conflicting versions detected explicitly. Applications decide how to merge.
4️⃣ CRDTs
Conflict-Free Replicated Data Types. Specialized data structures that automatically merge concurrent updates. Common in collaborative editing.

🎯 Interview Callout
Q
"When would you choose multi-leader replication?"
"When users write from multiple geographic regions and low write latency is more important than strict global consistency. I would avoid it for financial systems because conflict resolution becomes difficult."
🧠 Memory Trick
Multiple Writers = Multiple Conflicts
Always explain how conflicts are resolved.
