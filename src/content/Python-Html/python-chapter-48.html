📖 The Story — Flight Simulator
Safe Practice

Pilots train in flight simulators before flying real planes. Mock objects are the software equivalent - fake implementations for safe testing.

Imagine a pilot learning to fly. They don't start with a plane full of passengers. Instead, they train in a flight simulator that behaves like a real plane but without risks. If they make a mistake, nobody gets hurt. Mocking works the same way in testing. Instead of calling real APIs, databases, or external services (which are slow, expensive, or risky), we use fake objects that behave like the real thing but are completely under our control.

🔧 Basic Mock Example
Creating and using mocks:

from unittest.mock import Mock, MagicMock

# Create a mock object
mock_db = Mock()

# Configure return values
mock_db.get_user.return_value = {"id": 1, "name": "Alice"}

# Use the mock
user = mock_db.get_user(1)
print(user) # {"id": 1, "name": "Alice"}

# Verify it was called
mock_db.get_user.assert_called_once_with(1)
🔧 patch() Example
Using patch to replace dependencies:

from unittest.mock import patch
import requests

# Function that uses requests
def fetch_data(url):
  response = requests.get(url)
  return response.json()

# Test with mocked requests
@patch('requests.get')
def test_fetch_data(mock_get):
  # Configure mock
  mock_get.return_value.json.return_value = {"key": "value"}
  
  # Call function
  result = fetch_data("http://example.com")
  
  # Verify
  assert result == {"key": "value"}
  mock_get.assert_called_once()

⚠️ Common Mistakes
❌
Mocking everything.
✔ Only mock external dependencies. Don't mock the code you're testing.
❌
Testing implementation instead of behavior.
✔ Test what the code does, not how it does it. Focus on inputs and outputs.
❌
Chasing 100% coverage.
✔ Coverage measures quantity, not quality. 80% of critical paths is better than 100% of trivial code.
❌
Not testing edge cases.
✔ Mocks should simulate both success and failure scenarios.
🎯 Interview Questions
Q
"What is mocking and when should you use it?"
"Mocking replaces real objects with fake implementations during testing. Use it when: 1) Testing code that depends on external services (APIs, databases), 2) You need to simulate error conditions, 3) Tests would be slow or expensive with real dependencies, 4) You want to isolate the code being tested. Mocking makes tests fast, deterministic, and independent."
Q
"What is code coverage and is 100% coverage necessary?"
"Code coverage measures the percentage of your code executed during tests. While 100% coverage sounds ideal, it's not always necessary or cost-effective. Focus on covering critical paths, edge cases, and business logic. 80-90% coverage of important code is often sufficient. Quality of tests matters more than quantity."
