# Why Analytics Matter

For users,

a shortened URL is just a redirect.

For businesses,

it is also an analytics platform.

When someone clicks

```
tiny.ly/openai
```

companies want to know

- Number of clicks
- Country
- Browser
- Device
- Operating System
- Timestamp
- Referrer
- Campaign

Marketing teams use this data to measure campaign performance.

---

# The Wrong Approach

A beginner might design the redirect flow like this.

```text
User

↓

Redirect Service

↓

Database Lookup

↓

Update Analytics

↓

Return Redirect
```

This introduces a serious problem.

Every redirect now waits for analytics.

Suppose analytics takes

```
50 ms
```

Every user experiences additional latency.

The redirect becomes slower for everyone.

---

# Asynchronous Analytics

Instead,

analytics should be decoupled.

```text
User

↓

Redirect Service

↓

Redirect Immediately

↓

Publish Event

↓

Kafka
```

The user receives the redirect immediately.

Analytics happens in the background.

This is one of the most common production design patterns.

---

# Why Kafka?

Kafka acts as an event pipeline.

Every redirect generates an event.

```text
Redirect Event

↓

Kafka Topic

↓

Analytics Consumers

↓

Analytics Database
```

Advantages:

- High throughput
- Durable event storage
- Independent consumers
- Easy scaling

If analytics services become busy,

Kafka stores events until consumers catch up.

---

# Event Structure

A click event might look like this.

```json
{
  "shortCode": "AbC123",
  "timestamp": "2026-07-05T12:30:14Z",
  "country": "US",
  "browser": "Chrome",
  "device": "Mobile",
  "ip": "Masked"
}
```

Notice that the redirect has already completed.

This event is processed later.

# Real-Life Example

Suppose Nike launches a campaign.

```
tiny.ly/nike-sale
```

Millions of users click it.

The redirect service simply redirects users.

Meanwhile,

Kafka streams click events to analytics workers.

Marketing dashboards update every few seconds without affecting redirect performance.

---

# Analytics Database

Analytics queries differ from operational queries.

Operational query:

```sql
Find original URL
```

Analytics query:

```sql
Clicks by country

Last 30 days
```

These workloads should not share the same database.

Instead,

analytics is stored separately.

Possible choices:

- ClickHouse
- BigQuery
- Redshift
- Snowflake
- Elasticsearch

This separation improves performance for both workloads.

# Rate Limiting

Suppose someone creates

10 million URLs

in one hour.

This could exhaust storage or launch a spam campaign.

We need rate limiting.

```text
Client

↓

API Gateway

↓

Rate Limiter

↓

Allowed?

↓

Yes

↓

Continue
```

Common algorithms:

- Token Bucket
- Leaky Bucket
- Sliding Window

Redis is commonly used to implement these efficiently.

# Abuse Prevention

URL shorteners are often abused.

Examples include:

- Phishing
- Malware
- Spam
- Fake login pages

Production systems implement several layers of protection.

---

## URL Validation

Before shortening,

verify that the URL is valid.

Reject malformed URLs immediately.

---

## Safe Browsing Checks

Compare URLs against threat intelligence databases.

Example:

```text
User URL

↓

Safe Browsing API

↓

Safe?

↓

Yes

↓

Store
```

---

## Domain Blacklists

Maintain a blacklist of known malicious domains.

Example:

```
malicious-site.com

↓

Reject
```

---

## User Quotas

Limit the number of URLs each user can create.

Example:

```
Free Plan

↓

100 URLs/day
```


# Failure Scenario 1 — Redis Crash

Suppose Redis becomes unavailable.

What happens?

```text
Redirect Service

↓

Redis

↓

Unavailable

↓

Database

↓

Return Redirect
```

Latency increases,

but the system continues operating.

Redis can later rebuild its cache.

---

# Failure Scenario 2 — Database Failure

If the primary database fails,

a replica should take over.

```text
Primary

↓

Failure

↓

Replica Promotion

↓

New Primary
```

Users experience minimal disruption.

---

# Failure Scenario 3 — Kafka Failure

Suppose Kafka is temporarily unavailable.

Should redirects stop?

No.

The primary function of the system is redirection.

Possible approaches:

- Retry publishing.
- Buffer events temporarily.
- Accept temporary analytics loss if business requirements allow.

User experience should always take priority.

---

# Multi-AZ Deployment

Never deploy everything in one data center.

Instead,

spread services across multiple Availability Zones.

```text
        Load Balancer

        /          \

AZ-1            AZ-2

Redirect        Redirect

Redis           Redis

Database        Replica
```

If one Availability Zone fails,

traffic shifts automatically.

---

# Multi-Region Deployment

For global applications,

multiple regions reduce latency and improve resilience.

```text
US Region

Europe Region

Asia Region
```

DNS routes users to the nearest healthy region.

---

# Backup Strategy

Databases should be backed up regularly.

Example:

- Hourly snapshots
- Daily backups
- Cross-region replication

Backups protect against accidental deletion and catastrophic failures.

---

# Disaster Recovery

Suppose an entire cloud region becomes unavailable.

Production systems should support failover.

```text
Primary Region

↓

Failure

↓

Secondary Region

↓

Traffic Redirected
```

This minimizes downtime.

---

# Security Considerations

Production systems should implement:

- HTTPS everywhere
- TLS encryption
- Authentication for management APIs
- Authorization
- Secret Management
- Audit Logs
- WAF
- Rate Limiting

Security is a core architectural requirement,

not an afterthought.

# Key Takeaways

- Analytics should be asynchronous to avoid increasing redirect latency.
- Kafka decouples event generation from event processing, enabling scalable analytics.
- Operational data and analytical data should be stored separately.
- Rate limiting, URL validation, and blacklist checks protect the system from abuse.
- Monitoring, logging, and distributed tracing are essential for operating production systems.
- High availability is achieved through replication, Multi-AZ deployments, and failover mechanisms.
- Disaster recovery plans and backups ensure business continuity during major failures.
- Production architecture is about much more than functionality—it must also be secure, observable, scalable, and resilient.
