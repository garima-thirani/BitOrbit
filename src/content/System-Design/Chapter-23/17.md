# Designing for Failure

A beginner designs systems like this:

```text
Everything Works
```

An experienced engineer designs systems like this:

```text
Everything Will Eventually Fail
```

Failures include:

- Hardware failures
- Disk failures
- Memory corruption
- Network partitions
- Human mistakes
- Cloud outages
- Software bugs

Instead of preventing failures,

we build systems that survive them.

---

# Multi-AZ Deployment

Never deploy every component into one Availability Zone.

Instead:

```text
                 Global Load Balancer

                     /          \

             Availability   Availability

               Zone A         Zone B

          Connection S1   Connection S2

          Redis Primary   Redis Replica

         Database P       Database Replica
```

If Zone A fails,

traffic automatically moves to Zone B.

---

# Real-Life Example

Think of a hospital.

Would all operating rooms be in one building?

No.

If one building catches fire,

patients can still receive treatment elsewhere.

Cloud infrastructure follows the same philosophy.

---

# Multi-Region Deployment

WhatsApp serves users worldwide.

Instead of one giant deployment,

multiple regional clusters exist.

```text
                Global DNS

          /         |         \

      US-East    Europe     Asia

          |          |          |

      WhatsApp   WhatsApp   WhatsApp

       Cluster    Cluster    Cluster
```

Users connect to the nearest healthy region.

Benefits:

- Lower latency
- Better fault tolerance
- Faster disaster recovery

---

# Why Multiple Regions?

Suppose a user in India sends a message.

Should it travel to California?

No.

Instead,

the request stays within the Asia region whenever possible.

This reduces latency dramatically.

---

# Global DNS Routing

Global DNS determines

which region receives a user.

```text
User

↓

DNS

↓

Nearest Healthy Region
```

If Europe fails,

DNS redirects users elsewhere.

---

# Load Balancers

Within each region,

traffic is distributed.

```text
               Load Balancer

          /        |        \

     Server1   Server2   Server3
```

Benefits:

- Prevent overload
- Automatic failover
- Better utilization

---

# Connection Server Failure

Suppose Bob is connected to

```
Connection Server 12
```

The server crashes.

What happens?

```text
Connection Lost

↓

Reconnect

↓

Load Balancer

↓

Server 25

↓

Resume Session
```

The client reconnects automatically.

---

# Session Recovery

When reconnecting,

the client sends:

- User ID
- Authentication Token
- Last Received Message

The server resumes synchronization.

---

# Redis Failure

Redis stores temporary data.

Suppose Redis crashes.

```text
Presence Lookup

↓

Redis Down

↓

Database

↓

Restore Redis
```

Performance decreases,

but messaging continues.

---

# Redis Replication

Production Redis uses replication.

```text
Primary Redis

↓

Replica 1

↓

Replica 2
```

If the primary fails,

one replica becomes the new primary.

---

# Database Replication

Messages are permanent.

Databases require stronger guarantees.

```text
Primary Database

↓

Replication

↓

Replica Database
```

Writes go to the primary.

Reads may come from replicas.

---

# Database Failover

Suppose the primary database crashes.

```text
Primary Down

↓

Replica Promotion

↓

Applications Reconnect
```

The transition should be automatic.

---

# Why Read Replicas?

Suppose millions of users open old conversations.

Those are read operations.

Instead of overloading the primary,

read replicas answer those requests.

```text
Primary

↓

Replica A

Replica B

Replica C
```

---

# Kafka Failure

Suppose Kafka becomes unavailable.

Should messaging stop?

No.

Strategies include:

- Retry
- Local buffering
- Dead Letter Queue
- Event replay

Messaging should continue whenever possible.

---

# Dead Letter Queue (DLQ)

Suppose one notification repeatedly fails.

Instead of blocking everything,

move it to a DLQ.

```text
Notification

↓

Retry

↓

Retry

↓

Retry

↓

Dead Letter Queue
```

Engineers investigate later.

---

# Object Storage Failure

Cloud object storage automatically replicates data.

```text

↓

Zone A

↓

Zone B

↓

Zone C
```

Even if one storage node fails,

media remains available.

# WebSocket Scaling

Suppose one Connection Server supports

```
200,000 Connections
```

Need

```
500 Million
```

connections?

```text
500,000,000

÷

200,000

≈

2,500 Servers
```

Scaling becomes horizontal.

# Production Trade-offs

Every decision has advantages and disadvantages.

Advantages

- Low latency
- Persistent connection

Disadvantages

- Long-lived connections

## Redis

Advantages

- Fast lookups

Disadvantages

- Memory cost
- Cache invalidation

---

## Kafka

Advantages

- Decoupled architecture
- Event replay
- High throughput

Disadvantages

- Operational complexity

---

## Object Storage

Advantages

- Cheap
- Durable
- Massive scale

Disadvantages

- Higher latency than local storage

## Multi-Region

Advantages

- Low latency
- Disaster recovery

Disadvantages
