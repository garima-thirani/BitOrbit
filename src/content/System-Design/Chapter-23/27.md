# Designing for Failure

A beginner designs systems assuming:

```text
Everything Works
```

Production engineers assume:

```text
Everything Will Eventually Fail
```

Failures include:

- Server crashes
- Disk failures
- Network outages
- ISP failures
- Software bugs
- Cloud outages
- Human mistakes

Netflix is designed to survive all of them.

# Multi-AZ Deployment

Each Netflix service runs in multiple Availability Zones.

```text
                    API Gateway

                   /           \

              AZ-A             AZ-B

        Playback S1       Playback S2

        Metadata DB P     Metadata DB R

        Redis P           Redis Replica
```

If AZ-A fails,

traffic automatically shifts.

Users usually never notice.

---

# Multi-Region Deployment

Netflix operates globally.

```text
                  Global DNS

        /            |            \

   North America   Europe      Asia-Pacific

        │             │              │

   Netflix Cluster Netflix Cluster Netflix Cluster
```

Each region serves nearby users.

Benefits:

- Lower latency
- Regional isolation
- Disaster recovery

---

# Why Multiple Regions?

Suppose someone in Tokyo watches a movie.

Should every request travel to California?

No.

Instead,

the user connects to

```text
Tokyo

↓

Nearby Open Connect

↓

Streaming
```

Latency remains low.

---

# Global DNS Routing

The first step is DNS resolution.

```text
User

↓

DNS

↓

Nearest Healthy Region
```

If one region fails,

DNS redirects traffic.

# Netflix Open Connect

Unlike many companies,

Netflix built its own global CDN.

This is called

**Open Connect.**

---

# Open Connect Architecture

```text
                 Netflix Storage

                      │

                      ▼

            Open Connect Backbone

          /         |          \

      ISP-A      ISP-B      ISP-C

        │           │           │

     Users      Users      Users
```

Netflix installs caching appliances directly inside ISP networks.

---

# Why Inside ISPs?

Suppose

100,000 users

in one city

watch the same movie.

Without Open Connect:

```text
Users

↓

Internet

↓

Netflix
```

Huge bandwidth usage.

---

With Open Connect:

```text
Users

↓

ISP Cache

↓

Movie
```

Almost no long-distance traffic.

---

# Benefits of Open Connect

- Lower latency
- Reduced buffering
- Lower ISP costs
- Lower Netflix bandwidth costs
- Better user experience

This is one of Netflix's greatest engineering innovations.

# CDN Replication

Popular content is replicated aggressively.

```text

↓

USA

Europe

India

Japan

Australia
```

Less popular titles remain in fewer locations.

---

# Cache Eviction

CDNs have limited storage.

Old content eventually leaves.

Strategies include:

- LRU
- LFU
- Popularity-based eviction

Popular content stays longer.

---

# Playback Service Failure

Suppose the Playback Service crashes.

Should the movie stop?

No.

Remember:

Playback Service only authorizes streaming.

After playback begins,

the client communicates directly with the CDN.

Streaming continues uninterrupted.


# Metadata Database Replication

Metadata is critical.

Databases replicate continuously.

```text
Primary

↓

Replica 1

↓

Replica 2
```

Reads often come from replicas.

Writes go to the primary.

# Interview Tips

Interviewers often ask:

> **"Why did Netflix build Open Connect instead of relying entirely on cloud CDNs?"**

A strong answer is:

> "Video streaming consumes enormous bandwidth. By deploying Open Connect appliances inside ISP networks, Netflix serves content much closer to users, reducing latency, lowering transit costs, improving cache hit rates, and minimizing internet backbone traffic."

This demonstrates an understanding of large-scale content delivery.
