# Introduction

Our Uber architecture now supports:

- Driver matching
- GPS tracking
- Ride assignment
- WebSockets
- ETA calculation
- Surge pricing
- Payments
- Notifications

But production systems aren't evaluated based on how they work when everything is healthy.

They're evaluated based on **how they behave when things fail**.

Imagine:

- A Location Server crashes.
- Redis becomes unavailable.
- Kafka stops accepting events.
- A database fails.
- An entire cloud region goes offline.

Passengers still expect to book rides.

Drivers still expect navigation.

Payments must still work.

Let's design Uber for failures.

---

# Designing for Failure

A beginner assumes:

```text
Everything Works
```

A production engineer assumes:

```text
Everything Will Eventually Fail
```

Failures include:

- Server crashes
- Network failures
- Disk failures
- Memory corruption
- Power outages
- Cloud outages
- Human mistakes

Instead of preventing failures,

Uber is designed to recover automatically.

---

# Multi Availability Zone Deployment

Every service is deployed across multiple Availability Zones.

```text
                Global Load Balancer

                     /           \

                AZ-A             AZ-B

          Matching Service   Matching Service

          Redis Primary      Redis Replica

          DB Primary         DB Replica
```

If AZ-A fails,

traffic automatically moves to AZ-B.

---

# Why Multi-AZ?

Imagine one data center loses power.

Without redundancy,

Uber would stop working.

With Multi-AZ,

users usually don't notice.

---

# Multi-Region Deployment

Uber operates worldwide.

Instead of one global deployment,

multiple regional clusters exist.

```text
                    Global DNS

          /             |              \

     North America    Europe        Asia-Pacific

           │             │                │

      Uber Cluster  Uber Cluster   Uber Cluster
```

Each region handles nearby users.

Benefits:

- Lower latency
- Regional isolation
- Disaster recovery

# Ride Service Failure

Imagine a ride is already in progress.

The Ride Service crashes.

Can the ride continue?

Yes.

Why?

Because ride state is stored in durable databases.

Another Ride Service instance resumes processing.

# Redis Failure

Redis stores temporary data:

- Driver locations
- Driver availability
- Surge cache
- Session information

Suppose Redis crashes.

```text
Redis Down

↓

Fallback

↓

Database

↓

Restore Cache
```

Performance decreases,

but Uber continues operating.

---

# Redis Replication

Production Redis uses replication.

```text
Redis Primary

↓

Replica A

↓

Replica B
```

If the primary fails,

a replica is promoted.

---

# Database Replication

Ride history is permanent.

Databases use replication.

```text
Primary

↓

Replica 1

Replica 2

Replica 3
```

Writes go to the primary.

Reads are distributed.

---

# Database Failover

Suppose the primary database crashes.

```text
Primary Down

↓

Promote Replica

↓

Reconnect Applications
```

Applications continue automatically.

# Kafka Failure

Suppose Kafka becomes unavailable.

Should passengers stop requesting rides?

No.

Possible strategies:

- Retry publishing
- Local buffering
- Dead Letter Queue
- Event replay

Core ride functionality should continue whenever possible.

# Production Trade-offs

Every decision has advantages and disadvantages.

---

## Redis

Advantages

- Fast lookups
- Excellent for locations

Disadvantages

- Expensive memory
- Cache consistency

---

## Kafka

Advantages

- Event replay
- Loose coupling
- Scalability

Disadvantages

- Operational complexity

---

## WebSockets

Advantages

- Instant communication
- Low latency

Disadvantages

- Persistent connections consume memory

---

## Multi-Region

Advantages

- High availability
- Low latency

Disadvantages

- Data synchronization complexity

---

## Geospatial Index

Advantages

- Fast nearby searches

Disadvantages

- Additional indexing overhead
