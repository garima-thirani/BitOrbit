# Starting with the Simplest Architecture

Imagine there are only ten users.

Our architecture might look like this.

```text
           Client
              │
              ▼
        URL Shortener
              │
              ▼
         Database
```

The application receives a URL,

stores it,

and later retrieves it.

This works perfectly.

But what happens when millions of users begin using the service?

Immediately, new challenges appear.

- One server cannot handle all requests.
- One database becomes overloaded.
- Reads become much more frequent than writes.
- Analytics slow down redirects.

We need a better architecture.

---

# Building the High-Level Architecture

Let's introduce dedicated services.

```text
                        Users
                          │
                          ▼
                    DNS Resolution
                          │
                          ▼
                  Global Load Balancer
                          │
                          ▼
                     API Gateway
                          │
             ┌────────────┴─────────────┐
             ▼                          ▼
      URL Creation Service      Redirect Service
             │                          │
             ▼                          ▼
         Redis Cache              Redis Cache
             │                          │
             └────────────┬─────────────┘
                          ▼
                  Primary Database
                          │
                          ▼
                  Analytics Events
                          │
                          ▼
                         Kafka
                          │
                          ▼
                  Analytics Workers
                          │
                          ▼
                  Analytics Database
```

This architecture separates responsibilities.

Instead of one application doing everything,

multiple services specialize in individual tasks.

---

# Why Separate Services?

Suppose one user creates a shortened URL.

Another million users are simply opening existing links.

Should both operations use the same service?

Not necessarily.

Creating URLs is write-heavy.

Redirecting URLs is read-heavy.

Their scaling requirements are different.

By separating them,

each service can scale independently.

---

# Component 1 — Client

The client can be:

- Browser
- Mobile App
- Backend Service
- QR Scanner

The client performs two actions.

```text
Create URL

or

Open Short URL
```

Everything begins here.

---

# Component 2 — DNS

Before any request reaches our application,

DNS resolves

```text
tiny.ly
```

into an IP address.

The request is then forwarded to the nearest deployment.

This reduces latency for global users.

---

# Component 3 — Global Load Balancer

The Load Balancer distributes traffic across many servers.

```text
          Request

             │

             ▼

     Global Load Balancer

      ┌──────┼──────┐

      ▼      ▼      ▼

   Server1 Server2 Server3
```

Benefits include:

- High Availability
- Horizontal Scaling
- Fault Tolerance

If one server fails,

traffic automatically shifts elsewhere.

---

# Component 4 — API Gateway

The API Gateway acts as the front door.

It performs responsibilities such as:

- Authentication
- Rate Limiting
- Logging
- Routing
- API Versioning

Instead of exposing every internal service,

clients interact only with the gateway.

---

# Component 5 — URL Creation Service

This service handles

```text
POST /shorten
```

Responsibilities include:

- Validate URL
- Generate Short Code
- Store Mapping
- Return Short URL

Notice that this service rarely receives traffic compared to redirects.

Writes are relatively infrequent.

---

# Component 6 — Redirect Service

This service handles

```text
GET /abc123
```

Responsibilities:

- Lookup Short Code
- Find Original URL
- Redirect Browser

Since redirect requests dominate traffic,

this service is optimized for speed.

---

# Why Redis Sits in Front of the Database

Suppose

```text
tiny.ly/chatgpt
```

receives

100 million clicks.

Without caching,

every request hits the database.

```text
User

↓

Database

↓

Response
```

Millions of identical queries waste database resources.

Instead,

Redis stores frequently accessed mappings.

```text
User

↓

Redis

↓

Database (only if necessary)
```

Most redirects become memory lookups,

reducing latency dramatically.

---

# Component 7 — Primary Database

The database stores the permanent mapping.

Example:

| Short Code | Original URL |
|------------|--------------|
| abc123 | https://openai.com |
| xyz987 | https://github.com |

Unlike Redis,

the database provides durable storage.

If Redis is lost,

the mappings still exist.

---

# Component 8 — Kafka

Analytics should never slow user requests.

Imagine updating analytics synchronously.

```text
Redirect

↓

Update Database

↓

Update Analytics

↓

Return Response
```

Every redirect now waits.

Instead,

we publish an event.

```text
Redirect

↓

Kafka

↓

Return Response
```

Analytics processing happens later.

This keeps redirects extremely fast.

---

# Component 9 — Analytics Workers

Worker services continuously consume Kafka events.

Responsibilities include:

- Count Clicks
- Geo Analysis
- Browser Statistics
- Device Analytics
- Daily Reports

Because workers operate asynchronously,

they never delay users.

---

# Component 10 — Analytics Database

Analytics is stored separately.

Why?

Because analytics queries are very different.

Example:

```
How many clicks yesterday?
```

is an analytical query,

not an operational one.

Separating databases improves performance.

---

# Complete Redirect Flow

Suppose a user visits

```
tiny.ly/openai
```

The request travels through the system.

```text
User

↓

DNS

↓

Load Balancer

↓

API Gateway

↓

Redirect Service

↓

Redis

↓

Found?

│

├── Yes

│      ↓

│ Redirect

│

└── No

       ↓

Database

↓

Update Redis

↓

Redirect User
```

Notice that the database is only contacted on cache misses.

---

# Complete URL Creation Flow

Creating a new URL follows a different path.

```text
User

↓

API Gateway

↓

URL Creation Service

↓

Generate Short Code

↓

Store Mapping

↓

Database

↓

Return Short URL
```

This path is write-heavy,

whereas redirects are read-heavy.

Keeping them separate improves scalability.

---

# Database Design

The simplest relational schema looks like this.

| Column | Description |
|----------|-------------|
| id | Primary Key |
| short_code | Generated Code |
| original_url | Long URL |
| created_at | Creation Timestamp |
| expires_at | Optional Expiration |
| created_by | User ID |
| click_count | Optional Cached Counter |

---

# Primary Index

The most important lookup is

```text
short_code

↓

original_url
```

Therefore,

the primary index should be built on

```text
short_code
```

Every redirect depends on this lookup.

---

# SQL or NoSQL?

At this stage,

either approach works.

SQL advantages:

- Simplicity
- Strong Consistency
- ACID Transactions

NoSQL advantages:

- Easier Horizontal Scaling
- Flexible Storage
- Massive Throughput

For moderate workloads,

PostgreSQL is an excellent choice.

For internet-scale deployments,

distributed NoSQL databases may become preferable.

We'll revisit this decision when discussing sharding.

# Design Decisions So Far

Let's summarize the choices we've made.

| Problem | Solution |
|----------|----------|
| High Traffic | Load Balancer |
| Read-heavy Workload | Redis |
| Durable Storage | Database |
| Analytics | Kafka |
| Scalability | Independent Services |
| High Availability | Multiple Instances |

Each technology solves a specific problem.

Nothing has been added unnecessarily.

# Key Takeaways

- High-level architecture begins by separating responsibilities into specialized services.
- URL creation and redirection have very different traffic patterns and should scale independently.
- Redis dramatically reduces redirect latency by serving frequent lookups from memory.
- The primary database provides durable storage for URL mappings.
- Kafka enables asynchronous analytics processing without impacting user-facing latency.
- Load balancers, API gateways, and independent services create a scalable and fault-tolerant architecture.
- Database indexing on the `short_code` column is essential for fast redirects.
- Good architecture introduces components only when they solve a clearly identified problem.
