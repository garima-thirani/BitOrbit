# Introduction

One of the most common questions in System Design interviews is:

> **Design a URL Shortener like Bit.ly or TinyURL.**

At first glance, the problem appears deceptively simple.

> Take a long URL and return a shorter one.

How difficult could that be?

You might think the implementation is as simple as storing a mapping between two strings.

```text
https://www.example.com/products/electronics/mobile/samsung-galaxy-s24-ultra

↓

https://tiny.url/abc123
```

However, once millions of users begin shortening URLs every day, the complexity grows rapidly.

Questions immediately arise.

- How do we generate unique short URLs?
- How do we prevent collisions?
- How do we redirect users in milliseconds?
- How do we handle billions of redirects?
- How do we collect analytics without slowing down users?
- How do we support custom aliases?
- How do we prevent abuse?

A seemingly simple application becomes a distributed system involving databases, caching, load balancing, asynchronous processing, and global deployment.

This is precisely why URL Shortener is considered one of the best introductory System Design problems.

It combines many of the concepts you've learned throughout this handbook into a single, practical design exercise.

---

# Why Do URL Shorteners Exist?

Long URLs are difficult to:

- Remember
- Share
- Type
- Print
- Embed in documents
- Display on social media

For example,

```text
https://www.amazon.com/Samsung-Galaxy-Ultra-Unlocked-512GB/dp/B0CX123456?ref_=nav_signin&tracking_id=abc123xyz456
```

is inconvenient to send in a message.

A URL shortener transforms it into something much simpler.

```text
https://bit.ly/3Ax7P9Q
```

Both URLs point to exactly the same destination.

The short URL simply acts as a redirection layer.

# Understanding the Problem

Before designing anything,

we should understand what actually happens.

Suppose a user enters

```text
https://www.openai.com/research/transformers
```

The system returns

```text
https://tiny.ly/X7fQa
```

Later,

someone visits

```text
https://tiny.ly/X7fQa
```

The browser is redirected to

```text
https://www.openai.com/research/transformers
```

From the user's perspective,

the process appears instantaneous.

Internally,

multiple services may participate in this request.

---

# Functional Requirements

Functional requirements describe **what the system should do.**

For our URL Shortener,

the system should support:

### 1. Shorten URLs

Users can submit a long URL and receive a shorter one.

Example:

```text
Input

https://openai.com/blog/chatgpt

↓

Output

https://tiny.ly/AbC91X
```

---

### 2. Redirect Users

Visiting the shortened URL should immediately redirect users to the original destination.

This is the primary responsibility of the system.

---

### 3. Generate Unique Short Codes

Every shortened URL should be unique.

For example,

```text
tiny.ly/abc123
```

must map to only one destination.

---

### 4. Custom Aliases (Optional)

Users may request

```text
tiny.ly/chatgpt
```

instead of

```text
tiny.ly/X91afB
```

The system should verify that the alias is available.

---

### 5. URL Expiration (Optional)

Some URLs may automatically expire.

Example:

```text
Expires after 30 days
```

After expiration,

redirects should return

```text
404 Not Found
```

or

```text
410 Gone
```

---

### 6. Analytics

The service should collect information such as

- Number of clicks
- Country
- Device
- Browser
- Timestamp
- Referrer

Notice that analytics should **not slow down redirection**.

We'll solve this later using asynchronous processing.

---

# Non-Functional Requirements

Non-functional requirements describe **how well the system should perform.**

---

## Low Latency

Users expect redirection to happen almost instantly.

Target:

```text
< 100 ms
```

---

## High Availability

If the service becomes unavailable,

millions of existing links stop working.

Availability is critical.

Target:

```text
99.99%+
```

---

## High Scalability

The system should continue operating as traffic grows.

Examples:

- Millions of URLs
- Billions of redirects
- Global users

---

## Durability

Once a URL is created,

it should not disappear because of a server crash.

Persistent storage is required.

---

## Reliability

Every redirect should consistently return the correct destination.

Incorrect redirects could damage user trust.

---

# Assumptions

Because interview questions rarely specify everything,

we make reasonable assumptions.

For this design,

assume:

- URLs are immutable after creation.
- Redirects greatly outnumber URL creation.
- Most URLs remain active indefinitely.
- Analytics can be processed asynchronously.
- Global deployment is required.

Clearly stating assumptions demonstrates mature engineering thinking.

---

# Constraints

Every system operates under constraints.

For this design:

- Short URLs should be compact.
- Collisions must be avoided.
- Redirects must remain fast.
- Storage costs should remain reasonable.
- The system should support horizontal scaling.

---

# Capacity Estimation

Before choosing technologies,

estimate the scale.

Assume:

- 100 million Daily Active Users
- Each user shortens 2 URLs/day
- Each URL receives 100 redirects/day

---

## URLs Created Per Day

```text
100 million × 2

=

200 million URLs/day
```

---

## Redirect Requests

```text
200 million × 100

=

20 billion redirects/day
```

---

## Read-to-Write Ratio

```text
Writes

↓

200 million/day
```

```text
Reads

↓

20 billion/day
```

Ratio:

```text
100 : 1
```

This immediately tells us:

> **This is a highly read-heavy system.**

Later,

this insight will justify the use of Redis.

---

## Average QPS

Redirects:

```text
20,000,000,000

÷

86,400

≈

231,000 requests/sec
```

Peak traffic may be three to five times higher.

Design target:

```text
1 Million Requests/sec
```

---

## Storage Estimation

Assume each URL record stores:

- Original URL
- Short Code
- Creation Time
- Expiration
- Metadata

Average:

```text
500 Bytes
```

Daily storage:

```text
200 Million × 500 Bytes

≈

100 GB/day
```

Yearly storage:

```text
≈ 36 TB/year
```

This is manageable using distributed databases.

# API Design

A clean API makes the system easy to use.

---

## Create Short URL

```http
POST /api/v1/shorten
```

Request

```json
{
  "url": "https://openai.com/blog/chatgpt"
}
```

Response

```json
{
  "shortUrl": "https://tiny.ly/AbC91X"
}
```

---

## Redirect

```http
GET /AbC91X
```

Response

```http
301 Moved Permanently
Location: https://openai.com/blog/chatgpt
```

The browser automatically follows the redirect.

---

## Analytics

```http
GET /api/v1/analytics/AbC91X
```

Response

```json
{
  "clicks": 1254321,
  "countries": {
    "US": 54,
    "IN": 23,
    "UK": 12
  }
}
```

---

## Delete URL (Optional)

```http
DELETE /api/v1/shorten/AbC91X
```

Useful for expired or malicious links.

# Key Takeaways

- A URL Shortener converts long URLs into compact, shareable links.
- The system is read-heavy, with redirect requests greatly outnumbering URL creation.
- Functional requirements include URL shortening, redirection, analytics, and optional features such as custom aliases and expiration.
- Non-functional requirements emphasize low latency, scalability, availability, durability, and reliability.
- Capacity estimation guides architectural decisions and reveals where bottlenecks are likely to occur.
- A clean API should support URL creation, redirection, analytics, and optional management operations.
- The next step is to transform these requirements into a production-ready architecture.
