# The Real Problem

Suppose the document contains:

```text
Hello World
```

Alice and Bob both open it.

Now:

Alice inserts

```text
Beautiful
```

after "Hello".

At exactly the same time,

Bob deletes

```text
World
```

Both operations are correct.

Question:

**What should the final document be?**

---

# Simultaneous Editing

Initially

```text
Hello World
```

Alice:

```text
Hello Beautiful World
```

Bob:

```text
Hello
```

Which version wins?

If the system simply saves the latest request,

one user's work disappears.

That is unacceptable.

---

# Why Last Write Wins Doesn't Work

Traditional databases often use:

```text
Latest Timestamp

↓

Overwrite Previous Value
```

Example:

Alice:

```text
Hello Beautiful World
```

Bob:

```text
Hello
```

If Bob's request arrives last,

Alice's edit disappears forever.

Google Docs cannot behave like this.

---

# Goal of Collaborative Editing

The system should guarantee:

```text
No Edit Lost

↓

Eventually

↓

Everyone Sees

↓

Exactly Same Document
```

This property is called

**Convergence.**


# Operations Instead of Documents

Google Docs doesn't send the whole document.

Instead,

it sends operations.

Example:

Instead of

```text

```

```text

Position 6

Text = Beautiful
```

Much smaller.

Much faster.

# What Happens Now?

Suppose both operations reach the server.

```text
Insert

↓

Delete
```

Should the server execute:

Insert first?

Delete first?

Different orders produce different documents.

This is the core challenge.

---

# Operational Transform (OT)

Operational Transform is the algorithm Google Docs became famous for.

Core idea:

> **Transform one operation so it can be applied after another operation without changing user intent.**

Instead of rejecting edits,

OT rewrites them.

---

# Simple OT Example

Document:

```text
Hello World
```

Alice:

```text
Insert

Beautiful

Position 6
```

Bob:

```text
Delete

World

Position 6
```

If Bob's delete executes first,

Alice's insert position changes.

OT transforms Alice's operation

to the new position.

Both edits survive.

---

# OT Visualization

```text

Insert

↓

Transform

↓

Apply

↓

Final Document
```

```text
Bob

Delete

↓

Transform

↓

Apply

↓

Same Final Document
```

Every operation may be transformed before execution.

---

# Another Example

Original

```text
ABCDE
```

Alice inserts:

```text
X

after B
```

Bob deletes:

```text
C
```

Without transformation:

Different users obtain different documents.

With OT:

Both users eventually converge.

---

# How OT Works

Very simplified flow:

```text
Receive Operation

↓

Check Previous Operations

↓

Transform Position

↓

Apply

↓

Broadcast
```

The server continuously adjusts operations.

---

# Properties of OT

Operational Transform guarantees:

- No edits lost
- Intent preservation
- Convergence
- Real-time editing

These properties made Google Docs possible.

---

# Limitation of OT

OT is powerful,

but implementation is difficult.

Challenges include:

- Complex transformation rules
- Operation ordering
- Server coordination
- History management

Building OT correctly is extremely hard.

---

# Conflict-Free Replicated Data Types (CRDT)

A newer alternative is

CRDT.

Instead of transforming operations,

every character receives a unique identity.

---

# CRDT Idea

Instead of storing

```text
Hello
```

store

```text
H1

e2

l3

l4

o5
```

Each character has a permanent ID.

Edits manipulate IDs,

not positions.

---

# Why IDs?

Suppose Alice inserts:

```text
X
```

between

```
e2

l3
```

The new character becomes:

```text
X2.5
```

Other users can independently insert characters

without conflicts.

---

# CRDT Example

Original

```text
A B C
```

Alice inserts

```text
X
```

Bob inserts

```text
Y
```

Both operations eventually merge.

Possible result:

```text
A X Y B C
```

No central transformation required.

---

# OT vs CRDT

| OT | CRDT |
|----|------|
| Transform operations | Merge replicas |
| Central coordination | Decentralized |
| Smaller metadata | Larger metadata |
| More mature | Better offline support |
| Used historically by Google Docs | Used by Figma, Automerge, Yjs and others |

Modern collaborative editors increasingly adopt CRDTs,

especially for offline-first applications.

# Network Partition

Imagine:

Alice loses internet.

Bob continues editing.

Twenty minutes later,

Alice reconnects.

Now:

- Bob has Version 50.
- Alice has Version 30.

The system transforms Alice's queued edits

relative to the newer version.

Eventually,

everyone reaches the same document.

# Interview Tips

Interviewers frequently ask:

> **"How does Google Docs allow multiple people to edit the same document without conflicts?"**

A strong answer is:

> "Clients send editing operations—not entire documents—over WebSockets. The Collaboration Service orders these operations and uses Operational Transform (OT) to rewrite concurrent operations so user intent is preserved. The transformed operations are then broadcast to all connected clients, ensuring eventual convergence. Modern collaborative editors may also use CRDTs, which achieve convergence through replicated data structures instead of operation transformation."

This demonstrates an understanding of the core algorithms behind collaborative editing.

# Key Takeaways

- Google Docs sends operations instead of entire documents, reducing bandwidth and latency.
- Operational Transform (OT) preserves user intent and enables concurrent editing without losing changes.
- CRDTs provide an alternative approach based on replicated data structures and are popular in newer collaborative editors.
- Cursor positions, selections, and presence are synchronized independently from document content.
- Offline editing queues operations locally and synchronizes them after reconnection.
- Version numbers help order operations and support conflict resolution.
- Real-time collaboration depends on OT/CRDT, WebSockets, session management, and efficient operation broadcasting working together.
