# Interview Walkthrough

Suppose the interviewer asks

> Design Bit.ly.

A structured answer could begin like this.

---

## Step 1 — Clarify Requirements

"I'd first like to clarify the requirements."

Questions include:

- Should users create custom aliases?
- Should URLs expire?
- Do we need analytics?
- How many users are expected?
- Is the system global?
- Should links be private?

Never assume requirements.

---

## Step 2 — Estimate Scale

Example assumptions.

```
100 Million DAU

↓

200 Million URLs/day

↓

20 Billion Redirects/day

↓

1 Million Peak QPS
```

Immediately recognize:

```
Read Heavy System
```

This naturally motivates caching.

---

## Step 3 — Design APIs

```http
POST /shorten
```

```http
GET /{shortCode}
```

```http
GET /analytics/{shortCode}
```

Simple,

RESTful,

and easy to understand.

---

## Step 4 — Draw High-Level Architecture

Start with only the major components.

```text
Users

↓

Load Balancer

↓

API Gateway

↓

Services

↓

Redis

↓

Database
```

Avoid drawing dozens of boxes immediately.

Build the architecture incrementally.

---

## Step 5 — Explain the Database

Store

```
Short Code

↓

Original URL
```

Index on

```
short_code
```

Explain why.

---

## Step 6 — Introduce Redis

Explain

why

Redis exists.

Not

because

"everyone uses Redis."

Instead say

> Redirect requests are much more frequent than URL creation, making this a read-heavy workload. Redis allows frequently accessed mappings to be served directly from memory, reducing database load and latency.

This demonstrates engineering reasoning.

---

## Step 7 — Explain ID Generation

Discuss alternatives.

- Random IDs
- UUID
- Auto Increment
- Snowflake

Explain why you selected

Base62 encoding.

Interviewers appreciate understanding trade-offs.

---

## Step 8 — Analytics

Mention

Kafka.

Explain that

analytics should never slow user requests.

Use asynchronous processing.

---

## Step 9 — Production Readiness

Finally discuss

- Monitoring
- Logging
- Rate Limiting
- Multi-AZ
- Disaster Recovery
- Security

This is often what separates senior-level candidates.

# Common Interview Follow-Up Questions

Let's answer the questions interviewers frequently ask.

---

## Why not use UUID?

UUIDs are:

- Long
- Difficult to remember
- Increase URL length

The goal is to shorten URLs,

not increase them.

---

## Why Redis?

Because

```
Reads

>>

Writes
```

Most requests are redirects.

Memory lookups are much faster than database queries.

---

## Why Kafka?

Analytics should not delay redirects.

Kafka allows event processing asynchronously.

---

## Why Base62?

It produces

- Compact URLs
- URL-safe characters
- Efficient encoding

Example

```
1000000

↓

4C92
```

instead of

```
1000000
```

---

## Why Separate Analytics Database?

Operational queries

```
Lookup URL
```

and

analytical queries

```
Clicks by Country
```

have completely different workloads.

Separate databases prevent resource contention.

---

## How Would You Support Custom URLs?

Before creating

```
tiny.ly/openai
```

check

```
Does "openai" already exist?
```

If yes,

return an error.

Otherwise,

store the mapping.

---

## How Would You Support Expiring URLs?

Store

```
expires_at
```

During redirect,

verify

```
Current Time

<

Expiration Time
```

Otherwise,

return

```
410 Gone
```

---

## How Would You Delete Malicious URLs?

Delete mapping.

Invalidate Redis cache.

Update blacklist.

Reject future creations.

---

## How Would You Scale to Billions of URLs?

Introduce

- Database Sharding
- Read Replicas
- Redis Cluster
- Distributed ID Generator
- Multi-Region Deployment

Each solves a specific bottleneck.

# Common Mistakes

Many candidates lose marks because of these mistakes.

---

## Mistake 1

Jumping into technology choices.

Instead,

start with requirements.

---

## Mistake 2

Skipping capacity estimation.

Without understanding traffic,

it's impossible to justify architecture.

---

## Mistake 3

Using every technology.

Not every application needs

Kafka,

Redis,

Kubernetes,

and Elasticsearch.

Use only what solves a real problem.

---

## Mistake 4

Ignoring failures.

Always discuss

- Redis failures
- Database failures
- Region failures

---

## Mistake 5

Ignoring trade-offs.

Interviewers often care more about

why

than

what.

# Staff Engineer Discussion

A Staff Engineer thinks differently.

Instead of asking

> How do I build this?

they ask

> How will this behave when traffic grows by 100×?

Questions include:

- Where are the bottlenecks?
- Which component fails first?
- Can we scale horizontally?
- What happens during outages?
- What metrics should we monitor?
- What operational burden does this introduce?

This mindset distinguishes senior engineers.

# Key Takeaways

- A successful System Design interview is driven by structured thinking rather than memorized architectures.
- Begin with requirements and capacity estimation before discussing technologies.
- Explain the reasoning behind every architectural decision.
- Redis is introduced because the workload is read-heavy, not because it is popular.
- Kafka enables asynchronous analytics processing without increasing redirect latency.
- Production systems require monitoring, logging, security, and disaster recovery in addition to core functionality.
- Interviewers value trade-off analysis and clear communication more than a single "correct" solution.
- The URL Shortener case study demonstrates how databases, caching, messaging, cloud infrastructure, and observability work together to build a scalable distributed system.
