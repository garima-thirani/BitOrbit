# Naive Solution

Imagine every driver's location is stored in a SQL table.

```text
Drivers

ID

Latitude

Longitude
```

When Alice requests a ride,

the query becomes

```sql
SELECT *

FROM Drivers

WHERE Available = TRUE;
```

Then compute distance to every driver.

Problems:

- Millions of rows
- Millions of distance calculations
- Very slow

Clearly,

this doesn't scale.

---

# Why Traditional Databases Are Poor at Location Search

Suppose Uber has

```
10 Million Drivers
```

Alice requests a ride.

Searching every driver means

```text
10 Million Distance Calculations
```

for every ride request.

Suppose

```
20 Million Ride Requests/day
```

This becomes computationally impossible.

---

# The Real Problem

Uber doesn't need

every driver.

It only needs

drivers nearby.

Instead of searching the world,

search a tiny geographic region.

This idea leads to

**Geospatial Indexing**.

---

# What is Geospatial Indexing?

Geospatial indexing organizes locations so nearby places are stored together.

Instead of

```text
Search Entire World
```

we search

```text
Small Geographic Area
```

This reduces millions of candidates to perhaps

```
20 Drivers
```

---

# Real-Life Analogy

Imagine finding a restaurant in New York.

Would you search every restaurant on Earth?

No.

You first identify

```
New York

↓

Manhattan

↓

Times Square
```

Then search nearby restaurants.

Geospatial indexing works exactly like this.

# Why Redis?

Driver locations change constantly.

Updating SQL millions of times per second is expensive.

Redis provides:

- In-memory speed
- Fast writes
- Geo indexing support

Perfect for live locations.

---

# Redis GEO

Redis provides built-in commands.

Example:

```text
GEOADD

Driver

Latitude

Longitude
```

Later,

find nearby drivers.

```text
GEOSEARCH

Radius

5 km
```

Results appear almost instantly.

# Geohash

One popular indexing technique is

Geohash.

Instead of storing

```text
40.758896

-73.985130
```

convert coordinates into

```text

```

Nearby locations have similar prefixes.

# H3 Index

Modern mapping systems often use

Uber's own

**H3**.

Instead of squares,

H3 divides Earth into

hexagons.

```text
⬡ ⬡ ⬡

⬡ ⬡ ⬡

⬡ ⬡ ⬡
```

Why hexagons?

- Equal distance to neighbors
- Better coverage
- Fewer edge cases

Uber open-sourced H3,

and it's now widely used.

---

# Why H3 is Better Than Squares

Squares have awkward diagonal neighbors.

```text
□ □

□ □
```

Hexagons connect naturally.

```text
⬡ ⬡

⬡ ⬡
```

This produces more consistent proximity searches.

# Interview Tips

Interviewers often ask:

> **"How does Uber find nearby drivers so quickly?"**

A strong answer is:

> "Scanning every driver in a database would be far too slow. Instead, Uber stores driver locations in a geospatial index such as H3 or Geohash. When a rider requests a trip, the Matching Service searches only nearby geographic cells, filters available drivers, calculates ETA, ranks candidates, and sends the request to the best driver."

This demonstrates understanding of both algorithms and distributed systems.

# Key Takeaways

- Traditional SQL databases are inefficient for large-scale location searches.
- Geospatial indexing reduces the search space from millions of drivers to a small local set.
- Redis GEO, Geohash, Quadtrees, and H3 enable millisecond location queries.
- Uber's H3 hexagonal indexing provides efficient geographic partitioning.
- Driver matching considers availability, ETA, ratings, and other factors—not just distance.
- Separating Location, Matching, Ride, and ETA services enables independent scaling.
- Regional clustering keeps location searches local and reduces latency.
- The next step is designing real-time ride assignment, live tracking, and surge pricing.
