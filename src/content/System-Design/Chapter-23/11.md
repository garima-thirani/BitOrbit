# Designing for Failure

A common mistake made by beginners is assuming:

```text
Everything Works

Forever
```

Real systems assume exactly the opposite.

```text
Everything Will Eventually Fail
```

Examples include:

- Hardware failures
- Network failures
- Software bugs
- Human mistakes
- Cloud outages

Instead of preventing failures,

engineers build systems that survive them.

---

# Multi Availability Zone Deployment

Never deploy every service into one Availability Zone.

Instead,

spread services across multiple zones.

```text
                     Global Load Balancer

                     /              \

               Availability      Availability

                 Zone A            Zone B

             Feed Service      Feed Service

             Redis Replica     Redis Replica

            Database Primary Database Replica
```

If Zone A becomes unavailable,

traffic automatically shifts to Zone B.

---

# Why Multi-AZ?

Suppose a power outage affects one data center.

Without Multi-AZ,

Instagram becomes unavailable.

With Multi-AZ,

users barely notice.

High availability is achieved through redundancy.

---

# Multi-Region Deployment

Instagram serves users worldwide.

Instead of deploying everything in one country,

multiple regional deployments exist.

```text
               Global DNS

        ┌────────┼────────┐

        ▼        ▼        ▼

      US-East Europe Asia-Pacific

        │        │        │

   Regional Regional Regional

   Cluster   Cluster  Cluster
```

Users connect to the nearest healthy region.

Benefits include:

- Lower latency
- Better availability
- Disaster recovery

---

# CDN for Global Users

Suppose a user in Japan views a photo uploaded in California.

Without a CDN,

every request travels across the Pacific Ocean.

Instead,

the image is cached near the user.

```text
User

↓

Tokyo CDN

↓

Image Returned
```

Only cache misses reach object storage.

---

# Redis Failure

Redis is a cache.

Caches are disposable.

Suppose Redis crashes.

```text
Feed Request

↓

Redis

↓

Unavailable

↓

Database

↓

Rebuild Cache

↓

Continue
```

The application becomes slower,

but it continues working.

---

# Database Failure

Databases store permanent data.

Failure handling is more important.

```text
Primary Database

↓

Failure

↓

Replica Promotion

↓

New Primary
```

Applications reconnect automatically.

Users experience minimal disruption.

---

# Kafka Failure

Suppose Kafka becomes temporarily unavailable.

Should uploads stop?

No.

The upload should succeed.

Possible strategies:

- Retry publishing
- Local buffering
- Dead Letter Queue (DLQ)
- Event replay

The user experience remains unaffected whenever possible.

---

# Object Storage Failure

Images are stored redundantly.

Cloud providers replicate objects automatically.

Example:

```text
Image

↓

Availability Zone A

↓

Availability Zone B

↓

Availability Zone C
```

Even if one storage node fails,

images remain accessible.

---

# Database Sharding

As Instagram grows,

one database becomes insufficient.

Instead,

users are partitioned.

```text
User IDs

0–100M

↓

Shard 1

-----------------

100M–200M

↓

Shard 2

-----------------

200M+

↓

Shard 3
```

Each shard manages a subset of users.

---

# Read Replicas

Instagram performs many reads.

Instead of overloading one database,

multiple replicas serve read traffic.

```text
Primary

↓

Replication

↓

Replica 1

Replica 2

Replica 3
```

Writes go to the primary.

Reads are distributed.

---

# Horizontal Scaling

Every stateless service scales horizontally.

Example:

```text
Load Balancer

↓

Feed Service 1

Feed Service 2

Feed Service 3

Feed Service 4
```

As traffic grows,

new servers are added.

No application changes are required.

---

# Autoscaling

Traffic varies throughout the day.

Instead of running 500 servers constantly,

Instagram automatically adjusts capacity.

```text
Morning

↓

100 Pods

--------------

Afternoon

↓

300 Pods

--------------

Evening Peak

↓

1000 Pods
```

Kubernetes Horizontal Pod Autoscaler (HPA)

makes this possible.

# Trade-offs

Every architectural decision involves trade-offs.

---

## Redis

Advantages

- Low latency
- High throughput

Disadvantages

- Memory cost
- Cache invalidation

---

## Kafka

Advantages

- Loose coupling
- Scalability
- Event replay

Disadvantages

- Operational complexity

---

## Fan-out on Write

Advantages

- Fast feed loading

Disadvantages

- Expensive writes

---

## Fan-out on Read

Advantages

- Efficient writes

Disadvantages

- Slower feed generation

---

## Object Storage

Advantages

- Cheap
- Durable
- Massive scale

Disadvantages

- Higher latency than local storage

# Key Takeaways

- Production systems are designed assuming failures will happen.
- Multi-AZ and Multi-Region deployments improve availability and reduce latency.
- Redis failures should degrade performance, not break functionality.
- Kafka enables reliable asynchronous communication between services.
- Horizontal scaling and autoscaling allow Instagram to handle traffic spikes.
- Monitoring, logging, tracing, and alerting are essential for operating large-scale systems.
- Cost optimization is an important architectural concern alongside scalability and reliability.
- Instagram's architecture combines distributed systems, caching, messaging, cloud infrastructure, AI, and observability into a unified production platform.
