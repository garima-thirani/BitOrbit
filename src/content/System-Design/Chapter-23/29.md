# Introduction

Imagine Alice creates a Google Doc.

She shares it with:

- Bob
- Charlie
- David

Now all four users begin editing **the same document simultaneously**.

Alice types:

```
Hello
```

At the exact same moment,

Bob deletes a word,

Charlie changes the title,

David inserts a new paragraph.

Within milliseconds,

everyone sees **exactly the same document**.

No data is lost.

No refresh is required.

No merge conflicts appear.

This seemingly simple experience is one of the most sophisticated distributed systems ever built.

# Understanding the Problem

Suppose Alice opens a document.

```text
Document

↓

Share with Bob

↓

Both Start Editing

↓

Characters Appear Instantly

↓

Everyone Sees Same Document
```

Simple?

Not really.

Now imagine:

Alice inserts text at position 20.

Bob deletes text at position 18.

Charlie inserts an image.

David pastes three paragraphs.

All of these operations happen simultaneously.

The system must ensure:

- Everyone eventually sees the same document.
- No edits disappear.
- Order remains consistent.
- Editing remains smooth.

---

# Why Google Docs is Hard

Traditional applications follow this pattern:

```text
User

↓

Edit

↓

Save

↓

Database
```

Only one user edits at a time.

Google Docs supports:

```text
User A

↓

User B

↓

User C

↓

User D

↓

Same Document

↓

Same Time
```

Now concurrency becomes the biggest challenge.

# Functional Requirements

## Document Management

Users should be able to:

- Create documents
- Rename documents
- Delete documents
- Organize documents into folders

---

## Editing

Users should be able to:

- Insert text
- Delete text
- Replace text
- Format text
- Insert tables
- Insert images
- Undo
- Redo

---

## Collaboration

Multiple users should:

- Edit simultaneously
- View each other's edits
- See live cursors
- See selections
- See online status

---

## Sharing

Support permissions such as:

- Owner
- Editor
- Commenter
- Viewer

Users can invite others via email or shareable links.

---

## Comments & Suggestions

Users should be able to:

- Add comments
- Reply
- Resolve comments
- Suggest edits
- Accept or reject suggestions

---

## Version History

The system should support:

- Revision history
- Named versions
- Restore previous versions
- Audit changes

---

## Offline Editing

Users should continue editing even when disconnected.

Changes should synchronize automatically after reconnection.

---

# Non-Functional Requirements

---

## Low Latency

Character updates should appear almost instantly.

Target:

```text
<100 ms
```

Anything above a few hundred milliseconds becomes noticeable.

---

## High Availability

Target:

```text
99.99%
```

Documents should always remain accessible.

---

## Strong Consistency (Eventually)

Every user should eventually see the exact same document.

Temporary differences are acceptable,

permanent differences are not.

---

## Scalability

Support:

- Hundreds of millions of users
- Millions of concurrent editing sessions
- Billions of documents

---

## Durability

Documents must never be lost.

Every edit must eventually be persisted.

# Capacity Estimation

---

## Concurrent Editing Sessions

Suppose:

```text
50 Million

Concurrent Editors
```

Average collaborators:

```text
4 Users

Per Document
```

Active collaborative documents:

```text
50 Million

÷

4

≈ 12.5 Million Documents
```

---

## Editing Operations

Suppose one user types

```
2 Characters/sec
```

Total operations:

```text
50 Million

×

2

=

100 Million Operations/sec
```

These operations must be synchronized globally.

---

## Storage

Suppose:

```
5 Billion Documents
```

Average size:

```
150 KB
```

Storage:

```text
≈ 750 TB
```

Version history significantly increases storage requirements.

- Capacity planning reveals the massive scale of collaborative editing operations.
