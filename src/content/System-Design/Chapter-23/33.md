# Designing for Failure

A common beginner assumption is:

```text
Server

↓

Works Forever
```

Production systems assume the opposite.

```text
Everything
Eventually
Fails
```

Possible failures include:

- WebSocket server crashes
- Database failures
- Redis failures
- Network partitions
- Region outages
- Software bugs
- Power failures

The architecture must survive all of them.

# Multi-Region Deployment

Google Docs serves users worldwide.

```text
North America

↓

Europe

↓

Asia

↓

Australia
```

Each region hosts a complete collaboration stack.

Benefits:

- Lower latency
- Higher availability
- Regional fault isolation

---

# Why Multiple Regions?

Imagine a user in Tokyo.

Should every keystroke travel to California?

```text
Tokyo

↓

California

↓

Tokyo
```

Round-trip latency becomes too high.

Instead,

the user connects to the nearest region.

```text
Tokyo

↓

Tokyo Region
```

Editing feels much more responsive.

---

# Global Traffic Routing

Users first connect to a Global Load Balancer.

```text
User

↓

Global DNS

↓

Nearest Healthy Region
```

Routing decisions are based on:

- Geographic proximity
- Region health
- Current load

# Sticky Sessions

Suppose Alice edits

```
Document A
```

Every operation should reach the same Collaboration Service.

Routing strategy:

```text
Document ID

↓

Hash

↓

Server 12
```

All collaborators editing the same document connect to Server 12.

Benefits:

- Less synchronization
- Lower latency
- Simpler session management

---

# Document Sharding

Millions of active documents cannot be managed by one server.

Instead,

documents are partitioned.

```text
Documents

↓

Shard 1

↓

Shard 2

↓

Shard 3

↓

Shard 4
```

Each shard manages a subset of documents.

---

# Example

```text
Document IDs

1–1,000,000

↓

Shard A

------------------

1,000,001–2,000,000

↓

Shard B
```

Sharding allows independent scaling.

# Collaboration Server Failure

Suppose the server hosting a document crashes.

Recovery process:

```text
New Server

↓

Load Snapshot

↓

Replay Kafka Events

↓

Restore Session

↓

Reconnect Users
```

Users experience only a brief interruption.

---

# Redis Failure

Redis stores:

- Active sessions
- Presence
- Cursor positions

If Redis fails:

```text
Redis Replica

↓

Promoted

↓

Primary
```

Automatic failover minimizes downtime.

---

# Metadata Database Replication

Metadata includes:

- Owner
- Title
- Permissions
- Current Version

Replication strategy:

```text
Primary

↓

Replica 1

↓

Replica 2
```

Reads scale across replicas.

Writes go to the primary.

---

# Kafka Replication

Kafka stores document operations.

```text
Partition

↓

Leader

↓

Follower

↓

Follower
```

If the leader fails,

a follower becomes the new leader.

No edits are lost.

---

# Storage Replication

Document snapshots are replicated across zones.

```text
Snapshot

↓

Zone A

↓

Zone B

↓

Zone C
```

Durability remains extremely high.

# Cost Optimization

Google Docs reduces costs by:

- Compressing operations
- Delta storage
- Periodic snapshots
- Horizontal autoscaling

- Efficient Redis caching

# Trade-offs

## Delta Storage

Advantages:

- Small writes
- Efficient version history

Disadvantages:

- Slower reconstruction

---

## Snapshots

Advantages:

- Fast recovery

Disadvantages:

- Additional storage

---

## WebSockets

Advantages:

- Low latency
- Full duplex communication

Disadvantages:

- Millions of persistent connections

---

## Sticky Sessions

Advantages:

- Simple synchronization
- Low latency

Disadvantages:

- Session migration during failures

---

## Multi-Region

Advantages:

- Disaster recovery
- Lower latency

Disadvantages:

- Cross-region synchronization complexity

# Interview Tips

Interviewers often ask:

> **"How would you make Google Docs highly available?"**

A strong answer is:

> "I would deploy the collaboration stack across multiple Availability Zones and Regions. WebSocket Gateways and Collaboration Services would scale horizontally behind load balancers. Active document sessions would use sticky routing, Redis would replicate presence data, Kafka would durably replicate editing operations, and periodic snapshots would enable rapid recovery. If a region failed, Global DNS would redirect users to another healthy region."

This demonstrates understanding of both distributed systems and operational reliability.

- Production systems are designed with the assumption that failures are inevitable.
- Multi-region deployments reduce latency and provide disaster recovery.

- Redis, Kafka, and replicated storage provide resilience and durability.
- Monitoring, logging, and distributed tracing are essential for operating collaborative systems at scale.
