# Introduction

In Part 3A, we identified the requirements for WhatsApp.

Now let's answer the next question.

> **How does a message actually travel from Alice's phone to Bob's phone?**

Suppose Alice sends

```
Hello Bob 👋
```

From Alice's perspective,

the message appears on Bob's phone almost instantly.

But internally,

the message travels through multiple distributed services.

Understanding this journey is the key to understanding WhatsApp.

---

# The Simplest Architecture

Imagine building WhatsApp for just two users.

```text
Alice

↓

Server

↓

Bob
```

The server simply forwards messages.

This works perfectly.

Until...

- Thousands of users join.
- Millions of users join.
- Hundreds of millions stay online simultaneously.

A single server quickly becomes impossible.

---

# Why HTTP Doesn't Work

Most websites use HTTP.

Example:

```text
Browser

↓

HTTP Request

↓

Server

↓

HTTP Response

↓

Connection Closed
```

Every request opens a new connection.

Suppose Alice sends 100 messages.

That would require:

- 100 TCP connections
- 100 TLS handshakes
- 100 HTTP requests

This is extremely inefficient.

---

# Persistent Connections

Instead,

WhatsApp opens one connection.

```text
Alice

──────────── Connected ────────────

↓

WhatsApp

↑

──────────── Connected ────────────

Bob
```

The connection stays open for hours.

Messages travel instantly.

---

# Real-Life Analogy

Think about making a phone call.

After dialing,

both people remain connected.

Nobody hangs up after every sentence.

WebSockets work exactly the same way.

---

# What is WebSocket?

A WebSocket is a persistent,

full-duplex communication channel.

Full-duplex means

both sides can send data at any time.

```text
Alice

⇄

WhatsApp Server

⇄

Bob
```

Unlike HTTP,

the server can also push data to clients.

---

# HTTP vs WebSocket

| HTTP | WebSocket |
|-------|-----------|
| Request-Response | Persistent Connection |
| Stateless | Stateful |
| Connection closes | Connection stays open |
| Server cannot push | Server pushes instantly |
| Higher overhead | Very low overhead |

Messaging applications almost always prefer WebSockets.

# High-Level Architecture

A production WhatsApp architecture looks like this.

```text
                        Users
                           │
                           ▼
                          DNS
                           │
                           ▼
                  Global Load Balancer
                           │
                           ▼
                  Connection Servers
                           │
        ┌──────────────────┼──────────────────┐
        ▼                  ▼                  ▼
 Presence Service   Message Service    Notification Service
        │                  │                  │
        ▼                  ▼                  ▼
      Redis          Message Queue         Push Service
        │                  │
        └──────────────┬───┘
                       ▼
                 Chat Database
```

Every component has one responsibility.

---

# Component 1 — Connection Servers

Connection Servers maintain WebSocket connections.

Imagine

500 million users online.

Each user has an open socket.

The Connection Server keeps track of:

- User ID
- Connection ID
- Device
- Session

It does **not** permanently store messages.

---

# Why Separate Connection Servers?

Suppose Alice disconnects.

Only the Connection Server should notice.

The Message Service should not care.

Separating responsibilities keeps the architecture modular.

---

# Component 2 — Presence Service

Presence answers questions like:

```
Is Bob Online?
```

```
When was Bob last seen?
```

```
Is Alice typing?
```

These values change frequently.

Redis is ideal for storing them.

---

# Presence Example

Bob connects.

Redis stores:

```text
Bob

↓

Server-14

↓

Online

↓

Last Seen

10:42 AM
```

Now any server can locate Bob instantly.

---

# Component 3 — Message Service

The Message Service performs:

- Validate message
- Store message
- Find recipient
- Deliver message

It does **not** maintain network connections.

Instead,

it asks the Presence Service

where the recipient is connected.

---

# Component 4 — Redis

Redis stores temporary information.

Examples:

- Online users
- Session mapping
- Typing status
- Last Seen
- Connection lookup

Redis provides extremely fast lookups.

---

# Component 5 — Chat Database

The database stores:

- Conversations
- Messages
- Delivery status
- Attachments metadata

Unlike Redis,

this data must survive crashes.

---

# Complete Message Flow

Let's follow Alice sending

```
Hello Bob
```

```text
Alice

↓

WebSocket

↓

Connection Server

↓

Message Service

↓

Store Message

↓

Find Bob

↓

Bob's Connection Server

↓

Bob
```

Notice something important.

The message never travels directly from Alice to Bob.

Everything passes through WhatsApp's infrastructure.

---

# How Does the Server Find Bob?

Suppose Bob is connected.

Where?

Server 3?

Server 17?

Server 54?

Redis maintains the mapping.

```text
Bob

↓

Server-17
```

Now the Message Service knows exactly where to deliver.

---

# Connection Mapping

Example:

| User | Server |
|-------|---------|
| Alice | Server 4 |
| Bob | Server 17 |
| Charlie | Server 8 |

Redis acts as a giant phone directory.

---

# Message Routing

The routing process becomes

```text
Message

↓

Recipient ID

↓

Redis Lookup

↓

Connection Server

↓

Recipient
```

This lookup happens in milliseconds.

---

# What if Bob is Offline?

Suppose Bob disconnected.

Redis returns

```
Offline
```

Instead of failing,

the Message Service stores the message.

```text
Alice

↓

Database

↓

Pending Messages

↓

Bob Reconnects

↓

Deliver
```

This guarantees reliable delivery.

---

# Session Management

Suppose Bob opens WhatsApp.

The Connection Server registers him.

```text
Bob

↓

Server 17

↓

Redis

↓

Online
```

When Bob disconnects,

the entry updates.

```text
Bob

↓

Offline

↓

Last Seen

11:12 AM
```

---

# Why Redis?

Presence information changes constantly.

Imagine

500 million users.

Every few seconds,

someone connects or disconnects.

Databases would become overloaded.

Redis handles these updates efficiently.

---

# Horizontal Scaling

Initially,

one Connection Server is enough.

```text
Users

↓

Connection Server
```

Eventually,

traffic grows.

```text
Load Balancer

↓

Server 1

Server 2

Server 3

Server 4
```

Each server maintains only a subset of users.

---

# Scaling WebSocket Connections

Suppose one server supports

```
100,000 Connections
```

Need

```
500 Million
```

connections?

Simply add more servers.

```text
500 Million

÷

100,000

=

5,000 Connection Servers
```

Horizontal scaling makes this possible.

---

# Why Separate Message Service?

Imagine Connection Servers also handled databases,

notifications,

media,

and encryption.

They would become overloaded.

Instead,

Connection Servers simply:

- Maintain sockets
- Send packets
- Receive packets

Everything else belongs elsewhere.

---

# Real-Life Example

Think about an airport.

Passengers arrive.

The airport doesn't fly every plane itself.

Instead,

it directs passengers to the correct gate.

Connection Servers behave similarly.

They don't process business logic.

They simply ensure messages reach the correct destination.

# Design Decisions So Far

| Problem | Solution |
|----------|----------|
| Persistent Communication | WebSockets |
| Millions of Users | Connection Servers |
| Online Status | Redis |
| Message Storage | Chat Database |
| Routing | Presence Service |
| Horizontal Scaling | Load Balancer |

Every component exists because it solves one specific problem.

# Key Takeaways

- WhatsApp relies on **persistent WebSocket connections** rather than repeated HTTP requests.
- Connection Servers maintain millions of active client connections.
- Redis stores rapidly changing presence information, enabling instant user lookups.
- The Message Service routes messages independently of network connections.
- Chat databases provide durable message storage, while Redis stores temporary session state.
- Separating Connection Servers, Presence Services, and Message Services allows each component to scale independently.
- Horizontal scaling enables WhatsApp to support hundreds of millions of simultaneous users by distributing connections across many servers.
- The next step is designing reliable message delivery, acknowledgements, offline messaging, and group communication.
