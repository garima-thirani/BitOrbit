# High-Level Architecture

A production Google Docs architecture looks like this.

```text
                          Users
                             │
                             ▼
                      Global Load Balancer
                             │
                             ▼
                      WebSocket Gateway
                             │
        ┌─────────────┬──────────────┬─────────────┐
        ▼             ▼              ▼
 Collaboration   Presence Service  Document Service
    Service            │                │
        │              ▼                ▼
        │            Redis         Metadata DB
        │              │                │
        └──────────────┴────────────┬───┘
                                    ▼
                            Document Storage
                                    │
                                    ▼
                                 Kafka
                                    │
          ┌────────────┬────────────┬────────────┐
          ▼            ▼            ▼
     Autosave     Versioning    Analytics
```

Notice that every service owns exactly one responsibility.

---

# Architecture Overview

| Service | Responsibility |
|----------|----------------|
| WebSocket Gateway | Persistent Connections |
| Collaboration Service | Real-Time Editing |
| Presence Service | Online Users & Cursors |
| Document Service | Metadata |
| Document Storage | Persistent Content |
| Redis | Active Sessions |
| Kafka | Background Events |

# Why WebSockets?

Traditional HTTP works like this:

```text
Request

↓

Response

↓

Connection Closed
```

Imagine typing:

```
Hello World
```

Eleven characters would require eleven HTTP requests.

Very inefficient.

Instead,

Google Docs maintains one persistent connection.

```text
Client

⇄

WebSocket

⇄

Server
```

Every keystroke is transmitted immediately.

---

# WebSocket Gateway

Every client first connects here.

```text
User

↓

WebSocket Gateway

↓

Collaboration Service
```

Responsibilities:

- Authentication
- Connection Management
- Routing
- Heartbeats
- Reconnection

It does **not** modify documents.

---

# Why Separate the Gateway?

Imagine:

```
20 Million

Concurrent Connections
```

Managing connections is different from processing edits.

Separating responsibilities allows independent scaling.

---

# Document Service

The Document Service manages document metadata.

Example:

```text
Document ID

Title

Owner

Permissions

Created Time

Last Modified
```

It does **not** store document text.

---

# Why Separate Metadata?

Suppose Alice renames a document.

Only metadata changes.

The actual content remains identical.

Separating metadata improves performance and scalability.

---

# Document Storage

Document content is stored separately.

Example:

```text
Document

↓

Paragraphs

↓

Formatting

↓

Images

↓

Tables
```

This storage is optimized for durability,

not real-time collaboration.

---

# Collaboration Service

This is the heart of Google Docs.

Responsibilities:

- Receive edits
- Order operations
- Resolve conflicts
- Broadcast updates
- Maintain document sessions

Almost every edit passes through this service.

---

# What is a Document Session?

Imagine Alice opens:

```
Project Proposal
```

A session is created.

```text
Document

↓

Session

↓

Connected Users

↓

Operations
```

Every active document has its own collaboration session.

---

# Session Lifecycle

```text
Open Document

↓

Create Session

↓

Users Join

↓

Edit

↓

Last User Leaves

↓

Session Closed
```

Inactive sessions are removed automatically.

---

# Document Session Example

Suppose:

```text

Project Plan
```

Users:

```text
Alice

Bob

Charlie

David
```

The session tracks:

- Connected users
- Current version
- Pending operations
- Cursor locations

---

# Presence Service

Google Docs shows:

```text
Alice is editing...

Bob's cursor

Charlie's selection
```

This is handled by the Presence Service.

---

# Presence Information

The service stores:

| Field | Description |
|--------|-------------|
| User ID | Alice |
| Document | Project Plan |
| Cursor Position | 125 |
| Selection | Characters 120–150 |
| Online Status | Active |

---

# Why Redis?

Presence changes constantly.

Examples:

- Cursor movement
- User joins
- User leaves
- Selection changes

Redis stores:

- Active users
- Cursor positions
- Active sessions

because it's extremely fast.

---

# Presence Flow

```text
Cursor Moved

↓

Presence Service

↓

Redis

↓

Broadcast

↓

Other Users
```

Everyone immediately sees cursor updates.

# Multiple Sessions

Each document has its own session.

```text
Document A

↓

Session A

-----------------

Document B

↓

Session B

-----------------

Document C

↓

Session C
```

Sessions remain isolated.

---

# Why Not Store Everything in the Database?

Imagine:

```
100 Million

Operations/sec
```

Writing every keystroke directly to disk would be extremely slow.

Instead:

- Collaboration Service handles live edits.
- Database stores durable snapshots.

---

# Redis Session Cache

Redis stores active session data.

```text
Session ID

↓

Connected Users

↓

Current Version

↓

Recent Operations
```

When the session ends,

data is flushed to persistent storage.

---

# Load Balancing

Initially,

one Collaboration Server works.

```text
Users

↓

Server
```

Eventually,

millions of editors require:

```text
Load Balancer

↓

Server1

Server2

Server3

Server4
```

Sessions are distributed across servers.

---

# Sticky Sessions

Question:

How do all users editing the same document reach the same server?

Solution:

Sticky Routing.

```text
Document ID

↓

Hash

↓

Server 3
```

Everyone editing that document is routed to Server 3.

This minimizes synchronization overhead.

---

# Horizontal Scaling

As traffic grows,

simply add more Collaboration Servers.

```text
Gateway

↓

Collab1

Collab2

Collab3

Collab4
```

Each manages different document sessions.

---

# Event Streaming

Not every operation needs immediate persistence.

Instead:

```text

↓

↓

Analytics
```

Background services process edits asynchronously.

Imagine four people editing the same PowerPoint presentation in a conference room.

Instead of each person keeping their own copy,

there is one shared whiteboard.

# Interview Tips

Interviewers often ask:

> **"How do you ensure all users editing the same document stay synchronized?"**

A strong answer is:

> "Each active document has a collaboration session hosted by a Collaboration Service. Users maintain persistent WebSocket connections through a gateway. All editing operations are routed to the same session, ordered, processed, and broadcast to every participant. Redis stores transient session state, while Kafka asynchronously persists edits and updates version history."

This demonstrates an understanding of session management and real-time distributed communication.

# Key Takeaways

- Google Docs uses persistent WebSocket connections for low-latency collaboration.
- Every active document has a dedicated collaboration session.
- The Collaboration Service coordinates edits and broadcasts updates.
- Presence Service tracks active users, cursors, and selections.
- Redis stores transient session state for fast access.
- Sticky routing ensures all collaborators on the same document are handled by the same collaboration server.
- Kafka decouples real-time editing from persistence and analytics.
- The next step is understanding how Operational Transform (OT) and CRDT keep documents consistent during simultaneous edits.
