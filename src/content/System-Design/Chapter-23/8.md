# Evolution of the Architecture

Imagine the very first version of Instagram.

```text
              Users
                 │
                 ▼
          Instagram Server
                 │
                 ▼
             Database
```

This architecture works for a few thousand users.

However,

as traffic grows,

problems quickly appear.

- Large image uploads consume server resources.
- Feed generation becomes expensive.
- One database becomes overloaded.
- Millions of concurrent users overwhelm a single server.

To scale,

we divide responsibilities.

---

# High-Level Architecture

A production Instagram architecture might look like this.

```text
                          Users
                            │
                            ▼
                           DNS
                            │
                            ▼
                   Global Load Balancer
                            │
                            ▼
                       API Gateway
                            │
 ┌───────────────┬─────────────┬───────────────┐
 ▼               ▼             ▼               ▼
User Service  Upload Service Feed Service Notification Service
 │               │             │               │
 ▼               ▼             ▼               ▼
Redis         Object Storage  Redis          Kafka
 │               │             │               │
 └───────────────┴──────┬──────┴───────────────┘
                        ▼
                 Metadata Database
                        │
                        ▼
                  Read Replicas
```

Every service has one responsibility.

This follows the **Single Responsibility Principle** for distributed systems.

---

# Why Separate Services?

Imagine one user uploads a photo.

Another million users simply open their feeds.

Should both operations use the same application server?

No.

Uploading photos is write-heavy.

Feed loading is read-heavy.

These workloads scale differently.

Independent services allow each component to scale according to its own traffic.

---

# Component 1 — API Gateway

Every request enters through the API Gateway.

Responsibilities include:

- Authentication
- Authorization
- Rate Limiting
- Logging
- API Routing
- Request Validation

Clients never communicate directly with backend services.

---

# Component 2 — User Service

The User Service manages:

- Registration
- Login
- User Profiles
- Follow Relationships

Example request

```http
GET /users/alex
```

This service primarily manages user metadata.

It does **not** store images.

---

# Component 3 — Upload Service

The Upload Service receives photos and videos.

Responsibilities:

- Validate uploads
- Generate upload IDs
- Store metadata
- Upload media
- Trigger image processing

Notice that it **does not permanently store images itself**.

Instead,

it sends them to object storage.

---

# Why Not Store Images in the Database?

Imagine storing every Instagram photo inside PostgreSQL.

Each image might average

```
5 MB
```

Daily uploads

```
1.5 Billion Images
```

Daily storage

```
≈ 7.5 Petabytes
```

Relational databases are optimized for structured data,

not massive binary files.

Instead,

Instagram separates:

```text
Metadata

↓

Database
```

```text
Images

↓

Object Storage
```

---

# Object Storage

Large media files are stored in systems like:

- Amazon S3
- Google Cloud Storage
- Azure Blob Storage

Object storage provides:

- Durability
- Scalability
- Low Cost
- Replication

The database simply stores a reference.

Example:

| Post ID | Image URL |
|----------|-----------|
| 1204 | s3://images/post1204.jpg |

---

# CDN

Suppose millions of users view the same viral post.

Without a CDN,

every request reaches the storage service.

Instead,

Instagram uses a CDN.

```text
User

↓

CDN

↓

Cached Image

↓

Return Image
```

Only cache misses reach object storage.

This dramatically reduces latency.

---

# Component 4 — Feed Service

The Feed Service generates the home timeline.

Responsibilities:

- Retrieve followed accounts
- Fetch recent posts
- Rank content
- Return feed

This is one of Instagram's most heavily used services.

We'll dedicate an entire section to feed generation later.

---

# Component 5 — Notification Service

Whenever someone

- Likes your photo
- Comments
- Follows you

the Notification Service creates an event.

Notifications should never delay user actions.

Therefore,

they are processed asynchronously.

---

# Kafka

Instagram uses an event-driven architecture.

Example:

```text
Like Photo

↓

Kafka

↓

Notification Service

↓

Push Notification
```

The Like API returns immediately.

Notification delivery happens later.

---

# Redis

Instagram is extremely read-heavy.

Users repeatedly access

- Profiles
- Feeds
- Stories
- User Information

Redis caches frequently requested data.

Example:

```text
User

↓

Redis

↓

Found?

↓

Return Data
```

Only cache misses reach the database.

---

# Metadata Database

The database stores structured information.

Examples include:

- Users
- Posts
- Followers
- Likes
- Comments

Notice that

images themselves are not stored here.

---

# Photo Upload Lifecycle

Let's follow a photo upload.

```text
User

↓

API Gateway

↓

Authentication

↓

Upload Service

↓

Object Storage

↓

Store Metadata

↓

Database

↓

Publish Kafka Event

↓

Feed Service

↓

Notification Service
```

Notice something important.

Uploading a photo triggers multiple downstream services.

This is a classic event-driven architecture.

# Feed Request Lifecycle

Now let's examine feed loading.

```text

↓

API Gateway

↓

Feed Service

↓

Redis

↓

Cache Hit?

│

├── Yes

│

│ Return Feed

│

└── No

↓

Database

↓

Build Feed

Cache Feed

↓

```

Again,

# Read vs Write Workloads

Instagram handles different workloads.

---

## Writes

- Upload Photo
- Like
- Comment
- Follow

---

## Reads

- Load Feed
- View Profiles
- View Stories
- Search

Since reads dominate,

Instagram invests heavily in caching.

---

# Design Decisions So Far

| Problem | Solution |
|----------|----------|
| Large Images | Object Storage |
| Global Delivery | CDN |
| Read Heavy Workload | Redis |
| Event Processing | Kafka |
| High Traffic | Load Balancer |
| User Metadata | Relational Database |
| Independent Scaling | Microservices |

Each component exists because it solves a specific problem.

# Real-Life Example

Suppose Cristiano Ronaldo uploads a photo.

Within seconds,

millions of followers refresh Instagram.

Without caching,

every request would hit the database.

Instead,

the request flow becomes

```text
Millions of Users

↓

CDN (Images)

↓

Redis (Feed)

↓

Database (Only When Needed)
```

This architecture allows Instagram to serve enormous traffic spikes efficiently.

# Key Takeaways

- Instagram separates responsibilities into independent microservices.
- Images are stored in object storage, while metadata remains in relational databases.
- CDNs reduce latency by serving media close to users.
- Redis caches frequently accessed data such as feeds and profiles.
- Kafka enables asynchronous communication between services.
- The upload and feed workflows are fundamentally different and are handled by specialized services.
- Separating media storage, metadata, caching, and event processing allows Instagram to scale independently across billions of requests.
- The next challenge is designing Instagram's feed generation strategy, one of the most important topics in large-scale system design.
