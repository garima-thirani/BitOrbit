# Introduction

Google Docs is one of the most frequently discussed system design problems because it combines several advanced concepts into a single application.

Unlike previous case studies:

- Netflix → Large-scale streaming
- Uber → Real-time location tracking
- WhatsApp → Messaging
- Instagram → Social media

Google Docs introduces a completely different challenge:

> **Maintaining consistency while hundreds of users edit the same document simultaneously.**

There is no single database transaction that solves this.

Instead,

Google Docs combines networking,

distributed systems,

algorithms,

storage,

and synchronization.

# Step 6 — Explain Operations

Google Docs doesn't transmit


# Step 7 — Explain Operational Transform

This is usually the most important discussion.

Interviewers may ask:

> Why doesn't Google Docs simply overwrite conflicting edits?

Answer:

Because simultaneous edits would overwrite each other.

Instead,

Google Docs transforms concurrent operations

before applying them,

ensuring every user eventually reaches the same document.

---

# Simple OT Example

Original

```text
ABCDEF
```

Alice:

```text
Insert X

after B
```

Bob:

```text
Delete D
```

Without OT

different users could observe different documents.

With OT

operations are transformed

so every client converges to the same result.

---

# OT Properties

Operational Transform guarantees:

- Convergence
- Intent Preservation
- Low Latency
- No Lost Updates

These are the primary reasons Google Docs historically adopted OT.

---

# Step 8 — Discuss CRDT

Interviewers often ask:

> Why not use CRDT?

Answer:

CRDTs remove the need for operation transformation.

Each element has a unique identity,

allowing replicas to merge automatically.

---

# OT vs CRDT

| Operational Transform | CRDT |
|-----------------------|------|
| Operations transformed | Replicas merged |
| Smaller metadata | Larger metadata |
| Mature ecosystem | Excellent offline support |
| Central coordination | Decentralized |
| Historically Google Docs | Used in Figma, Yjs, Automerge |

There is no universally "better" approach.

The choice depends on system requirements.

# Why Deltas?

Instead of storing

```text

↓

Document V2

↓

Document V3
```

```text

+

Delta

+

+

```

---

# Why Snapshots?

Interviewers often ask:

> Why not store only deltas?

Answer:

Recovery becomes increasingly expensive.

Instead,

Google Docs periodically creates snapshots,

reducing replay time.

# Common Interview Questions

---

## Why WebSockets?

HTTP requires repeated requests.

WebSockets provide:

- Persistent connections
- Low latency
- Bidirectional communication

Ideal for collaborative editing.

---

## Why Kafka?

Kafka decouples:

- Collaboration
- Autosave
- Analytics
- Version History

Background processing does not block editing.

---

## Why Redis?

Redis stores:

- Presence
- Active sessions
- Cursor locations

Because these datasets change rapidly.

---

## Why Not Save Every Keystroke?

Saving the full document after each edit causes:

- High storage cost
- High disk I/O
- Poor scalability

Instead,

store operations.

---

## Why Separate Metadata?

Metadata changes infrequently.

Document content changes constantly.

Separating them allows independent scaling.

---

## How Does Offline Editing Work?

Operations are queued locally.

Upon reconnection:

```text
Queued Operations

↓

Transform

↓

Apply

↓

Broadcast
```

Users eventually synchronize.

---

## How Does Version History Work?

Version history combines:

```text
Snapshots

+

Deltas
```

Older document states

can be reconstructed efficiently.

---

## How Are Permissions Managed?

An Access Control List (ACL)

stores:

```text
Owner

Editor

Commenter

Viewer
```

Every operation checks permissions

before execution.

# Key Takeaways

- Google Docs is fundamentally a **real-time collaborative editing system**, not just a document storage service.
- WebSockets provide low-latency, bidirectional communication for live collaboration.
- Operational Transform (OT) resolves concurrent edits by transforming operations while preserving user intent.
- CRDTs provide an alternative synchronization strategy with stronger offline capabilities.
- Autosave, delta storage, and periodic snapshots enable efficient persistence and version history.
- Redis, Kafka, and sticky sessions support scalable collaboration and reliable event processing.
- Multi-region deployment, replication, and observability ensure high availability and fault tolerance.
- Google Docs is one of the best examples of combining distributed systems, networking, storage, and synchronization algorithms into a production-grade application.
