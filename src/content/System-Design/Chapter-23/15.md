# Introduction

So far, our architecture can:

- Maintain millions of WebSocket connections
- Route messages
- Track online users
- Store conversations

But we're still missing one of the hardest problems.

> **How do we guarantee that messages are delivered correctly?**

Imagine Alice sends Bob:

```
Hello Bob 👋
```

Questions immediately arise.

- What if Bob is offline?
- What if the server crashes?
- What if Alice presses Send twice?
- What if the network disconnects halfway?
- What if Bob has three devices?
- What if messages arrive in the wrong order?

Messaging systems spend much more effort handling failures than successful deliveries.

---

# The Message Lifecycle

Every WhatsApp message goes through multiple stages.

```text
Alice Types Message

↓

Send

↓

Server Receives

↓

Store Message

↓

Deliver

↓

Bob Receives

↓

Bob Reads
```

Each stage changes the message status.

---

# Message States

WhatsApp displays three delivery states.

```text
✓

Sent
```

```text
✓✓

Delivered
```

```text
✓✓ (Blue)

Read
```

Each status represents a different event inside the system.

---

# Stage 1 — Sent

Alice presses Send.

```text
Alice

↓

Connection Server

↓

Message Service

↓

Database

↓

ACK

↓

✓
```

The first tick simply means:

> The WhatsApp server successfully accepted the message.

It **does not** mean Bob received it.

---

# Stage 2 — Delivered

Bob's device receives the message.

```text
Alice

↓

Server

↓

Bob

↓

Delivery ACK

↓

Alice

↓

✓✓
```

The second tick means:

> Bob's device received the message.

Bob may not have opened it yet.

---

# Stage 3 — Read

Bob opens the conversation.

```text
Bob Opens Chat

↓

Read Receipt

↓

Server

↓

Alice

↓

Blue ✓✓
```

This tells Alice that Bob has actually viewed the message.

---

# Why Acknowledgements Matter

Suppose Alice sends

```
Hello
```

The internet disconnects.

Did the server receive it?

Alice doesn't know.

Without acknowledgements,

the client cannot determine whether to retry.

---

# Message Acknowledgement Flow

```text
Alice

↓

Send Message

↓

Server

↓

Store Message

↓

ACK

↓

Alice Removes Pending Status
```

Only after receiving the ACK does Alice know the message is safely stored.

You receive:

```

```

Later,

```
Package Delivered
```

Finally,

```
Recipient Signed
```

WhatsApp's ticks behave almost identically.

# Message IDs

Every message receives a unique identifier.

Example

```text
MSG-9384721
```

Why?

Suppose Alice accidentally presses Send twice.

Without IDs,

the receiver might see duplicates.

Instead,

servers recognize duplicate IDs.

---

# Duplicate Detection

```text
Message

↓

ID

↓

Already Exists?

│

├── Yes

│

│ Ignore

│

└── No

↓

Store
```

This prevents duplicate deliveries.

---

# Why Exactly-Once Delivery is Difficult

In distributed systems,

networks are unreliable.

Imagine:

```text
Server Stores Message

↓

ACK Lost
```

Alice thinks the message failed.

She retries.

Without duplicate detection,

Bob receives

```
Hello

Hello
```

twice.

This is why message IDs are essential.

# Offline Messaging

Suppose Bob is offline.

What happens?

```text
Alice

↓

Server

↓

Bob Offline

↓

Store Pending

↓

Bob Reconnects

↓

Deliver
```

The server temporarily stores undelivered messages.

---

# Offline Queue

Each offline user maintains a pending queue.

```text
Bob

↓

Message 1

Message 2

Message 3
```

When Bob reconnects,

messages are delivered sequentially.

---

# Offline Delivery Flow

```text
Alice

↓

Message Service

↓

Store

↓

Pending Queue

↓

Bob Connects

↓

Deliver Messages

↓

ACK

↓

Delete Pending Queue
```

The sender doesn't need to resend anything.

---

# Multi-Device Synchronization

Modern WhatsApp supports multiple devices.

Suppose Bob has:

- Phone
- Laptop
- Tablet

Which device receives the message?

Answer:

All active devices.

```text
Server

↓

Phone

Laptop

Tablet
```

Each device maintains its own connection.

# Session Registry

Redis stores active sessions.

```text
Bob

↓

Phone

↓

Connection 1

-------------------

Laptop

↓

Connection 2
```

Now the Message Service knows where to deliver.

# Group Messaging

Suppose Alice sends a message to

```
Family Group
```

containing

5 members.

Should the server send

one message?

No.

Internally,

the group expands.

```text
Alice

↓

Group

↓

Bob

Charlie

David

Emma

Frank
```

Each recipient receives an individual delivery.

---

# Group Message Flow

```text
Alice

↓

Group Service

↓

Fetch Members

↓

Message Queue

↓

Deliver Individually
```

Notice something important.

The server never forwards messages through other users.

Everything passes through WhatsApp's infrastructure.

---

# Why Use a Queue?

Suppose a group contains

5,000 users.

Sending

5,000 messages synchronously

would slow Alice's request.

Instead,

the Group Service publishes delivery tasks.

```text
Alice

↓

Queue

↓

Workers

↓

Recipients
```

Now delivery scales horizontally.

# Message Ordering

Imagine Alice sends

```
Hi

↓

How are you?

↓

Let's meet.
```

Bob should receive

```
Hi

How are you?

Let's meet.
```

Not

```
Let's meet.

Hi.

How are you?
```

Maintaining order becomes difficult in distributed systems.

# Sequence Numbers

Every conversation maintains sequence numbers.

```text
Message 1

↓

Sequence 101

----------------

Message 2

↓

Sequence 102

----------------

Message 3

↓

Sequence 103
```

Recipients sort using sequence numbers.

---

# Why Networks Reorder Packets

Packets travel through different routes.

```text
Packet 1

↓

Route A

--------------

Packet 2

↓

Route B
```

Sometimes

Packet 2

arrives first.

Applications must reorder messages.

---

# Ordering Pipeline

```text
Receive Messages

↓

Sort by Sequence

↓

Display Chat
```

The user never notices network reordering.

---

# Retry Mechanism

Suppose Bob's phone loses internet.

```text
Deliver

↓

Timeout

↓

Retry
```

Retries continue until:

- Success
- Expiration
- User Disconnect

---

# Retry Queue

```text
Pending Messages

↓

Retry Worker

↓

Deliver Again
```

Workers continuously process failed deliveries.

---

# Idempotency

Suppose retries occur.

We must avoid duplicates.

Rule:

```
Same Message ID

↓

Process Once
```

This is called

**idempotent message processing**.

# Scaling Delivery Workers

Suppose

100 billion messages/day.

One worker isn't enough.

```text

↓

Worker 3

Worker 4
```

Each worker processes different messages.

Horizontal scaling enables massive throughput.

# Real-Life Example

Imagine sending invitations for a wedding.

Instead of personally visiting

500 guests,

you hand the invitations to a courier company.

The courier distributes them independently.

Similarly,

WhatsApp places delivery tasks into queues,

This keeps the sender's experience fast,

even when millions of deliveries are happening simultaneously.

# Design Decisions So Far

| Problem | Solution |
|----------|----------|
| Reliable Delivery | ACKs |
| Duplicate Messages | Message IDs |
| Offline Users | Pending Queue |
| Multiple Devices | Session Registry |
| Large Groups | Queue-Based Delivery |
| Message Ordering | Sequence Numbers |
| Retry Logic | Delivery Workers |
| Duplicate Prevention | Idempotency |

Every mechanism solves a specific failure scenario.

# Interview Tips

Interviewers frequently ask:

> **"How would you guarantee messages aren't delivered twice?"**

A strong answer is:

> "Every message has a globally unique Message ID. Delivery operations are idempotent, so if the same message is retried due to a network failure, the receiver processes it only once. Acknowledgements confirm successful delivery, while retries handle temporary failures."

This demonstrates an understanding of distributed systems beyond simple messaging.

# Key Takeaways

- Reliable messaging requires acknowledgements, retries, and unique message identifiers.
- WhatsApp tracks three message states: Sent, Delivered, and Read.
- Offline users receive messages later through pending delivery queues.
- Group messages are expanded into individual deliveries for each recipient.
- Sequence numbers preserve message ordering despite network delays.
- Idempotent processing prevents duplicate message delivery during retries.
- Delivery workers and queues enable horizontal scaling for billions of daily messages.
