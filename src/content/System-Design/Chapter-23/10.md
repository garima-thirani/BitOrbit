# Introduction

At this point, our Instagram architecture can:

- Upload posts
- Generate feeds
- Cache frequently accessed data
- Scale horizontally

However, modern Instagram offers much more than simply displaying photos.

Whenever a user uploads a picture,

multiple systems immediately begin working.

One upload may trigger:

- Thumbnail generation
- Image compression
- AI moderation
- Feed updates
- Search indexing
- Notification delivery
- Recommendation updates
- Analytics collection

Instead of one large application performing all these tasks,

Instagram uses an **Event-Driven Architecture**.

---

# Why Event-Driven Architecture?

Imagine uploading a photo.

Should the user wait while Instagram:

- Creates thumbnails
- Compresses images
- Detects inappropriate content
- Sends notifications
- Updates recommendations

Of course not.

The upload should finish immediately.

Everything else should happen in the background.

---

# Upload Pipeline

The upload process looks like this.

```text
User Uploads Image

↓

API Gateway

↓

Upload Service

↓

Object Storage (S3)

↓

Store Metadata

↓

Database

↓

Publish Event

↓

Kafka
```

Notice that the upload completes before any additional processing begins.

---

# Kafka Event Pipeline

Kafka becomes the communication backbone.

```text
                Kafka

     ┌──────────┼──────────┐
     ▼          ▼          ▼

Image Worker Notification Search Indexer
     ▼          ▼          ▼

Thumbnail     Push      Elasticsearch

Generator Notification
```

Each consumer processes the same event independently.

This is one of Kafka's greatest strengths.

---

# Why Kafka?

Without Kafka,

the Upload Service would need to call every downstream service directly.

```text
Upload

↓

Image Service

↓

Notification

↓

Search

↓

Analytics

↓

Recommendation
```

If one service becomes slow,

the entire upload becomes slow.

Instead,

Kafka decouples producers and consumers.

```text
Upload

↓

Kafka

↓

Consumers
```

Now every service works independently.

# Notification System

Suppose Alice likes Bob's photo.

Should Bob immediately receive a notification?

Yes.

But Likes should remain fast.

Instead of sending notifications directly,

Instagram publishes an event.

```text
Like Post

↓

Kafka

↓

Notification Service

↓

Push Notification
```

The Like API returns immediately.

---

# Notification Database

Notifications are stored separately.

Example schema:

| Notification ID | User | Type | Created |
|-----------------|------|------|----------|
| 1 | Bob | Like | 10:30 |
| 2 | Bob | Comment | 10:31 |
| 3 | Bob | Follow | 10:33 |

This enables notification history.

# Likes

Likes appear simple,

but they generate enormous traffic.

Suppose

100 billion likes/day.

The Like Service performs:

```text
User

↓

Like Service

↓

Database

↓

Redis Counter

↓

Kafka Event
```

Redis stores frequently changing counters.

---

# Why Redis for Likes?

Imagine displaying

```
❤️ 4,932,124 Likes
```

Reading the database every time is expensive.

Instead,

Redis maintains an in-memory counter.

```text
Redis

↓

Like Count

↓

Database Updated Later
```

This dramatically reduces database load.

# Stories

Stories disappear after 24 hours.

Unlike regular posts,

they are temporary.

Database:

| Story ID | User | Created | Expires |
|-----------|------|----------|----------|

Background workers periodically remove expired stories.

```text
Scheduler

↓

Find Expired Stories

↓

Delete
```

Object Storage also removes associated media.

# Search

Instagram supports searching:

Not efficiently.

Instead,

```text

Elasticsearch
```

# CDN

Images should never be served directly from object storage.

Instead,

they pass through a CDN.

```text
User

↓

Nearest CDN

↓

Cached Image

↓

Object Storage (Cache Miss)
```

Benefits:

- Lower latency
- Reduced storage traffic
- Global availability

# Real-Life Example

Suppose Taylor Swift uploads a concert photo.

Within seconds,

millions of fans open Instagram.

The system performs:

- Store original image
- Generate thumbnails
- Cache images in CDN
- Update follower feeds
- Send notifications
- Index hashtags
- Update recommendations
- Record analytics

Yet,

Taylor only experiences a quick upload.

Everything else happens asynchronously through Kafka.

This illustrates the power of event-driven architecture.

# Interview Tips

Interviewers often ask:

> "Why use Kafka instead of direct service calls?"

A strong answer is:

> "Kafka decouples services, allows asynchronous processing, supports retries, enables independent scaling, and prevents one slow downstream service from delaying the user's upload."

This demonstrates an understanding of distributed systems rather than simply knowing Kafka.

# Key Takeaways

- Instagram relies heavily on an event-driven architecture powered by Kafka.
- Media uploads are processed asynchronously to provide fast user responses.
- Images are stored in object storage while multiple optimized versions are generated in the background.
- Likes, comments, notifications, search indexing, and recommendations are handled by independent services.
- Redis accelerates counters, feeds, and frequently accessed metadata.
- Elasticsearch powers fast user and hashtag search.
- AI moderation and recommendation systems continuously process user activity.
- Kubernetes, Kafka, Redis, CDNs, and object storage together form the backbone of Instagram's production architecture.
