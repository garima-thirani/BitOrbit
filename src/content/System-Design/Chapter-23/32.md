# The Save Button Problem

Traditional applications work like this.

```text
Open File

↓

Edit

↓

Click Save

↓

Write Entire File

↓

Close
```

Microsoft Word originally followed this model.

Google Docs does not.

Instead,

```text
Open

↓

Type

↓

Automatically Saved

↓

Type

↓

Automatically Saved

↓

Close

↓

Nothing To Save
```

Autosave fundamentally changes how persistence works.

---

# Why Not Save Every Keystroke?

Imagine Alice types:

```text
Hello World
```

That's eleven individual edits.

Should Google Docs write the entire document

to disk

eleven times?

```text
Insert H

↓

Disk Write

↓

Insert e

↓

Disk Write

↓

Insert l

↓

Disk Write
```

For millions of users,

this would generate an enormous number of writes.

Very inefficient.

---

# Goals of the Persistence Layer

The persistence system should guarantee:

- No edits are lost.
- Low write latency.
- Efficient storage.
- Fast document recovery.
- Version history.
- Scalable storage.

Notice that durability and performance often conflict.

The challenge is balancing both.

---

# Persistence Architecture

A simplified persistence pipeline looks like this.

```text
              User Types

                   │

                   ▼

        Collaboration Service

                   │

          Operation Generated

                   │

                   ▼

               Kafka Log

         ┌─────────┴─────────┐

         ▼                   ▼

    Autosave Service    Version Service

         ▼                   ▼

     Snapshot Store     Delta Store

              └──────────┬─────────┘

                         ▼

                 Document Storage
```

Instead of writing synchronously,

operations are processed asynchronously.

---

# Operations Before Documents

Remember from Part 6C:

Google Docs stores

operations,

not complete documents.

Example:

Instead of

```text
Hello Beautiful World
```

store

```text
Insert

Position = 6

Text = Beautiful
```

Operations are much smaller than documents.

---

# Autosave

Autosave is one of Google Docs' most famous features.

It continuously persists document changes

without user interaction.

From the user's perspective,

everything simply "just works."

---

# How Autosave Works

The Collaboration Service receives operations.

```text
Insert

↓

Delete

↓

Replace

↓

Format
```

Instead of immediately writing them to disk,

it publishes them to Kafka.

```text
Operation

↓

Kafka

↓

Autosave Worker
```

Autosave workers perform persistence independently.

---

# Why Asynchronous Persistence?

Suppose disk writes take

```
15 ms
```

If every keystroke waited,

typing would feel sluggish.

Instead,

the editor immediately acknowledges the edit,

while persistence occurs in the background.

This keeps editing responsive.

---

# Write-Ahead Log (WAL)

Before applying edits permanently,

operations are first recorded in a durable log.

```text
Operation

↓

Write-Ahead Log

↓

Acknowledged

↓

Applied
```

If a server crashes,

the log can replay missing operations.

This technique is common in databases such as PostgreSQL and MySQL.

---

# Delta Storage

Imagine writing a book.

Version 1:

```text
100 Pages
```

You change

one sentence.

Should the system store

another complete copy?

No.

Instead,

store only the difference.

This difference is called a **Delta**.

---

# What is a Delta?

A delta represents only the modification.

Example:

Original:

```text
Hello World
```

Delta:

```text
Insert

Position = 6

Text = Beautiful
```

Storage size becomes dramatically smaller.

---

# Delta Storage Example

Instead of storing:

```text
Version 1

150 KB

Version 2

151 KB

Version 3

152 KB
```

Store:

```text
Snapshot

150 KB

+

Delta 1

+

Delta 2

+

Delta 3
```

Much more efficient.

---

# Advantages of Delta Storage

Benefits:

- Lower storage usage.
- Faster writes.
- Complete edit history.
- Efficient versioning.

However,

reading very old versions becomes slower,

because many deltas must be replayed.

---

# The Problem with Infinite Deltas

Suppose a document has

```
500,000 edits.
```

Reconstructing it means replaying

500,000 operations.

```text
Snapshot

↓

Delta

↓

Delta

↓

Delta

↓

...

↓

500,000 Times
```

Clearly,

this becomes inefficient.

---

# Solution — Snapshots

Periodically,

Google Docs stores

the complete document.

```text
Snapshot

↓

Delta

↓

Delta

↓

Delta

↓

Snapshot

↓

Delta

↓

Delta
```

Recovery now starts from the nearest snapshot.

---

# Snapshot Strategy

A common strategy is:

```text
Every N Operations

OR

Every Few Minutes

↓

Create Snapshot
```

This balances:

- Storage
- Recovery speed
- Write performance

---

# Snapshot Example

Imagine:

```text
Snapshot

Version 1000
```

Current version:

```text
Version 1025
```

Recovery requires replaying only

25 operations,

not 1025.

# Undo & Redo

Undo is different from Version History.

Version History restores

old document states.

Undo reverses

the user's most recent operation.

---

# Undo Stack

Suppose Alice types:

```text
Hello
```

Operations:

```text
Insert H

Insert e

Insert l

Insert l

Insert o
```

Undo removes

the latest operation.

---

# Redo

Redo simply reapplies

the previously undone operation.

```text
Undo

↓

Redo

↓

Original State
```

---

# Why Undo is Hard in Collaboration

Imagine:

Alice inserts:

```text
Hello
```

Bob immediately edits

the same paragraph.

Now Alice presses Undo.

Should Bob's changes disappear?

No.

Undo must respect

other users' edits.

This is why collaborative Undo is significantly harder than single-user Undo.

# Sharing Architecture

Every document has an Access Control List (ACL).

Example:

| User | Permission |
|------|------------|
| Alice | Owner |
| Bob | Editor |
| Charlie | Commenter |
| David | Viewer |

The ACL determines allowed operations.

---

# Permission Levels

Typical roles include:

```text
Owner

↓

Editor

↓

Commenter

↓

Viewer
```

Each role has progressively fewer privileges.

---

# Sharing Flow

```text

↓

↓

↓

↓

```

Permissions are checked before every edit.

# Metadata Storage

Document metadata contains:

| Field | Description |

# Recovery After Failure

Suppose the Collaboration Server crashes.

Fortunately,

every operation already exists in Kafka.

Recovery becomes:

```text
Latest Snapshot

↓

Replay Deltas

↓

Restore Session

↓

Reconnect Users
```

No edits are lost.

---

# User Reconnection

Suppose Alice disconnects.

While offline,

Bob makes ten edits.

When Alice reconnects:

```text
Reconnect

↓

Current Version

↓

Missing Operations

↓

Replay

↓

Latest Document
```

Synchronization happens automatically.

# Design Decisions

| Problem | Solution |
|----------|----------|
| Frequent Saves | Autosave |
| Excessive Storage | Delta Storage |
| Slow Recovery | Periodic Snapshots |
| Audit Trail | Version History |
| Accidental Changes | Undo/Redo |
| Unauthorized Access | ACL |
| Crash Recovery | WAL + Kafka Replay |
| Scalability | Asynchronous Persistence |

# Real-World Analogy

Imagine writing a book with an editor.

Instead of photocopying the entire manuscript after every sentence,

the editor writes down only what changed.

Occasionally,

they create a fresh complete copy of the manuscript.

If anything goes wrong,

they start from the latest complete copy

and replay only the recent edits.

Google Docs follows the same strategy using **snapshots** and **deltas**.

---

# Interview Tips

Interviewers often ask:

> **"Why doesn't Google Docs save the entire document after every keystroke?"**

A strong answer is:

> "Saving the full document for every edit would create enormous write amplification and waste storage. Instead, Google Docs persists lightweight editing operations (deltas). Periodically, it creates full snapshots to speed up recovery. During reconstruction, the latest snapshot is loaded and only the newer deltas are replayed. This balances write efficiency, storage cost, and recovery speed."

# Key Takeaways

- Google Docs persists **operations (deltas)** rather than rewriting the entire document after each edit.
- **Autosave** is asynchronous, allowing users to edit without waiting for disk writes.
- **Write-Ahead Logs (WALs)** and **Kafka** provide durable operation logs for crash recovery.
- **Snapshots** are created periodically to avoid replaying long chains of deltas.
- **Version History** is built from snapshots plus deltas, enabling efficient restoration of previous document states.
- **Undo/Redo** is more complex in collaborative editing because it must preserve other users' concurrent changes.
- **ACLs** separate sharing metadata from document content and enforce authorization.
- Efficient persistence is achieved by combining **deltas, snapshots, asynchronous writes, and durable logs**.
