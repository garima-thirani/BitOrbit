# Introduction

Think about everything that sends you notifications.

Instagram:

> "Alice liked your photo."

LinkedIn:

> "John viewed your profile."

Amazon:

> "Your order has shipped."

Bank:

> "₹5,000 debited from your account."

Google Calendar:

> "Meeting starts in 10 minutes."

Although these products are completely different,

they usually rely on a **shared Notification Service**.

Instead of every application implementing its own notification logic,

they publish notification events to a centralized system.

---

# Why Notification Service is a Good System Design Problem

Notification systems appear simple,

but they involve many distributed system concepts.

| Concept | Used? |
|----------|--------|
| Kafka | ✓ |
| Queues | ✓ |
| Retry | ✓ |
| Rate Limiting | ✓ |
| Scheduling | ✓ |
| Push Notifications | ✓ |
| Email | ✓ |
| SMS | ✓ |
| Dead Letter Queue | ✓ |
| Event-Driven Architecture | ✓ |

The challenge isn't sending one notification.

The challenge is sending **billions reliably**.

```text

                       │
       ┌───────────────┼──────────────┐

```

Notice that

sending

and

are separated.

# Why Use a Queue?

Suppose one million users receive a notification.

Without a queue:

```text
Application

↓

Wait

↓

Send

↓

Wait

↓

Send
```

The application becomes slow.

Instead:

```text
Application

↓

Kafka

↓

Return Success
```

Workers process notifications asynchronously.

---

# Notification Pipeline

```text

↓

Kafka

↓

Notification Worker

↓

Provider

↓

User Device
```

Applications remain fast,

even during traffic spikes.

# Retry Mechanism

Suppose FCM is temporarily unavailable.

Should the notification disappear?

No.

Retry.

---

# Retry Flow

```text
Send

↓

Failure

↓

Retry

↓

Failure

↓

Retry

↓

Success
```

Transient failures are common.

---

# Exponential Backoff

Retries should not happen immediately.

Example:

```text
1 Second

↓

2 Seconds

↓

4 Seconds

↓

8 Seconds
```

This reduces pressure on downstream services.

---

# Dead Letter Queue (DLQ)

Suppose every retry fails.

Where should the notification go?

```text
Retry

↓

Retry

↓

Retry

↓

DLQ
```

The Dead Letter Queue stores permanently failed messages for later investigation.

---

```text
↓

↓

```

Otherwise:

```text
Skip
```

User preferences are always respected.

# Design Decisions

| Problem | Solution |
|----------|----------|
| Traffic Spikes | Kafka |
| Multiple Channels | Workers |
| Temporary Failures | Retry |
| Permanent Failures | DLQ |
| Scheduled Messages | Scheduler |
| User Choices | Preference Service |

# Real-World Example

Imagine a postal service.

Letters arrive continuously.

Instead of every employee delivering letters immediately,

they first sort them into different bins:

- Local
- International
- Express

Each delivery team specializes in one category.

A Notification Service works similarly,

using specialized workers for Push, Email, and SMS.

---

# Interview Tips

Interviewers often ask:

> **"Why use Kafka in a Notification Service?"**

A strong answer is:

> "Kafka decouples applications from notification delivery. Applications simply publish notification events and continue processing user requests. Dedicated workers consume events asynchronously, enabling retries, scheduling, and independent scaling without affecting the main application."

# Key Takeaways

- A Notification Service centralizes Push, Email, SMS, and scheduled messaging.
- Kafka decouples notification creation from delivery, improving scalability and responsiveness.
- Dedicated workers handle each delivery channel independently.
- Retries with exponential backoff recover from temporary failures.
- Dead Letter Queues store permanently failed notifications for investigation.
- User preferences determine which channels are used.
- The next step is designing the production architecture for reliable notification delivery at internet scale.
