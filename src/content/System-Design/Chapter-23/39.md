# Introduction

Imagine Alice has three devices:

- Laptop
- Mobile Phone
- Tablet

She saves a file on her laptop:

```text
Project_Report.pdf
```

Within a few seconds,

the same file appears on all her other devices.

No manual upload.

No USB drive.

No email attachment.

Just seamless synchronization.

This is the core problem Dropbox solves.

Unlike Google Drive or Google Docs,

Dropbox is **primarily a file synchronization system**, not a collaborative editor.

# Understanding the Problem

Suppose Alice edits:

```text
Resume.docx
```

She changes one sentence.

Should Dropbox upload the **entire file again?**

Suppose the file is

```text
2 GB
```

Uploading the entire file after every small edit would waste bandwidth and increase synchronization time.

Instead,

Dropbox uploads only the modified parts.

# Metadata vs File Data

Every uploaded file consists of two parts.

## Metadata

Stores:

- File Name
- Owner
- Size
- Permissions
- Version
- Last Modified

Example:

```text
Resume.pdf

Size: 2 MB

Owner: Alice
```

---

## File Data

Stores the actual bytes.

```text
010101010101...

(Binary Data)
```

Separating them improves scalability.

---

# Why Separate Metadata?

Suppose Alice renames:

```text
Vacation.jpg

↓

Trip.jpg
```

Only metadata changes.

The file contents remain identical.

No need to upload the image again.

---

# Chunking

Large files are divided into smaller pieces called **chunks**.

Example:

```text
1 GB File

↓

Chunk 1

Chunk 2

Chunk 3

Chunk 4
```

Instead of transferring one massive file,

Dropbox transfers many smaller chunks.

---

# Why Chunk Files?

Imagine uploading a

```text
20 GB
```

video.

The upload fails after

```text
19 GB
```

Without chunking,

the upload must restart from the beginning.

With chunking,

only the missing chunk is retried.

---

# Chunk Example

Suppose a file is:

```text
16 MB
```

Chunk size:

```text
4 MB
```

Result:

```text
Chunk A

Chunk B

Chunk C

Chunk D
```

Each chunk can be uploaded independently.

---

# Parallel Uploads

Chunks can upload simultaneously.

```text
Chunk A

↓

Server A

----------------

Chunk B

↓

Server B

----------------

Chunk C

↓

Server C
```

Parallelism greatly improves upload speed.

---

# Delta Sync

Suppose Alice edits one paragraph in a

```text
500 MB
```

presentation.

Uploading the whole file would be wasteful.

Instead,

Dropbox identifies only the changed chunks.

```text
File

↓

Chunk 5 Changed

↓

Upload Chunk 5
```

This is called **Delta Sync**.

---

# Delta Sync Example

Original:

```text
Chunk 1

Chunk 2

Chunk 3

Chunk 4
```

Only

```text
Chunk 3
```

changes.

Upload:

```text
Chunk 3 Only
```

Synchronization becomes much faster.

---

# Deduplication

Suppose Alice uploads:

```text
Ubuntu.iso
```

Bob uploads the **exact same file**.

Should Dropbox store two copies?

No.

Instead,

it stores one copy.

Both users reference it.

---

# Hash-Based Deduplication

Every chunk receives a cryptographic hash.

Example:

```text
SHA-256

↓

AB12CD34...
```

If another uploaded chunk has the same hash,

Dropbox simply reuses the existing chunk.

---

# Deduplication Flow

```text
Upload Chunk

↓

Compute Hash

↓

Already Exists?

│

├── Yes → Reuse Existing Chunk

│

└── No

↓

Store New Chunk
```

This significantly reduces storage costs.

---

# File Versioning

Every edit creates a new version.

Example:

```text
Version 1

↓

Version 2

↓

Version 3

↓

Version 4
```

Users can restore previous versions if needed.

---

# Version Storage

Instead of copying the whole file,

Dropbox stores:

```text
Metadata

+

Changed Chunks
```

This minimizes storage usage.

---

# Upload Flow

```text
User Selects File

↓

Split Into Chunks

↓

Compute Hash

↓

Upload Missing Chunks

↓

Update Metadata

↓

Notify Other Devices
```

Every upload follows this pipeline.

---

# Design Decisions

| Problem | Solution |
|----------|----------|
| Large Files | Chunking |
| Interrupted Uploads | Resume by Chunk |
| Slow Uploads | Parallel Upload |
| Duplicate Files | Deduplication |
| Small Changes | Delta Sync |
| Version History | Metadata + Chunks |

# Real-World Example

Imagine moving a library of books.

Instead of transporting an entire bookshelf whenever one book changes,

you move only the updated book.

Dropbox applies the same principle:

rather than uploading the entire file,

it transfers only the changed chunks.

---

# Interview Tips

Interviewers often ask:

> **"Why doesn't Dropbox upload the entire file after every edit?"**

A strong answer is:

> "Uploading the full file after every modification would waste bandwidth and increase synchronization time. Dropbox divides files into chunks and computes hashes for each chunk. During synchronization, only the modified chunks are uploaded, significantly reducing network usage and improving sync performance."

# Key Takeaways

- Dropbox is fundamentally a **distributed file synchronization system**.
- Files are divided into chunks to support resumable and parallel uploads.
- Delta Sync transfers only modified chunks instead of the entire file.
- Metadata and file contents are stored separately for scalability.
- Hash-based deduplication eliminates duplicate storage of identical chunks.
- File versioning enables users to restore previous versions efficiently.
- The next step is designing the production synchronization architecture for millions of devices.
