# What is a Payment Gateway?

A Payment Gateway acts as a secure intermediary between a merchant and financial institutions.

It is responsible for:

- Receiving payment requests.
- Authenticating requests.
- Routing transactions.
- Preventing duplicate payments.
- Handling retries.
- Returning the payment result.

Think of it as the **traffic controller** for online payments.

# Authorization vs Capture

Payment processing usually occurs in two phases.

## Authorization

The bank verifies:

- Card is valid.
- Sufficient balance exists.
- Fraud checks pass.

Money is reserved,

but not transferred.

---

## Capture

Later,

the merchant requests:

```text
Capture Payment
```

Now the money is actually collected.

This two-step model allows merchants to cancel orders before charging customers.

---

# Payment State Machine

Every payment moves through well-defined states.

```text
Created

↓

Authorized

↓

Captured

↓

Settled

↓

Completed
```

Failure paths include:

```text
Created

↓

Failed

↓

Cancelled
```

Refunds create additional states.

---

# Why State Machines?

Without clear states,

the system cannot answer:

- Has the customer paid?
- Has money been captured?
- Has settlement completed?

State machines simplify recovery and reconciliation.

# The Double Payment Problem

Suppose Alice clicks:

```text
Pay Now
```

Nothing happens.

She clicks again.

```text
Pay Now

↓

Pay Now
```

Did she pay twice?

If the gateway creates two transactions,

the customer may be charged twice.

This is unacceptable.

---

# Idempotency

The solution is **Idempotency**.

Each payment request includes a unique key.

Example:

```text
Idempotency-Key

=

abc123xyz
```

If the same request arrives again,

the gateway returns the previous result instead of processing it again.

---

# Idempotent Flow

```text
Payment Request

↓

Check Idempotency Key

↓

Already Processed?

      │

 Yes ─┴──► Return Existing Result

 No

↓

Process Payment
```

This guarantees:

> **One customer action produces one payment.**

---

# Ledger

A ledger is the financial source of truth.

Every money movement becomes an immutable record.

Example:

| Account | Debit | Credit |
|----------|-------|--------|
| Customer | $100 | |
| Merchant | | $100 |

Money is never updated in place.

Instead,

new ledger entries are appended.

---

# Why Not Update Balances Directly?

Suppose we simply change:

```text
Balance

1000

↓

900
```

What if the server crashes?

We lose auditability.

Instead,

financial systems store every transaction permanently.

This makes reconciliation and auditing possible.

---

# Double-Entry Accounting

Every transaction has equal debit and credit.

```text
Customer

Debit

$100

↓

Merchant

Credit

$100
```

This guarantees that money is neither created nor destroyed inside the ledger.

# Design Decisions

| Problem | Solution |
|----------|----------|
| Duplicate Payments | Idempotency |
| Money Tracking | Ledger |
| Secure Routing | Payment Gateway |
| Authorization | Issuing Bank |
| Fund Transfer | Capture |
| Payment Lifecycle | State Machine |

# Real-World Example

Imagine buying coffee with a credit card.

The cashier first checks whether your bank will approve the payment.

That's **authorization**.

Later,

the coffee shop submits all approved transactions to actually receive the money.

That's **capture and settlement**.

Online payment gateways follow the same principle.

---

# Interview Tips

Interviewers often ask:

> **"How do you prevent charging a customer twice if they click the payment button multiple times?"**

A strong answer is:

> "Every payment request carries an idempotency key generated by the client or merchant. Before creating a transaction, the gateway checks whether that key has already been processed. If it has, the gateway returns the existing payment result instead of creating a new transaction. This guarantees that repeated requests caused by retries, network failures, or double-clicks do not result in duplicate charges."

# Key Takeaways

- A payment gateway coordinates payment requests between merchants and financial institutions.
- Payments typically follow **Authorization → Capture → Settlement** rather than transferring money immediately.
- Every payment follows a well-defined state machine to simplify processing and recovery.
- Idempotency is essential to prevent duplicate charges caused by retries or repeated user actions.
- Financial systems rely on immutable ledgers and double-entry accounting for correctness and auditing.
- The gateway itself does not move money; it orchestrates communication between banks, processors, and networks.
- The next step is designing the production architecture with settlement, reconciliation, fraud detection, and high availability.
