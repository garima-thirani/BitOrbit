# Engineering Notes

## Modern NoSQL Databases Are Optimized for Sequential Writes

Systems

such as

Cassandra,

RocksDB,

LevelDB,

and

ScyllaDB

favor

append-only writes

because

sequential disk operations

are significantly faster

than random updates.

This design

enables

millions of writes

per second,

especially

on SSDs.

---

## Every Storage Engine Optimizes for Different Workloads

There is

no universally

best storage engine.

B+ Trees

excel

at transactional workloads

with

frequent point lookups

and updates.

LSM Trees

excel

at write-heavy workloads,

large datasets,

and distributed storage,

but require

background compaction

and

more complex reads.

# Interview Questions & Solutions

## Question 1

### Question

Why is Cassandra optimized for writes?

### Ideal Answer

Cassandra uses an LSM Tree storage engine where writes are appended to a commit log for durability and then stored in an in-memory MemTable. Data is later flushed sequentially to immutable SSTables. This append-only design minimizes random disk writes and delivers extremely high write throughput.

---

## Question 2

### Question

What problem do Bloom Filters solve?

### Ideal Answer

Bloom Filters quickly determine whether an SSTable cannot contain a requested key. This allows the database to skip unnecessary disk reads, significantly improving read performance when many SSTables exist.

---

## Question 3

### Question

Why are SSTables immutable?

### Ideal Answer

Immutable SSTables avoid expensive in-place updates and enable highly efficient sequential writes. Background compaction later merges files and removes obsolete or deleted data.

---

## Question 4

### Question

What is the difference between Bigtable and Spanner?

### Ideal Answer

Bigtable is a distributed NoSQL storage system optimized for scalability using tablets, whereas Spanner builds on similar storage concepts but adds SQL support, globally consistent transactions, Paxos-based replication, and TrueTime for externally consistent distributed transactions.

---

## Question 5 (FAANG)

### Question

Design the storage engine for a write-heavy telemetry platform receiving millions of events per second.

### Ideal Answer

Choose an LSM Tree–based storage engine such as Cassandra or RocksDB. Use a commit log for durability, MemTables for in-memory buffering, immutable SSTables for sequential disk writes, Bloom Filters to reduce read amplification, and background compaction to merge files efficiently. Replicate data across nodes using quorum-based writes and monitor compaction, SSTable count, and write amplification to maintain predictable performance.

# Revision Notes

- Bigtable introduced scalable tablet-based storage that influenced many distributed databases.
- Spanner extends Bigtable with SQL, Paxos replication, and TrueTime for globally consistent transactions.
- Dynamo introduced leaderless replication, quorum reads/writes, and consistent hashing.
- Cassandra combines Dynamo's replication model with Bigtable-inspired storage using LSM Trees.
- LSM Trees optimize write throughput through append-only writes, MemTables, SSTables, and background compaction.
- Bloom Filters minimize unnecessary disk reads, while compaction merges immutable files and removes obsolete data.
- Modern distributed databases choose storage engines based on workload characteristics rather than using a one-size-fits-all approach.
