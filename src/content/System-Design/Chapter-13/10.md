# Part 1 — Why Indexes Exist

## Problem

Without indexes

database

checks

every row.

```text
Query

↓

Row 1

↓

Row 2

↓

...

↓

Row N
```

Complexity

```
O(n)
```

---

## Solution

Indexes

provide

fast lookup.

```text
Query

↓

Index

↓

Pointer

↓

Row
```

---

## Benefits

✔ Faster reads

✔ Lower CPU

✔ Less disk I/O

✔ Better scalability

---

## Costs

✘ Extra storage

✘ Slower writes

✘ Maintenance overhead

---

# Full Table Scan

Reads

every row.

Good only for

- Tiny tables
- Large result sets
- Missing indexes

---

# Selectivity

High Selectivity

↓

Excellent index

Example

```text
Email

CustomerID
```

---

Low Selectivity

↓

Poor index

Example

```text
Gender

Status
```

# Part 2 — B-Trees & B+ Trees

## Why B+ Trees?

Binary Trees

↓

Too many levels.

---

B+ Trees

↓

High fan-out

↓

Few disk reads.

---

# B+ Tree Structure

```text
Root

↓

Internal Nodes

↓

Leaf Nodes

↓

Actual Row Pointers
```

---

# B+ Tree Advantages

✔ Balanced

✔ Sorted

✔ Range queries

✔ Sequential scans

✔ Few page reads

---

# B-Tree vs B+ Tree

| Feature | B-Tree | B+ Tree |
|----------|---------|----------|
| Data in Internal Nodes | Yes | No |
| Linked Leaves | No | Yes |
| Range Scan | Good | Excellent |
| Used by Databases | Rarely | Yes |

---

# Complexity

| Operation | Complexity |
|------------|------------|
| Search | O(log n) |
| Insert | O(log n) |
| Delete | O(log n) |

# Part 3 — Clustered vs Non-Clustered

## Clustered Index

Determines

physical row order.

Only

one

per table.

---

## Non-Clustered Index

Separate

B+ Tree.

Contains

key

+

pointer.

Many allowed.

---

# Comparison

| Clustered | Non-Clustered |
|------------|---------------|
| Physical order | Separate structure |
| One only | Many |
| Better range scan | Flexible lookup |
| Leaf = Data | Leaf = Pointer |

---

# Covering Index

Contains

everything

query needs.

No table lookup.

---

# Bookmark Lookup

↓

Result

# Leftmost Prefix Rule

Index

```text
(A,

B,

C)
```

Works for

✔ A

✔ A+B

✔ A+B+C

Not efficient for

✘ B

✘ C

alone.

# Part 5 — Other Index Types

## Hash Index

Best for

exact lookup.

```text
Key

↓

Hash

↓

Bucket
```

Cannot support

range queries.

---

## Bitmap Index

Best for

analytics

with

low-cardinality columns.

---

## Full-Text Index

Uses

Inverted Index.

Supports

✔ Keyword search

✔ Ranking

✔ Phrase search

---

## Prefix Index

Indexes

only

beginning

of values.

---

## Trigram Index

Supports

LIKE

and

fuzzy search.

---

# Index Selection

| Query | Best Index |
|---------|------------|
| ID Lookup | Hash / B+ Tree |
| Range | B+ Tree |
| Analytics | Bitmap |
| Text Search | Full-Text |
| LIKE '%abc%' | Trigram |

# Top 40 FAANG Revision Facts

1. Indexes reduce search time.
2. Full Table Scan is O(n).
3. B+ Trees dominate relational databases.
4. High fan-out reduces tree height.
5. Linked leaf nodes optimize range scans.
6. Clustered indexes define physical row order.
7. Only one clustered index exists per table.
8. Non-clustered indexes store pointers.
9. Composite indexes support multi-column queries.
10. Leftmost Prefix Rule governs composite indexes.
11. Covering indexes avoid table lookups.
12. Included columns support covering indexes.
13. High-cardinality columns are better index candidates.
14. Hash indexes optimize equality lookups.
15. Bitmap indexes excel in analytics.
16. Full-text indexes rely on inverted indexes.
17. Trigram indexes accelerate fuzzy searches.
18. Prefix indexes reduce storage.
19. Cost-Based Optimizers evaluate multiple plans.
20. EXPLAIN reveals execution plans.
21. EXPLAIN ANALYZE measures actual execution.
22. Index Seek is preferred over Table Scan.
23. Nested Loop works well for small joins.
24. Hash Join handles large unsorted joins.
25. Merge Join requires sorted inputs.
26. Statistics guide execution plans.
27. Histograms model data distribution.
28. Accurate cardinality estimates are essential.
29. SARGable queries maximize index usage.
30. Avoid functions on indexed columns.
31. EXISTS often outperforms IN on large subqueries.
32. Keyset pagination scales better than OFFSET.
33. UNION ALL is faster than UNION.
34. Window functions enable advanced analytics.
35. Materialized views accelerate reporting.
36. VACUUM removes dead tuples.
37. Fragmentation slows index performance.
38. Rebuild recreates indexes completely.
39. Slow query logs identify bottlenecks.
40. Monitor execution plans continuously.
