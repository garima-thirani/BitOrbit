# Introduction

One of the biggest mistakes candidates make during System Design interviews is trying to memorize architectures.

They remember

- Instagram uses Redis.
- Uber uses Kafka.
- Netflix uses Cassandra.
- YouTube uses CDN.

But when interviewers ask

> **Why?**

they cannot explain the reasoning.

Senior engineers rarely memorize architectures.

Instead,

they use **decision trees**.

A decision tree is a systematic framework that helps engineers select the most appropriate technology or architecture based on requirements and constraints.

Throughout this handbook, you've learned dozens of technologies.

Now it's time to learn **when** and **why** to use them.

---

# What is an Architecture Decision Tree?

An Architecture Decision Tree is a sequence of questions that guides architectural choices.

Instead of asking

> "Should I use Redis?"

you ask

> "Do I actually need a cache?"

If yes,

then

> "What kind of cache should I use?"

This approach prevents unnecessary complexity.

---

# Real-Life Analogy

Imagine a doctor diagnosing a patient.

The doctor doesn't immediately prescribe medicine.

Instead,

they ask questions.

- What are the symptoms?
- How severe are they?
- How long have they existed?
- Are there underlying conditions?

Only after gathering information do they recommend treatment.

System Design follows the same principle.

Requirements drive architecture.

---

# The Universal System Design Decision Tree

Every design problem should begin with the same sequence of questions.

```text
Understand Requirements
          │
          ▼
Estimate Scale
          │
          ▼
Identify Bottlenecks
          │
          ▼
Choose Architecture
          │
          ▼
Select Components
          │
          ▼
Validate Trade-offs
          │
          ▼
Production Considerations
```

This framework works for almost every interview.

---

# Step 1 — Understand the Requirements

Never start drawing architecture immediately.

Ask questions.

Examples include:

- Who are the users?
- What problem are we solving?
- Is the system read-heavy or write-heavy?
- Is low latency important?
- Is strong consistency required?
- Are there global users?
- Is real-time communication required?

Without requirements,

there is no correct architecture.

---

# Example

Suppose the interviewer says

> Design a Notification Service.

Do not immediately start drawing Kafka.

Instead ask

- Email only?
- Push notifications?
- SMS?
- Millions of users?
- Delivery guarantees?
- Retry requirements?

These answers completely change the architecture.

---

# Step 2 — Estimate the Scale

Before choosing technologies,

estimate

- Daily Active Users
- Queries Per Second (QPS)
- Storage
- Bandwidth
- Peak Traffic

Scale determines architecture.

---

# Example

Suppose

100 users/day

A single server

may be enough.

Now suppose

100 million users/day.

You immediately begin thinking about

- Load Balancers
- Horizontal Scaling
- Redis
- Sharding
- Kafka
- CDN

The same application

requires a completely different architecture.

---

# Step 3 — Identify the Primary Bottleneck

Every distributed system has a bottleneck.

Your goal is to identify it early.

Common bottlenecks include

- Database
- Network
- CPU
- Memory
- Disk I/O
- External APIs

---

# Example

A URL Shortener

typically has

far more reads

than writes.

The bottleneck

is database read traffic.

The solution?

Introduce

Redis

before scaling the database.

---

Now decide

# Step 5 — Select the Right Components

After choosing the architecture,

select the technologies.

Think of this as assembling building blocks.

```text
Database

↓

Cache

↓

Message Queue

↓

Storage

↓

API

↓

Deployment

↓

Monitoring
```

Each choice should solve a specific problem.

---

# Example

A social media feed might require

- PostgreSQL for metadata
- Redis for caching
- Kafka for asynchronous processing
- Elasticsearch for search
- S3 for media
- Kubernetes for deployment

Each component has a clear purpose.

---

# Step 6 — Validate Trade-offs

Every technology has advantages

and disadvantages.

Ask yourself

- What problem does this solve?
- What new complexity does it introduce?
- Is there a simpler alternative?

Interviewers care more about reasoning

than the final answer.

---

# Real-Life Example

Suppose you choose

Kafka.

Expect follow-up questions.

Why Kafka?

Why not RabbitMQ?

Why not SQS?

Can ordering be relaxed?

What happens if a broker fails?

Good candidates explain the trade-offs.

# Key Takeaways

- Architecture decisions should always be driven by requirements, not by technology popularity.
- A structured decision-making process is more valuable than memorizing complete architectures.
- Every System Design interview should begin with requirement gathering and capacity estimation.
- Identify the primary bottleneck before selecting technologies.
- Architecture choices should be validated by understanding their trade-offs.
- Decision trees simplify complex design problems by breaking them into smaller questions.
- Technologies such as SQL, NoSQL, Redis, Kafka, Elasticsearch, Kubernetes, and Vector Databases each solve specific problems and should only be introduced when those problems exist.
- Thinking systematically like a Senior or Staff Engineer is one of the most valuable skills in System Design interviews.
- The next part introduces **Technology Comparison Matrices**, helping you confidently choose between commonly compared technologies such as **SQL vs NoSQL, Redis vs Memcached, RabbitMQ vs Kafka, REST vs GraphQL vs gRPC, Docker vs Kubernetes, and Monolith vs Microservices**.
