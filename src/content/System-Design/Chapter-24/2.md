# Introduction

One of the most common interview questions is not

> Design Instagram.

Instead,

it is often

> Why Redis instead of Memcached?

or

> Why Kafka instead of RabbitMQ?

or

> Why GraphQL instead of REST?

Interviewers ask these questions because they want to understand your decision-making process.

Good engineers know many technologies.

Great engineers know **when not to use them.**

Throughout this handbook, you've learned many databases, messaging systems, APIs, deployment platforms, and architectural styles.

This chapter consolidates them into comparison matrices that help you quickly choose the right tool.

---

# Comparison Framework

Whenever comparing two technologies, evaluate them using the same dimensions.

- Purpose
- Data Model
- Performance
- Scalability
- Consistency
- Complexity
- Best Use Cases
- Limitations

This structured comparison demonstrates mature architectural thinking.

# SQL vs NoSQL

Both SQL and NoSQL databases store data.

The difference lies in **how** they organize it and **what problems they optimize for.**

---

## SQL

Relational databases organize information into tables with predefined schemas.

Example databases

- PostgreSQL
- MySQL
- SQL Server
- Oracle

---

## NoSQL

NoSQL databases provide flexible schemas and are optimized for scale and availability.

Examples include

- MongoDB
- Cassandra
- DynamoDB
- Redis

---

## Comparison

| Feature | SQL | NoSQL |
|----------|-----|--------|
| Schema | Fixed | Flexible |
| Relationships | Excellent | Limited |
| Horizontal Scaling | Harder | Easier |
| ACID | Strong | Often BASE |
| Joins | Yes | Usually No |
| Transactions | Excellent | Limited |
| Consistency | Strong | Often Eventual |

---

## Use SQL When

- Banking
- Payments
- Inventory
- ERP
- CRM
- Order Management

---

## Use NoSQL When

- Social Networks
- IoT
- Logging
- User Sessions
- Analytics
- Large-scale Applications

---

## Real-Life Example

Amazon Orders

↓

SQL

because

transactions matter.

Instagram Feed

↓

NoSQL

because

scale matters more than joins.

# Redis vs Memcached

Both are in-memory caching systems.

However,

they solve different problems.

---

## Redis

Redis is an in-memory data structure server.

Supports

- Strings
- Lists
- Sets
- Sorted Sets
- Hashes
- Pub/Sub
- Streams

---

## Memcached

Memcached is a very simple

key-value cache.

Nothing more.

---

## Comparison

| Feature | Redis | Memcached |
|----------|--------|-----------|
| Persistence | Yes | No |
| Replication | Yes | No |
| Data Structures | Rich | Key-Value Only |
| Pub/Sub | Yes | No |
| Transactions | Yes | No |
| Performance | Excellent | Slightly Faster for Simple Cache |

---

## Use Redis When

- Session Store
- Leaderboards
- Pub/Sub
- Distributed Cache
- Rate Limiting

---

## Use Memcached When

- Very Simple Cache
- Read-heavy Applications
- Temporary Objects

---

## Real-Life Example

A gaming leaderboard

requires

Sorted Sets.

Only Redis supports this naturally.

# RabbitMQ vs Kafka

Both move messages.

But they were built for different workloads.

---

## RabbitMQ

Designed as a traditional

Message Queue.

Focuses on

- Reliable delivery
- Flexible routing
- Task processing

---

## Kafka

Designed as an

Event Streaming Platform.

Focuses on

- High throughput
- Ordered logs
- Replay
- Streaming

---

## Comparison

| Feature | RabbitMQ | Kafka |
|----------|-----------|--------|
| Message Model | Queue | Log |
| Ordering | Queue-level | Partition-level |
| Replay | No | Yes |
| Throughput | High | Extremely High |
| Persistence | Optional | Built-in |
| Consumers | Remove Messages | Read by Offset |

---

## Use RabbitMQ When

- Background Jobs
- Email Queue
- Payment Processing
- Task Scheduling

---

## Use Kafka When

- Event Streaming
- Clickstream Analytics
- Logs
- Real-time Pipelines
- Microservices Events

---

## Real-Life Example

Password Reset Email

↓

RabbitMQ

User Activity Stream

↓

Kafka

# REST vs GraphQL vs gRPC

These are communication protocols.

Each serves different needs.

---

## REST

Resource-oriented APIs

based on HTTP.

Most common API style.

---

## GraphQL

Clients specify

exactly

which fields they need.

---

## gRPC

Binary protocol

built on HTTP/2

optimized for

internal service communication.

---

## Comparison

| Feature | REST | GraphQL | gRPC |
|----------|------|----------|-------|
| Transport | HTTP | HTTP | HTTP/2 |
| Data Format | JSON | JSON | Protobuf |
| Performance | Good | Good | Excellent |
| Browser Friendly | Yes | Yes | Limited |
| Streaming | Limited | Limited | Native |

---

## Use REST When

- Public APIs
- CRUD Applications
- Simplicity

---

## Use GraphQL When

- Mobile Apps
- Complex UI
- Flexible Queries

---

## Use gRPC When

- Microservices
- Internal APIs
- High Performance
- Streaming

---

## Real-Life Example

Mobile App

↓

GraphQL

Microservice Communication

↓

gRPC

Public API

↓

REST

# Docker vs Kubernetes

These technologies

are often confused.

They solve different problems.

---

## Docker

Docker packages applications

into containers.

---

## Kubernetes

Kubernetes manages

thousands of containers.

---

## Comparison

| Feature | Docker | Kubernetes |
|----------|---------|------------|
| Creates Containers | Yes | No |
| Runs Containers | Yes | Yes |
| Scheduling | Limited | Advanced |
| Scaling | Manual | Automatic |
| Self Healing | No | Yes |
| Load Balancing | Basic | Built-in |

---

## Use Docker When

- Development
- Small Deployments
- Local Testing

---

## Use Kubernetes When

- Production
- Large Scale
- Microservices
- High Availability

---

## Real-Life Example

One Restaurant

↓

Docker

Entire Food Delivery Network

↓

Kubernetes

# Monolith vs Microservices

Every large application eventually faces this decision.

---

## Monolith

One application.

One deployment.

One database.

---

## Microservices

Multiple independently deployable services.

Each owns

its own data.

---

## Comparison

| Feature | Monolith | Microservices |
|----------|-----------|---------------|
| Deployment | Single | Independent |
| Scaling | Entire App | Individual Services |
| Complexity | Low | High |
| Development | Easier | Harder |
| Fault Isolation | Poor | Excellent |

---

## Use Monolith When

- Startups
- MVPs
- Small Teams
- Simple Products

---

## Use Microservices When

- Large Teams
- Independent Scaling
- Multiple Domains
- Continuous Deployment

---

## Real-Life Example

A neighborhood grocery store

is easier to manage

as one shop.

A multinational supermarket chain

requires

specialized departments.

That is the difference

between

Monolith

and

Microservices.

# Interview Tips

When comparing technologies,

never say

> Technology A is better.

Instead,

say

> Technology A is better **for this use case because...**

Every technology is a trade-off.

Interviewers evaluate your reasoning,

not your preference.

---

# Key Takeaways

- Technology selection should always be driven by requirements.
- SQL excels at consistency and relationships, while NoSQL excels at scalability and flexibility.
- Redis is a feature-rich in-memory data store, whereas Memcached is a lightweight cache.
- RabbitMQ is optimized for reliable task queues, while Kafka is designed for high-throughput event streaming.
- REST is ideal for public APIs, GraphQL for flexible client queries, and gRPC for high-performance internal communication.
- Docker packages applications into containers, while Kubernetes orchestrates and manages them at scale.
- Monoliths are ideal for smaller systems and teams, whereas Microservices enable independent scaling and deployment for large organizations.
- During interviews, explain **why** a technology fits the problem instead of simply stating that it is better.
