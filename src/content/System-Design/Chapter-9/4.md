# Story – The Shared Database Disaster

A company successfully migrated its monolith into six Microservices.

They proudly announced

```
Orders Service

Payments Service

Inventory Service

Shipping Service

Catalog Service

Notification Service
```

Everyone celebrated.

Until someone looked at the architecture.

```text
Orders

Payments

Inventory

Shipping

Catalog

Notifications

↓

One Database
```

The services were independent.

The data wasn't.

Nothing had actually changed.

The company had built

**a distributed monolith.**

# Why Data is the Hardest Problem

Splitting code

is relatively easy.

Splitting data

is extremely difficult.

Every business capability

needs data.

Example

Order Service needs

- Customer
- Inventory
- Payment
- Shipping

Question

Should it directly query

everyone else's database?

Absolutely not.

# Database per Service

One of the most fundamental Microservice principles.

Every service owns

its own database.

Architecture

```text
Orders

↓

Orders DB

--------------------

Payments

↓

Payments DB

--------------------

Inventory

↓

Inventory DB

--------------------

Shipping

↓

Shipping DB
```

Ownership

creates independence.

# Why Ownership Matters

Suppose

Payment Team

changes

its schema.

If Orders directly queries

Payment tables,

Orders breaks.

Instead

Orders communicates

through APIs

or Events.

---

# Shared Database Anti-pattern


# Engineering Notes

## Why Database per Service Exists

Many engineers believe

Microservices are about splitting code.

In reality,

they're about

splitting ownership.

Database ownership

is what enables

independent deployment,

schema evolution,

and team autonomy.

Without it,

services remain tightly coupled.

---

## Accepting Temporary Inconsistency

Engineers transitioning from monoliths often struggle with eventual consistency.

Remember:

Users usually care more about

fast responses

than

instant synchronization.

For example,

it's acceptable if

"Your order has shipped"

appears

two seconds later,

provided the order itself was placed successfully.

# Interview Questions & Solutions

## Question 1

### Question

Why should each Microservice own its database?

### Ideal Answer

Owning the database ensures independent schema evolution, deployments, security, and scaling. Other services communicate through APIs or events rather than direct database access, reducing coupling.

---

## Question 2

### Question

What is the Shared Database anti-pattern?

### Ideal Answer

Multiple services sharing the same database create tight coupling, coordinated deployments, schema conflicts, and hidden dependencies. It prevents true service independence.

---

## Question 3

### Question

What is Polyglot Persistence?

### Ideal Answer

Polyglot Persistence is the practice of using different database technologies for different workloads. For example, PostgreSQL for transactions, Elasticsearch for search, Redis for caching, and ClickHouse for analytics.

---

## Question 4

### Question

How do Microservices perform queries involving multiple services?

### Ideal Answer

Common approaches include API Composition, where an aggregator calls multiple services at request time, or CQRS projections, where events build precomputed read models optimized for the required query.

---

## Question 5 (FAANG)

### Question

Design the data architecture for Amazon Orders, Payments, Inventory, and Shipping.

### Ideal Answer

Each service owns its own database. Orders publish events after successful transactions. Inventory, Shipping, and Analytics consume these events asynchronously. Customer dashboards use CQRS projections instead of cross-service joins. Redis accelerates read-heavy workloads, Elasticsearch powers search, and historical events flow into a data lake for analytics.

# Revision Notes

- Every Microservice should own its database.
- Never perform cross-service SQL joins.
- Use APIs or events for communication.
- Choose databases based on workload (Polyglot Persistence).
- Use CQRS projections for complex queries.
- Accept eventual consistency where appropriate.
- Duplicate small amounts of data when it reduces coupling.
- Treat data ownership as a core architectural principle.
