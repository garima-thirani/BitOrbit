# Engineering Notes

## The "Golden Rule"

Use synchronous communication only when the caller **must** wait for the answer.

Everything else should be asynchronous if business requirements allow.

Example:

- Payment authorization → synchronous.
- Sending confirmation email → asynchronous.
- Updating analytics → asynchronous.
- Recommendation updates → asynchronous.

This minimizes latency while improving resilience.

---

## Avoid Distributed Monoliths

A common anti-pattern is a request flowing through many services synchronously:

```text
API

↓

Service A

↓

Service B

↓

Service C

↓

Service D

↓

Service E
```

If Service E is slow, the entire request becomes slow.

Limit synchronous dependency chains wherever possible.

# Interview Questions & Solutions

## Question 1

### Question

When should you choose REST over Kafka?

### Ideal Answer

Use REST when the caller requires an immediate response, such as payment authorization or user authentication. Use Kafka when downstream processing can occur asynchronously, such as analytics, notifications, recommendations, or audit logging.

---

## Question 2

### Question

Why do companies use gRPC internally?

### Ideal Answer

gRPC uses Protocol Buffers and HTTP/2, making it faster and more efficient than JSON-based REST. It reduces serialization overhead, supports streaming, and is well suited for low-latency service-to-service communication.

---

## Question 3

### Question

What problem does Backend for Frontend (BFF) solve?

### Ideal Answer

Different clients often require different APIs. A BFF provides client-specific endpoints optimized for web, mobile, or TV applications, reducing unnecessary data transfer and simplifying frontend development.

---

## Question 4

### Question

What is API Composition?

### Ideal Answer

API Composition aggregates data from multiple services into a single response. It prevents clients from making numerous network requests and centralizes response assembly.

---

## Question 5 (FAANG)

### Question

Design the communication architecture for Amazon Checkout.

### Ideal Answer

Critical operations like payment authorization and inventory validation should use synchronous communication (REST or gRPC). Once the order is successfully created, publish an `OrderCreated` event to Kafka. Independent consumer groups process shipping, notifications, analytics, recommendations, warehouse updates, and fraud detection asynchronously. This minimizes checkout latency while enabling scalable background processing.

# Revision Notes

- Synchronous communication is best for immediate business decisions.
- Asynchronous communication improves scalability and resilience.
- REST is ideal for public APIs.
- gRPC excels at internal service communication.
- Kafka distributes events to multiple independent consumers.
- API Composition reduces client-side complexity.
- Backend for Frontend tailors APIs for different client types.
- Minimize long synchronous dependency chains to avoid distributed monoliths.
