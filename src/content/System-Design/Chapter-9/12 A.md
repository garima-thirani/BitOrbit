# Why Transactional Outbox?

Suppose

Database write succeeds.

Kafka publish fails.

Without Outbox

Order exists.

Nobody knows about it.

Inventory never reserves stock.

Customer never receives shipment.

---

Transactional Outbox guarantees

```
Database Commit

+

Event Publish
```

remain consistent.

Amazon's architecture demonstrates that Event-Driven systems are designed to optimize user experience.

Everything else is delegated to asynchronous consumers.

# Production Case Study 2

# Uber Ride Platform

---

# Problem Statement

Design Uber's backend supporting

- Millions of drivers
- Hundreds of millions of passengers
- Millions of rides/day
- Real-time location updates
- Dynamic pricing
- Fraud detection
- Driver earnings
- Heat maps
- Recommendations

The system must respond within seconds while continuously processing location and ride events.

---

# Functional Requirements

Passengers should be able to

- Request rides
- Cancel rides
- Track drivers
- Pay fares
- Rate drivers

Drivers should be able to

- Accept rides
- Navigate
- Complete trips
- Receive payments

Internal systems should

- Calculate surge pricing
- Detect fraud
- Generate receipts
- Produce heat maps
- Update demand forecasts

---

# High-Level Architecture

```text
Passenger App

        │

API Gateway

        │

Ride Service

        │

Ride Database

        │

Transactional Outbox

        │

Kafka

────────────────────────────────────────

Driver Matching

Pricing

Payments

Driver Earnings

Fraud Detection

Notifications

Maps

Analytics

Machine Learning

Customer Timeline
```

Unlike Amazon,

Uber also ingests continuous GPS updates, making it one of the highest event-volume platforms in the world.

---

# Ride Lifecycle

```text
RideRequested

↓

DriverMatched

↓

DriverAccepted

↓

DriverArrived

↓

RideStarted

↓

LocationUpdated (many times)

↓

RideCompleted

↓

PaymentCompleted

↓

ReceiptGenerated

↓

DriverRated

↓

PassengerRated
```

Everything after the initial request is represented as immutable events.

---

# Why Event-Driven?

A completed ride immediately triggers:

- Billing
- Driver earnings
- Fraud analysis
- Customer receipts
- Analytics
- Surge model updates
- Heat-map generation
- ML feature updates

None of these systems should delay the passenger's experience.

---

# Kafka Topic Design

Typical topics include:

```text
rides

locations

pricing

payments

drivers

notifications

analytics
```

Location updates are isolated because they generate extremely high throughput.

---

# Partition Strategy

Ride-related events

↓

Partition by

```
Ride ID
```

Location events

↓

Partition by

```
Driver ID
```

This preserves ordering while distributing load.

---

# CQRS Usage

Write Model

```text
Ride Service

↓

PostgreSQL
```

Read Models

```text
Driver Dashboard

Passenger Timeline

Operations Dashboard

Heat Maps

Pricing Dashboard
```

Each dashboard is independently projected from ride events.
