# Engineering Notes

## Exactly-Once is Often a Business Requirement, Not a Technical Requirement

Many systems

do not actually

need

exactly-once processing.

If consumers

At-Least-Once delivery

is usually

Reserve

Exactly-Once

for

billing,

or inventory

workloads

## Event Time Produces More Accurate Results

Distributed systems

Using

Event Time

and monitoring.

# Interview Questions & Solutions

## Question 1

### Question

What is the difference between Batch Processing and Stream Processing?

### Ideal Answer

Batch processing collects data and processes it periodically, making it suitable for reports and ETL. Stream processing handles events continuously as they arrive, enabling low-latency applications such as fraud detection, monitoring, and recommendations.

---

## Question 2

### Question

What is the difference between Stateless and Stateful processing?

### Ideal Answer

Stateless processing treats each event independently without retaining history. Stateful processing maintains information from previous events, enabling operations such as running totals, session tracking, joins, and aggregations.

---

## Question 3

### Question

Why are Watermarks used?

### Ideal Answer

Watermarks define how long a stream processor waits for late-arriving events before finalizing a window. They balance result accuracy against processing latency.

---

## Question 4

### Question

Explain At-Most-Once, At-Least-Once, and Exactly-Once processing.

### Ideal Answer

At-Most-Once may lose messages but never duplicates them. At-Least-Once guarantees no message loss but may process duplicates. Exactly-Once guarantees that each message is processed exactly one time, avoiding both loss and duplication, typically through transactions and checkpointing.

---

## Question 5 (FAANG)

### Question

Design a real-time fraud detection pipeline for a global payment system.

### Ideal Answer

Publish payment events to Kafka, process them using Apache Flink with stateful operators and event-time windows, maintain customer transaction history in a state store, use watermarks to accommodate late events, checkpoint processor state for recovery, emit fraud alerts to downstream services, and use exactly-once processing for critical financial updates or idempotent consumers with at-least-once delivery where appropriate.

# Revision Notes

- Stream processing analyzes events continuously rather than waiting for batches.
- Stateful processing enables aggregations, joins, and running calculations.
- Tumbling, sliding, and session windows support different analytical needs.
- Watermarks manage late-arriving events using event time.
- Checkpointing allows processors to recover after failures.
- At-least-once delivery combined with idempotent consumers is often sufficient.
- Exactly-once processing is reserved for workloads where duplicate processing cannot be tolerated.
