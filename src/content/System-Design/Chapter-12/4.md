# Why Cache Invalidation Exists

A cache

```text
Database

↓

Copy

↓

Cache
```

Whenever

the database changes,

the cache

must eventually

change too.

# What is Stale Data?

Stale data

means

Example

```text
Database

↓

Balance = $500

------------

Cache

↓

Balance = $700
```

Cache

---

# Source of Truth

Always remember:

```text
Database

↓

Source of Truth
```

Cache

only

---

# Cache Consistency

Consistency means

the cache

matches

the database.

Higher consistency

usually means

higher complexity.

---

# Strong Consistency

Every read

returns

the latest value.

```text
Write

↓

Database

↓

Cache

↓

Read
```

No stale reads.

---

# Eventual Consistency

Updates

propagate

later.

For a short time,

old values

may still exist.

Eventually,

everything

becomes consistent.

---

# Comparison

| Strong | Eventual |
|---------|----------|
| Latest data | May be stale |
| Slower | Faster |
| More coordination | Better scalability |

# Engineering Notes

## Cache Invalidation is a Distributed Systems Problem

In a single server,

invalidating

one cache entry

is easy.

In production,

the same data

may exist

in

browser caches,

CDNs,

application memory,

Redis clusters,

and regional replicas.

Keeping

all copies

synchronized

requires

careful system design.

---

## Most Systems Prefer Delete Over Update

Although

updating

the cache

appears faster,

many production systems

simply delete

the cached value

after a write.

The next read

rebuilds

the cache

from

the database,

reducing

the risk

of inconsistent updates.

This is why

Cache-Aside

is so popular.

# Interview Questions & Solutions

## Question 1

### Question

Why is cache invalidation considered difficult?

### Ideal Answer

Because cached data exists in multiple locations and must remain synchronized with the database despite concurrent writes, network delays, failures, and distributed deployments. Ensuring freshness without sacrificing performance is a fundamental distributed systems challenge.

---

## Question 2

### Question

What is the difference between Write Invalidate and Write Update?

### Ideal Answer

Write Invalidate removes the cached entry after updating the database, allowing the next read to reload fresh data. Write Update updates both the database and cache immediately, reducing future cache misses but requiring coordinated writes.

---

## Question 3

### Question

What is stale data?

### Ideal Answer

Stale data is cached information that no longer reflects the latest value stored in the database because the cache has not yet been updated or invalidated.

---

## Question 4

### Question

Why are version numbers useful in distributed caches?

### Ideal Answer

Version numbers prevent older updates from overwriting newer values when updates arrive out of order. Consumers can compare versions and ignore stale updates.

---

## Question 5 (FAANG)

### Question

Design the cache invalidation strategy for a global e-commerce platform.

### Ideal Answer

Use Cache-Aside with write invalidation for product data. After every database update, publish an invalidation event through Kafka to all cache clusters. Apply version numbers to prevent stale updates, configure TTL as a safety mechanism, monitor invalidation latency and stale-read rates, and synchronize regional Redis clusters using event-driven propagation. This approach balances scalability, simplicity, and consistency.

# Revision Notes

- The database is the source of truth; the cache is only a temporary copy.
- Stale data occurs when cache values no longer match the database.
- Strong consistency prioritizes correctness, while eventual consistency prioritizes scalability.
- Write Invalidate (Cache-Aside) is the most common production strategy.
- Event-driven invalidation scales well across distributed systems.
- Versioning prevents stale updates from overwriting newer values.
- Multi-layer caches require coordinated invalidation and monitoring to remain consistent.
