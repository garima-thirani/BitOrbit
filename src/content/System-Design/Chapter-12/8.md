# Engineering Notes

## Stampedes Are Synchronization Problems

A cache stampede

is not caused

by

slow databases.

It is caused

by

many requests

performing

the same expensive work

at the same time.

Preventing

duplicate work

is usually

more effective

than simply

adding

more database servers.

---

## Bloom Filters Protect Databases Efficiently

Without

a Bloom Filter,

every invalid request

must reach

the database.

With

a Bloom Filter,

most invalid requests

are rejected

using

just a few bits

of memory,

making it

one of the most

cost-effective

defenses

against

cache penetration attacks.

# Interview Questions & Solutions

## Question 1

### Question

What is a cache stampede?

### Ideal Answer

A cache stampede occurs when many requests simultaneously encounter an expired cache entry and all attempt to rebuild it by querying the database, causing a sudden spike in backend load.

---

## Question 2

### Question

How can you prevent a cache avalanche?

### Ideal Answer

Use randomized TTL values to stagger expirations, replicate cache nodes for availability, preload frequently accessed data, and employ multiple cache layers so that the simultaneous expiration of many entries does not overwhelm the database.

---

## Question 3

### Question

What is cache penetration?

### Ideal Answer

Cache penetration occurs when repeated requests target data that does not exist. Since the cache cannot satisfy these requests, they repeatedly hit the database. Solutions include caching null results and using Bloom Filters.

---

## Question 4

### Question

Why are Bloom Filters useful?

### Ideal Answer

Bloom Filters efficiently determine whether a key definitely does not exist, allowing systems to reject invalid requests before reaching the database. They use very little memory and guarantee no false negatives.

---

## Question 5 (FAANG)

### Question

Design a caching strategy that can survive Black Friday traffic without overwhelming the database.

### Ideal Answer

Deploy a multi-level cache consisting of browser cache, CDN, Redis Cluster, and local application cache. Use Cache-Aside with randomized TTLs, refresh popular entries proactively, protect cache rebuilds with distributed mutex locks, coalesce duplicate requests, cache null values for missing records, apply Bloom Filters to reject invalid keys, replicate hot objects, and monitor cache hit ratio, lock contention, and hot keys. Configure graceful degradation to serve slightly stale data during cache failures and protect the database with circuit breakers.

# Revision Notes

- Cache stampedes occur when many requests rebuild the same expired cache entry.
- Cache avalanches happen when many cache entries expire or fail simultaneously.
- Cache penetration results from repeated requests for nonexistent data.
- Mutex locks and request coalescing prevent duplicate cache rebuilds.
- Randomized TTLs and refresh-ahead reduce synchronized expirations.
- Bloom Filters efficiently reject invalid requests before they reach the database.
- Multi-level caching and hot key mitigation improve resilience during traffic spikes.
