# Introduction

We learned about

- Producers
- Brokers

- Partitions
- Leaders
- Followers
- Replication
- ISR

However, one important question remains.

> **How does Kafka actually store millions of events every second while remaining so fast?**

Unlike traditional message queues,

Kafka does **not** treat messages as individual objects that are constantly inserted and removed.

Instead,

Kafka treats every partition as a continuously growing **log file**.

This simple design decision is one of the biggest reasons Kafka can process millions of events per second.

---

# Kafka as a Distributed Commit Log

The easiest way to understand Kafka is to stop thinking about it as a queue.

Instead,

think of it as an **append-only log file**.

---

## Real-Life Analogy

Imagine writing in a diary.

Every day you add a new page.

```text
Day 1

↓

Day 2

↓

Day 3

↓

Day 4
```

You never insert pages in the middle.

You never reorder pages.

You simply keep writing at the end.

Kafka follows exactly the same principle.

Events are **always appended** to the end of a partition.

---

# Append-Only Storage

Suppose users place orders.

Instead of modifying previous records,

Kafka simply appends new events.

```text
Partition 0

Offset 0

Order Created
```

↓

```text
Offset 1

Payment Completed
```

↓

```text
Offset 2

Order Shipped
```

↓

```text
Offset 3

Order Delivered
```

Nothing is deleted immediately.

Nothing is overwritten.

Everything is appended sequentially.

---

## Why Append-Only Is Fast

Imagine writing on paper.

Writing the next sentence is easy.

Finding an empty space in the middle of previous pages is difficult.

Similarly,

Hard disks and SSDs perform sequential writes much faster than random writes.

Kafka leverages this hardware characteristic.

This is one reason why Kafka achieves such high throughput.

---

# Log Segments

Suppose a partition receives billions of events.

Should Kafka store everything in one enormous file?

Imagine a

```text
20 TB
```

single log file.

Searching,

backing up,

or recovering it would be extremely inefficient.

Instead,

Kafka divides every partition into **Log Segments**.

---

## Example

```text
Partition 0

│

├── Segment 1

├── Segment 2

├── Segment 3

└── Segment 4
```

Each segment stores a fixed range of events.

When one segment becomes full,

Kafka creates another.

---

## Real-Life Analogy

Imagine a notebook.

Instead of using one notebook for your entire career,

you create

Notebook 1

↓

Notebook 2

↓

Notebook 3

↓

Notebook 4

Each notebook represents one Log Segment.

When a notebook becomes full,

you simply begin a new one.

---

# Segment Lifecycle

A partition grows like this.

```text
New Partition

↓

Segment 0

↓

Segment 1

↓

Segment 2

↓

Segment 3
```

Old segments remain unchanged.

New events are always written only to the latest segment.

---

# Offsets

Every event inside a partition receives a unique number called an **Offset**.

Example

```text
Partition

Offset 0

User Registered
```

↓

```text
Offset 1

Order Created
```

↓

```text
Offset 2

Payment Completed
```

↓

```text
Offset 3

Notification Sent
```

Offsets are unique **within a partition**.

They are not global across Kafka.

---

# Why Offsets Matter

Suppose a consumer crashes after reading

```text
Offset 105
```

When it restarts,

should it begin again from the beginning?

Of course not.

Instead,

Kafka remembers

```text
Last Processed Offset

↓

105
```

The consumer resumes from

```text
106
```

No data is lost.

---

## Real-Life Analogy

Imagine watching a Netflix series.

After Episode 8,

you stop watching.

Netflix remembers

```text
Episode 8
```

The next day,

playback resumes from Episode 9.

Offsets work exactly the same way.

Kafka remembers where every consumer stopped reading.

---

# Consumer Groups

Suppose an Orders Topic receives

```
500,000 events per second
```

Can one consumer process everything?

Probably not.

Kafka allows multiple consumers to work together.

This collection is called a **Consumer Group**.

---

## Example

```text
Orders Topic

↓

Consumer Group

├── Consumer A

├── Consumer B

└── Consumer C
```

Instead of every consumer processing every message,

Kafka divides partitions among them.

---

# Partition Assignment

Suppose a topic has

```text
6 Partitions
```

and

```text
3 Consumers
```

Kafka distributes them.

```text
Consumer A

Partition 0

Partition 3
```

```text
Consumer B

Partition 1

Partition 4
```

```text
Consumer C

Partition 2

Partition 5
```

Every partition belongs to exactly one consumer within the same consumer group.

This prevents duplicate processing.

---

## Real-Life Analogy

Imagine three cashiers working in a supermarket.

Customers are divided among the cashiers.

Cashier A

↓

Lane 1

Lane 4

Cashier B

↓

Lane 2

Lane 5

Cashier C

↓

Lane 3

Lane 6

Each cashier handles only their assigned lanes.

Kafka partitions work similarly.

# Producer Internals

Earlier,

we said producers send events.

But how exactly?

Suppose an Order Service creates an event.

The producer performs several steps.

```text
Application

↓

Serializer

↓

Partition Selection

↓

Compression

↓

Batching

↓

Broker
```

---

## Serialization

Objects cannot be transmitted directly.

Kafka converts them into bytes.

Example

```json
{
"id":501,
"status":"PAID"
}
```

↓

Binary Data

Serialization reduces network overhead.

---

## Partition Selection

The producer decides which partition receives the event.

This can happen using

- Round Robin
- Hashing
- Message Keys

For example,

all events belonging to

```text
Order 501
```

may always go to

Partition 2,

preserving ordering.

---

## Batching

Instead of sending

1 message

↓

1 network request,

Kafka groups multiple messages together.

```text
Message

Message

Message

Message

↓

One Network Request
```

This significantly improves throughput.

---

# Consumer Internals

Consumers continuously poll Kafka.

```text
Consumer

↓

Poll()

↓

Receive Records

↓

Process Records

↓

Commit Offset
```

Unlike traditional queues,

Kafka does not push messages.

Consumers pull messages whenever they are ready.

---

## Why Pull Instead of Push?

Imagine drinking water.

Would you rather

control how much you drink,

or have someone continuously pour water into your mouth?

Obviously,

you want control.

Consumers work the same way.

They request messages when ready.

This prevents overload.

---

# Consumer Rebalancing

Suppose a new consumer joins the group.

Originally,

```text
Consumer A

Consumer B
```

After adding another consumer,

Kafka redistributes partitions.

```text
Consumer A

Consumer B

Consumer C
```

This process is called **Rebalancing**.

---

## Real-Life Analogy

Imagine four delivery drivers.

Each driver serves one neighborhood.

A fifth driver joins.

Instead of leaving one driver idle,

the company redistributes neighborhoods.

Everyone now has approximately equal work.

Kafka performs the same operation automatically.

---

# Backpressure

Sometimes producers generate events faster than consumers can process them.

Imagine

```text
Producer

↓

1,000,000 Events/Second
```

Consumers process

```text
300,000 Events/Second
```

The difference accumulates.

This situation is called **Backpressure**.

---

## Real-Life Analogy

Imagine pouring water into a funnel.

If water enters faster than it exits,

the funnel fills up.

Eventually,

it overflows.

Kafka avoids this by

- buffering events,
- batching writes,
- allowing consumers to process at their own pace,
- retaining events on disk.

Unlike traditional queues,

Kafka does not immediately discard unread messages.

---

# Complete Event Lifecycle

Suppose an e-commerce application creates an order.

The journey looks like this.

```text
Order Service
      │
      ▼
Producer
      │
      ▼
Serialization
      │
      ▼
Partition Selection
      │
      ▼
Broker
      │
      ▼
Append to Log Segment
      │
      ▼
Assign Offset
      │
      ▼
Replicate to Followers
      │
      ▼
Consumer Poll()
      │
      ▼
Process Event
      │
      ▼
Commit Offset
```

Every event follows this lifecycle.

---

# Real-World Example

Consider Uber.

When a ride is booked,

the Ride Service publishes an event.

Kafka appends it to a partition.

Several Consumer Groups independently process it.

- Driver Matching
- Pricing Engine
- Notifications
- Billing
- Analytics
- Fraud Detection

Each consumer tracks its own offsets.

If the Analytics service crashes,

it simply resumes from its last committed offset.

Other services continue unaffected.

This independence is one of Kafka's greatest strengths.

# Key Takeaways

- Kafka stores data as an **append-only distributed commit log**, making sequential writes extremely efficient.
- Every partition is divided into multiple **Log Segments**, allowing Kafka to manage massive datasets efficiently.
- Each event receives a unique **Offset** within its partition, enabling consumers to resume processing after failures.
- **Consumer Groups** distribute partitions among multiple consumers to achieve parallel processing.
- Producers serialize, batch, and route events before sending them to brokers.
- Consumers continuously **poll** Kafka for new events and commit offsets after processing.
- **Partition Assignment** ensures that each partition is processed by only one consumer within a consumer group.
- **Consumer Rebalancing** automatically redistributes partitions when consumers join or leave the group.
- Kafka handles **Backpressure** by storing events durably on disk and allowing consumers to process data at their own speed.
