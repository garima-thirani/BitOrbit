# Production Search Architecture

Regardless of the company,

most search systems follow this architecture.

```text
                 Data Sources
                      │
        ┌─────────────┼─────────────┐
        ▼             ▼             ▼
   Database      User Activity   External Data
        │             │             │
        └─────────────┼─────────────┘
                      ▼
              Event Streaming
                 (Kafka)
                      │
                      ▼
            Indexing Pipeline
                      │
                      ▼
          Elasticsearch Cluster
                      │
                      ▼
             Search API Service
                      │
                      ▼
                 User Query
```

Notice something important.

Users never search the primary database directly.

Instead,

search indexes are continuously updated from the source databases.

This architecture keeps transactional workloads and search workloads independent.

# Google Search Architecture

Google indexes hundreds of billions of web pages.

Scanning the web every time a user searches would be impossible.

Instead,

Google continuously crawls the internet.

---

## Step 1 — Crawling

Special programs called **Web Crawlers** (or spiders) visit web pages.

```text
Internet

↓

Crawler

↓

HTML Pages
```

The crawler downloads pages and sends them to the indexing pipeline.

---

## Step 2 — Indexing

Downloaded pages undergo

- Tokenization
- Normalization
- Language Detection
- Duplicate Removal
- Link Extraction

An inverted index is built.

---

## Step 3 — Ranking

When a user searches

```text
Distributed Systems
```

Google retrieves millions of candidate pages.

It then applies ranking algorithms such as

- BM25-like relevance
- Link analysis (PageRank)
- Freshness
- User behavior
- Personalization

The highest-ranked pages are returned.

---

## Real-Life Analogy

Imagine a librarian who reads every new book arriving at a library.

Instead of waiting for visitors to ask questions,

the librarian prepares a detailed catalog beforehand.

When someone asks,

"Books on Distributed Systems,"

the answer is almost instantaneous.

Google works in exactly the same way.

# Netflix Search

Searching movies appears simple,

but Netflix solves a much harder problem.

Suppose a user searches

```text
Batman
```

Should Netflix return only movies with "Batman" in the title?

No.

It also considers

- Actors
- Genres
- User preferences
- Watch history
- Region
- Language

Two users may receive completely different search results for the same query.

---

```text
Elasticsearch
      │
      ▼
Candidate Movies
      │
      ▼

      │
      ▼

```

Notice that search is only the first step.

Recommendation systems further personalize the results.

# Amazon Product Search

Amazon's search system differs from Google.

Customers usually have purchasing intent.

Searching

```text

```

must consider much more than keyword matching.

Amazon ranks products using signals such as

- BM25 relevance
- Sales history
- Product ratings
- Availability
- Delivery time
- Sponsored products
- Customer preferences

---

## Real-Life Analogy

Imagine entering a supermarket.

The most popular products are placed at eye level.

Rarely purchased products remain on lower shelves.

Amazon follows the same principle.

Products are ranked not only by textual relevance,

but also by business importance.

# Common Design Patterns

Although Google,

Netflix,

Amazon,

LinkedIn,

and GitHub solve different problems,

their architectures share several common patterns.

---

## Pattern 1 — Separate Search from Transactions

Primary Database

↓

Source of Truth

Search Index

↓

Fast Retrieval

Never use Elasticsearch as the primary database.

Instead,

build indexes from transactional data.

---

## Pattern 2 — Event-Driven Index Updates

Whenever data changes,

an event is published.

```text
Database

↓

Kafka

↓

Indexing Service

↓

Elasticsearch
```

The search index remains synchronized with the database.

---

## Pattern 3 — Distributed Indexes

Large indexes are divided into

- Shards
- Replicas

allowing

- Parallel Search
- Fault Tolerance
- Horizontal Scaling

---

## Pattern 4 — Multi-Stage Ranking

Ranking rarely relies on BM25 alone.

Instead,

companies combine

- BM25
- Personalization
- Popularity
- Business Rules
- Machine Learning Models

to produce final results.

---

## Pattern 5 — Caching

Popular searches are cached.

Example

```text
iPhone

MacBook

ChatGPT

Taylor Swift
```

Millions of users search for these terms.

Caching prevents repeated execution of identical queries.

# Search System Design Interview Tips

Search systems are a common topic in Staff and Senior-level interviews.

Interviewers often evaluate whether candidates understand **both search theory and production architecture**.

---

## Questions Frequently Asked

- Why not search directly from a relational database?
- Why does Elasticsearch use inverted indexes?
- Why are segments immutable?
- How does Elasticsearch scale horizontally?
- How do replicas improve availability?
- How does Kafka help keep search indexes synchronized?
- What happens when documents are updated?
- How would you design autocomplete?
- How would you support typo correction?
- How would you build a search system for billions of documents?

---

## Common Mistakes

### Using SQL for Full-Text Search

Databases are optimized for transactions,

not large-scale information retrieval.

---

### Ignoring Ranking

Finding matching documents is only the beginning.

Ranking often determines the quality of the search experience.

---

### Forgetting Synchronization

The database and search index must remain consistent.

Event-driven indexing using Kafka is the industry standard.

---

### No Caching

Popular queries should never execute repeatedly.

Caching significantly reduces latency.

---

### No Fault Tolerance

Production systems require

- Replication
- Sharding
- Monitoring
- Disaster Recovery

# Key Takeaways

- Modern search systems separate **transactional storage** from **search infrastructure**.
- Production search engines continuously build and update indexes using **event-driven pipelines**, often powered by Kafka.
- Elasticsearch provides distributed indexing and querying, while Lucene performs the underlying Information Retrieval operations.
- Large-scale search systems rely on **multi-stage ranking**, combining relevance algorithms with business rules, personalization, and machine learning.
- Horizontal scaling is achieved through **sharding**, while **replication** provides high availability and fault tolerance.
- Caching, monitoring, and asynchronous index updates are essential for achieving low latency at scale.
- Understanding search systems requires both theoretical knowledge (Information Retrieval) and practical knowledge (distributed architecture and production operations).
- The search architectures used by Google, Amazon, Netflix, LinkedIn, and GitHub differ in implementation details but share common design principles that appear frequently in System Design interviews.
