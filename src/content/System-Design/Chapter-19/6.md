# The Elasticsearch Indexing Pipeline

Suppose an e-commerce application receives a new product.

```json
{
  "id": 501,
  "name": "Wireless Mechanical Keyboard",
  "brand": "Keychron",
  "price": 120
}
```

The application sends this document to Elasticsearch.

Does Elasticsearch immediately write it into the search index?

No.

Instead,

the document passes through several stages.

```text
Client
   │
   ▼
REST API
   │
   ▼
Coordinating Node
   │
   ▼
Primary Shard
   │
   ▼
Memory Buffer
   │
   ▼
Lucene Segment
   │
   ▼
Replica Shards
```

Every stage exists for a reason.

---

# Step 1 — Client Sends the Document

The client sends an indexing request.

```http
POST /products/_doc
```

The request reaches any node in the cluster.

This node becomes the **Coordinating Node**.

The coordinating node does not necessarily store the document itself.

Instead,

it decides where the document belongs.

---

# Step 2 — Routing

Suppose our Products Index contains

```text
5 Primary Shards
```

How does Elasticsearch decide which shard stores the new document?

It computes a routing value.

Conceptually,

```text
Document ID

↓

Hash Function

↓

Shard Number
```

Example

```text
Product ID

501

↓

Hash

↓

Shard 3
```

Every document always belongs to one primary shard.

This keeps writes evenly distributed.

---

# Real-World Analogy

Imagine a courier company.

Every parcel arrives at a central warehouse.

The warehouse doesn't keep every package.

Instead,

it examines the destination ZIP code.

Packages are then routed to the appropriate regional warehouse.

Elasticsearch performs exactly the same operation using a hash function.

---

# Step 3 — Writing to Memory

Once the correct shard receives the document,

it is **not immediately written to disk**.

Instead,

it is placed inside an in-memory indexing buffer.

```text
Primary Shard

↓

Memory Buffer
```

Why?

Because writing to disk is expensive.

Writing one document at a time would significantly reduce throughput.

Instead,

Elasticsearch accumulates multiple writes before creating a new segment.

---

# Why Buffering Improves Performance

Imagine writing a notebook.

Suppose every sentence required saving the entire notebook to disk.

It would take forever.

Instead,

you write several paragraphs,

then save once.

Similarly,

Elasticsearch batches writes before creating immutable Lucene segments.

This dramatically improves indexing performance.

---

# Step 4 — Replication

Once the primary shard accepts the document,

it forwards the same write request to every replica.

```text
Primary Shard

↓

Replica A

↓

Replica B
```

Only after the required replicas acknowledge the write does Elasticsearch confirm success.

This ensures that multiple copies of the document exist.

# Search Query Flow

Now imagine a customer searches

```text
wireless keyboard
```

The query reaches the cluster.

How does Elasticsearch search billions of documents so quickly?

---

## Step 1 — Coordinating Node

The request first reaches a coordinating node.

```text
Client

↓

Node A
```

Node A now coordinates the entire search.

---

## Step 2 — Scatter Phase

The coordinating node sends the query to every shard.

```text
Coordinator

↓

Shard 1

Shard 2

Shard 3

Shard 4

Shard 5
```

Each shard searches independently.

---

# Real-Life Analogy

Imagine searching for a book inside a university.

The university has

- Engineering Library
- Medical Library
- Law Library
- Science Library

Instead of one librarian visiting every building,

each library searches simultaneously.

Afterwards,

every librarian reports back.

The head librarian combines the answers and gives you the best result.

That is exactly how Elasticsearch performs distributed search.

---

## Step 3 — Local Search

Each shard searches only its own documents.

Internally,

Lucene computes

- BM25 scores
- phrase matches
- fuzzy matches

Every shard returns only its highest-ranking documents.

Example

```text
Shard 1

Top 10 Results
```

```text
Shard 2

Top 10 Results
```

```text
Shard 3

Top 10 Results
```

---

## Step 4 — Gather Phase

The coordinating node receives results from every shard.

It merges them into one ranked list.

```text
Shard Results

↓

Merge

↓

Sort

↓

Top Results
```

Finally,

the response is returned to the client.

# Refresh

Now comes one of the most misunderstood concepts in Elasticsearch.

Suppose we index a document.

Should users immediately be able to search for it?

Intuitively,

yes.

Internally,

the answer is **not always**.

---

# Why Refresh Exists

Documents first enter the memory buffer.

They are not immediately visible to search.

Every few seconds,

Elasticsearch performs a **Refresh**.

Refresh creates a new searchable Lucene segment.

```text
Memory Buffer

↓

Refresh

↓

New Segment

↓

Searchable
```

Notice something important.

Refresh **does not** permanently save data.

It simply makes newly indexed documents visible to search.

---

# Real-Life Analogy

Imagine a newspaper office.

Journalists continuously write articles.

Readers cannot see unfinished articles.

Every morning,

the editor publishes a new newspaper edition.

Only then do readers see the new content.

Refresh is similar.

Documents exist,

but they become searchable only after the next "edition" is published.

---

# Flush

Refresh often causes confusion with Flush.

They solve different problems.

Refresh

↓

Makes documents searchable.

Flush

↓

Makes documents durable.

---

# What is Flush?

Elasticsearch maintains a **Transaction Log (Translog)**.

Every write is recorded there.

Eventually,

Elasticsearch permanently commits data to disk.

```text
Memory

↓

Disk

↓

Commit Point
```

This operation is called **Flush**.

After flushing,

the Translog can be safely cleared.

---

# Real-Life Analogy

Imagine writing lecture notes.

While attending class,

you write quickly on loose sheets of paper.

Those sheets represent the Translog.

Later,

you neatly copy everything into a permanent notebook.

That notebook represents the committed Lucene index.

Refresh lets others read your loose notes.

Flush permanently stores them.

---

# Merge

Lucene segments are immutable.

Every Refresh creates a new segment.

Suppose indexing continues for hours.

Eventually,

the shard contains hundreds of tiny segments.

Searching every segment becomes inefficient.

---

# Why Too Many Segments Are Bad

Imagine a student using

100 sticky notes.

Finding information becomes difficult.

Eventually,

the student rewrites everything into

5 organized notebooks.

The total information stays the same,

but reading becomes much easier.

Segment merging follows the same principle.

---

# Segment Merge

Initially

```text
Segment A

Segment B

Segment C

Segment D
```

After merging

```text
Large Segment AB

Large Segment CD
```

Eventually

```text
Large Optimized Segment
```

Searching a few large segments is significantly faster than searching hundreds of tiny ones.

---

# Segment Lifecycle

Every document follows the same lifecycle.

```text
Document Write
      │
      ▼
Memory Buffer
      │
      ▼
Refresh
      │
      ▼
Small Segment
      │
      ▼
Multiple Small Segments
      │
      ▼
Background Merge
      │
      ▼
Large Optimized Segment
```

This continuous process allows Elasticsearch to maintain both fast indexing and efficient searching.

# Cluster Scaling

Suppose your application grows dramatically.

Instead of

```text
100 Million Documents
```

you now have

```text
10 Billion Documents
```

Elasticsearch allows you to add new nodes.

```text
Old Cluster

Node 1

Node 2

Node 3
```

↓

```text
New Cluster

Node 1

Node 2

Node 3

Node 4

Node 5
```

The cluster automatically redistributes shards across the new machines.

This process is called **Shard Rebalancing**.

---

# Real-Life Analogy

Imagine a warehouse.

Originally,

three workers handle all incoming boxes.

Business grows rapidly.

The warehouse hires three additional workers.

Boxes are redistributed so that no single worker becomes overloaded.

Similarly,

Elasticsearch redistributes shards across newly added nodes.

---

# Failure Recovery

Suppose one node suddenly crashes.

Does the cluster stop working?

No.

Replica shards immediately take over.

```text
Primary Shard

↓

Node Failure

↓

Replica Promotion

↓

New Primary
```

The cluster continues serving search requests while creating another replica in the background.

---

# Real-Life Analogy

Imagine a supermarket with ten checkout counters.

One cashier suddenly leaves.

Customers immediately move to another cashier.

The supermarket continues operating with minimal disruption.

Replica promotion works exactly the same way.

# Key Takeaways

- Elasticsearch uses an indexing pipeline to efficiently convert documents into searchable Lucene segments.
- Documents are first routed to a primary shard using a hash-based routing mechanism.
- Writes are buffered in memory before being converted into immutable Lucene segments.
- Replication ensures multiple copies of each document exist for fault tolerance and high availability.
- Search requests follow a **Scatter–Gather** model, where multiple shards search in parallel and the coordinating node merges the results.
- **Refresh** makes newly indexed documents searchable without permanently writing them to disk.
- **Flush** commits indexed data to disk, ensuring durability and allowing the transaction log to be cleared.
- **Merge** combines many small immutable segments into fewer larger segments, improving long-term search performance.
- Shard rebalancing enables horizontal scaling as new nodes are added to the cluster.
- Replica promotion allows Elasticsearch to recover automatically from node failures with minimal disruption.
- In the next part, we will dive into **Apache Lucene Internals**, the search library that powers Elasticsearch and implements the core indexing and retrieval algorithms behind every search request.
