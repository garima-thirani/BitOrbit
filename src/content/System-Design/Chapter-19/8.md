# Why Kafka Was Built

To understand Kafka, let's first understand the problem.

Around 2010, LinkedIn faced a massive engineering challenge.

Different systems continuously generated events.

Examples included:

- Profile updates
- Connection requests
- Messages
- Job applications
- Search queries
- Advertisement clicks

Initially, every application communicated independently.

```text
Application A

↓

Database
```

```text
Application B

↓

Analytics
```

```text
Application C

↓

Notification Service
```

Every system built its own integration.

As the company grew,

this architecture became increasingly difficult to maintain.

Problems included:

- Tight coupling
- Duplicate data pipelines
- Difficult scalability
- High operational complexity

LinkedIn needed a central platform capable of handling millions of events every second.

That platform eventually became **Apache Kafka**.

# What is Apache Kafka?

Apache Kafka is a **distributed event streaming platform**.

It is designed to:

- receive events,
- store events,
- distribute events,
- replay events,
- process events,

all at extremely high throughput.

Unlike traditional message queues,

Kafka stores events on disk for configurable periods of time.

This allows multiple applications to consume the same event independently.

# High-Level Kafka Architecture

A Kafka cluster consists of several components working together.

```text
              Producers
                   │
                   ▼
             Kafka Cluster
                   │
      ┌────────────┼────────────┐
      ▼            ▼            ▼
   Broker 1     Broker 2     Broker 3
                   │
                   ▼
              Consumers
```

The components are:

- Producers
- Brokers
- Topics
- Partitions
- Consumers

We will study each one individually.

---

# Producers

A **Producer** is any application that sends events to Kafka.

Examples:

- Payment Service
- User Service
- Mobile Application
- IoT Device
- Logging System

Whenever an event occurs,

the producer publishes it to Kafka.

---

## Example

Suppose a customer places an order.

The Order Service generates:

```json
{
  "event":"Order Created",
  "orderId":901,
  "userId":27
}
```

Instead of sending this directly to multiple services,

it sends the event to Kafka.

Kafka becomes the central distribution hub.

# Brokers

A **Broker** is a Kafka server.

Its responsibilities include:

- storing events,
- accepting writes,
- serving reads,
- replicating data,
- communicating with other brokers.

A Kafka cluster usually consists of many brokers.

Example

```text
Kafka Cluster

↓

Broker 1

Broker 2

Broker 3

Broker 4
```

Adding brokers increases storage capacity and throughput.

---

# Partitions

Suppose a topic receives

```
1 Million Events Per Second
```

One machine cannot process that much traffic.

Kafka therefore divides every topic into **Partitions**.

```text
Orders Topic

↓

Partition 0

Partition 1

Partition 2

Partition 3
```

Each partition stores only part of the events.

Different partitions can be stored on different brokers.

---

## Real-Life Analogy

Imagine a supermarket.

Instead of one checkout counter,

the store has

```text
Counter 1

Counter 2

Counter 3

Counter 4
```

Customers spread across all counters.

The workload becomes balanced.

Kafka partitions work the same way.

Instead of events waiting in one long line,

they are distributed across multiple partitions.

---

# Ordering Inside Partitions

One extremely important property of Kafka is:

> **Ordering is guaranteed only within a partition.**

Example

Partition 0

```text
Order 101

↓

Order 102

↓

Order 103
```

The order never changes.

However,

events in different partitions may be processed independently.

This trade-off allows Kafka to scale horizontally.

---

# Leaders

Every partition has one **Leader**.

The Leader handles:

- writes
- reads
- replication

Example

```text
Partition 0

↓

Leader

Broker 2
```

Every producer communicates with the Leader.

Followers never receive writes directly.

---

# Followers

Each Leader has one or more **Follower Replicas**.

Followers continuously copy data from the Leader.

Example

```text
Leader

↓

Follower A

↓

Follower B
```

If the Leader fails,

one follower becomes the new Leader.

This provides fault tolerance.

---

# Replication

Replication ensures that multiple copies of every partition exist.

Suppose

```text
Replication Factor = 3
```

Then every partition has

- One Leader
- Two Followers

Example

```text
Partition 2

Leader

Broker 1
```

```text
Replica

Broker 3
```

```text
Replica

Broker 4
```

Even if Broker 1 crashes,

the data is still available.

---

# In-Sync Replicas (ISR)

Not every replica is always fully updated.

Some replicas may fall behind.

Kafka maintains a set called the **In-Sync Replica (ISR)**.

ISR contains replicas that are fully synchronized with the Leader.

Example

```text
Partition 0

Leader

Broker 1
```

ISR

```text
Broker 1

Broker 2

Broker 3
```

If Broker 4 is slow,

it is excluded from the ISR until it catches up.

---

# Why ISR Matters

Imagine a classroom.

The teacher writes notes on the board.

Three students copy every word immediately.

Another student is constantly distracted.

If the teacher suddenly leaves,

which student should continue teaching?

Obviously,

one of the students with complete notes.

Kafka follows the same principle.

Only replicas in the ISR are eligible to become the new Leader.

This prevents data loss.

# Putting Everything Together

Suppose an Order Service creates a new order.

The event flows through Kafka like this.

```text
Order Service
       │
       ▼
Producer
       │
       ▼
Orders Topic
       │
       ▼
Partition 2
       │
       ▼
Leader Broker
       │
       ▼
Follower Replicas
       │
       ▼
Consumers
```

This architecture allows Kafka to process millions of events every second while remaining fault tolerant and horizontally scalable.

# Key Takeaways

- Apache Kafka is a distributed event streaming platform designed for high-throughput, fault-tolerant event processing.
- Kafka was originally developed at LinkedIn to simplify large-scale data pipelines.
- **Producers** publish events to Kafka.
- Events are organized into **Topics**, which represent logical streams of related data.
- Topics are divided into **Partitions**, enabling horizontal scalability and parallel processing.
- Each partition has one **Leader** responsible for handling reads and writes.
- **Follower Replicas** continuously replicate data from the Leader to provide fault tolerance.
- The **In-Sync Replica (ISR)** set contains replicas that are fully synchronized and eligible to become the next Leader if a failure occurs.
- Kafka's architecture allows thousands of producers and consumers to exchange millions of events per second while remaining highly available.
