# Introduction

So far, we've learned how Kafka stores and distributes events.

However, production systems introduce new challenges.

Imagine a banking application.

A customer transfers **$10,000**.

The producer sends the payment event.

Unfortunately, the network fails before the producer receives an acknowledgment.

The producer assumes the message was lost and retries.

Now the payment appears **twice**.

Did the customer pay twice?

Did Kafka store the event twice?

Did the consumer process it twice?

In distributed systems, these situations happen frequently.

Advanced Kafka features exist to solve problems like these.

---

# Idempotent Producer

## The Problem

Suppose a producer sends an event.

```text
Transfer $10,000

↓

Kafka
```

The broker successfully stores it.

However,

the acknowledgment packet is lost.

The producer assumes the message failed.

It retries.

```text
Transfer $10,000

↓

Retry
```

Without additional safeguards,

Kafka stores two identical events.

---

## Real-Life Analogy

Imagine ordering food online.

You press

**Place Order**

Nothing happens for a few seconds.

You assume the request failed.

You press the button again.

Now you've accidentally ordered two pizzas.

The restaurant cannot determine whether you intended two separate orders or accidentally clicked twice.

Kafka faces the same problem.

---

# What is Idempotency?

An operation is **idempotent** if performing it multiple times produces the same result as performing it once.

Example:

```text
Set Temperature = 22°C
```

Sending this command twice still leaves the thermostat at **22°C**.

Compare this with:

```text
Increase Temperature by 2°C
```

Sending it twice changes the temperature twice.

Only the first operation is idempotent.

---

# Idempotent Producer in Kafka

Kafka assigns every producer a unique **Producer ID (PID)**.

Each message also receives a **Sequence Number**.

```text
Producer ID

↓

Message 1

Sequence 1
```

↓

```text
Message 2

Sequence 2
```

↓

```text
Message 3

Sequence 3
```

If Kafka receives

Sequence 3

twice,

it immediately recognizes it as a duplicate.

The second message is discarded.

---

# Benefits

Idempotent Producers provide

- No duplicate writes
- Reliable retries
- Better fault tolerance
- Safer distributed systems

They are enabled by default in modern Kafka versions.

# Transactions

Sometimes one event is not enough.

Imagine an online payment.

A purchase requires

1. Withdraw money
2. Update inventory
3. Send confirmation

Suppose step 2 fails.

Should Kafka keep step 1?

No.

All operations should succeed together.

This is exactly what Kafka Transactions provide.

---

# Real-Life Analogy

Imagine transferring money between two bank accounts.

If

Money leaves Account A

but

never reaches Account B,

the system becomes inconsistent.

Banks therefore treat the transfer as **one transaction**.

Kafka follows the same idea.

---

# Kafka Transactions

A transaction groups multiple writes into one atomic unit.

```text
Begin Transaction

↓

Write Event A

↓

Write Event B

↓

Write Event C

↓

Commit
```

Only after the commit do consumers see the events.

If anything fails,

Kafka aborts the transaction.

---

# Exactly-Once Semantics (EOS)

One of Kafka's most misunderstood features is

**Exactly-Once Semantics**.

Many people think it means

> Kafka guarantees every event is processed exactly once.

That statement is incomplete.

Kafka guarantees that

> **the combination of producer, broker, and transactional consumer can avoid duplicate processing when configured correctly.**

---

## Why This Matters

Imagine processing payments.

Duplicate events could

- charge customers twice,
- ship products twice,
- send duplicate emails.

EOS prevents these situations.

---

## How Kafka Achieves EOS

Kafka combines

- Idempotent Producers
- Transactions
- Offset Management

into one coordinated workflow.

```text
Producer

↓

Transaction

↓

Broker

↓

Consumer

↓

Offset Commit

↓

Success
```

Either everything succeeds,

or nothing becomes visible.

# Schema Registry

Imagine two teams.

Team A produces

```json
{
"id":1,
"name":"Alice"
}
```

Months later,

they change the schema.

```json
{
"id":1,
"fullName":"Alice"
}
```

Consumers expecting

"name"

suddenly fail.

Schema evolution becomes difficult.

---

# What is Schema Registry?

Schema Registry stores the structure of every message.

Before producers publish events,

they register the schema.

Consumers validate incoming messages against the schema.

Benefits include

- Compatibility
- Versioning
- Validation
- Safe evolution

---

## Real-Life Analogy

Imagine construction engineers.

Every building follows approved blueprints.

Workers cannot suddenly invent new dimensions.

Schema Registry serves as Kafka's blueprint repository.

# KRaft Architecture

Earlier versions of Kafka required **ZooKeeper**.

ZooKeeper managed

- Broker metadata
- Leader election
- Cluster configuration

This introduced operational complexity.

Modern Kafka replaces ZooKeeper with **KRaft (Kafka Raft Metadata Mode).**

---

# Why Replace ZooKeeper?

Running Kafka required

```text
Kafka Cluster

+

ZooKeeper Cluster
```

Administrators had to manage two distributed systems.

KRaft simplifies everything.

```text
Kafka Cluster

↓

Metadata Management

↓

Leader Election

↓

Configuration
```

Everything now happens inside Kafka itself.

---

# Benefits of KRaft

- Simpler deployment
- Faster startup
- Better scalability
- Easier maintenance
- No external dependency

Today,

KRaft is the recommended architecture for new Kafka deployments.

# Log Compaction

Normally,

Kafka retains every event until the retention period expires.

However,

some applications only care about the latest value.

Example

```text
User Balance

↓

100

↓

150

↓

200

↓

220
```

Do we need every historical balance?

Sometimes,

only the latest value matters.

---

# What is Log Compaction?

Log Compaction removes outdated records while preserving the newest value for every key.

Example

Before

```text
User A = 100

User A = 150

User A = 220
```

After Compaction

```text
User A = 220
```

Old versions disappear.

The latest state remains.

---

## Real-Life Analogy

Imagine editing a Word document.

The software stores many intermediate versions while you type.

Eventually,

only the latest version is kept.

Log Compaction works similarly.

---

# Tiered Storage

Suppose a Kafka cluster stores

```
10 Petabytes
```

of historical events.

Keeping everything on expensive SSDs would be extremely costly.

Tiered Storage solves this problem.

Recent events remain on fast local disks.

Older events move to cheaper cloud storage.

```text
Recent Events

↓

SSD
```

↓

```text
Older Events

↓

Object Storage
```

Consumers can still read historical data when necessary.

# Key Takeaways

- **Idempotent Producers** prevent duplicate writes during retries by assigning sequence numbers to messages.
- **Transactions** group multiple writes into a single atomic unit, ensuring either all events are committed or none are.
- **Exactly-Once Semantics (EOS)** combines idempotent producers, transactions, and coordinated offset management to avoid duplicate processing.
- **Kafka Streams** enables real-time stream processing directly within the Kafka ecosystem.
- **Kafka Connect** provides reusable connectors for integrating Kafka with databases, data warehouses, search engines, and cloud storage.
- **Schema Registry** manages message schemas, enabling compatibility, validation, and safe schema evolution.
- **KRaft** replaces ZooKeeper by integrating metadata management and leader election directly into Kafka.
- **Log Compaction** retains only the latest value for each key, making Kafka suitable for stateful applications.
- **Tiered Storage** reduces storage costs by moving older data from local disks to cheaper object storage.
- Production Kafka deployments act as the central event backbone connecting hundreds of distributed services across an organization.
