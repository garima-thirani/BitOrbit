# Introduction

So far in this chapter, we have learned:

- Why search systems exist.
- How Information Retrieval works.
- How search engines process text.
- How search engines rank documents.

But one important question remains.

> **How do companies search billions of documents distributed across hundreds or even thousands of servers?**

Building an inverted index on a single machine works well for small datasets.

However, companies like

- Amazon
- Netflix
- LinkedIn
- GitHub
- Stack Overflow

must search enormous datasets distributed across multiple data centers.

This is where **Elasticsearch** comes in.

Elasticsearch is a distributed search engine built on top of **Apache Lucene**.

Lucene provides the powerful search library.

Elasticsearch adds

- Distribution
- Replication
- High Availability
- REST APIs
- Cluster Management
- Horizontal Scalability

Think of the relationship like this.

```text
             Elasticsearch
                   │
                   ▼
               Apache Lucene
                   │
                   ▼
          Information Retrieval
```

Lucene performs the actual indexing and searching.

Elasticsearch makes Lucene work across distributed systems.

---

# Why Elasticsearch?

Suppose your application stores

- 10 billion products
- 100 billion web pages
- trillions of log entries

A single machine can no longer store the complete search index.

Even if it could,

CPU, memory and disk throughput would eventually become bottlenecks.

The solution is obvious.

Instead of one server,

use hundreds.

But now several new problems appear.

- How do we divide the data?
- Which server receives new documents?
- Which server answers search requests?
- What happens when one server crashes?
- How do we keep multiple copies of data?

Elasticsearch solves all of these problems automatically.

---

# Elasticsearch Architecture

At a high level, Elasticsearch consists of multiple nodes working together as a cluster.

```text
                Elasticsearch Cluster
────────────────────────────────────────────

        Node A       Node B       Node C
          │            │            │
          ▼            ▼            ▼
      Search       Search       Search
       Index        Index        Index

────────────────────────────────────────────
```

Each node stores only part of the total data.

Together,

the nodes behave like one massive search engine.

The user never interacts with individual machines.

Instead,

they communicate with the cluster.

---

# Cluster

A **Cluster** is a collection of Elasticsearch nodes working together.

Think of it as one logical search engine.

```text
               Cluster

       ┌───────────────┐
       │               │
       │   Node 1      │
       │   Node 2      │
       │   Node 3      │
       │   Node 4      │
       │               │
       └───────────────┘
```

Even though multiple physical servers exist,

applications interact with the cluster as a single system.

---

## Responsibilities of a Cluster

The cluster is responsible for

- storing search indexes
- distributing data
- routing queries
- balancing workloads
- recovering failed nodes
- maintaining replicas

The cluster continuously monitors the health of every node.

---

# Node

A **Node** is an individual Elasticsearch server.

Each node

- stores part of the index
- executes search requests
- indexes documents
- communicates with other nodes

Example

```text
Cluster

├── Node 1
├── Node 2
├── Node 3
└── Node 4
```

Adding more nodes increases

- storage capacity
- search throughput
- indexing throughput
- fault tolerance

This is horizontal scaling.

---

## Types of Nodes

Although every node can perform multiple responsibilities,

production clusters often assign specialized roles.

Examples include

- Master Node
- Data Node
- Coordinating Node
- Ingest Node
- Machine Learning Node

Separating responsibilities improves scalability and cluster stability.

For this chapter, it is sufficient to understand that all nodes cooperate to provide distributed search.

---

# Index

An **Index** is similar to a database in relational systems.

Consider a traditional database.

```text
E-Commerce Database

Products

Customers

Orders
```

In Elasticsearch,

the equivalent is

```text
Products Index

Customers Index

Orders Index
```

Each index stores documents belonging to a particular domain.

For example,

```text
products
```

might contain

```json
{
  "id": 101,
  "name": "Mechanical Keyboard",
  "brand": "Keychron",
  "price": 120
}
```

Another index

```text
users
```

contains user documents.

Indexes provide logical organization.

---

# Document

The smallest searchable unit in Elasticsearch is called a **Document**.

A document is typically represented using JSON.

Example

```json
{
  "id": 5001,
  "title": "Distributed Systems Handbook",
  "author": "Alex",
  "year": 2024
}
```

Each document belongs to exactly one index.

Unlike SQL rows,

documents may contain nested objects and flexible schemas.

---

# Why One Index Is Not Enough

Imagine an index containing

```text
10 Billion Documents
```

Storing everything on one machine becomes impossible.

Instead,

Elasticsearch divides the index into multiple smaller pieces.

These pieces are called **Shards**.

---

# Shards

A **Shard** is a partition of an index.

Instead of storing

```text
Products Index

↓

One Server
```

Elasticsearch stores

```text
Products Index

↓

Shard 1

Shard 2

Shard 3

Shard 4
```

Each shard stores only part of the documents.

---

## Example

Suppose an index contains

```text
100 Million Products
```

We configure

```text
5 Primary Shards
```

The distribution becomes

```text
Shard 1

20 Million Documents
```

```text
Shard 2

20 Million Documents
```

```text
Shard 3

20 Million Documents
```

```text
Shard 4

20 Million Documents
```

```text
Shard 5

20 Million Documents
```

Now,

multiple servers can process searches simultaneously.

---

# Why Sharding Matters

Sharding provides three major benefits.

## Scalability

Each server stores only a fraction of the data.

---

## Parallel Search

Every shard searches independently.

The cluster merges the results.

---

## Fault Isolation

A problem affecting one shard does not necessarily affect the entire system.

---

# Replicas

What happens if one machine suddenly crashes?

Without backups,

part of the search index becomes unavailable.

Elasticsearch solves this using **Replicas**.

A replica is an exact copy of a primary shard.

Example

```text
Primary Shard 1

↓

Replica Shard 1
```

If the primary server fails,

the replica immediately takes over.

---

# Primary vs Replica Shards

Suppose we configure

```text
3 Primary Shards

1 Replica
```

The cluster becomes

```text
Node A

Primary 1
Replica 3
```

```text
Node B

Primary 2
Replica 1
```

```text
Node C

Primary 3
Replica 2
```

Notice that

no replica resides on the same node as its primary.

This prevents a single machine failure from losing both copies.

---

# Benefits of Replicas

Replicas improve

- High Availability
- Fault Tolerance
- Search Performance

Search requests can be executed against both

- Primary Shards
- Replica Shards

This increases overall throughput.

---

# Segments

Inside every shard,

Lucene stores data in smaller immutable units called **Segments**.

```text
Shard

│

├── Segment 1

├── Segment 2

├── Segment 3

└── Segment 4
```

Segments are created whenever new documents are indexed.

Instead of modifying existing segments,

Lucene creates new ones.

This immutable design simplifies concurrency and improves performance.

We will study segments in detail in the next part.

# Distributed Search

Suppose a user searches

```text
distributed systems
```

The request enters the cluster.

```text
                Search Request
                      │
                      ▼
            Coordinating Node
                      │
──────────────────────────────────────
      │         │          │
      ▼         ▼          ▼
   Shard 1   Shard 2    Shard 3
      │         │          │
      ▼         ▼          ▼
 Partial     Partial     Partial
 Results     Results     Results
──────────────────────────────────────
               │
               ▼
        Merge & Rank Results
               │
               ▼
          Return Response
```

Each shard searches independently.

The coordinating node combines and ranks the partial results before returning them to the client.

This allows Elasticsearch to search billions of documents within milliseconds.

---

# Horizontal Scaling

One of Elasticsearch's biggest strengths is its ability to scale horizontally.

Suppose your application grows from

```text
100 Million Documents
```

to

```text
5 Billion Documents
```

Instead of upgrading one server,

you simply add more nodes.

```text
Old Cluster

Node A

Node B

Node C
```

↓

```text
Expanded Cluster

Node A

Node B

Node C

Node D

Node E

Node F
```

The cluster automatically redistributes shards across the new nodes.

This makes scaling significantly easier than scaling a traditional database.

---

# Real-World Example

Imagine an e-commerce platform like Amazon.

Every product is indexed inside Elasticsearch.

When a customer searches

```text
wireless mechanical keyboard
```

the coordinating node sends the query to every relevant shard.

Each shard searches its own documents,

returns its highest-ranking matches,

and Elasticsearch merges all partial results into one globally ranked list.

To the customer,

the entire process appears instantaneous,

even though dozens or hundreds of machines participated in answering the request.

# Key Takeaways

- Elasticsearch is a distributed search engine built on top of Apache Lucene.
- A **Cluster** is a collection of Elasticsearch nodes working together as one logical search engine.
- A **Node** is an individual Elasticsearch server responsible for storing data and processing requests.
- An **Index** is similar to a database and stores related documents.
- A **Document** is the basic searchable unit and is typically represented as JSON.
- Large indexes are divided into **Primary Shards**, enabling horizontal scalability.
- **Replica Shards** provide fault tolerance, high availability, and increased search throughput.
- Each shard internally consists of multiple immutable **Lucene Segments**.
- Search requests are executed in parallel across shards and merged by a coordinating node.
- In the next part, we will explore **Elasticsearch Internals**, where we examine how documents are indexed, how searches are executed, and how Lucene manages segments behind the scenes.
