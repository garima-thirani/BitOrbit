# Introduction

Throughout this chapter we have discussed Elasticsearch.

However, Elasticsearch itself does **not** implement search algorithms.

Instead, it delegates almost everything related to indexing and searching to **Apache Lucene**.

Think of Elasticsearch as the operating system and Lucene as the search engine running underneath.

Whenever you:

- create an index,
- insert a document,
- execute a search,
- rank documents,

Elasticsearch eventually calls Lucene.

Understanding Lucene is therefore essential to understanding how Elasticsearch actually works.

---

# What is Apache Lucene?

Apache Lucene is an open-source **Information Retrieval library** written in Java.

It is **not** a database.

It is **not** a search server.

Instead,

it is a highly optimized search library capable of

- indexing documents,
- building inverted indexes,
- ranking search results,
- executing full-text queries.

Many well-known systems are built on top of Lucene.

- Elasticsearch
- OpenSearch
- Apache Solr
- Jira Search
- Confluence Search
- Adobe Experience Manager
- IBM Watson Explorer

---

# Why Doesn't Everyone Use Lucene Directly?

A natural question is:

> If Lucene is so powerful, why do we need Elasticsearch?

Because Lucene only solves the search problem.

It does **not** provide

- REST APIs
- Cluster management
- Replication
- Distributed indexing
- Sharding
- Node discovery
- High availability

Imagine buying a car engine.

The engine is incredibly powerful.

But it has

- no wheels,
- no steering,
- no seats.

Lucene is the engine.

Elasticsearch builds the complete vehicle around it.

---

# Lucene's Internal Architecture

At a very high level,

Lucene stores data like this.

```text
Index

│

├── Segment A

├── Segment B

├── Segment C

└── Segment D
```

Each segment is a completely independent searchable index.

When Elasticsearch searches,

Lucene searches every segment independently and merges the results.

---

# Segment Files

One of the most important ideas in Lucene is the **Segment**.

Earlier we learned that every Elasticsearch shard consists of multiple segments.

But what exactly is a segment?

A segment is simply

> **a small immutable search index stored on disk.**

Instead of one enormous index,

Lucene creates many smaller indexes.

---

## Real-Life Analogy

Imagine writing lecture notes.

Instead of maintaining one notebook forever,

you create

Notebook 1

↓

Notebook 2

↓

Notebook 3

↓

Notebook 4

Each notebook is complete.

You never rewrite previous notebooks.

When someone asks a question,

you simply search all notebooks.

Lucene segments behave exactly this way.

---

# Why Small Segments?

Suppose every new document required rewriting

```
1 TB
```

of indexed data.

Indexing would become impossibly slow.

Instead,

Lucene creates

```
New Segment

↓

Only contains newly indexed documents
```

This makes indexing extremely efficient.

---

# Immutable Segments

One of Lucene's most important design decisions is

> **Segments are Immutable.**

Once a segment is written,

it is never modified.

Instead,

new documents create entirely new segments.

---

## Why Immutability?

Imagine editing a 5,000-page book.

Every small correction would require printing the entire book again.

Instead,

publishers create

Edition 1

Edition 2

Edition 3

Each edition remains unchanged forever.

Lucene follows the same idea.

---

## Benefits of Immutable Segments

Immutable structures provide several advantages.

### No Locking

Multiple threads can search the same segment simultaneously.

No synchronization is required.

---

### Safe Concurrent Reads

Readers never see partially updated indexes.

Every segment is complete.

---

### Faster Writes

Instead of updating existing files,

Lucene simply creates a new segment.

Writing becomes sequential,

which is much faster for SSDs and HDDs.

---

### Simpler Recovery

If a crash occurs,

existing segments remain untouched.

Only the newest segment may require recovery.

---

# Inside a Segment

A segment is not a single file.

Instead,

it contains multiple specialized files.

Conceptually,

```text
Segment

├── Dictionary

├── Posting Lists

├── Stored Fields

├── Doc Values

├── Term Statistics

├── Metadata

└── Compression Information
```

Each file serves a specific purpose.

---

# Posting Lists

Earlier we introduced Posting Lists conceptually.

Now let's see how Lucene stores them.

Suppose three documents exist.

```text
D1

Distributed Systems
```

```text
D2

Distributed Databases
```

```text
D3

Kafka Systems
```

Lucene creates

| Word | Documents |
|------|-----------|
| Distributed | D1 D2 |
| Systems | D1 D3 |
| Kafka | D3 |
| Databases | D2 |

Searching

```text
Systems
```

requires reading only

```
D1

D3
```

instead of every document.

---

# Posting List Positions

Lucene stores much more than document IDs.

Example

```text
Document

Distributed Systems are scalable
```

Lucene records

| Word | Position |
|------|-----------|
| Distributed | 1 |
| Systems | 2 |
| Are | 3 |
| Scalable | 4 |

Why?

Because phrase searches need word positions.

Searching

```text
Distributed Systems
```

requires

Distributed

↓

Position 1

Systems

↓

Position 2

Only documents where positions match are returned.

Instead,

# Doc Values

One common misconception is

> Everything is stored in the inverted index.

This is not true.

Consider the query

```
Sort by Price
```

The inverted index cannot efficiently answer this.

Instead,

Lucene creates **Doc Values.**

---

## What are Doc Values?

Doc Values store field values in a **column-oriented format.**

Example

| Document | Price |
|-----------|-------|
| D1 | 120 |
| D2 | 80 |
| D3 | 150 |

Instead of

Document

↓

Fields

Lucene stores

Field

↓

Values

This is much faster for

- Sorting
- Aggregations
- Analytics
- Faceted Search

---

## Real-Life Analogy

Imagine Excel.

Finding

Employee #105

works well row by row.

But computing

Average Salary

is easier when every salary is stored together in one column.

Doc Values work exactly this way.

---

# Stored Fields

The inverted index stores searchable terms.

But what happens after matching documents are found?

The user expects the original document.

Example

```json
{
  "title":"Distributed Systems Handbook",
  "author":"Alex",
  "year":2024
}
```

Lucene stores the original document separately as **Stored Fields**.

Searching uses the inverted index.

Displaying results uses stored fields.

---

# Indexed Fields vs Stored Fields

This distinction is extremely important.

| Indexed Field | Stored Field |
|--------------|--------------|
| Used for searching | Used for displaying |
| Tokenized | Original value |
| Optimized for retrieval | Optimized for output |

Many beginners assume both are the same.

They are completely different data structures.

---

# Compression Techniques

Search indexes become enormous.

Google,

Amazon,

LinkedIn,

GitHub

all index billions of documents.

Without compression,

storage costs would explode.

Lucene therefore compresses

- Posting Lists
- Document IDs
- Positions
- Stored Fields
- Metadata

Compression not only saves storage,

it also improves search speed because fewer bytes must be read from disk.

---

# How Everything Fits Together

Suppose we index

```json
{
"id":100,
"title":"Learning Elasticsearch",
"price":40
}
```

Internally,

Lucene creates

```text
                Document
                     │
                     ▼
              Text Processing
                     │
                     ▼
              Inverted Index
                     │
        ┌────────────┴────────────┐
        ▼                         ▼
 Posting Lists              Stored Fields
        │                         │
        ▼                         ▼
  Search Queries          Display Results
        │
        ▼
    Doc Values
        │
        ▼
Sorting & Aggregations
```

Notice that different data structures serve different purposes.

This specialization is one of the reasons Lucene is so fast.

---

# Real-World Example

Consider GitHub Code Search.

Suppose millions of developers search

```
binary search tree
```

Lucene

- tokenizes every source file,
- builds posting lists,
- stores positions,
- compresses indexes,
- maintains Doc Values,
- stores the original files separately.

When the search arrives,

Lucene

- jumps directly to the posting list,
- skips irrelevant documents,
- computes BM25 scores,
- retrieves the original code snippet,

and returns results within milliseconds.

Without these optimized internal data structures,

searching millions of repositories would be far slower.

# Lucene vs Elasticsearch

| Apache Lucene | Elasticsearch |
|---------------|---------------|
| Search Library | Distributed Search Engine |
| Runs inside one JVM | Runs across clusters |
| Builds inverted indexes | Manages distributed indexes |
| Performs ranking | Coordinates distributed search |
| Stores segments | Manages shards |
| Executes local search | Executes cluster-wide search |

Think of it this way.

```
User

↓

Elasticsearch

↓

Lucene

↓

Disk
```

Every search eventually reaches Lucene.

# Key Takeaways

- Apache Lucene is the core search library powering Elasticsearch.
- Lucene stores indexes as multiple immutable **Segments**, allowing efficient writes and concurrent reads.
- Each segment contains specialized files such as dictionaries, posting lists, stored fields, and Doc Values.
- **Posting Lists** map terms to document IDs, enabling fast keyword retrieval.
- **Skip Lists** act as shortcuts within large posting lists, reducing search time.
- **Doc Values** store field values in a column-oriented format, making sorting and aggregations efficient.
- **Stored Fields** preserve the original document so that search results can be displayed after matching.
- Lucene compresses its internal data structures to reduce storage requirements and improve I/O performance.
- Elasticsearch provides distributed capabilities, while Lucene performs the actual indexing and searching.
