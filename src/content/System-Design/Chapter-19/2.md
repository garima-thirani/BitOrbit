# Introduction to Information Retrieval

In the previous part, we learned why traditional databases are not suitable for large-scale search.

But this naturally raises another question.

> **If search engines don't scan every document like a database, how do they find information so quickly?**

The answer lies in an entire field of computer science called **Information Retrieval (IR).**

Information Retrieval is the science of storing, organizing, retrieving, and ranking information efficiently from very large collections of documents.

Unlike relational databases, which focus on structured records and exact matches, Information Retrieval systems are designed for:

- Large collections of text
- Relevance-based retrieval
- Fast keyword search
- Ranked results
- Approximate matching

Every modern search engine—Google, Elasticsearch, Solr, OpenSearch, GitHub Search, Amazon Search—builds upon Information Retrieval principles.

---

# What is Information Retrieval?

Information Retrieval (IR) is the process of finding documents that satisfy a user's information need.

Notice the wording.

It does **not** say:

> Find documents that exactly match the query.

Instead, it says:

> Find documents that best satisfy the user's intent.

For example,

Suppose we have three documents.

```text
Document 1

System Design Interview by Alex Xu
```

```text
Document 2

Distributed Systems Design Handbook
```

```text
Document 3

Learning Docker and Kubernetes
```

A user searches

```text
system design
```

An Information Retrieval system should rank:

1. Document 1
2. Document 2
3. Document 3

Even though Document 2 does not exactly contain the phrase "System Design Interview."

The goal is to retrieve **the most relevant documents**, not merely matching ones.

# Components of an Information Retrieval System

Every search engine consists of two major phases.

```text
                 Documents
                      │
                      ▼
               Index Construction
                      │
                      ▼
              Search Index Storage
────────────────────────────────────────
                      │
                 User Query
                      │
                      ▼
               Query Processing
                      │
                      ▼
              Candidate Retrieval
                      │
                      ▼
                  Ranking
                      │
                      ▼
                 Search Results
```

The indexing phase is performed offline.

The querying phase happens in milliseconds.

This separation is one of the biggest reasons modern search engines scale efficiently.

---

# Forward Index

The most intuitive way to organize documents is called a **Forward Index**.

A Forward Index stores every document along with the words it contains.

Consider three documents.

```text
Document 1

Distributed systems are scalable.
```

```text
Document 2

Search systems use inverted indexes.
```

```text
Document 3

Kafka powers event streaming.
```

A Forward Index looks like this.

| Document | Terms |
|-----------|--------------------------------|
| D1 | Distributed, systems, scalable |
| D2 | Search, systems, inverted, indexes |
| D3 | Kafka, powers, event, streaming |

Notice what happened.

Each document stores its own words.

This organization is excellent when reading documents.

However, it performs poorly for searching.

Suppose a user searches for

```text
systems
```

The engine must inspect every document individually until it finds matches.

For millions or billions of documents, this approach becomes extremely inefficient.

---

# The Problem with Forward Indexes

Imagine Google storing

- 100 billion web pages

using a Forward Index.

Searching for

```text
database
```

would require examining every web page.

That is impossible to perform in real time.

Instead of asking

> Which words belong to this document?

Search engines reverse the relationship.

They ask

> Which documents contain this word?

This simple idea completely changes search performance.

---

# Inverted Index

The most important data structure in Information Retrieval is the **Inverted Index**.

Instead of storing

```text
Document → Words
```

it stores

```text
Word → Documents
```

Consider the same documents again.

```text
Document 1

Distributed systems are scalable.
```

```text
Document 2

Search systems use inverted indexes.
```

```text
Document 3

Kafka powers event streaming.
```

The Inverted Index becomes:

| Term | Documents |
|------|-----------|
| Distributed | D1 |
| Systems | D1, D2 |
| Scalable | D1 |
| Search | D2 |
| Inverted | D2 |
| Indexes | D2 |
| Kafka | D3 |
| Event | D3 |
| Streaming | D3 |

Now imagine a user searches for

```text
systems
```

The engine immediately retrieves

```text
D1
D2
```

without inspecting any other document.

This single optimization reduces search time from scanning billions of documents to performing a simple dictionary lookup.

---

# Why Inverted Indexes Are Fast

Think of a traditional book.

To find the word

```text
consistency
```

you could read every page.

Or,

you could open the index at the back of the book.

```
Consistency

Pages

12

28

91

144
```

The index tells you exactly where the word appears.

An Inverted Index works in precisely the same way.

Instead of page numbers,

it stores document identifiers.

This is why search engines can retrieve results in milliseconds.

---

# Posting Lists

Each entry in an Inverted Index points to a **Posting List**.

A Posting List contains all documents where a term appears.

For example,

```
systems

↓

D1

D2

D7

D15

D108
```

Each posting may also include additional information such as:

- Term Frequency
- Position inside the document
- Character offsets
- Payload data

A more detailed Posting List looks like this.

| Document | Frequency | Positions |
|-----------|----------|-----------|
| D1 | 2 | 3, 17 |
| D2 | 1 | 8 |
| D15 | 4 | 2, 6, 20, 41 |

These statistics become extremely important later when computing TF-IDF and BM25 scores.

---

# Dictionary

How does the search engine know where each Posting List begins?

It uses a **Dictionary**.

The Dictionary is a lookup table that maps every term to its Posting List.

Example:

| Term | Posting List |
|------|--------------|
| database | P1 |
| kafka | P2 |
| redis | P3 |
| search | P4 |

Searching for

```text
redis
```

becomes:

```
Dictionary

↓

redis

↓

P3

↓

Posting List

↓

Matching Documents
```

Since dictionary lookups are extremely fast, search engines spend almost no time locating candidate documents.

---

# Compression

Large search engines store trillions of terms.

Without compression,

their indexes would consume enormous amounts of storage.

Compression reduces:

- Disk usage
- Memory usage
- Network transfer
- Query latency

Modern search engines compress:

- Posting Lists
- Document IDs
- Term Frequencies
- Positions

using specialized integer compression algorithms.

Compression allows much larger indexes to fit into memory, making search significantly faster.

# Query Processing Pipeline

Everything we've discussed comes together when a user performs a search.

Suppose the user types:

```text
distributed systems
```

The search engine executes the following pipeline.

```text
User Query
      │
      ▼
Query Parsing
      │
      ▼
Tokenization
      │
      ▼
Dictionary Lookup
      │
      ▼
Retrieve Posting Lists
      │
      ▼
Intersect Candidate Documents
      │
      ▼
Ranking
      │
      ▼
Top Results
```

Notice something important.

The search engine **never scans every document**.

Instead, it:

1. Breaks the query into tokens.
2. Looks up each token in the Dictionary.
3. Retrieves Posting Lists.
4. Combines matching documents.
5. Passes the candidates to the ranking engine.

Only a very small subset of documents is ever evaluated.

This design makes modern search systems capable of searching billions of documents within milliseconds.

---

# Real-World Example

Consider GitHub Code Search.

When searching for

```text
binary search tree
```

GitHub does not inspect every repository on demand.

Instead,

source files have already been indexed.

The query is tokenized,

Posting Lists are retrieved,

candidate files are ranked,

and the most relevant repositories are returned almost instantly.

This same architecture powers Google Search, Elasticsearch, OpenSearch, and many enterprise search platforms.

---

# Key Takeaways

- Information Retrieval focuses on retrieving the most relevant documents rather than exact matches.
- A Forward Index stores **Document → Terms** and is efficient for document storage but inefficient for searching.
- An Inverted Index stores **Term → Documents**, enabling extremely fast keyword lookups.
- Posting Lists maintain the list of documents containing each term and may store additional metadata such as frequency and positions.
- The Dictionary maps search terms to Posting Lists, enabling constant-time lookups.
- Compression minimizes storage and memory requirements while improving search performance.
- Modern search engines process queries by tokenizing the input, retrieving Posting Lists, generating candidate documents, and ranking the most relevant results.
