# Compatibility

Schema evolution revolves around one question.

Can old producers communicate with new consumers?

Can new producers communicate with old consumers?

Depending on the answer,

we have different compatibility models.

---

# Backward Compatibility

New consumers can read old events.

Example

Old Event

```json
{
 "orderId":100,
 "amount":400
}
```

New Schema

```json
{
 "orderId":100,
 "amount":400,
 "currency":"USD"
}
```

Currency has a default value.

Old events still work.

Backward compatible.

---

# Forward Compatibility

Old consumers can read new events.

Producer sends

```json
{
 "orderId":100,
 "amount":400,
 "coupon":"SAVE20"
}
```

Old consumer ignores

```
coupon
```

Still works.

Forward compatible.

---

# Full Compatibility

Supports both

Old Producer

↓

New Consumer

AND

New Producer

↓

Old Consumer

Safest option.

Most difficult to maintain.

# Production Engineering Notes

## Deployment Strategy

Never deploy:

```
Producer

↓

Consumers
```

at the same time.

Instead:

1. Make consumers compatible with both old and new schemas.
2. Deploy consumers.
3. Deploy producers emitting the new schema.
4. Monitor errors.
5. Remove deprecated fields only after all consumers migrate.

This minimizes production risk.

---

## Monitoring

Track:

- Schema validation failures
- Consumer deserialization errors
- Unknown field usage
- Deprecated schema usage
- Registry availability
- Serialization latency

Schema changes should be treated as production changes.

# Interview Questions & Solutions

## Question 1

### Question

Why is schema evolution difficult in Event-Driven Architecture?

### What Interviewer Tests

Understanding of distributed ownership.

### Ideal Answer

Events are consumed by many independent services that upgrade at different times. Changing an event schema without maintaining compatibility can break downstream systems. Therefore, schemas must evolve gradually while preserving compatibility.

---

## Question 2

### Question

What is backward compatibility?

### Ideal Answer

Backward compatibility means newer consumers can successfully process events produced using older schemas, usually by providing default values for newly introduced fields.

---

## Question 3

### Question

Why is Schema Registry important?

### Ideal Answer

Schema Registry provides a centralized repository for versioned schemas. Producers and consumers validate against it, preventing incompatible changes and enabling controlled schema evolution.

---

## Question 4

### Question

When would you choose Avro over JSON?

### Ideal Answer

Avro provides compact binary serialization, built-in schema evolution, and strong integration with Kafka Schema Registry. JSON is easier to debug but results in larger payloads and weaker schema governance.

---

## Question 5 (FAANG)

### Question

Your company needs to add a new field to an event consumed by 200 services. How would you roll it out?

### Ideal Answer

Add the field as optional or provide a default value. Register the new schema version, update consumers to accept both old and new schemas, deploy consumers first, then deploy producers. Monitor schema validation and consumer errors before deprecating older versions.

# Revision Notes

- Event schemas inevitably evolve.
- Prefer additive changes over destructive ones.
- Backward compatibility is often the safest default.
- Schema Registry centralizes governance.
- Avro and Protobuf are common production formats.
- Roll out schema changes gradually.
- Never rename or remove fields without a migration strategy.
- Treat schema evolution as a production engineering discipline.
