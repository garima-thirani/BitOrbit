# Story – The Invisible Failure

Imagine you're an engineer at Uber.

Everything appears healthy.

- Kafka brokers are running.
- CPU usage is low.
- Memory usage is normal.
- Network latency is fine.

Yet customers are complaining:

> "My ride completed 20 minutes ago, but I still haven't received my receipt."

Where is the problem?

You inspect:

- Payment Service ✔
- Kafka ✔
- Notification Service ✔
- Email Service ✔

Everything looks healthy.

Eventually you discover

One malformed event entered the notification pipeline.

Every consumer kept retrying it.

The queue became blocked.

Thousands of valid receipts waited behind one bad event.

# Poison Messages

A Poison Message is an event that consistently causes processing failures.

Example

```json
{
 "amount":"INVALID"
}
```

Consumer

↓

Crash

↓

Retry

↓

Crash

↓

Retry

Forever.

---

# Why Poison Messages Are Dangerous

Imagine

Queue

```text
Message 1

↓

Poison Message

↓

Message 3

↓

Message 4
```

If processing is sequential,

everything behind the poison message waits.

This is called

Queue Blocking.

---

# Solution – Dead Letter Queue (DLQ)

Instead of retrying forever

Move failed messages elsewhere.

```text
Consumer

↓

Retry

↓

Retry

↓

Retry

↓

Dead Letter Queue
```

Processing continues.

# Retry Strategy

Never retry immediately.

Bad

```text
Fail

↓

Retry

↓

Retry

↓

Retry
```

Creates retry storms.

---

Good

```text
Fail

↓

1 sec

↓

2 sec

↓

4 sec

↓

8 sec

↓

16 sec

↓

DLQ
```

This is

Exponential Backoff.

---

# Add Jitter

Suppose

10,000 consumers fail simultaneously.

Without jitter

All retry

Exactly

8 seconds later.

System overloads again.

Instead

Randomize retry.

```
8 ± Random
```

This is

Jitter.

# Production Engineering Notes

## Golden Signals

Every Event-Driven platform should monitor:

- **Latency** – Event processing time
- **Traffic** – Events/sec
- **Errors** – Failed processing rate
- **Saturation** – Queue depth, consumer lag, broker utilization

These four metrics often reveal problems before users notice them.

---

## Operational Runbook

When consumer lag spikes:

1. Check broker health.
2. Check consumer CPU/memory.
3. Inspect DLQ growth.
4. Verify schema compatibility.
5. Scale consumer group if necessary.
6. Replay failed events after recovery.

Never blindly restart consumers without understanding the root cause.

# Interview Questions & Solutions

## Question 1

### Question

What is a Poison Message?

### What Interviewer Tests

Knowledge of production failure handling.

### Ideal Answer

A Poison Message is an event that repeatedly fails processing due to invalid data or application bugs. Instead of retrying indefinitely, it should be moved to a Dead Letter Queue after a limited number of retries.

---

## Question 2

### Question

Why are Dead Letter Queues important?

### Ideal Answer

DLQs isolate permanently failing messages so healthy events can continue processing. They prevent queue blocking and allow operators to inspect, fix, and replay problematic events later.

---

## Question 3

### Question

What is Consumer Lag?

### Ideal Answer

Consumer Lag is the difference between the latest produced offset and the latest consumed offset. It indicates how far consumers are behind producers and is one of the most important health metrics in Kafka-based systems.

---

## Question 4

### Question

How do you debug a request that spans twenty microservices?

### Ideal Answer

Assign a Correlation ID to the original request and propagate it through every event and log entry. Use distributed tracing tools such as OpenTelemetry with Jaeger, Tempo, or Zipkin to visualize the complete request path.

---

## Question 5 (FAANG)

### Question

Your Kafka cluster is healthy, but customers report delayed order confirmations. How would you investigate?

### Ideal Answer

First examine consumer lag, retry counts, and DLQ growth. Use distributed tracing to follow a delayed order through all services. Check for poison messages, schema validation failures, slow downstream dependencies, and backpressure. Scale consumers or replay failed events after resolving the root cause.
