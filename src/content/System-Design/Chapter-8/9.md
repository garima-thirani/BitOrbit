The history itself becomes the database.

# Production Engineering Notes

## Snapshot Strategy

Create snapshots based on replay cost.

Typical guidelines:

- ≤100 events: No snapshot needed.
- 100–1000 events: Snapshot periodically.
- >1000 events: Snapshot aggressively.

Always measure replay latency before choosing a strategy.

---

## Monitoring

Monitor:

- Replay duration
- Snapshot creation time
- Snapshot size
- Event store growth
- Stream length
- Aggregate reconstruction latency
- Event append latency

Storage growth should be predictable and monitored continuously.

# Interview Questions & Solutions

## Question 1

### Question

What problem does Event Sourcing solve?

### What Interviewer Tests

Understanding of historical state.

### Ideal Answer

Event Sourcing preserves every state transition instead of only storing the latest state. This enables complete auditability, replay, debugging, historical analysis, and reconstruction of current state from immutable events.

---

## Question 2

### Question

Why are snapshots necessary?

### Ideal Answer

Without snapshots, rebuilding an aggregate may require replaying thousands or millions of events. Snapshots periodically capture the aggregate's current state so reconstruction only requires replaying events after the latest snapshot.

---

## Question 3

### Question

Can Kafka replace an Event Store?

### Ideal Answer

Not completely. Kafka is designed for event streaming and message distribution, while an Event Store is the authoritative source of business history with aggregate streams, optimistic concurrency, and permanent retention. Some architectures use Kafka as the transport layer and an Event Store as the source of truth.

---

## Question 4

### Question

When should Event Sourcing be avoided?

### Ideal Answer

Avoid Event Sourcing for simple CRUD applications, small internal tools, or domains where historical reconstruction has little business value. The additional complexity is often not justified.

---

## Question 5 (FAANG)

### Question

Design the transaction history system for a global bank.

### Ideal Answer

Represent every balance change as an immutable event stored in an Event Store. Use aggregate streams per account, optimistic concurrency for updates, snapshots for efficient reconstruction, CQRS projections for dashboards, and Kafka to distribute transaction events to fraud detection, analytics, notifications, and reporting systems.

# Revision Notes

- Event Sourcing stores history instead of current state.
- The Event Store becomes the system of record.
- State is rebuilt by replaying immutable events.
- Snapshots improve reconstruction performance.
- Aggregate streams isolate business entities.
- CQRS commonly complements Event Sourcing.
- Kafka distributes events; the Event Store preserves them.
- Use Event Sourcing only when historical traceability justifies the added complexity.
