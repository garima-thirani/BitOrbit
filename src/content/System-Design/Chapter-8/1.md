# Story – The Growing E-Commerce Company

Imagine you are the first backend engineer at a small e-commerce startup.

Initially, your application looks like this.

```text
Customer

↓

Web Server

↓

Database
```

Simple.

Everything is inside one application.

A customer places an order.

The application:

- Saves the order
- Updates inventory
- Sends an email
- Updates analytics
- Creates an invoice
- Updates recommendations

Everything happens inside a single process.

Life is good.

---

A year later...

The company becomes successful.

Now you have

- 5 million users
- 200 million products
- Thousands of orders every minute

The architecture evolves.

```text
Order Service

↓

Payment Service

↓

Inventory Service

↓

Email Service

↓

Recommendation Service

↓

Analytics Service
```

Each service owns its own database.

Each service scales independently.

Everything still looks good.

---

Until...

One Friday evening.

Inventory becomes slow.

Immediately:

- Checkout becomes slow.
- Payment waits.
- Shipping waits.
- Emails stop.
- Recommendations stop.
- Analytics stop.

One service slowed down.

The entire company slowed down.

The architecture had become tightly coupled.

---

The engineering team realized something important.

The Order Service should not care who needs the order.

It should simply announce:

> "An order has been created."

Anyone interested can react.

This simple idea became the foundation of **Event-Driven Architecture**.

# What is Event-Driven Architecture?

Event-Driven Architecture (EDA) is a software architecture in which services communicate by producing and consuming **events** instead of directly calling each other.

Instead of saying

```text
Inventory,

please reserve stock.
```

A service simply publishes

```text
OrderCreated
```

Interested services react independently.

---

# Definition

An **event** is an immutable record describing something that has already happened.

Examples

```
OrderCreated

PaymentCompleted

RideStarted

RideCompleted

InventoryReserved

UserRegistered

VideoUploaded

ProductViewed
```

Notice the naming.

Events are written in the **past tense**.

Because an event represents a fact.

Not a command.

# Evolution of Distributed Architectures

Understanding EDA becomes much easier if we see how software architecture evolved over time.

---

## Stage 1 – Monolith

Everything inside one application.

```text
Application

├── Orders

├── Inventory

├── Payments

├── Email

└── Database
```

Advantages

- Simple
- Easy deployment
- Easy debugging

Problems

- Difficult to scale
- One deployment affects everything
- Large codebase

---

## Stage 2 – Service-Oriented Architecture (SOA)

Business functions become independent services.

```text
Order Service

↓

Payment Service

↓

Inventory Service

↓

Email Service
```

Advantages

- Better modularity
- Independent deployments

Problems

- Services become tightly coupled.
- Many synchronous API calls.
- Cascading failures.

---

## Stage 3 – Microservices

Smaller independently deployable services.

```text
Order

↓

Payment

↓

Inventory

↓

Shipping
```

This improves ownership.

But communication is still often synchronous.

---

## Stage 4 – Event-Driven Architecture

Instead of direct calls

```text
Order Service

↓

OrderCreated Event

↓

Broker

↓

Inventory

↓

Shipping

↓

Analytics

↓

Email
```

Nobody knows who consumes the event.

This is loose coupling.

---

# The Biggest Idea Behind EDA

Imagine a newspaper.

The newspaper prints today's news.

Millions of people read it.

The newspaper doesn't know:

- Who reads it
- When they read it
- Why they read it

It simply publishes information.

Event-Driven systems work exactly the same way.

Services publish facts.

Consumers decide what to do.

---

# Push vs Pull Communication

Traditional APIs follow a pull model.

```text
Inventory Service

↓

GET /orders
```

Inventory constantly asks:

"Anything new?"

Wasteful.

---

EDA follows push.

```text
OrderCreated

↓

Broker

↓

Inventory
```

The event is pushed automatically.

No polling required.

# Event-Driven Approach

# Events vs Commands

This distinction is critical.

Many engineers confuse them.

---

## Command

A command tells someone to perform an action.

Examples

```
ReserveInventory

SendEmail

ProcessPayment

GenerateInvoice
```

Commands are imperative.

They expect one receiver.

---

## Event

An event describes something that already happened.

Examples

```
InventoryReserved

EmailSent

PaymentCompleted

InvoiceGenerated
```

Events describe facts.

Many consumers may react.

# Characteristics of Events

Good events are

- Immutable
- Timestamped
- Durable
- Replayable
- Self-describing

Once published

They never change.

If something changes

Publish another event.

---

# Event Immutability

Suppose

```text
PaymentCompleted
```

was published.

Later the payment is refunded.

Do we modify the old event?

No.

Instead publish

```text
PaymentRefunded
```

History remains intact.

# Event Metadata

Every production event contains metadata.

Example

```json
{
  "eventId": "evt_12345",
  "eventType": "OrderCreated",
  "timestamp": "2026-01-15T10:30:45Z",
  "version": 1,
  "source": "OrderService",
  "correlationId": "req_56789"
}
```

Business data appears separately.

Metadata enables tracing, debugging, replay, and monitoring.

# Correlation IDs

Imagine one customer order.

It triggers

- Payment
- Inventory
- Email
- Shipping

How do we trace everything?

Every event carries

```
Correlation ID
```

Example

```
Order

↓

Correlation ID

abc-123
```

Every downstream event contains

```
abc-123
```

Distributed tracing becomes possible.

# Benefits of Event-Driven Architecture

## Loose Coupling

Services don't know each other.

---

## Independent Scaling

Inventory can scale separately from Analytics.

---

## Easy Feature Addition

Need Fraud Detection?

Create another consumer.

No producer changes.

---

## Better Fault Isolation

Analytics failure shouldn't stop Checkout.

EDA naturally isolates failures.

---

## Event Replay

Replay yesterday's events.

Retrain ML models.

Recover databases.

Rebuild projections.

Traditional APIs cannot do this.

---

# Trade-offs

EDA introduces complexity.

## Eventual Consistency

Updates are no longer immediate.

Different services become consistent over time.

---

## Harder Debugging

One user request may generate hundreds of events.

Tracing requires proper observability.

---

## Duplicate Events

Consumers must be idempotent.

---

## Ordering Challenges

Ordering across multiple partitions is difficult.

We'll study this later.

# Interview Questions & Solutions

## Question 1

### Question

Why was Event-Driven Architecture invented?

### What the Interviewer is Testing

Whether you understand the limitations of synchronous microservices.

### Ideal Answer

EDA was introduced to reduce tight coupling between services. Instead of directly calling downstream services, producers publish events describing completed actions. Interested consumers subscribe independently, improving scalability, fault isolation, extensibility, and allowing event replay.

---

## Question 2

### Question

What is the difference between an event and a command?

### Ideal Answer

A command instructs another service to perform an action and typically has a single intended receiver. An event describes something that has already happened and may be consumed by many independent services.

---

## Question 3

### Question

Why are events immutable?

### Ideal Answer

Events represent historical facts. Modifying them would change history. If the business state changes, publish a new event rather than modifying the old one. Immutability simplifies auditing, replay, and debugging.

---

## Question 4

### Question

What problems does Event-Driven Architecture introduce?

### Ideal Answer

EDA introduces eventual consistency, more complex debugging, event ordering challenges, duplicate event handling, schema evolution, and the need for observability. These trade-offs are accepted because they improve scalability and resilience.

---

## Question 5 (FAANG)

### Question

Design Amazon's checkout using Event-Driven Architecture.

### Ideal Answer

Use synchronous APIs for payment authorization and inventory reservation when immediate responses are required. Publish an `OrderCreated` event after a successful transaction using a Transactional Outbox. Downstream services such as shipping, analytics, recommendations, fraud detection, and notifications consume the event independently through Kafka, allowing the system to scale while remaining loosely coupled.

- Producers publish; consumers react.
