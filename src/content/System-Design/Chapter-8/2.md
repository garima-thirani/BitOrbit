# Story – The Digital Newspaper

Imagine a newspaper company.

Every morning they print:

```
Today's News
```

Millions of people read it.

Some readers only care about sports.

Some read finance.

Some only read politics.

The newspaper doesn't customize itself for every reader.

It simply publishes facts.

Readers decide what interests them.

An event works exactly the same way.

A producer publishes facts.

Consumers independently decide whether to react.

# What Exactly Is an Event?

Many engineers think:

> "An event is just a message."

This is incomplete.

A message is simply a way to transport data.

An event represents a **business fact**.

Example

```
UserRegistered
```

This tells us

A user has already registered.

History changed.

That fact will never become false.

---

# Definition

An event is:

> **An immutable business fact describing something that has already happened inside the system.**

Examples

```
OrderCreated

PaymentCompleted

InventoryReserved

ShipmentStarted

ShipmentDelivered

RideCompleted

VideoUploaded

CommentAdded

PasswordChanged
```

Notice something.

Every event uses the **past tense**.

---

# Why Past Tense?

Suppose we publish

```
CreateOrder
```

Is this an event?

No.

It is a command.

Commands request work.

Events announce completed work.

Example

```text
CreateOrder

↓

Business Logic

↓

OrderCreated
```

Only after success does the event exist.

# Event Creation

Imagine Alice places an order.

Business logic executes.

```text
Validate User

↓

Validate Inventory

↓

Payment

↓

Save Database

↓

Create Event
```

Only after the transaction succeeds should the event be published.

Never publish events before the business action commits.

# Component 1 – Event Metadata

Metadata describes the event itself.

Typical metadata includes

```json
{
  "eventId": "evt_123",
  "eventType": "OrderCreated",
  "timestamp": "2026-06-01T10:15:00Z",
  "version": 1,
  "source": "OrderService"
}
```

Metadata is not business data.

It helps infrastructure understand the event.

---

# Event ID

Every event should have a globally unique identifier.

Example

```
evt_84fa93c0
```

Why?

- Duplicate detection
- Tracing
- Debugging
- Idempotency

Never reuse Event IDs.

---

# Timestamp

Example

```
2026-07-01T14:30:25Z
```

Timestamps help with

- Ordering
- Debugging
- Auditing
- Analytics

Always use UTC in distributed systems.

---

# Event Type

# Version

Systems evolve.

Today's event:

```json
{
 "orderId":123
}
```

Tomorrow

```json
{
 "orderId":123,
 "coupon":"SAVE20"
}
```

Versioning prevents breaking older consumers.

We'll study schema evolution later.

# Correlation ID

One user request may generate

```
OrderCreated

↓

InventoryReserved

↓

ShipmentCreated

↓

EmailSent

↓

InvoiceGenerated
```

How do we know all these belong together?

Correlation ID.

Example

```
req_981237
```

Every downstream event carries

```
req_981237
```

Distributed tracing becomes easy.

---

# Causation ID

Often confused with Correlation ID.

Example

```
OrderCreated

↓

PaymentCompleted

↓

ShipmentCreated
```

ShipmentCreated happened because of PaymentCompleted.

The Causation ID identifies the immediate parent event.

```text
OrderCreated

↓

PaymentCompleted

↓

ShipmentCreated
```

Each child knows what caused it.

# Producers

A producer creates events.

Examples

```

Inventory Service

```

Responsibilities

- Create events
- Validate payload
- Publish reliably
- Never know consumers

---

# Producer Responsibilities

A producer should

✔ Validate business logic

✔ Commit database

✔ Publish event

✔ Continue execution

A producer should **not**

❌ Wait for every consumer.

# Consumers

Consumers subscribe to events.

Examples

```

Recommendations

Shipping

Fraud

```

Consumers decide independently whether an event matters.

# Consumer Responsibilities

Consumers should

- Validate schema
- Process event
- Handle duplicates
- Retry failures
- Record metrics

Consumers should never modify the original event.

# Event Ownership

Who owns

```

```

No other service should publish

# Event Contracts

Consumers depend on event structure.

Example

```json
{
 "orderId":123
}
```

If producer suddenly changes to

```json
{
 "id":123
}
```

Consumers break.

The event structure is called the

**Event Contract**.

Contracts must evolve carefully.

# Fat vs Thin Events

## Thin Event

```json
{
 "orderId":123
}
```

Consumer fetches details.

Advantages

- Small payload

Disadvantages

- Extra API calls

---

## Fat Event

```json
{
 "orderId":123,
 "customer":"Alice",
 "items":[...],
 "total":899
}
```

Advantages

- Self-contained

Disadvantages

- Larger messages

Most production systems choose a balanced approach.

# Interview Questions & Solutions

## Question 1

### Question

What makes an event different from a message?

### Ideal Answer

A message is a transport mechanism. An event represents an immutable business fact describing something that has already happened. Events carry business meaning, while messages are simply containers used to transmit data.

---

## Question 2

### Question

Why should events be immutable?

### Ideal Answer

Events represent historical facts. Changing them would alter history and make replay, auditing, and debugging unreliable. If the business state changes, publish a new event rather than modifying an existing one.

---

## Question 3

### Question

What is the difference between Correlation ID and Causation ID?

### Ideal Answer

A Correlation ID links all events generated as part of the same business request, enabling end-to-end tracing. A Causation ID identifies the immediate parent event that directly triggered the current event, helping reconstruct event chains.

---

## Question 4

### Question

Should producers know who consumes their events?

### Ideal Answer

No. Producers should publish events without knowledge of downstream consumers. This loose coupling allows new consumers to be added without modifying producers.

---

## Question 5 (FAANG)

### Question

Design the structure of an `OrderCreated` event for a global e-commerce platform.

### Ideal Answer

Include immutable business data (order ID, customer ID, total, currency), metadata (event ID, timestamp, version, source), tracing information (correlation ID, causation ID), and ensure the event follows a versioned contract. Publish it only after the database transaction commits, typically using a Transactional Outbox.

- Events describe completed business facts.
- Producers publish; consumers react.
- Events contain metadata and payload.
- Correlation IDs trace requests across services.
- Causation IDs identify parent events.
- Event contracts must evolve through versioning.
- Good event design is immutable, versioned, and self-describing.
