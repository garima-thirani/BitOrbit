# Story – The Impossible Race

Imagine two customers buying the last PlayStation 5.

Customer A lives in London.

Customer B lives in Tokyo.

Both click **Buy Now** at nearly the same time.

```text
London

↓

Buy

-------------------

Tokyo

↓

Buy
```

Which order arrived first?

Simple?

Not really.

London's request traveled through:

- ISP
- CDN
- Load Balancer
- API Gateway

Tokyo's request took a completely different path.

Different networks.

Different delays.

Different clocks.

Now imagine the London server says:

```
10:00:00.120
```

Tokyo server says:

```
10:00:00.118
```

Did Tokyo really happen first?

Not necessarily.

Clock synchronization itself is imperfect.

This is why ordering in distributed systems is far more complicated than sorting timestamps.

# Happens-Before Relationship

Leslie Lamport introduced one of the most important ideas in distributed systems.

Event A

**Happened Before**

Event B

if

- A caused B
- A sent a message received by B
- A occurred earlier in the same process

Notation

```
A → B
```

Meaning

A happened before B.

---

# Concurrent Events

Sometimes

Two events have no causal relationship.

```text
User A Likes Post

----------------

User B Updates Profile
```

Neither caused the other.

They are concurrent.

Ordering doesn't matter.

---

# Lamport Logical Clock

Instead of relying on timestamps

Every process keeps a logical counter.

Rules

1. Increment before every event.
2. Include the counter in every message.
3. Receiver updates its clock.

---

# Example

Server A

```
Clock = 1

↓

Order Created

Clock = 2
```

Message sent with

```
Clock = 2
```

Server B

Current Clock

```
5
```

Receives message

```
2
```

Updates

```
max(5,2)+1

=

6
```

Ordering preserved.

# Limitation of Lamport Clocks

Suppose

```
Event A

Clock = 5

Event B

Clock = 6
```

We know

5 happened before 6.

But

Two unrelated events can also receive increasing numbers.

Lamport clocks cannot detect concurrency.

---

# Vector Clocks

Vector Clocks solve this.

Instead of

One number

Store one number per process.

Example

```text
Server A

[4,2,1]

Server B

[4,3,1]

Server C

[4,3,5]
```

Each entry tracks another node.

---

# How Vector Clocks Work

Three servers

```
A

B

C
```

Clock

```
[0,0,0]
```

Server A processes event

```
[1,0,0]
```

Message reaches B

B updates

```
[1,1,0]
```

C receives

```
[1,1,1]
```

Relationships become visible.

---

# Advantages

Vector Clocks can determine

- Happens-before
- Concurrent events

Unlike Lamport clocks.

# Production Engineering Notes

## Monitoring Ordering Problems

Track:

- Out-of-order event count
- Duplicate event rate
- Consumer lag
- Partition skew
- Late event percentage
- Event processing latency

These metrics help detect ordering issues before they affect users.

---

## Design Recommendation

For business entities requiring strict ordering:

Always partition by a stable business identifier such as:

- Order ID
- Ride ID
- Conversation ID
- Account ID

Never use random partition keys for stateful workflows.

# Interview Questions & Solutions

## Question 1

### Question

Why can't distributed systems rely on timestamps for event ordering?

### What Interviewer Tests

Understanding of distributed time.

### Ideal Answer

Physical clocks on different machines are never perfectly synchronized due to clock drift, network latency, and synchronization delays. Therefore, timestamps cannot reliably establish causal ordering between distributed events.

---

## Question 2

### Question

What is the Happens-Before relationship?

### Ideal Answer

The Happens-Before relationship defines whether one event causally precedes another. If Event A causes Event B or sends a message that triggers B, then A happened before B. Concurrent events have no Happens-Before relationship.

---

## Question 3

### Question

What is the difference between Lamport Clocks and Vector Clocks?

### Ideal Answer

Lamport Clocks provide a logical ordering of events but cannot distinguish concurrent events. Vector Clocks track logical time for each participating process and can identify both causal relationships and concurrency, though they require more storage.

---

## Question 4

### Question

How does Kafka preserve event ordering?

### Ideal Answer

Kafka guarantees ordering only within a single partition. To preserve ordering for a business entity, all related events should use the same partition key, such as Order ID or Conversation ID.

---

## Question 5 (FAANG)

### Question

Design the event ordering strategy for WhatsApp.

### Ideal Answer

Partition messages by Conversation ID so all messages in the same conversation are written to the same Kafka partition. Assign sequence numbers to messages, maintain idempotent consumers, buffer out-of-order events briefly if necessary, and use message IDs to eliminate duplicates.
