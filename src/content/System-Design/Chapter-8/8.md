# Story – Amazon's Product Page

Imagine opening an Amazon product page.

You immediately see:

- Product name
- Price
- Images
- Reviews
- Rating
- Stock availability
- Similar products
- Delivery estimate
- Seller information
- Frequently bought together

One simple page.

Behind the scenes?

Data comes from at least ten different services.

```text
Product Service

Inventory Service

Pricing Service

Review Service

Recommendation Service

Shipping Service

Seller Service
```

Question:

Should every page request call all ten services?

Absolutely not.

The page would take seconds to load.

Instead, Amazon builds a **Read Model** optimized for queries.

This idea is the heart of CQRS.

# What is CQRS?

CQRS stands for

```
Command Query Responsibility Segregation
```

It separates

```
Writes

and

Reads
```

into different models.

Instead of

```text
One Database

↓

Reads

Writes
```

we build

```text
Write Model

↓

Events

↓

Read Model
```

Each model is optimized independently.

# CQRS Architecture

```text
              Client

                 │

       ┌─────────┴─────────┐

       ▼                   ▼

Commands             Queries

       │                   │

Write Model       Read Model

       │                   ▲

       ▼                   │

 Event Stream ──────────────┘
```

Commands update data.

Queries never modify data.

# Commands vs Queries

| Command | Query |
|----------|--------|
| Changes state | Reads state |
| Can fail | Cannot change data |
| Produces events | Returns data |
| Business rules | Optimized for speed |

# Production Engineering Notes

## Designing Read Models

Every read model should answer one business question efficiently.

Bad design:

```
One generic read database
```

Better design:

```
Dashboard View

Search View

Analytics View

Fraud View

Reporting View
```

Each projection is optimized for its consumers.

---

## Monitoring

Monitor:

- Projection lag
- Kafka consumer lag
- Read model freshness
- Replay duration
- Projection failures
- Query latency
- Read/write throughput

Freshness of read models is one of the most important operational metrics in CQRS systems.

# Interview Questions & Solutions

## Question 1

### Question

Why does CQRS separate reads and writes?

### What Interviewer Tests

Understanding of workload optimization.

### Ideal Answer

Read and write workloads have different characteristics. Writes prioritize consistency and business rules, while reads prioritize speed and aggregation. CQRS allows each to be optimized independently, improving scalability and flexibility.

---

## Question 2

### Question

What is a Projection?

### Ideal Answer

A Projection is a component that consumes domain events and builds one or more read models optimized for querying. It continuously synchronizes the read side with the write side.

---

## Question 3

### Question

Why is CQRS usually paired with Event-Driven Architecture?

### Ideal Answer

Commands update the write model and publish events. Those events drive projections that build read models. Event-driven messaging naturally keeps read models synchronized without tight coupling.

---

## Question 4

### Question

What happens if a projection crashes?

### Ideal Answer

The write model remains unaffected because it is the source of truth. After recovery, the projection replays missed events from Kafka or another event store and rebuilds the read model.

---

## Question 5 (FAANG)

### Question

Design Amazon's product page using CQRS.

### Ideal Answer

Maintain a transactional write model for product updates, inventory, reviews, and pricing. Publish events when changes occur. Projection services consume these events and build specialized read models for product pages, search, recommendations, and dashboards. Cache frequently accessed read models in Redis and rebuild projections through Kafka replay if necessary.

# Revision Notes

- CQRS separates reads from writes.
- Commands modify state; queries retrieve state.
- Projections transform events into read models.
- Read models are optimized for specific business queries.
- Kafka is commonly used to synchronize write and read models.
- Eventual consistency is expected and must be communicated to users.
- Replay allows read models to be rebuilt after failures.
