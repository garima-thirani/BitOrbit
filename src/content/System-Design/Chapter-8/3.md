# Story – Amazon's Order Service

Imagine you're working on Amazon.

A customer places an order.

Internally, the Order Service performs dozens of operations.

```
Validate Coupon

↓

Calculate Tax

↓

Reserve Order Number

↓

Update Inventory Cache

↓

Persist Database

↓

Generate Audit Log

↓

Create Shipment

↓

Notify Analytics
```

Question:

Should every internal step become a Kafka event?

Absolutely not.

Imagine exposing:

```
CouponValidated

↓

InventoryCacheUpdated

↓

TemporaryDiscountApplied

↓

OrderChecksumGenerated
```

Now every service in the company starts depending on these events.

Months later...

The Order team changes an internal algorithm.

Suddenly,

Analytics breaks.

Fraud breaks.

Recommendations break.

Shipping breaks.

The Order team realizes they accidentally exposed their internal implementation.

This is why we distinguish between **Domain Events** and **Integration Events**.

---

# Why This Distinction Exists

In Event-Driven Architecture, not every event is public.

Some events exist only inside one service.

Others are shared across the entire company.

Understanding this distinction is essential for designing maintainable systems.

---

# Domain Event

A Domain Event represents something meaningful **inside a bounded context**.

Example

Order Service

```
OrderValidated

↓

TaxCalculated

↓

CouponApplied

↓

InventoryChecked

↓

OrderPersisted
```

These events help organize business logic.

They are **internal**.

No other service should depend on them.

---

# Characteristics of Domain Events

Domain Events are

- Internal
- Business-oriented
- Highly detailed
- Owned by one service
- Free to evolve

They describe what happened **inside the service**.

---

# Integration Event

Integration Events are different.

They are intended for **other services**.

Example

```
OrderCreated

↓

PaymentCompleted

↓

InventoryReserved

↓

ShipmentDispatched
```

These events become contracts.

Many teams depend on them.

---

# Domain vs Integration Events

Imagine a restaurant.

Kitchen

```
Vegetables Chopped

↓

Sauce Prepared

↓

Steak Cooked
```

Customers don't care.

They only see

```
Order Ready
```

Kitchen events are Domain Events.

Order Ready is an Integration Event.

Integration events evolve much more slowly.

# Anti-Corruption Layer (ACL)

Suppose

Your company acquires another business.

Their events

```
PurchaseCompleted
```

Your events

```
OrderCreated
```

Different terminology.

Instead of changing every service

Create an ACL.

```text
External Events

↓

ACL

↓

Internal Events
```

ACL protects your domain model.

---

# Example

Vendor Event

```json
{
 "purchaseId":44
}
```

ACL transforms

```json
{
 "orderId":44
}
```

Consumers remain unchanged.

---

# Why ACL Matters

Without ACL

Every service

Bad architecture.

Instead

Only ACL understands external systems.

# Interview Questions & Solutions

---

## Question 1

### Question

What is the difference between a Domain Event and an Integration Event?

### What Interviewer Tests

Understanding of service boundaries.

### Ideal Answer

A Domain Event represents something that happened within a single bounded context and is intended only for internal use. An Integration Event is a stable, public contract published for other services to consume. Domain Events can change frequently, while Integration Events should evolve carefully because multiple consumers depend on them.

---

## Question 2

### Question

Why shouldn't every Domain Event be published?

### Ideal Answer

Publishing every Domain Event exposes internal implementation details and creates tight coupling. Other services may begin depending on events that were never intended as public contracts, making future refactoring difficult.

---

## Question 3

### Question

What is an Anti-Corruption Layer?

### Ideal Answer

An Anti-Corruption Layer translates external models into internal domain models, preventing external systems from leaking their terminology and design into your services. It protects domain boundaries and simplifies integration.

---

## Question 4

### Question

Who owns an Integration Event?

### Ideal Answer

Every Integration Event should have exactly one authoritative producer. For example, only the Payment Service should publish `PaymentCompleted`, ensuring consistency and avoiding conflicting event sources.

---

## Question 5 (FAANG)

### Question

Design an event strategy for an e-commerce platform.

### Ideal Answer

Use Domain Events for internal workflow steps such as tax calculation and inventory validation. Publish only stable Integration Events like `OrderCreated`, `PaymentCompleted`, and `ShipmentDelivered`. Introduce an Event Translation Layer to convert internal events into public contracts and use an Anti-Corruption Layer for external integrations.

# Revision Notes

- Domain Events are internal and implementation-focused.
- Integration Events are public and contract-focused.
- Never expose unnecessary internal events.
- Use Event Translation to convert internal workflows into stable external contracts.
- Protect your domain using an Anti-Corruption Layer.
- Public events should evolve slowly and remain backward compatible.
- Every public event must have one authoritative owner.
