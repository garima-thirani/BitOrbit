# Engineering Notes

## Every Cache Is Eventually Wrong

The moment

data changes

inside

the database,

every cached copy

becomes

a potential source

of stale information.

Good cache design

focuses

not on

preventing

staleness forever,

but on

detecting,

limiting,

and correcting it

quickly.

---

## Simplicity Usually Wins

Many production systems

prefer

deleting

cache entries

rather than

trying to update

every cached copy.

Deleting

allows

the next read

to rebuild

the cache

from

database,

reducing

complexity

and failure cases.

# Interview Questions & Solutions

## Question 1

### Question

Why is cache invalidation considered difficult?

### Ideal Answer

Because multiple copies of the same data exist across browsers, CDNs, application caches, and distributed cache clusters. Keeping every copy synchronized after updates requires careful invalidation strategies and coordination.

---

## Question 2

### Question

Why do many systems delete cache entries after updating the database instead of updating the cache?

### Ideal Answer

Deleting cache entries simplifies consistency. If cache updates fail or race conditions occur, the next read automatically reloads fresh data from the database, reducing the likelihood of stale or inconsistent cache entries.

---

## Question 3

### Question

What is event-driven cache invalidation?

### Ideal Answer

After the database is updated, an event is published to a messaging system. Cache services subscribe to these events and invalidate or refresh affected cache entries, enabling scalable cache synchronization across distributed systems.

---

## Question 4

### Question

What problem do versioned cache keys solve?

### Ideal Answer

Versioned keys prevent race conditions by ensuring that new data is written under a new cache key rather than overwriting the old one. Applications always request the latest version, while outdated keys expire naturally.

---

## Question 5 (FAANG)

### Question

Design the cache consistency mechanism for a global e-commerce platform.

### Ideal Answer

Use Cache-Aside with explicit invalidation after successful database updates, event-driven invalidation using Kafka for distributed services, short TTLs for frequently changing data, refresh-ahead for popular products, Redis Pub/Sub for cache synchronization, monitoring for stale reads and invalidation failures, and versioned cache keys where race conditions are likely.

# Revision Notes

- Cache invalidation ensures cached data remains consistent with the database.
- TTL provides automatic expiration but may temporarily serve stale data.
- Explicit invalidation removes cache entries immediately after database updates.
- Event-driven invalidation scales well across microservices.
- Versioned cache keys help prevent race conditions.
- Redis Pub/Sub and shared distributed caches synchronize cache updates.
- Monitoring stale reads, invalidation events, and cache hit ratios is essential for production systems.
