# The Problem Before Virtual Networks

Imagine a company with

- Web Servers
- Database Servers
- Cache Servers
- Internal APIs

If every server were directly connected to the Internet,

anyone could access them.

This creates enormous security risks.

Instead,

companies isolate their infrastructure inside private networks.

Cloud providers offer the same capability through **Virtual Private Clouds (VPCs).**

---

# Real-Life Analogy

Imagine a large corporate office.

The office building has

- Public Reception
- Employee Offices
- Finance Department
- Server Room

Visitors can enter the reception.

They cannot directly walk into the finance department or server room.

The building controls who can access each area.

A VPC works exactly the same way.

---

# What is a Virtual Private Cloud (VPC)?

A **Virtual Private Cloud (VPC)** is a logically isolated private network inside a cloud provider.

It allows organizations to create their own secure network with complete control over

- IP Address Ranges
- Routing
- Firewalls
- Internet Access
- Private Communication

Think of it as

> **Your own private data center inside AWS, Azure, or GCP.**

---

# VPC Architecture

```text
Cloud Provider

↓

Virtual Private Cloud (VPC)

↓

Applications

Databases

Caches

Internal Services
```

Everything inside the VPC communicates securely.

External access is tightly controlled.

---

# Why VPCs Exist

Without VPCs,

every cloud resource would share one massive public network.

This would create

- Security risks
- IP conflicts
- Poor isolation

A VPC provides

- Isolation
- Security
- Flexible networking
- Controlled communication

---

# Real-Life Analogy

Imagine renting office space inside a skyscraper.

Although many companies occupy the building,

each company has its own office,

employees,

meeting rooms,

and security systems.

A VPC is your private office within the cloud provider's infrastructure.

---

# What are Subnets?

A VPC can become very large.

Instead of placing every resource in one network,

we divide it into smaller sections called **Subnets.**

A **Subnet** is a subdivision of a VPC.

Each subnet contains a group of related resources.

---

# Real-Life Analogy

Imagine a university campus.

The campus represents the VPC.

Inside the campus,

there are separate buildings for

- Engineering
- Medicine
- Business
- Administration

Each building serves a different purpose.

Subnets work the same way.

---

# Public and Private Subnets

Production systems usually use two kinds of subnets.

## Public Subnet

Resources that must be accessible from the Internet.

Examples

- Load Balancers
- Bastion Hosts
- Public APIs

---

## Private Subnet

Resources that should never be directly accessible.

Examples

- Databases
- Redis
- Kafka
- Internal Microservices

---

# Example Architecture

```text
VPC

├── Public Subnet

│     Load Balancer

│     Bastion Host

│

└── Private Subnet

      Backend

      Redis

      PostgreSQL
```

Users interact only with the Public Subnet.

The backend infrastructure remains hidden.

---

# Why Private Subnets?

Suppose your PostgreSQL database is publicly accessible.

Anyone on the Internet could attempt to connect.

This is a major security risk.

Instead,

the database is placed inside a Private Subnet,

where only internal services can access it.

---

# Internet Gateway

Suppose your web server is running inside a VPC.

How does it communicate with users on the Internet?

This is the role of the **Internet Gateway.**

---

# What is an Internet Gateway?

An **Internet Gateway (IGW)** connects a VPC to the public Internet.

Without an Internet Gateway,

resources inside the VPC cannot communicate with external users.

---

# Real-Life Analogy

Imagine a gated community.

Residents live inside a secure neighborhood.

The main entrance connects the community to the outside world.

The Internet Gateway serves as that entrance.

---

# Traffic Flow

```text
Internet

↓

Internet Gateway

↓

Public Subnet

↓

Application
```

Only resources connected through the Internet Gateway can receive external traffic.

---

# NAT Gateway

Now consider the opposite problem.

Suppose a backend server inside a Private Subnet needs to

- Download software updates
- Access cloud APIs
- Retrieve packages

It needs Internet access.

However,

we still don't want the Internet reaching the server.

This is solved using a **NAT Gateway.**

---

# What is a NAT Gateway?

A **Network Address Translation (NAT) Gateway** allows resources in Private Subnets to initiate outbound Internet connections while blocking inbound Internet traffic.

In simple terms

Private Servers

✔ Can access the Internet

Internet

✘ Cannot directly access Private Servers

---

# Real-Life Analogy

Imagine employees inside a company making phone calls.

Employees can call customers.

Customers cannot directly dial individual employee desks.

All communication passes through the company's reception desk.

The NAT Gateway behaves similarly.

---

# NAT Gateway Architecture

```text
Private Server

↓

NAT Gateway

↓

Internet
```

The request goes out.

Responses return.

No external system can initiate communication directly.

---

# Why NAT Matters

Without a NAT Gateway,

Private Subnets would have

- No Internet access
- No software updates
- No package downloads
- No external API access

With a NAT Gateway,

servers remain private while still accessing external services.

---

# Load Balancers

Imagine your application has

10 Web Servers.

Should users know which server to contact?

No.

Instead,

all traffic passes through a **Load Balancer.**

---

# What is a Load Balancer?

A Load Balancer distributes incoming traffic across multiple servers.

Benefits include

- High Availability
- Fault Tolerance
- Better Performance
- Scalability

Cloud providers offer multiple types of load balancers.

---

# Application Load Balancer (ALB)

An **Application Load Balancer** operates at

**Layer 7 (Application Layer)**

It understands

- HTTP
- HTTPS
- URLs
- Hostnames
- Cookies
- Headers

This allows intelligent request routing.

---

# Example

```text
shop.example.com

↓

Shopping Service
```

```text
api.example.com

↓

API Service
```

One ALB can route requests to multiple applications.

---

# Real-Life Analogy

Imagine a receptionist in a hospital.

Patients describe their problem.

The receptionist directs them to

- Cardiology
- Orthopedics
- Pediatrics

The receptionist understands the request.

An ALB behaves the same way.

---

# Network Load Balancer (NLB)

A **Network Load Balancer** operates at

**Layer 4 (Transport Layer).**

Instead of understanding HTTP,

it forwards

- TCP
- UDP
- TLS

traffic with extremely low latency.

---

# Real-Life Analogy

Imagine a highway.

Cars are directed toward different roads.

The highway doesn't inspect passengers or cargo.

It simply forwards traffic efficiently.

NLB works similarly.

---

# ALB vs NLB

| Application Load Balancer | Network Load Balancer |
|----------------------------|-----------------------|
| Layer 7 | Layer 4 |
| Understands HTTP/HTTPS | Understands TCP/UDP |
| URL Routing | Port Routing |
| Host-based Routing | High Performance Networking |
| API Gateways | Databases, Gaming, Streaming |

# Complete Cloud Networking Architecture

A production cloud network typically looks like this.

```text
                   Internet
                       │
                       ▼
              Internet Gateway
                       │
                       ▼
                Public Subnet
                       │
                       ▼
            Application Load Balancer
                       │
                       ▼
              Private Subnet
          ┌────────────┼────────────┐
          ▼            ▼            ▼
     Frontend      Backend      Worker
          │            │            │
          ▼            ▼            ▼
     Redis       PostgreSQL     Kafka
          │
          ▼
     NAT Gateway
          │
          ▼
      Internet
```

Notice that

Users only interact with the Load Balancer.

Databases remain completely private.

# Key Takeaways

- A **Virtual Private Cloud (VPC)** provides an isolated private network inside a cloud provider.
- **Subnets** divide a VPC into smaller logical networks, typically separating public-facing resources from internal services.
- **Public Subnets** host Internet-facing components such as Load Balancers, while **Private Subnets** host databases, caches, and internal applications.
- An **Internet Gateway (IGW)** enables inbound and outbound Internet communication for resources in Public Subnets.
- A **NAT Gateway** allows resources in Private Subnets to initiate outbound Internet connections while preventing inbound access.
- An **Application Load Balancer (ALB)** operates at Layer 7 and routes HTTP/HTTPS traffic based on application-level information.
- A **Network Load Balancer (NLB)** operates at Layer 4 and provides high-performance TCP/UDP load balancing.
- Production cloud architectures combine VPCs, Subnets, Gateways, and Load Balancers to build secure, scalable, and resilient distributed systems.
