# Introduction

In the previous part, we introduced the three pillars of observability:

- Metrics
- Logs
- Traces

We also learned how

- Prometheus collects metrics.
- Grafana visualizes dashboards.

However, production systems consist of hundreds or even thousands of microservices.

Imagine debugging a request that travels through

- API Gateway
- User Service
- Payment Service
- Notification Service
- Inventory Service
- Kafka
- Redis
- PostgreSQL

How do you connect logs from every service?

How do you follow a single request?

How do you define whether your system is reliable enough?

This is where advanced observability tools and Site Reliability Engineering (SRE) practices become essential.

---

# The Problem with Distributed Systems

Imagine Netflix receives a request to play a movie.

The request flows through

```text
Gateway

↓

Authentication

↓

Recommendation

↓

Video Metadata

↓

CDN

↓

Streaming Service
```

Suppose the request fails.

Every service generates its own logs.

Without a way to connect them,

engineers must inspect thousands of unrelated log entries.

Finding the actual problem becomes extremely difficult.

---

# Real-Life Analogy

Imagine investigating a package delivery.

The package travels through

- Warehouse
- Sorting Center
- Regional Hub
- Delivery Vehicle
- Customer

Each location keeps separate records.

Without a common tracking number,

you would never know where the package was delayed.

Distributed systems require a similar tracking mechanism.

---

# Loki

Metrics are stored by Prometheus.

But where should logs go?

One popular solution is

**Grafana Loki.**

---

# What is Loki?

Loki is a centralized log aggregation system.

Instead of storing logs on individual servers,

applications send logs to Loki.

Engineers can search logs from the entire system in one place.

---

# Why Loki?

Suppose your Kubernetes cluster has

```
300 Pods
```

Each Pod generates logs.

If every Pod stores logs locally,

debugging becomes impossible.

Loki centralizes them.

---

# Real-Life Analogy

Imagine every department in a hospital maintaining its own patient records.

Finding a patient's history would require visiting every department.

Instead,

all records are stored in a centralized medical system.

Loki serves the same purpose for logs.

---

# Loki Architecture

```text
Applications

↓

Log Collectors

↓

Loki

↓

Grafana
```

Grafana can visualize both

- Metrics from Prometheus
- Logs from Loki

using a single dashboard.

---

# Jaeger

Logs explain events.

Metrics summarize health.

Sometimes,

engineers need to follow

one request

through dozens of services.

This is the purpose of

**Jaeger.**

---

# What is Jaeger?

Jaeger is a distributed tracing platform.

It records

the complete journey

of a request across microservices.

---

# Example

```text
User Request

↓

API Gateway

↓

User Service

↓

Payment Service

↓

Inventory Service

↓

Database
```

Jaeger measures

- Time spent in every service
- Request dependencies
- Bottlenecks
- Errors

---

# Real-Life Analogy

Imagine tracking a food delivery.

The app shows

- Restaurant accepted order
- Food prepared
- Driver picked up food
- Driver approaching
- Delivered

Jaeger provides similar visibility for API requests.

---

# Zipkin

Another popular tracing platform is

**Zipkin.**

---

# What is Zipkin?

Zipkin also performs distributed tracing.

It records

- Request Flow
- Latency
- Dependencies
- Service Communication

Functionally,

Zipkin and Jaeger solve very similar problems.

---

# Jaeger vs Zipkin

| Jaeger | Zipkin |
|----------|---------|
| CNCF Project | Originally from Twitter |
| Advanced UI | Lightweight |
| Kubernetes Friendly | Simple Deployment |
| Rich Trace Analysis | Fast Setup |

Both are widely used in production.

# OpenTelemetry

Suppose your company uses

- Prometheus
- Grafana
- Jaeger
- Loki

Should every application send telemetry differently?

That would be difficult.

Instead,

modern systems use

**OpenTelemetry.**

---

# What is OpenTelemetry?

OpenTelemetry (OTel)

is an open standard for collecting

- Metrics
- Logs
- Traces

Instead of instrumenting applications separately for every tool,

developers instrument once using OpenTelemetry.

Data can then be exported to multiple observability platforms.

---

# Real-Life Analogy

Imagine USB.

Instead of creating a different cable for every device,

USB standardizes communication.

OpenTelemetry does the same for observability.

---

# OpenTelemetry Architecture

```text
Application

↓

OpenTelemetry SDK

↓

Collector

↓

Prometheus

Grafana

Jaeger

Loki

Datadog

New Relic
```

Instrument once.

Export anywhere.

# Correlation IDs

Suppose a user request generates

```
200 Log Entries
```

across

20 microservices.

How do engineers identify

which logs belong to the same request?

They use

**Correlation IDs.**

---

# What is a Correlation ID?

A Correlation ID is

a unique identifier

assigned to a request.

Every service handling that request

includes the same ID in its logs.

---

# Example

```text
Request ID

REQ-84731
```

API Gateway

```
REQ-84731
```

↓

User Service

```
REQ-84731
```

↓

Payment Service

```
REQ-84731
```

↓

Notification Service

```
REQ-84731
```

Searching

```
REQ-84731
```

immediately retrieves every related log.

---

# Real-Life Analogy

Imagine tracking a shipment.

Every warehouse records

the same tracking number.

Correlation IDs work exactly like package tracking numbers.

# Service Level Indicators (SLIs)

Engineering teams need measurable indicators

to evaluate system health.

These measurements are called

**Service Level Indicators (SLIs).**

---

# What is an SLI?

An SLI is

a measurable metric

that reflects service performance.

Examples

- Availability
- Latency
- Error Rate
- Throughput

---

# Example

Availability

```
99.97%
```

Average Response Time

```
210 ms
```

Error Rate

```
0.02%
```

These values are SLIs.

---

# Service Level Objectives (SLOs)

Collecting metrics isn't enough.

Organizations also define

targets.

These targets are

**Service Level Objectives (SLOs).**

---

# Example

Availability

```
99.9%
```

Latency

```
< 300 ms
```

Error Rate

```
< 1%
```

These become engineering goals.

---

# Real-Life Analogy

Imagine a restaurant.

The owner promises

Meals served within

```
15 Minutes
```

That promise becomes an objective.

---

# Service Level Agreements (SLAs)

Sometimes,

organizations legally guarantee performance.

This is called an

**SLA.**

---

# Example

Cloud Provider

```
99.99% Availability
```

If availability drops,

customers may receive financial compensation.

An SLA is therefore

a contractual commitment,

not merely an engineering goal.

---

# SLI vs SLO vs SLA

| SLI | SLO | SLA |
|------|------|------|
| Measurement | Internal Target | Customer Contract |
| Observed | Desired | Guaranteed |
| Engineering Metric | Engineering Goal | Business Commitment |

A useful way to remember them is

```text
SLI

↓

Measures Reality
```

```text
SLO

↓

Defines Target
```

```text
SLA

↓

Promises Customers
```

# Error Budgets

Perfect uptime is impossible.

Servers fail.

Networks fail.

Software contains bugs.

Instead of chasing

100% availability,

Google introduced

**Error Budgets.**

---

# What is an Error Budget?

Suppose your SLO is

```
99.9% Availability
```

That allows

```
0.1%
```

acceptable downtime.

This allowable downtime

is called

the Error Budget.

---

# Why Error Budgets Matter

Imagine your application has already consumed

95%

of its monthly error budget.

Should engineers deploy risky new features?

Probably not.

Instead,

they focus on improving reliability.

Error Budgets balance

Innovation

and

Reliability.

---

# Real-Life Analogy

Imagine a monthly household budget.

Once most of the money has been spent,

you become more careful with new purchases.

Engineering teams treat downtime similarly.

# Alerting

Monitoring only becomes useful

if someone knows when something is wrong.

This is the role of

**Alerting.**

---

# What is Alerting?

Alerting automatically notifies engineers

when important conditions occur.

Examples

- CPU > 90%
- Error Rate > 5%
- Disk Usage > 95%
- Database Down
- High Latency

Alerts may be delivered through

- Slack
- Email
- PagerDuty
- SMS
- Microsoft Teams

---

# Good Alerts vs Bad Alerts

Good alerts

- Actionable
- Meaningful
- Rare

Bad alerts

- Too Frequent
- Noisy
- Ignore Root Cause

Too many unnecessary alerts cause

**Alert Fatigue**,

where engineers begin ignoring notifications.

# Real-World Example

Imagine Spotify.

A user presses

```
Play Song
```

The request travels through

- API Gateway
- Authentication Service
- Recommendation Engine
- Music Metadata Service
- CDN
- Streaming Service

Every service generates

Metrics,

Logs,

and

Traces.

OpenTelemetry collects telemetry data.

Prometheus stores metrics.

Loki stores logs.

Jaeger traces the request across every service.

Grafana visualizes dashboards.

Correlation IDs connect every log entry.

If latency exceeds the SLO,

Prometheus triggers an alert.

Engineers immediately identify the bottleneck and restore service before most users notice any issue.

This is how modern SRE teams operate Internet-scale systems.

# Key Takeaways

- **Loki** centralizes logs from distributed applications and integrates seamlessly with Grafana.
- **Jaeger** and **Zipkin** provide distributed tracing, allowing engineers to follow requests across multiple microservices.
- **OpenTelemetry** standardizes telemetry collection for Metrics, Logs, and Traces, enabling vendor-neutral observability.
- **Correlation IDs** link logs and traces generated by the same request, making distributed debugging significantly easier.
- **SLIs** measure system performance, **SLOs** define reliability targets, and **SLAs** represent contractual commitments to customers.
- **Error Budgets** help organizations balance rapid feature delivery with long-term system reliability.
- **Alerting** notifies engineers about meaningful production issues while avoiding unnecessary alert fatigue.
- **Capacity Planning** estimates future infrastructure requirements to ensure systems continue scaling reliably.
- Together, Prometheus, Grafana, Loki, Jaeger, Zipkin, OpenTelemetry, and SRE principles form the foundation of modern production observability.
