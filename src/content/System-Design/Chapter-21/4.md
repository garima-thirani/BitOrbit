- Scalable
- Reliable
- Highly Available

- Millions of users
- Auto Scaling
- Multi-Region Deployment
- Kubernetes
- Redis
- Kafka

# Why Security Matters

Every day,

modern applications handle

- Passwords
- Credit Cards
- Personal Messages
- Medical Records
- Financial Transactions
- Government Documents

A single security flaw can expose millions of users.

Some of the largest data breaches in history happened because of

- Weak authentication
- Poor authorization
- Exposed credentials
- Misconfigured APIs

Understanding security is therefore essential for every system designer.

---

# Real-Life Analogy

Imagine a bank.

- Security Guards

- CCTV Cameras

- Access Control

# The CIA Triad

The foundation of modern cybersecurity is called the

**CIA Triad.**

CIA does **not** refer to the intelligence agency.

It stands for

- Confidentiality
- Integrity
- Availability

Every security mechanism ultimately protects one or more of these principles.

---

# CIA Triad Overview

```text
          Security

      ┌──────┼──────┐
      ▼      ▼      ▼

Confidentiality

Integrity

Availability
```

Think of these as the three pillars of secure systems.

---

# Confidentiality

Confidentiality means

> **Only authorized people should access sensitive information.**

Examples include

- Passwords
- Medical Records
- Credit Card Numbers
- Private Messages

Unauthorized users should never be able to read this data.

---

# Real-Life Analogy

Imagine a diary.

Only the owner should be able to read it.

If anyone can open it,

confidentiality has been lost.

---

# How Confidentiality is Achieved

Common techniques include

- Authentication
- Authorization
- Encryption
- Access Control
- Secrets Management

---

# Integrity

Integrity means

> **Data must not be modified without authorization.**

Consider a banking transaction.

```
Transfer

₹1000
```

If an attacker changes it to

```
₹100000
```

the integrity of the data has been compromised.

---

# Real-Life Analogy

Imagine signing an important legal contract.

Nobody should be able to secretly change the agreement afterward.

Integrity ensures documents remain trustworthy.

---

# How Integrity is Achieved

Common techniques include

- Hashing
- Digital Signatures
- Checksums
- Database Transactions
- Version Control

---

# Availability

Availability means

> **Systems should remain accessible whenever authorized users need them.**

Imagine Amazon during Black Friday.

Even with millions of users,

the website should remain available.

If the website crashes,

availability has failed.

---

# Real-Life Analogy

Imagine a hospital emergency room.

Doctors must always be available.

If patients arrive and nobody can help them,

the system has failed.

---

# How Availability is Achieved

Common approaches include

- Load Balancing
- Replication
- Auto Scaling
- Failover
- Disaster Recovery
- Multi-Region Deployment

---

# Authentication

Before a system grants access,

it must answer one important question.

> **Who are you?**

This process is called

**Authentication.**

---

# What is Authentication?

Authentication verifies a user's identity.

Examples include

- Username & Password
- Fingerprint
- Face Recognition
- OTP
- Multi-Factor Authentication (MFA)

Authentication confirms identity.

Nothing more.

---

# Real-Life Analogy

Imagine entering an airport.

Security first checks your passport.

They verify

**who you are.**

This is authentication.

---

# Authorization

Once identity is verified,

another question arises.

> **What are you allowed to do?**

This is called

**Authorization.**

---

# What is Authorization?

Authorization determines

which resources a user may access.

Example

Alice

↓

Can View Dashboard

Can Edit Profile

Cannot Delete Database

Different users receive different permissions.

---

# Real-Life Analogy

Imagine an office building.

Your employee ID allows you to enter.

That's Authentication.

Whether you can enter the CEO's office

is Authorization.

---

# Authentication vs Authorization

| Authentication | Authorization |
|----------------|---------------|
| Verifies Identity | Determines Permissions |
| "Who are you?" | "What can you access?" |
| Login | Access Control |
| Happens First | Happens After Authentication |

Both are essential,

but they solve different problems.

---

# Why OAuth 2.0 Was Created

Imagine registering for a new application.

Instead of creating another password,

you click

```
Continue with Google
```

or

```
Continue with GitHub
```

How does that work?

It uses **OAuth 2.0.**

---

# The Problem Before OAuth

Years ago,

applications asked users for

their Google username

and

their Google password.

This was extremely dangerous.

Every third-party application learned your credentials.

OAuth solved this problem.

---

# What is OAuth 2.0?

OAuth 2.0 is an

**Authorization Framework.**

Notice the wording.

OAuth does **not** authenticate users.

Instead,

it allows one application to access another application's resources

without sharing passwords.

---

# Real-Life Analogy

Imagine hiring a valet.

Instead of giving the valet

your house key,

your office key,

and your bank locker key,

you give a parking token.

The valet can park your car,

but nothing else.

OAuth tokens work exactly like that parking token.

---

# OAuth Flow

```text
User

↓

Application

↓

Google Login

↓

User Grants Permission

↓

Access Token

↓

Application Accesses Google API
```

The application never learns the user's password.

---

# OpenID Connect (OIDC)

OAuth answers

> "Can this application access my resources?"

It does **not** answer

> "Who is the user?"

To solve this,

OpenID Connect was introduced.

---

# What is OpenID Connect?

OpenID Connect (OIDC)

is an identity layer built on top of OAuth 2.0.

It adds

- User Identity
- Login
- User Profile Information

to OAuth.

---

# Simple Rule

Remember this interview rule.

```text
OAuth

↓

Authorization
```

```text
OIDC

↓

Authentication
```

OIDC extends OAuth to support secure user login.

---

# JWT (JSON Web Token)

After users successfully log in,

applications need a way to remember them.

One popular solution is

JWT.

---

# What is JWT?

A JSON Web Token is a compact,

digitally signed token

that contains user information.

Instead of storing sessions on the server,

the token itself carries the necessary identity data.

---

# JWT Structure

A JWT consists of three parts.

```text
Header

.

Payload

.

Signature
```

Each section is Base64 encoded.

---

# Real-Life Analogy

Imagine boarding a flight.

Instead of repeatedly proving your identity,

you receive a boarding pass.

The boarding pass contains

- Your Name
- Flight Number
- Seat Number

Airport staff trust the boarding pass because it is officially issued.

JWT works the same way.

---

# JWT Authentication Flow

```text
User Logs In

↓

Server Verifies Credentials

↓

JWT Generated

↓

Client Stores JWT

↓

Future Requests Include JWT

↓

Server Verifies Signature

↓

Access Granted
```

The server doesn't need to remember every logged-in user.

The token carries the information.

---

# Sessions

Before JWT became popular,

most applications used

**Server Sessions.**

---

# What is a Session?

After login,

the server stores user information.

The browser receives

a Session ID.

Future requests send this Session ID back to the server.

The server looks up the user's session.

---

# Session Workflow

```text
Login

↓

Session Created

↓

Session ID Sent

↓

Browser Stores Cookie

↓

Future Requests

↓

Server Looks Up Session
```

---

# Cookies

A Cookie is a small piece of data stored inside the user's browser.

Cookies often store

- Session IDs
- User Preferences
- Language Settings

Cookies themselves are **not authentication mechanisms.**

They simply store information.

---

# Real-Life Analogy

Imagine a movie theater.

After buying a ticket,

you receive a wristband.

The wristband isn't your identity.

It simply references your purchase.

Cookies work similarly.

---

# Sessions vs JWT

| Sessions | JWT |
|-----------|-----|
| Server Stores State | Client Stores Token |
| Requires Session Database | Stateless |
| Easier Revocation | Better Scalability |
| Traditional Web Apps | APIs & Microservices |

Modern distributed systems often prefer JWT because it scales well across multiple servers.

---

# API Keys

Not every client is a human.

Sometimes,

one application needs to communicate with another.

Example

Payment Service

↓

Weather API

↓

Maps API

↓

Email Service

Instead of user login,

these services use

**API Keys.**

---

# What is an API Key?

An API Key is a unique identifier assigned to an application.

It identifies

the calling application,

not the user.

---

# Real-Life Analogy

Imagine a company's delivery truck.

The security guard checks the vehicle's company badge,

not the individual driver.

API Keys identify applications in the same way.

---

# When to Use API Keys

API Keys are commonly used for

- Public APIs
- Internal Service APIs
- Third-party Integrations
- Rate Limiting
- Billing

Sensitive APIs often combine API Keys with stronger authentication methods.

---

# Putting Everything Together

A secure authentication flow looks like this.

```text
User
    │
    ▼
Login Page
    │
    ▼
Authentication
    │
    ▼
OAuth / OIDC
    │
    ▼
JWT Issued
    │
    ▼
API Requests
    │
    ▼
Authorization
    │
    ▼
Protected Resources
```

Every request must first prove identity,

then verify permissions.

---

# Real-World Example

Imagine using GitHub.

You click

```
Continue with Google.
```

Google authenticates you using OIDC.

GitHub receives an identity token.

GitHub creates a JWT for your session.

Every API request includes the JWT.

GitHub verifies

- Your identity
- Your permissions

before allowing access to repositories.

Throughout this process,

GitHub never learns your Google password.

This architecture is used by thousands of modern web applications.

---

# Key Takeaways

- Security is built upon the **CIA Triad**: Confidentiality, Integrity, and Availability.
- **Authentication** verifies identity, while **Authorization** determines permissions.
- **OAuth 2.0** is an authorization framework that allows applications to access user resources without exposing passwords.
- **OpenID Connect (OIDC)** extends OAuth 2.0 by adding user authentication and identity information.
- **JWTs** are stateless authentication tokens containing digitally signed user information.
- **Sessions** store authentication state on the server, while **JWTs** store identity information on the client.
- **Cookies** are browser storage mechanisms commonly used to store Session IDs or authentication tokens.
- **API Keys** identify applications rather than users and are widely used for service-to-service communication.
- Modern distributed systems often combine **OIDC, OAuth 2.0, JWTs, and API Keys** to build scalable and secure authentication architectures.
- In the next part, we will explore **TLS, Mutual TLS (mTLS), Encryption, Hashing, Digital Signatures, IAM, Secrets Management, Vault, and KMS**, which protect data both in transit and at rest.
