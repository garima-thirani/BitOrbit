# Introduction

In the previous part, we learned how modern systems protect communication and secrets using

- TLS
- mTLS
- Encryption
- Hashing
- Digital Signatures
- IAM
- Vault
- KMS

These technologies answer the question

> **Can we trust the communication and the credentials?**

However, another equally important question remains.

> **Even after a user is authenticated, what exactly should they be allowed to access?**

Imagine an employee logging into Amazon's internal systems.

Should every employee be able to

- Delete production databases?
- View payroll information?
- Access customer payment details?

Of course not.

Authentication proves **who you are**.

Access control determines **what you can do**.

This part explores how modern organizations enforce access control and defend their applications from attackers.

---

# Why Access Control Matters

Imagine a hospital.

Doctors,

Nurses,

Receptionists,

Patients,

Administrators

all use the same hospital system.

Should every user see every patient's medical history?

Should patients modify prescriptions?

Should receptionists access payroll?

Every user requires different permissions.

This is the purpose of Access Control.

---

# Real-Life Analogy

Think of an airport.

Every person enters through the same entrance.

But after authentication,

different people can access different areas.

- Passengers → Boarding Gates
- Pilots → Cockpit
- Maintenance Crew → Engineering Areas
- Air Traffic Controllers → Control Tower

Everyone is authenticated.

Only some are authorized.

---

# Role-Based Access Control (RBAC)

The simplest and most widely used authorization model is

**Role-Based Access Control (RBAC).**

---

# What is RBAC?

RBAC grants permissions based on predefined roles.

Instead of assigning permissions directly to every user,

users are assigned roles,

and roles contain permissions.

---

# Example

Imagine a company.

```text
Employee

↓

Developer Role

↓

Deploy Applications

Read Logs

View Metrics
```

Another employee.

```text
Employee

↓

Database Administrator

↓

Manage Databases

Create Backups

Restore Databases
```

Permissions belong to the role,

not the individual.

---

# Real-Life Analogy

Imagine a university.

Instead of assigning classroom access individually,

the university defines roles.

```text
Student

↓

Access Classrooms
```

```text
Professor

↓

Access Labs

Grade Students
```

```text
Administrator

↓

Access Financial Systems
```

Every person inherits permissions through their role.

---

# RBAC Architecture

```text
User

↓

Role

↓

Permissions

↓

Resources
```

Changing a user's role automatically updates their permissions.

---

# Advantages of RBAC

RBAC is popular because it is

- Easy to understand
- Easy to manage
- Easy to audit
- Scalable for large organizations

This is why RBAC is used extensively in

- Kubernetes
- AWS IAM
- Azure IAM
- Enterprise Applications

---

# Limitations of RBAC

Suppose a hospital has

100 Doctors.

A doctor should only access

their own patients.

RBAC cannot easily express this rule.

Every doctor shares the same role.

Something more flexible is required.

---

# Attribute-Based Access Control (ABAC)

This leads to

**Attribute-Based Access Control (ABAC).**

---

# What is ABAC?

ABAC makes authorization decisions using attributes rather than fixed roles.

Attributes may belong to

- User
- Resource
- Environment
- Action

---

# Example

Suppose a rule says

```text
Allow access if

Department = Finance

AND

Location = Office

AND

Time < 6 PM
```

Instead of assigning permissions through roles,

the system evaluates attributes dynamically.

---

# Real-Life Analogy

Imagine entering a research laboratory.

Access depends on

- Your Job Title
- Security Clearance
- Time of Day
- Building Location

Security evaluates all these conditions before opening the door.

That is ABAC.

---

# ABAC Architecture

```text
User Attributes

+

Resource Attributes

+

Environment Attributes

↓

Policy Engine

↓

Access Decision
```

Every request is evaluated individually.

---

# RBAC vs ABAC

| RBAC | ABAC |
|-------|------|
| Based on Roles | Based on Attributes |
| Simple | Highly Flexible |
| Easy to Manage | More Complex |
| Good for Enterprises | Good for Dynamic Policies |
| Kubernetes RBAC | AWS IAM Policies |

---

# When to Use RBAC

RBAC is ideal when

- Permissions rarely change
- Users fit clear organizational roles
- Simplicity is important

Examples

- Corporate Portals
- HR Systems
- Kubernetes

---

# When to Use ABAC

ABAC is ideal when

access depends on

- User location
- Time
- Device
- Project
- Department
- Data Classification

Examples

- Banking
- Government
- Healthcare
- Military Systems

# Zero Trust Architecture

Traditional enterprise security assumed

> **Everything inside the corporate network is trusted.**

This assumption is no longer valid.

Modern organizations use

**Zero Trust.**

---

# What is Zero Trust?

Zero Trust follows one simple principle.

> **Never Trust. Always Verify.**

Every request,

every user,

every device,

every service

must continuously prove its identity.

---

# Real-Life Analogy

Imagine entering a high-security government building.

Showing your ID once is not enough.

Every secure area requires another verification.

Zero Trust works exactly this way.

Trust is never permanent.

---

# Traditional Security Model

```text
Internet

↓

Firewall

↓

Trusted Internal Network
```

Once inside,

systems trusted each other.

This model worked when applications lived inside a single data center.

---

# Zero Trust Model

```text
User

↓

Identity Verification

↓

Authorization

↓

Policy Evaluation

↓

Application
```

Every request is independently verified.

There is no trusted internal network.

---

# Why Zero Trust?

Modern organizations use

- Cloud Computing
- Kubernetes
- Remote Employees
- Mobile Devices
- APIs
- Multi-Cloud

Applications are no longer protected by one perimeter.

Identity becomes the new security boundary.

---

# Components of Zero Trust

Zero Trust commonly includes

- Strong Authentication
- Multi-Factor Authentication
- Least Privilege
- Device Verification
- Continuous Authorization
- mTLS
- Microsegmentation
- Policy Enforcement

---

# Real-World Example

Imagine Google.

Employees work from

- Home
- Airports
- Coffee Shops
- Offices

Instead of trusting corporate Wi-Fi,

Google verifies

- Identity
- Device Health
- Location
- Risk Score

before granting access.

---

# Web Application Firewall (WAF)

Applications exposed to the Internet constantly receive malicious traffic.

Examples include

- SQL Injection
- Cross-Site Scripting
- Bot Traffic
- Credential Stuffing

Applications need protection before requests reach backend servers.

---

# What is a WAF?

A **Web Application Firewall (WAF)** filters HTTP requests before they reach the application.

It blocks suspicious requests automatically.

---

# Real-Life Analogy

Imagine airport security.

Passengers first pass through security screening.

Dangerous items are stopped before reaching the airplane.

A WAF performs the same function for web applications.

---

# WAF Architecture

```text
Internet

↓

WAF

↓

Load Balancer

↓

Application
```

Malicious requests are filtered before reaching production systems.

---

# What Can a WAF Detect?

A modern WAF detects

- SQL Injection
- Cross-Site Scripting (XSS)
- Command Injection
- Directory Traversal
- Malicious Bots
- Rate Limit Violations
- Known Attack Patterns

Many cloud providers offer managed WAF services.

# OWASP API Top 10

OWASP

(Open Worldwide Application Security Project)

publishes the most common API security risks.

Every backend engineer should understand these threats.

---

# Why OWASP Matters

Most successful cyberattacks exploit

basic application mistakes,

not advanced hacking techniques.

Understanding OWASP helps developers avoid these common vulnerabilities.

---

# OWASP API Top 10 (High Level)

## 1. Broken Object Level Authorization

Users access resources belonging to other users.

Example

Changing

```
/users/123
```

to

```
/users/124
```

and retrieving someone else's data.

---

## 2. Broken Authentication

Weak authentication mechanisms allow attackers to impersonate users.

Examples

- Weak Passwords
- Stolen Tokens
- Session Hijacking

---

## 3. Broken Object Property Level Authorization

Sensitive fields are exposed or modified without proper authorization.

---

## 4. Unrestricted Resource Consumption

Attackers exhaust server resources using excessive requests.

Examples

- API Abuse
- Expensive Queries
- Large File Uploads

---

## 5. Broken Function Level Authorization

Users access administrator functions without sufficient permissions.

---

## 6. Unrestricted Access to Sensitive Business Flows

Business workflows lack proper rate limits or abuse protection.

Example

Unlimited coupon generation.

---

## 7. Server Side Request Forgery (SSRF)

Attackers trick servers into making requests to internal systems.

---

## 8. Security Misconfiguration

Improper configuration exposes sensitive functionality.

Examples

- Debug Mode Enabled
- Open Buckets
- Default Passwords

---

## 9. Improper Inventory Management

Forgotten or deprecated APIs remain publicly accessible.

---

## 10. Unsafe Consumption of APIs

Applications blindly trust external APIs without proper validation.

# Secure Production Architecture

A secure cloud-native application combines multiple security layers.

```text
                   User
                     │
                     ▼
             Authentication
                     │
                     ▼
             Authorization
          (RBAC / ABAC Policies)
                     │
                     ▼
               Zero Trust
                     │
                     ▼
                   WAF
                     │
                     ▼
              Load Balancer
                     │
                     ▼
             Kubernetes Cluster
                     │
                     ▼
          mTLS Between Services
                     │
                     ▼
        Databases & Internal APIs
```

Security exists at every layer.

No single mechanism is sufficient.

---

# Real-World Example

Imagine an online banking application.

A customer logs in using OAuth and MFA.

RBAC ensures they can only access their own accounts.

The backend also checks ABAC policies,

such as preventing international transfers from unknown devices.

Every API request passes through a WAF,

which blocks SQL Injection and malicious bots.

Communication between microservices uses mTLS.

Even if an attacker gains access to one service,

Zero Trust requires every subsequent request to be re-authenticated and authorized.

Multiple security layers work together to protect customer data.

# Key Takeaways

- **RBAC** grants permissions through predefined roles and is widely used in enterprise applications and Kubernetes.
- **ABAC** makes authorization decisions using user, resource, action, and environment attributes, enabling fine-grained access control.
- **Zero Trust** replaces the traditional trusted-network model with continuous identity verification and least-privilege access.
- **Web Application Firewalls (WAFs)** inspect and filter HTTP traffic to block common web attacks before they reach applications.
- The **OWASP API Top 10** highlights the most common security vulnerabilities affecting modern APIs and should guide secure API design.
- Enterprise security relies on multiple layers including authentication, authorization, Zero Trust, WAFs, encryption, and secure infrastructure rather than any single security mechanism.
