# Introduction

In the previous part, we learned how Kubernetes works internally.

We learned about:

- API Server
- etcd
- Scheduler
- Worker Nodes
- Kubelet

However, Kubernetes still needs a way to describe **what should run inside the cluster.**

Imagine telling Kubernetes:

> "Run my application."

That isn't enough.

Kubernetes needs much more information.

- Which application?
- How many copies?
- Should failed containers restart?
- Should updates happen automatically?
- Does the application store data?
- Should it run once or continuously?

Instead of asking these questions every time,

Kubernetes introduces **Objects.**

Objects describe the **desired state** of the cluster.

---

# What are Kubernetes Objects?

A Kubernetes Object is a configuration that tells Kubernetes

> **what should exist inside the cluster.**

Instead of manually starting containers,

developers declare

```text
"I want three replicas of my application."
```

Kubernetes continuously works to make reality match that declaration.

---

# Real-Life Analogy

Imagine placing an online shopping order.

You don't tell the warehouse

- Pick Box A
- Walk to Shelf 3
- Pack the item
- Call the courier

Instead,

you simply place the order.

The warehouse figures out **how** to fulfill it.

Kubernetes works the same way.

You describe the desired outcome.

Kubernetes handles the implementation.

---

# Desired State vs Actual State

This is one of Kubernetes' most important ideas.

Desired State

```text
Run 5 Containers
```

Actual State

```text
Only 4 Containers Running
```

Kubernetes immediately notices the difference.

It automatically starts another container.

```text
Desired

↓

Actual

↓

Mismatch

↓

Automatic Recovery
```

This continuous reconciliation loop is one of Kubernetes' defining features.

---

# Pod

The smallest deployable unit in Kubernetes is **not** a container.

It is a **Pod**.

---

# What is a Pod?

A Pod is

> **A group of one or more containers that share networking and storage.**

Most Pods contain exactly one container.

However,

multiple tightly coupled containers can run together inside the same Pod.

---

# Why Doesn't Kubernetes Run Containers Directly?

Imagine a web application.

Besides the main application,

you might also need

- Logging Agent
- Monitoring Agent
- Proxy Server

These components should always stay together.

Instead of managing each container independently,

Kubernetes groups them into one Pod.

---

# Real-Life Analogy

Imagine a family living in a house.

The house contains

- Parents
- Children
- Shared Kitchen
- Shared Bathroom

They live together because they are closely related.

A Pod is that house.

Containers inside the Pod share resources just like family members share the house.

---

# Pod Architecture

```text
Pod

├── Application Container

├── Logging Sidecar

└── Shared Network
```

Every container inside the Pod shares

- IP Address
- Network Namespace
- Storage Volumes

---

# Pod Lifecycle

A Pod typically follows this lifecycle.

```text
Created

↓

Scheduled

↓

Running

↓

Succeeded / Failed

↓

Deleted
```

Pods are designed to be **temporary**.

If a Pod fails,

Kubernetes usually creates a brand-new Pod instead of repairing the old one.

---

# ReplicaSet

Suppose your application has only one Pod.

```text
Web Application

↓

Pod
```

If that Pod crashes,

your application becomes unavailable.

Clearly,

one Pod is not enough.

---

# What is a ReplicaSet?

A ReplicaSet ensures that a specified number of identical Pods are always running.

Example

Desired State

```text
3 Pods
```

Current State

```text
2 Pods
```

ReplicaSet immediately creates

```text
1 New Pod
```

until the desired state is restored.

---

# Real-Life Analogy

Imagine a hotel.

Management requires

```
10 Receptionists
```

If one receptionist resigns,

the hotel hires another immediately.

Customers should never notice a shortage.

ReplicaSets behave exactly like this.

---

# ReplicaSet Architecture

```text
ReplicaSet

↓

Pod 1

↓

Pod 2

↓

Pod 3
```

If Pod 2 fails

```text
ReplicaSet

↓

Pod 1

↓

Pod 3

↓

New Pod
```

The ReplicaSet restores the missing replica automatically.

---

# Deployment

Although ReplicaSets are useful,

developers rarely create them directly.

Instead,

they use **Deployments**.

---

# Why Deployments?

Imagine version updates.

Application Version 1

↓

Application Version 2

Without Deployments,

updating thousands of Pods would be difficult.

Deployments automate this process.

---

# What is a Deployment?

A Deployment manages ReplicaSets.

It provides

- Rolling Updates
- Rollbacks
- Version History
- Replica Management

Think of it as a higher-level controller.

---

# Real-Life Analogy

Imagine a school principal.

The principal doesn't teach students directly.

Instead,

the principal manages teachers.

Teachers manage classrooms.

Similarly,

Deployment

↓

ReplicaSet

↓

Pods

Each level manages the next.

---

# Deployment Architecture

```text
Deployment

↓

ReplicaSet

↓

Pods
```

Developers usually interact only with the Deployment.

---

# Rolling Updates

Suppose your application runs

```text
Version 1
```

You release

```text
Version 2
```

Should Kubernetes stop all Pods and restart everything?

No.

Instead,

it performs a **Rolling Update**.

```text
Pod V1

↓

Pod V2

↓

Pod V1

↓

Pod V2

↓

Pod V2

↓

Pod V2
```

Users experience little or no downtime.

---

# StatefulSet

Not every application is stateless.

Databases require

- Persistent Storage
- Stable Hostnames
- Ordered Startup

ReplicaSets cannot guarantee these properties.

---

# What is a StatefulSet?

A StatefulSet manages stateful applications.

Examples include

- MySQL
- PostgreSQL
- MongoDB
- Cassandra
- Kafka
- Elasticsearch

Unlike Deployments,

Pods receive stable identities.

Example

```text
mysql-0

mysql-1

mysql-2
```

These names never change.

---

# Real-Life Analogy

Imagine a hotel assigning room numbers.

Guests always know

Room 101

Room 102

Room 103

Changing room numbers every day would create chaos.

StatefulSets maintain stable identities in the same way.

---

# Deployment vs StatefulSet

| Deployment | StatefulSet |
|------------|-------------|
| Stateless Applications | Stateful Applications |
| Dynamic Pod Names | Stable Pod Names |
| Shared Storage | Dedicated Persistent Storage |
| Parallel Startup | Ordered Startup |
| Web Servers | Databases |

---

# DaemonSet

Some applications must run on **every node**.

Examples include

- Monitoring Agents
- Logging Agents
- Security Scanners

Instead of creating Pods manually,

Kubernetes provides DaemonSets.

---

# What is a DaemonSet?

A DaemonSet ensures

> **Exactly one Pod runs on every Worker Node.**

Suppose the cluster has

```
5 Nodes
```

The DaemonSet automatically creates

```
5 Pods
```

One on each node.

---

# Real-Life Analogy

Imagine installing CCTV cameras.

Every floor of a building requires one camera.

Whenever a new floor is constructed,

another camera is installed automatically.

DaemonSets behave the same way.

---

# DaemonSet Architecture

```text
Node 1

↓

Monitoring Agent
```

```text
Node 2

↓

Monitoring Agent
```

```text
Node 3

↓

Monitoring Agent
```

---

# Job

Most Kubernetes applications run continuously.

However,

some workloads should execute only once.

Example

- Database Migration
- Backup Script
- Report Generation

---

# What is a Job?

A Job ensures

> **A task runs until it successfully completes.**

After completion,

the Pod exits.

Unlike Deployments,

Jobs are not restarted indefinitely.

---

# Real-Life Analogy

Imagine printing payroll.

Once the payroll report finishes,

the printer stops.

There is no need to keep printing forever.

Jobs work similarly.

---

# CronJob

Some tasks should execute repeatedly.

Examples include

- Nightly Database Backup
- Daily Reports
- Weekly Cleanup
- Monthly Billing

---

# What is a CronJob?

A CronJob schedules Jobs automatically.

Example

```text
Every Midnight

↓

Database Backup
```

↓

```text
Every Sunday

↓

Cleanup Logs
```

---

# Real-Life Analogy

Imagine setting an alarm.

Every morning at

```
7:00 AM
```

the alarm rings automatically.

CronJobs work exactly the same way.

---

# Choosing the Right Kubernetes Object

| Requirement | Kubernetes Object |
|-------------|-------------------|
| Run one application | Pod |
| Maintain fixed replicas | ReplicaSet |
| Deploy production applications | Deployment |
| Run databases | StatefulSet |
| Run one Pod per node | DaemonSet |
| Execute once | Job |
| Execute on a schedule | CronJob |

---

# Complete Object Hierarchy

A production deployment typically looks like this.

```text
Deployment
      │
      ▼
ReplicaSet
      │
      ▼
Pods
      │
      ▼
Containers
```

This hierarchy is the foundation of nearly every Kubernetes application.

---

# Real-World Example

Imagine Spotify deploying its recommendation service.

The application uses:

- Deployment → manages application updates.
- ReplicaSet → maintains 20 running Pods.
- Pods → run the recommendation containers.
- DaemonSet → deploys monitoring agents on every node.
- StatefulSet → manages Kafka and PostgreSQL.
- CronJob → performs nightly database backups.

Each Kubernetes Object has a specific responsibility,

and together they form a complete production platform.

---

# Key Takeaways

- Kubernetes Objects define the **desired state** of the cluster.
- A **Pod** is the smallest deployable unit and contains one or more tightly coupled containers.
- **ReplicaSets** maintain a fixed number of running Pods and provide high availability.
- **Deployments** manage ReplicaSets and support rolling updates, rollbacks, and version management.
- **StatefulSets** are designed for stateful applications requiring stable identities and persistent storage.
- **DaemonSets** ensure one Pod runs on every Worker Node, making them ideal for monitoring and logging agents.
- **Jobs** execute one-time tasks, while **CronJobs** schedule recurring tasks.
- Understanding when to use each Kubernetes Object is essential for designing reliable, scalable, and production-ready cloud-native applications.
