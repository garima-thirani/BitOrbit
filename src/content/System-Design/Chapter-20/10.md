# Introduction

So far in this chapter, we have learned how Kubernetes

- Runs containers
- Manages Pods
- Provides networking
- Handles storage
- Automatically scales applications
- Packages deployments using Helm

However, one critical question remains.

> **How do companies deploy new software without taking their applications offline?**

Imagine you're Netflix.

Millions of users are watching movies.

You discover a bug.

You need to deploy a fix.

Should you stop every server,

install the update,

and restart everything?

Obviously not.

- Automated
- Reversible
- Zero downtime

---

# The Traditional Deployment Problem

Years ago, deployments looked like this.

```text
Developer

↓

SSH into Server

↓

Copy Files

↓

Restart Application

↓

Hope Everything Works
```

Problems quickly appeared.

- Human mistakes
- Inconsistent servers
- No deployment history
- Difficult rollbacks
- Configuration drift

Every production server slowly became different.

---

# Real-Life Analogy

Imagine maintaining 500 restaurants.

Instead of following a recipe,

each chef modifies dishes independently.

After six months,

every restaurant serves different food.

Chaos.

This is exactly what happens when engineers manually update servers.

---

# Infrastructure as Code

Modern cloud systems follow a different philosophy.

Instead of modifying infrastructure manually,

everything is defined as code.

Examples include

- Kubernetes YAML
- Helm Charts
- Terraform
- Git

If infrastructure changes,

the code changes first.

Production automatically follows.

This principle forms the foundation of GitOps.

---

# What is GitOps?

GitOps is an operational model where

> **Git becomes the single source of truth for infrastructure and application deployments.**

Instead of engineers directly changing production,

they update Git.

Git then drives the deployment.

---

# Traditional Deployment

```text
Developer

↓

Production Server

↓

Manual Changes
```

---

# GitOps Deployment

```text
Developer

↓

Git Repository

↓

GitOps Controller

↓

Kubernetes Cluster
```

Notice something important.

Nobody manually changes production anymore.

Everything originates from Git.

---

# Real-Life Analogy

Imagine building construction.

Workers never modify blueprints on-site.

Instead,

architects update the master blueprint.

Construction always follows the latest approved version.

Git plays the role of the master blueprint.

---

# Why GitOps?

GitOps provides several advantages.

---

## Version Control

Every infrastructure change is recorded.

You know

- who changed it,
- when it changed,
- why it changed.

---

## Automatic Deployment

Once code is merged,

deployment happens automatically.

No manual intervention is required.

---

## Easy Rollbacks

Every previous version already exists inside Git.

Returning to an earlier deployment becomes simple.

---

## Auditing

Every deployment has a complete history.

This is especially important for regulated industries.

---

# ArgoCD

GitOps requires software that continuously watches Git.

One of the most popular tools is **ArgoCD**.

---

# What is ArgoCD?

ArgoCD is a Kubernetes-native GitOps controller.

Its responsibility is simple.

```text
Watch Git

↓

Detect Changes

↓

Synchronize Kubernetes
```

Whenever Git changes,

ArgoCD automatically updates the cluster.

---

# Real-Life Analogy

Imagine Google Drive.

When you edit a document,

everyone automatically receives the latest version.

You don't manually email updated copies.

ArgoCD behaves similarly.

It continuously synchronizes Kubernetes with Git.

---

# ArgoCD Workflow

```text
Developer

↓

Git Push

↓

Git Repository

↓

ArgoCD

↓

Kubernetes Cluster

↓

Running Application
```

Git always remains the source of truth.

---

# Drift Detection

Suppose someone manually changes production.

The Kubernetes cluster no longer matches Git.

ArgoCD immediately detects this difference.

It can automatically restore production to the desired state.

This process is called

**Drift Detection.**

---

# Real-Life Analogy

Imagine a school timetable.

Someone manually changes one classroom assignment.

The central scheduling system detects the mismatch

and restores the official schedule.

GitOps controllers perform the same function.

# Deployment Strategies

Deploying new software isn't simply

```
Replace Old Version
```

Modern systems use carefully designed deployment strategies.

The most common are

- Blue-Green Deployment
- Canary Deployment
- Rolling Update

---

# Blue-Green Deployment

Imagine two production environments.

```text
Blue

(Current Version)
```

```text
Green

(New Version)
```

Users initially access

```
Blue
```

Meanwhile,

the new application is deployed to

```
Green.
```

After testing,

traffic switches instantly.

---

# Architecture

```text
Users

↓

Load Balancer

↓

Blue Environment
```

↓

Deploy New Version

↓

```text
Green Environment
```

↓

Switch Traffic

↓

```text
Users

↓

Green Environment
```

---

# Real-Life Analogy

Imagine replacing a bridge.

Instead of repairing the existing bridge,

engineers build a brand-new bridge beside it.

Once completed,

traffic moves to the new bridge.

The old bridge remains available if something goes wrong.

---

# Advantages

- Zero Downtime
- Instant Rollback
- Safe Testing

---

# Disadvantages

Maintaining two production environments doubles infrastructure costs during deployment.

# Canary Deployment

Instead of switching all users,

Canary Deployments expose the new version gradually.

Example

```
5%

↓

20%

↓

50%

↓

100%
```

Traffic increases only if the application remains healthy.

---

# Real-Life Analogy

Imagine launching a new restaurant menu.

Instead of offering it nationwide,

you test it in one city first.

If customers like it,

you expand nationally.

Canary Deployments follow the same idea.

---

# Canary Architecture

```text
Users

↓

Load Balancer

├── 95% → Version 1

└── 5% → Version 2
```

If Version 2 performs well,

its percentage increases.

---

# Advantages

- Lower deployment risk.
- Early bug detection.
- Easy rollback.
- Real user validation.

---

# Rolling Updates

Kubernetes uses Rolling Updates by default.

Instead of replacing every Pod simultaneously,

Pods are updated gradually.

---

# Example

```text

Pod V1
```

Deployment begins.

```text
Pod V2

Pod V1

Pod V1

Pod V1
```

↓

```text
Pod V2

Pod V2

Pod V1

Pod V1
```

↓

```text
Pod V2

Pod V2

Pod V2

Pod V2
```

Users continue using the application throughout the update.

---

# Real-Life Analogy

Imagine replacing seats in a movie theater.

Instead of closing the entire theater,

workers replace one row at a time.

The theater continues operating.

---

# Rollbacks

Despite careful testing,

deployments sometimes fail.

Applications may experience

- Bugs
- Performance Issues
- Crashes

Production systems must recover immediately.

---

# What is a Rollback?

A Rollback restores the previous stable version.

Example

```text
Version 1

↓

Deploy Version 2

↓

Errors Detected

↓

Rollback

↓

Version 1 Restored
```

Downtime remains minimal.

---

# Real-Life Analogy

Imagine updating your smartphone.

The new update causes problems.

You restore yesterday's backup.

Rollbacks work exactly the same way.

# Real-World Example

Imagine Spotify deploying a new music recommendation algorithm.

The developer commits code.

GitHub Actions automatically builds a Docker Image.

The image is pushed to a container registry.

The Helm Chart is updated with the new image version.

ArgoCD detects the Git change.

Kubernetes performs a Canary Deployment.

Initially,

only **5%** of users receive the new recommendation engine.

Monitoring systems watch

- Error Rate
- Latency
- CPU Usage

If everything looks healthy,

traffic gradually increases to

100%.

If errors increase,

ArgoCD rolls back automatically.

Millions of users continue streaming music without interruption.

# Best Practices

Production organizations typically follow these practices.

- Treat Git as the single source of truth.
- Never modify production manually.
- Use GitOps controllers such as ArgoCD.
- Automate deployments through CI/CD pipelines.
- Prefer Rolling Updates for standard services.
- Use Canary Deployments for high-risk releases.
- Use Blue-Green Deployments when instant rollback is critical.
- Continuously monitor deployments and automate rollback on failures.

# Key Takeaways

- Traditional deployments relied on manual server changes, leading to configuration drift and operational risk.
- **GitOps** uses Git as the single source of truth for both infrastructure and application deployments.
- **ArgoCD** continuously synchronizes Kubernetes clusters with Git repositories and detects configuration drift.
- **Blue-Green Deployments** use two identical production environments, enabling instant traffic switching and rollbacks.
- **Canary Deployments** gradually expose new versions to a small percentage of users before full rollout.
- **Rolling Updates** replace application Pods incrementally, allowing zero-downtime deployments.
- **Rollbacks** restore previous stable versions when new deployments fail.
- Modern cloud-native organizations combine **CI/CD, Docker, Helm, ArgoCD, and Kubernetes** to automate safe, reliable software delivery.
