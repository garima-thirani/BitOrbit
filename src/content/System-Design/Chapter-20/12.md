# Multi-AZ Architecture

One of the first production principles is

**Never depend on a single data center.**

Cloud providers divide Regions into multiple

**Availability Zones (AZs).**

Each Availability Zone contains

- Independent power
- Independent networking
- Independent cooling

This prevents localized failures.

---

# Real-Life Analogy

Imagine opening three bank branches.

Instead of placing every employee in one building,

you distribute them across

- Downtown
- East Side
- West Side

If one branch loses power,

the other branches continue serving customers.

Multi-AZ works exactly the same way.

---

# Kubernetes Across Multiple AZs

A production cluster distributes Worker Nodes across multiple zones.

```text
Region

├── AZ-1

│      Node A

│      Node B

├── AZ-2

│      Node C

│      Node D

└── AZ-3

       Node E

       Node F
```

If one Availability Zone fails,

the remaining zones continue serving traffic.

# Health Checks

Production Kubernetes continuously monitors applications.

Two important health checks are

### Liveness Probe

Answers

> "Should this container be restarted?"

If the application becomes stuck,

Kubernetes restarts it automatically.

---

### Readiness Probe

Answers

> "Can this Pod receive traffic?"

Suppose a Pod is still starting.

The application should not receive requests yet.

The Readiness Probe prevents traffic until initialization completes.

---

# Real-Life Analogy

Imagine opening a restaurant.

Customers should only enter after

- Tables are arranged
- Kitchen is ready
- Staff are prepared

Readiness Probes ensure applications receive traffic only when ready.

# Self-Healing in Production

Suppose a Worker Node suddenly crashes.

The sequence looks like this.

```text
Node Failure

↓

Pods Become Unavailable

↓

Scheduler Detects Failure

↓

Pods Created on Healthy Nodes

↓

Load Balancer Redirects Traffic
```

The system automatically heals itself.

# Disaster Recovery

Even highly available systems can experience catastrophic failures.

Examples include

- Entire Region Failure
- Natural Disaster
- Cloud Outage
- Human Error
- Data Corruption

Disaster Recovery prepares for these situations.

---

# What is Disaster Recovery?

Disaster Recovery (DR) is the ability to restore services after a catastrophic failure.

Unlike High Availability,

which handles small failures,

Disaster Recovery focuses on large-scale outages.

---

# Real-Life Analogy

Imagine a city hospital.

If one operating room becomes unavailable,

patients move to another room.

That's High Availability.

If the entire hospital is destroyed,

patients move to another hospital.

That's Disaster Recovery.

---

# Real-World Example

Imagine Spotify's music streaming platform.

A user opens the mobile app.

The request flows through

```text
DNS

↓

Load Balancer

↓

Ingress

↓

Frontend Pods

↓

Recommendation Service

↓

User Service

↓

Playlist Service

↓

Database
```

Meanwhile,

Kubernetes continuously performs background operations.

- HPA adds Pods during peak listening hours.
- Cluster Autoscaler provisions additional cloud instances.
- Istio encrypts communication using mTLS.
- Prometheus collects metrics.
- Grafana displays dashboards.
- ArgoCD deploys new versions.
- Helm manages application releases.
- If a Node crashes, Pods restart automatically.
- If an Availability Zone fails, traffic shifts to healthy zones.
- If an entire Region fails, disaster recovery activates the backup cluster.

To the user,

music never stops playing.

This level of reliability is the goal of Production Kubernetes.
