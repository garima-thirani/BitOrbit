# Introduction

So far, we have learned how Kubernetes

- deploys applications,
- manages Pods,
- provides networking,
- performs load balancing.

However, every production application requires more than just code.

Consider a simple E-Commerce application.

It needs

- Database URL
- Redis Host
- API Keys
- JWT Secret
- AWS Credentials
- SSL Certificates
- Uploaded Images
- Database Storage

Should all of these values be hardcoded into the application?

Absolutely not.

Imagine changing the production database password.

Would you rebuild the entire Docker image?

That would be inefficient and dangerous.

Kubernetes solves this problem using

- ConfigMaps
- Secrets
- Volumes
- Persistent Volumes
- Storage Classes

---

# The Problem with Hardcoded Configuration

Suppose we write

```text
Database Host = localhost

Database Password = admin123
```

inside our application.

Everything works during development.

Now we deploy to production.

The production database is

```text
db.production.company.com
```

The password is different.

The application must now be rebuilt.

Every environment requires different code.

This quickly becomes impossible to manage.

---

# Real-Life Analogy

Imagine printing a restaurant menu.

The food recipes remain the same.

Only today's prices change.

Would the chef rewrite every recipe every morning?

Of course not.

The recipe stays constant.

Only the menu changes.

Configuration works exactly the same way.

Application code stays the same.

Configuration changes depending on the environment.

---

# Configuration vs Application

A production application consists of two parts.

```text
Application Code

+

Configuration
```

The application should never depend on hardcoded values.

Instead,

configuration should be injected during deployment.

---

# What is a ConfigMap?

A **ConfigMap** stores non-sensitive configuration data outside the application.

Examples include

- Database Host
- Redis Host
- API URLs
- Feature Flags
- Application Mode
- Logging Level

Instead of storing these values inside the application,

Kubernetes stores them separately.

---

# Real-Life Analogy

Imagine buying a smartphone.

The operating system is the same for everyone.

Only the settings differ.

- Language
- Wi-Fi Password
- Time Zone
- Wallpaper

The operating system is the application.

The settings are the ConfigMap.

---

# Example

Instead of

```text
Database Host = localhost
```

inside the application,

Kubernetes stores

```text
Database Host

↓

db.company.internal
```

When the Pod starts,

it automatically receives this value.

The application never changes.

Only the configuration changes.

---

# Why ConfigMaps Matter

Imagine three environments.

```text
Development

↓

localhost
```

```text
Testing

↓

test-db.company.com
```

```text
Production

↓

prod-db.company.com
```

The same Docker Image runs everywhere.

Only the ConfigMap changes.

---

# Kubernetes Secrets

Some configuration is public.

Some configuration is highly sensitive.

Examples include

- Database Passwords
- API Keys
- JWT Signing Keys
- OAuth Credentials
- TLS Certificates

These should never be stored inside ConfigMaps.

Kubernetes provides **Secrets**.

---

# What is a Secret?

A Secret stores **sensitive configuration data**.

Unlike ConfigMaps,

Secrets are intended for confidential information.

Examples include

```text
Database Password
```

```text
AWS Access Key
```

```text
Stripe API Key
```

```text
TLS Certificate
```

---

# Real-Life Analogy

Imagine an office.

Everyone knows

- Office Address
- Reception Phone Number

Those are like ConfigMaps.

Only managers know

- Safe Combination
- Bank Password
- Security Codes

Those are Secrets.

---

# ConfigMap vs Secret

| ConfigMap | Secret |
|------------|---------|
| Non-sensitive data | Sensitive data |
| Application Settings | Passwords, Keys |
| Database Host | Database Password |
| Feature Flags | OAuth Tokens |
| Logging Level | TLS Certificates |

---

# Important Note

Although Kubernetes stores Secrets separately,

they are **Base64 encoded, not encrypted by default**.

Production environments usually combine Secrets with

- HashiCorp Vault
- AWS Secrets Manager
- Azure Key Vault
- Google Secret Manager

to provide stronger protection.

# Volumes

Containers are temporary.

Suppose an application stores

```
User Uploaded Images
```

inside the container.

The container crashes.

A new container starts.

All uploaded images disappear.

Clearly,

containers cannot permanently store important data.

---

# What is a Volume?

A Volume provides storage that exists independently of the container.

Instead of storing files inside the container,

they are stored in a separate location.

```text
Container

↓

Volume

↓

Storage
```

If the container restarts,

the data remains.

---

# Real-Life Analogy

Imagine renting an apartment.

Furniture belongs to the apartment.

Your luggage belongs to you.

Even if you move to another apartment,

your luggage stays with you.

Volumes behave similarly.

Containers come and go.

Data remains.

---

# Types of Volumes

Kubernetes supports multiple volume types.

Examples include

- EmptyDir
- HostPath
- Persistent Volumes
- Cloud Storage
- NFS

Production systems usually use Persistent Volumes.

---

# Persistent Volume (PV)

Suppose a PostgreSQL Pod stores

```
1 TB
```

of customer data.

The Pod crashes.

Should the database disappear?

Obviously not.

The database must survive Pod failures.

Persistent Volumes solve this problem.

---

# What is a Persistent Volume?

A Persistent Volume (PV) represents durable storage managed by Kubernetes.

Unlike containers,

Persistent Volumes continue to exist even after Pods are deleted.

Examples include

- AWS EBS
- Azure Managed Disks
- Google Persistent Disks
- NFS
- SAN Storage

---

# Real-Life Analogy

Imagine buying a house.

People may move in or out.

The house remains.

The house represents the Persistent Volume.

The tenants represent Pods.

---

# Persistent Volume Claim (PVC)

Pods should not directly manage storage.

Instead,

they request storage.

This request is called a

**Persistent Volume Claim (PVC).**

---

# Why PVC Exists

Imagine staying in a hotel.

You don't choose

Room 407

specifically.

You simply request

```
One Deluxe Room
```

The hotel assigns an available room.

Similarly,

Pods request

```
100 GB SSD Storage
```

Kubernetes finds a suitable Persistent Volume.

---

# PV and PVC Relationship

```text
Application

↓

Persistent Volume Claim

↓

Persistent Volume

↓

Cloud Storage
```

Pods communicate only with the PVC.

Kubernetes handles everything else.

---

# Storage Classes

Suppose an organization offers multiple storage types.

- SSD
- HDD
- High IOPS SSD
- Encrypted Storage

Should administrators manually create every Persistent Volume?

That wouldn't scale.

Kubernetes introduces **Storage Classes**.

---

# What is a Storage Class?

A Storage Class defines

**how storage should be created automatically.**

Instead of creating storage first,

developers simply specify

```text
SSD Storage
```

or

```text
High Performance Storage
```

Kubernetes provisions the storage automatically.

---

# Real-Life Analogy

Imagine booking a hotel.

Instead of choosing

Room 301

you simply choose

```
Deluxe Room
```

The hotel assigns an available room matching that category.

Storage Classes work exactly the same way.

---

# Dynamic Provisioning

Without Storage Classes

```text
Administrator

↓

Create Storage

↓

Developer Uses Storage
```

With Storage Classes

```text
Developer Requests Storage

↓

Storage Class

↓

Automatic Provisioning

↓

Persistent Volume Created
```

No administrator intervention is required.

---

# Complete Storage Lifecycle

Suppose a PostgreSQL database is deployed.

The process looks like this.

```text
Deployment
      │
      ▼
PostgreSQL Pod
      │
      ▼
Persistent Volume Claim
      │
      ▼
Storage Class
      │
      ▼
Persistent Volume
      │
      ▼
Cloud Disk
```

Even if the Pod crashes,

the Cloud Disk remains.

A new Pod reconnects to the same storage.

---

# Real-World Example

Imagine Netflix.

Their recommendation service stores user preferences.

The application runs inside Pods.

Application settings such as

- Recommendation Threshold
- Cache Duration
- Feature Flags

are stored in ConfigMaps.

Database passwords are stored in Secrets.

User viewing history is stored on Persistent Volumes backed by cloud storage.

When Kubernetes replaces a failed Pod,

the new Pod reconnects to the existing Persistent Volume.

No user data is lost.

---

# Putting Everything Together

A production Kubernetes application typically looks like this.

```text
                 Deployment
                      │
                      ▼
                    Pod
      ┌─────────────┼─────────────┐
      ▼             ▼             ▼
 ConfigMap      Secret         Volume
      │             │             │
      ▼             ▼             ▼
 Application   Credentials   Persistent Data
                                    │
                                    ▼
                         Persistent Volume Claim
                                    │
                                    ▼
                           Storage Class
                                    │
                                    ▼
                           Persistent Volume
                                    │
                                    ▼
                           Cloud Storage / Disk
```

Notice how configuration,

credentials,

and persistent data are all managed independently of the application itself.

---

# Best Practices

For production Kubernetes applications:

- Never hardcode configuration inside Docker Images.
- Store application settings in ConfigMaps.
- Store sensitive information in Secrets.
- Use Persistent Volumes for databases and uploaded files.
- Use Storage Classes for automatic storage provisioning.
- Use external secret managers for highly sensitive credentials.
- Treat containers as **stateless** whenever possible.

---

# Key Takeaways

- Configuration should always be separated from application code to enable the same container image to run across multiple environments.
- **ConfigMaps** store non-sensitive configuration such as hostnames, feature flags, and application settings.
- **Secrets** store sensitive information such as passwords, API keys, certificates, and authentication tokens.
- **Volumes** provide storage that persists beyond the lifetime of an individual container.
- **Persistent Volumes (PV)** represent durable storage resources managed by Kubernetes.
- **Persistent Volume Claims (PVC)** allow applications to request storage without needing to know the underlying implementation.
- **Storage Classes** automate storage provisioning, enabling dynamic allocation of cloud storage resources.
- Production Kubernetes environments separate application code, configuration, credentials, and persistent data into independent components.
