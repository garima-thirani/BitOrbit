# Introduction

So far in this handbook, we have designed distributed systems.

We've learned about

- Databases
- Distributed Systems
- Kafka
- Elasticsearch
- Microservices
- Event-Driven Architecture

But one important question remains.

> **Once we've built these services, where do they actually run?**

Suppose you've developed a microservice called

```
Payment Service
```

You push the code to GitHub.

Now what?

- Which operating system should run it?
- Which libraries should be installed?
- Which version of Java or Python is required?
- How do we deploy the same application on hundreds of servers?

Understanding this problem is the key to understanding containers.

# The Deployment Problem

Imagine you build a Java application on your laptop.

It works perfectly.

You send it to another developer.

They execute it.

Immediately,

they receive

```text
Java Version Not Found
```

You install Java.

Now another error appears.

```text
Database Driver Missing
```

You fix that.

Another problem appears.

```text
Operating System Dependency Error
```

Eventually someone says the famous sentence every developer has heard.

> **"But it works on my machine."**

---

# Real-Life Analogy

Imagine you're baking a cake.

You carefully measure

- flour
- sugar
- butter
- eggs

The cake comes out perfectly.

Now you give only the recipe to someone else.

They use

- different flour
- different oven
- different measuring cups

The result is completely different.

The recipe wasn't enough.

The environment mattered too.

Software works exactly the same way.

Your code depends on

- Operating System
- Libraries
- Runtime
- Environment Variables
- Configuration Files

Without the correct environment,

the application may fail.

# Before Containers

Before containers,

applications were installed directly on servers.

```text
Application

↓

Operating System

↓

Hardware
```

This created several problems.

---

## Dependency Conflicts

Suppose Server A hosts two applications.

Application 1 requires

```
Python 3.8
```

Application 2 requires

```
Python 3.12
```

Only one version can usually be installed globally.

One application eventually breaks.

---

## Resource Conflicts

Suppose

Application A

consumes

```
95% CPU
```

Application B suddenly becomes extremely slow.

All applications compete for the same resources.

---

## Environment Drift

Development

↓

Testing

↓

Production

All three environments slowly become different.

Example

Development

```
Ubuntu 22
```

Testing

```
Ubuntu 20
```

Production

```
CentOS
```

Eventually,

bugs appear that only exist in production.

---

# The First Solution — Virtual Machines

Virtual Machines attempted to solve these problems.

Instead of installing applications directly on one operating system,

each application received its own virtual computer.

```text
Server

↓

Hypervisor

↓

VM 1

↓

Operating System

↓

Application
```

```text
VM 2

↓

Operating System

↓

Application
```

Each Virtual Machine contained

- Its own OS
- Its own libraries
- Its own runtime
- Its own filesystem

Applications became isolated.

---

# What is a Virtual Machine?

A Virtual Machine (VM) is software that emulates an entire physical computer.

Every VM includes

- Operating System
- Kernel
- Drivers
- Libraries
- Runtime
- Application

To the application,

the VM looks like a real computer.

---

# Real-Life Analogy

Imagine an apartment building.

Every family has

- Their own kitchen
- Their own bedroom
- Their own bathroom
- Their own electricity

They are completely isolated.

Virtual Machines work the same way.

Each VM owns everything independently.

---

# Problems with Virtual Machines

Virtual Machines solved deployment issues,

but introduced new challenges.

---

## Heavyweight

Each VM contains an entire operating system.

Suppose Linux requires

```
1.5 GB
```

Ten VMs require

```
15 GB
```

just for operating systems.

Most of that storage is duplicated.

---

## Slow Startup

Starting a VM is like booting a computer.

It may take

- 30 seconds
- 1 minute
- several minutes

depending on the operating system.

Modern cloud systems often need to scale in seconds.

---

## Resource Waste

Every VM duplicates

- Kernel
- Drivers
- System Libraries

This wastes memory.

---

# Enter Containers

Containers solve the same deployment problem,

but much more efficiently.

Instead of virtualizing hardware,

containers virtualize the operating system.

```text
Applications

↓

Containers

↓

Container Runtime

↓

Host Operating System

↓

Hardware
```

Notice something important.

There is only

**ONE Operating System.**

Every container shares it.

---

# Real-Life Analogy

Imagine a large office building.

Instead of every company constructing its own building,

multiple companies rent offices in the same building.

They share

- Electricity
- Elevators
- Internet
- Water Supply

Yet,

each company has its own

- Employees
- Files
- Computers

Containers work exactly like this.

Applications share the operating system,

but remain isolated.

---

# What is a Container?

A container is

> **A lightweight, isolated runtime environment that packages an application together with everything it needs to run.**

This includes

- Application Code
- Libraries
- Runtime
- Dependencies
- Environment Variables
- Configuration Files

Everything travels together.

Whether the container runs on

- your laptop,
- a cloud VM,
- Kubernetes,
- AWS,
- Azure,
- GCP,

it behaves exactly the same.

---

# Virtual Machines vs Containers

Let's compare them.

## Virtual Machines

```text
Application

↓

Libraries

↓

Guest Operating System

↓

Hypervisor

↓

Host Operating System

↓

Hardware
```

---

## Containers

```text
Application

↓

Libraries

↓

Container Runtime

↓

Host Operating System

↓

Hardware
```

Notice the missing Guest Operating System.

This makes containers dramatically lighter.

---

# Comparison

| Virtual Machine | Container |
|-----------------|-----------|
| Virtualizes Hardware | Virtualizes Operating System |
| Includes Guest OS | Shares Host OS |
| Heavyweight | Lightweight |
| Slow Startup | Starts in Seconds |
| Large Disk Usage | Small Disk Usage |
| Strong Isolation | Process Isolation |
| Higher Resource Usage | Efficient Resource Usage |

---

# Why Containers Became Popular

Containers solved nearly every deployment problem.

## Consistency

The application behaves the same everywhere.

---

## Portability

Build once.

Run anywhere.

---

## Fast Startup

Containers typically start within seconds.

This makes autoscaling practical.

---

## Efficient Resource Utilization

Because containers share the host operating system,

many more containers can run on the same machine than Virtual Machines.

---

## Better Developer Experience

Instead of documenting dozens of installation steps,

developers simply share a container image.

Everyone runs the exact same environment.

---

# Open Container Initiative (OCI)

By 2015,

containers became extremely popular.

However,

every company began creating its own container format.

This threatened compatibility.

The industry needed a common standard.

---

# What is OCI?

The **Open Container Initiative (OCI)** is an open standard that defines

- how container images should be built,
- how containers should run,
- how runtimes should behave.

Think of OCI as the universal specification for containers.

---

# Real-Life Analogy

Imagine USB devices.

Before USB,

every manufacturer had different connectors.

Today,

any USB-compatible device works with any USB-compatible computer.

OCI plays the same role for containers.

It ensures compatibility across different platforms.

---

# Container Runtime

Creating a container image is only the beginning.

Something must actually execute it.

That software is called the **Container Runtime**.

---

# What Does a Container Runtime Do?

The runtime is responsible for

- Creating containers
- Starting processes
- Managing namespaces
- Managing cgroups
- Allocating CPU
- Allocating Memory
- Managing Networking
- Managing Storage

In short,

the runtime turns a container image into a running container.

---

# Real-Life Analogy

Imagine buying furniture from IKEA.

The box contains

- wood
- screws
- instructions

But nothing happens until someone assembles it.

The container image is the IKEA box.

The container runtime is the person assembling it.

---

# Popular Container Runtimes

Some common runtimes include

- runc
- containerd
- CRI-O

Docker itself is **not** the runtime.

Instead,

Docker uses container runtimes underneath.

We'll study this in the next part.

---

# Putting Everything Together

A modern container platform looks like this.

```text
Application Code
        │
        ▼
Container Image
        │
        ▼
Container Runtime
        │
        ▼
Host Operating System
        │
        ▼
Physical Server / Cloud VM
```

This layered architecture makes modern cloud-native deployments possible.

---

# Real-World Example

Imagine Netflix deploying a new recommendation service.

Instead of sending developers a long document saying

- Install Java 21
- Install Redis Client
- Install OpenSSL
- Configure Environment Variables
- Install Dependencies

Netflix builds one container image.

Every production server runs the exact same image.

Whether deployed in

- AWS,
- Kubernetes,
- Testing,
- Production,

the application behaves identically.

This consistency is one of the biggest reasons containers revolutionized software deployment.

# Key Takeaways

- Traditional application deployments often suffered from dependency conflicts, environment drift, and inconsistent runtime environments.
- Virtual Machines solved isolation problems by running separate operating systems but introduced significant storage and memory overhead.
- Containers share the host operating system while packaging applications together with their dependencies, making them lightweight and portable.
- A container is an isolated runtime environment that behaves consistently across development, testing, and production.
- The **Open Container Initiative (OCI)** defines industry standards for container images and runtimes, ensuring interoperability across platforms.
- A **Container Runtime** is responsible for creating, starting, and managing running containers.
- Containers start much faster than Virtual Machines, consume fewer resources, and are the foundation of modern cloud-native applications.
- In the next part, we will explore **Docker**, including its architecture, images, layers, Dockerfiles, and how Docker transformed container technology into a practical tool for developers and production systems.
