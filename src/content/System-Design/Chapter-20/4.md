# Docker Image Build Process

Earlier we learned that Docker builds images from a Dockerfile.

Let's now understand **how** Docker actually builds an image.

Suppose we have a Dockerfile like this.

```dockerfile
FROM ubuntu

RUN apt-get update

RUN apt-get install openjdk

COPY app.jar /app

CMD java -jar /app/app.jar
```

Docker does **not** execute this file all at once.

Instead,

it executes one instruction at a time.

```text
Dockerfile

↓

Instruction 1

↓

Layer 1

↓

Instruction 2

↓

Layer 2

↓

Instruction 3

↓

Layer 3

↓

Instruction 4

↓

Layer 4

↓

Final Image
```

Each instruction creates a brand-new image layer.

---

# Why Layered Builds?

Imagine painting a wall.

First,

you apply primer.

Then,

white paint.

Then,

wall decorations.

If you later change only the decorations,

you don't repaint the entire wall.

You reuse the earlier layers.

Docker follows exactly the same principle.

---

# Build Cache

Docker automatically caches image layers.

Suppose you modify only your application code.

Docker notices that

- Ubuntu didn't change.
- Java didn't change.
- Dependencies didn't change.

Only the application layer is rebuilt.

Instead of rebuilding everything,

Docker reuses cached layers.

---

## Real-Life Analogy

Imagine baking cookies.

The dough,

oven,

and trays remain the same.

Only the chocolate chips change.

Instead of preparing everything again,

you reuse the existing setup.

Docker's build cache works exactly like this.

# Docker Registries

Building an image locally is useful.

But how do we deploy it to

- Testing
- Staging
- Production
- Kubernetes
- Cloud Servers

We need a central image repository.

This is called a **Docker Registry**.

---

# What is a Docker Registry?

A Docker Registry stores Docker Images.

Developers push images.

Servers pull images.

```text
Developer

↓

Push Image

↓

Docker Registry

↓

Pull Image

↓

Production Server
```

The registry becomes the central distribution point.

---

# Popular Registries

Some commonly used registries include

- Docker Hub
- Amazon ECR
- Google Artifact Registry
- Azure Container Registry
- GitHub Container Registry
- Harbor (Self-hosted)

---

# Real-Life Analogy

Imagine the Apple App Store.

Developers upload applications.

Users download applications.

Nobody sends applications directly to every phone.

Docker Registries work the same way.

Images are uploaded once,

then downloaded wherever needed.

# Docker Networking

Containers rarely run alone.

Imagine an e-commerce application.

You might have

```text
Frontend

↓

Backend

↓

Redis

↓

PostgreSQL
```

These containers must communicate with one another.

Docker Networking makes this possible.

---

# Why Networking Matters

Suppose

Frontend

needs to call

Backend.

Backend

needs to connect to

Redis.

Redis

needs to communicate with

PostgreSQL.

Without networking,

none of these containers could exchange data.

---

# Default Docker Network

When Docker starts,

it automatically creates a default network.

```text
Container A

↓

Docker Network

↓

Container B
```

Containers connected to the same network can communicate securely.

---

# Bridge Network

The most common Docker network is the **Bridge Network**.

```text
Host Machine

↓

Bridge Network

├── Backend

├── Redis

├── PostgreSQL
```

Each container receives its own private IP address.

Containers communicate internally,

while remaining isolated from the outside world.

---

# Real-Life Analogy

Imagine an office building.

Employees use the company's private network.

People outside the company cannot directly access internal systems.

Docker Bridge Networks work similarly.

---

# Host Network

Sometimes applications need maximum performance.

Instead of creating a virtual network,

the container directly uses the host's network.

```text
Container

↓

Host Network

↓

Internet
```

This removes network isolation,

but reduces overhead.

---

# Overlay Network

Suppose containers run on multiple servers.

```text
Server A

↓

Container 1
```

```text
Server B

↓

Container 2
```

These containers still need communication.

Docker provides **Overlay Networks**

to connect containers across multiple hosts.

This becomes especially useful in Kubernetes clusters.

# Docker Volumes

Containers are temporary.

Suppose a database runs inside a container.

The container stores

```
Customer Data
```

Now imagine deleting the container.

Without additional storage,

all customer data disappears.

Clearly,

this is unacceptable.

---

# What is a Volume?

A Docker Volume provides **persistent storage**.

Instead of storing data inside the container,

Docker stores it outside.

```text
Container

↓

Volume

↓

Disk
```

If the container is deleted,

the data remains.

---

# Real-Life Analogy

Imagine renting a hotel room.

Your luggage belongs to you,

not the hotel.

Even if you change rooms,

your luggage stays with you.

Docker Volumes work exactly the same way.

Containers come and go.

Data remains.

---

# Why Volumes Matter

Volumes are commonly used for

- Databases
- Uploaded Files
- Logs
- Machine Learning Models
- Configuration Files

Without persistent storage,

containers would lose all information after restarting.

# Docker Compose

Modern applications rarely consist of one container.

Imagine an online shopping platform.

```text
Frontend

Backend

Redis

PostgreSQL

Kafka
```

Starting each container manually would be tedious.

Docker Compose solves this problem.

---

# What is Docker Compose?

Docker Compose manages multiple containers as one application.

Instead of starting containers individually,

developers define everything in a single configuration file.

Conceptually,

Docker Compose describes

- Which containers exist.
- Which images they use.
- How they communicate.
- Which ports they expose.
- Which volumes they mount.

---

# Real-Life Analogy

Imagine organizing a concert.

Instead of calling

- lighting,
- sound,
- security,
- catering,

one by one,

the event organizer coordinates everything.

Docker Compose acts as that organizer.

---

# Production Best Practices

Docker makes deployment simple,

but production environments require additional discipline.

---

## Keep Images Small

Smaller images

- download faster,
- deploy faster,
- consume less storage.

Only install necessary software.

---

## Use Official Base Images

Prefer

```text
ubuntu

python

node

openjdk
```

from trusted sources.

Avoid unknown third-party images.

---

## Avoid Running as Root

Containers should execute using non-root users whenever possible.

This reduces security risks.

---

## Separate Configuration

Do not hardcode

- passwords,
- API keys,
- database credentials.

Instead,

use

- Environment Variables
- Secrets Management
- Kubernetes Secrets

---

## One Process Per Container

A container should have a single responsibility.

Instead of

```text
Web Server

Database

Redis

Cron Job
```

inside one container,

split them into separate containers.

This improves scalability and maintainability.

---

## Health Checks

Containers can fail unexpectedly.

Production systems continuously verify

- Is the application running?
- Is it responding?
- Is it healthy?

Health checks allow orchestrators like Kubernetes to restart unhealthy containers automatically.

# Docker Alone Isn't Enough

Docker is excellent for running containers.

But imagine managing

```
10,000 Containers
```

across

```
500 Servers
```

Questions quickly arise.

- Which server should run each container?
- What happens if a server crashes?
- How do we automatically scale containers?
- How do we update applications without downtime?
- How do we distribute traffic?

Docker does **not** solve these problems.

This is exactly why **Kubernetes** was created.

# Key Takeaways

- Docker builds images incrementally using **layered builds**, allowing efficient caching and faster rebuilds.
- **Docker Registries** store and distribute images across development, testing, and production environments.
- Docker Networking enables containers to communicate using **Bridge**, **Host**, and **Overlay** networks.
- **Docker Volumes** provide persistent storage independent of a container's lifecycle, making them essential for databases and stateful applications.
- **Docker Compose** simplifies multi-container application management by defining services, networks, and volumes in a single configuration.
- Production-ready Docker applications follow best practices such as using small images, avoiding root users, separating configuration, and implementing health checks.
- Docker standardizes application packaging and deployment but does **not** provide orchestration or cluster management.
- In the next part, we begin **Kubernetes**, the container orchestration platform that automates deployment, scaling, networking, and recovery for containerized applications running at production scale.
