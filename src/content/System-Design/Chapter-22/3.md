# Introduction

In the previous part, we learned that Large Language Models convert text into **Embeddings**.

But a question naturally arises.

> **Where do these embeddings get stored?**

Suppose a company has

- 500 million documents
- 20 million products
- 5 billion support tickets

Every document has already been converted into an embedding.

When a user asks

> "How do I reset my password?"

the AI system must search through billions of embeddings and find the most relevant documents.

Scanning every embedding would be far too slow.

This is the problem Vector Databases solve.

---

# The Problem with Traditional Databases

Suppose you have a SQL database containing books.

| ID | Title |
|----|----------------------------|
| 1 | Learning Kubernetes |
| 2 | Mastering Redis |
| 3 | AI System Design |

Finding

```
Title = 'Learning Kubernetes'
```

is easy.

Databases excel at exact lookups.

---

Now imagine searching

```
Books about deploying distributed applications
```

None of the titles contain those exact words.

Yet,

"Learning Kubernetes"

is clearly the most relevant result.

Traditional databases cannot understand meaning.

They only compare values.

---

# Real-Life Analogy

Imagine asking a librarian

> "Give me books similar to Harry Potter."

A traditional database behaves like a robot.

It searches only for

```
Harry Potter
```

A human librarian understands

- Magic
- Fantasy
- Wizards
- Adventure

and recommends

- Percy Jackson
- The Hobbit
- Eragon

Vector databases behave more like the librarian.

---

# Why Vector Databases?

Large Language Models understand meaning using embeddings.

Traditional databases understand

- Numbers
- Strings
- Dates

These are completely different worlds.

Vector databases bridge that gap.

Instead of storing text,

they store **vectors representing meaning.**

---

# What is a Vector Database?

A Vector Database is a database optimized for storing, indexing, and searching high-dimensional vectors.

Unlike SQL databases,

queries are based on

> **Similarity**

instead of

> **Exact Matching**

---

# Traditional Database vs Vector Database

| Traditional Database | Vector Database |
|----------------------|-----------------|
| Exact Match | Similarity Search |
| SQL Queries | Vector Queries |
| Strings | Embeddings |
| B+ Trees | ANN Indexes |
| Equality Search | Semantic Search |

---

# Embedding Vectors

Earlier,

we learned that LLMs convert text into embeddings.

But what exactly is an embedding?

---

# What is an Embedding?

An embedding is a numerical representation of meaning.

Instead of storing words,

the model stores hundreds or thousands of numbers.

Example

```
Redis
```

may become

```text
[0.23, -0.41, 0.92, ...]
```

Another word

```
Memcached
```

may become

```text
[0.20, -0.39, 0.88, ...]
```

Because both technologies are related,

their vectors are close together.

---

# Real-Life Analogy

Imagine every city represented by GPS coordinates.

Cities close together

are geographically similar.

Embeddings create a similar map,

except instead of physical distance,

they represent semantic distance.

---

# Semantic Space

Imagine a two-dimensional world.

```text
Programming

        Java

Python

C++

             Redis

Database

MongoDB
```

Related concepts naturally cluster together.

In reality,

embeddings often contain

768,

1024,

1536,

or even thousands of dimensions.

Humans cannot visualize them,

but the principle remains identical.

---

# Similarity Search

Instead of asking

```
Does this document contain "Redis"?
```

Vector databases ask

```
Which vectors are closest to this vector?
```

This is called

**Similarity Search.**

---

# Example

Suppose a user searches

```
Fast in-memory caching
```

The query is converted into an embedding.

The vector database finds nearby vectors representing

- Redis
- Memcached
- Distributed Cache

rather than relying on exact words.

---

# Why Similarity Search Matters

Imagine searching

```
Automobile
```

A keyword search may not find documents containing only

```
Car
```

A vector search recognizes that

```
Car

≈

Automobile
```

because their embeddings are very similar.

This enables semantic search.

---

# Measuring Similarity

To compare vectors,

we need a mathematical definition of "closeness."

The two most common methods are

- Cosine Similarity
- Euclidean Distance

---

# Cosine Similarity

Cosine Similarity measures

how closely two vectors point in the same direction.

It ignores magnitude

and focuses on orientation.

---

# Real-Life Analogy

Imagine two arrows.

```text
Arrow A →

Arrow B →
```

Both point in nearly the same direction.

Their cosine similarity is high.

Now compare

```text
Arrow A →

Arrow B ←
```

They point in opposite directions.

Their cosine similarity is low.

---

# Why Cosine Similarity?

Suppose two documents

have different lengths.

One contains

500 words.

Another contains

5,000 words.

Cosine Similarity ignores document size

and compares meaning instead.

This makes it ideal for Natural Language Processing.

---

# Euclidean Distance

Euclidean Distance measures

the straight-line distance

between two vectors.

---

# Real-Life Analogy

Imagine Google Maps.

The shortest distance

between two cities

is their Euclidean distance.

Vectors behave similarly.

Closer vectors

are considered more similar.

---

# Cosine vs Euclidean

| Cosine Similarity | Euclidean Distance |
|-------------------|-------------------|
| Measures Angle | Measures Distance |
| Ignores Magnitude | Includes Magnitude |
| NLP Preferred | Geometry Applications |
| Semantic Comparison | Spatial Comparison |

Most language applications prefer Cosine Similarity.

---

# The Scalability Problem

Suppose your application stores

```
2 Billion Embeddings
```

Searching every vector

for every query

would require billions of comparisons.

Even modern GPUs would struggle.

Searching must be faster.

---

# Approximate Nearest Neighbor (ANN)

Instead of finding

the absolute nearest vectors,

ANN algorithms quickly find

almost the nearest vectors.

This small compromise dramatically improves performance.

---

# Real-Life Analogy

Imagine searching for

the best coffee shop in New York.

Walking into every café

would take weeks.

Instead,

you check

Google Maps.

You may not visit every café,

but you'll almost certainly find an excellent one.

ANN works similarly.

---

# Why Approximate Search?

Exact Search

```text
100% Accurate

↓

Very Slow
```

Approximate Search

```text
99.9% Accurate

↓

Thousands of Times Faster
```

Production AI systems almost always choose ANN.

---

# HNSW (Hierarchical Navigable Small World)

One of the most popular ANN algorithms is

**HNSW.**

---

# What is HNSW?

HNSW organizes vectors into multiple graph layers.

Searching begins at the top,

then gradually moves toward increasingly accurate neighbors.

---

# Real-Life Analogy

Imagine navigating a city.

You first use

Highways

↓

Main Roads

↓

Local Streets

↓

Destination

HNSW searches similarly.

It avoids examining every vector.

---

# IVF (Inverted File Index)

IVF groups vectors into clusters.

When a query arrives,

only the nearest clusters are searched.

---

# Real-Life Analogy

Imagine finding a book.

Instead of searching the entire library,

you first locate

Computer Science

↓

Databases

↓

Distributed Systems

↓

Redis

The search space becomes dramatically smaller.

---

# Product Quantization (PQ)

Large vectors consume significant memory.

Product Quantization compresses vectors

while preserving most similarity information.

---

# Why PQ?

Without compression,

billions of embeddings would require enormous RAM.

PQ reduces

- Memory Usage
- Storage Cost
- Search Latency

while maintaining high accuracy.

---

# Real-Life Analogy

Imagine compressing a high-resolution image into JPEG.

The file becomes much smaller,

yet still looks almost identical.

PQ applies a similar idea to vectors.

---

# FAISS

FAISS

(Facebook AI Similarity Search)

is one of the world's most popular vector search libraries.

Developed by Meta,

it provides extremely fast similarity search.

---

# When to Use FAISS

FAISS is ideal when

- Running locally
- Building research projects
- Creating custom AI systems

It is a library,

not a complete database.

---

# Pinecone

Pinecone is a fully managed cloud vector database.

Developers focus on applications,

while Pinecone manages

- Indexing
- Scaling
- Replication
- Availability

---

# Milvus

Milvus is an open-source vector database

designed for large-scale AI applications.

It supports

- Billions of vectors
- Distributed deployment
- GPU acceleration
- High-performance ANN search

---

# Weaviate

Weaviate combines

Vector Search

with

Knowledge Graph capabilities.

It also supports

- Hybrid Search
- Metadata Filtering
- AI-native APIs

---

# pgvector

Many organizations already use PostgreSQL.

Instead of deploying another database,

they install

**pgvector**.

pgvector adds vector search capabilities

directly inside PostgreSQL.

This simplifies architecture

for small and medium-sized AI applications.

---

# Comparison of Popular Vector Databases

| Technology | Type | Best Use Case |
|------------|------|---------------|
| FAISS | Library | Local AI Applications |
| Pinecone | Managed Cloud | Production SaaS |
| Milvus | Open Source Database | Large AI Platforms |
| Weaviate | AI-native Database | Semantic Search |
| pgvector | PostgreSQL Extension | Existing PostgreSQL Systems |

# Complete Vector Search Pipeline

Everything we've learned now fits together.

```text
             User Query
                  │
                  ▼
          Embedding Model
                  │
                  ▼
          Query Embedding
                  │
                  ▼
          Vector Database
                  │
          ANN Search (HNSW/IVF)
                  │
                  ▼
      Top Similar Embeddings
                  │
                  ▼
         Retrieved Documents
                  │
                  ▼
          Large Language Model
                  │
                  ▼
           Final Response
```

Notice something important.

The LLM

does **not**

search documents directly.

The Vector Database performs retrieval.

The LLM only generates the response.

This separation is the foundation of Retrieval-Augmented Generation (RAG),

which we will study in the next part.

---

# Real-World Example

Imagine GitHub Copilot.

A developer writes

```python
connect to postgres
```

The IDE converts the surrounding code into an embedding.

That embedding is sent to a vector database containing millions of code snippets.

Instead of searching for the exact phrase,

the vector database retrieves semantically similar examples,

such as

- PostgreSQL connection pools
- SQLAlchemy examples
- Async database connections

These retrieved snippets are passed to the LLM,

which generates context-aware code suggestions.

Without vector databases,

the model would lack relevant project-specific knowledge.

---

# Key Takeaways

- Vector Databases store and search high-dimensional embedding vectors rather than traditional rows and columns.
- Embeddings represent the semantic meaning of text, allowing AI systems to understand similarity instead of exact matches.
- Similarity Search retrieves documents based on meaning rather than keywords.
- **Cosine Similarity** compares vector direction and is widely used for language applications, while **Euclidean Distance** measures straight-line distance.
- **Approximate Nearest Neighbor (ANN)** algorithms dramatically accelerate vector search with minimal loss in accuracy.
- **HNSW**, **IVF**, and **Product Quantization** are foundational indexing techniques used to scale vector search to billions of embeddings.
- **FAISS**, **Pinecone**, **Milvus**, **Weaviate**, and **pgvector** are among the most widely used vector search technologies, each serving different deployment needs.
- Modern AI applications such as ChatGPT, GitHub Copilot, Perplexity AI, and enterprise RAG systems depend on vector databases for fast semantic retrieval.
- In the next part, we will combine LLMs and Vector Databases to study **Retrieval-Augmented Generation (RAG)**, the architecture powering most production AI assistants today.
